## D — Subtasks / Components

**D1 · Scope definition**
Enumerate all production data stores (OLTP DBs, OLAP/warehouse, caches, message queues, object stores, file systems, search indices, secrets managers, config stores, audit/event logs, session stores, CDC connector offset stores — Debezium schema-history topics, Kafka Connect internal-offsets topics, DMS task checkpoints); include an explicit SaaS inventory section — every SaaS system that holds authoritative state with production RPO/RTO obligations is either (a) declared in scope with a documented export/backup mechanism and verified RPO/RTO, or (b) declared out of scope with a signed business-acceptance rationale for the data-loss exposure. Classify each store as authoritative state or derived/reconstructable (derived stores still require a documented rebuild path with timed estimate); assign a business-criticality tier (drives RPO/RTO targets); declare which environments are in scope (any environment running prod data is in, regardless of label); document ephemeral/transient state disposition (acceptable loss or idempotency design — no silent assumption of zero loss).
*Falsifier*: diff inventory against live infrastructure and SaaS platforms — zero unregistered stores; every store has a tier, a state/derived classification, and — if derived — a timed rebuild procedure ≤ its RTO; ephemeral-state section exists with an explicit ruling per item; SaaS inventory section exists and every SaaS system is either in-scope with verified backup mechanism or explicitly out-of-scope with signed rationale; CDC connector offset store inventory exists and covers all active CDC pipelines.

**D2 · RPO/RTO target assignment**
For each store (keyed to its criticality tier), specify: maximum tolerable data age (RPO) in time units; maximum tolerable restore/failover duration (RTO) per failure scenario; PITR requirement flag for stores with RPO < 15 min; recovery tier priority ordering for multi-store failure (derived from the versioned store dependency graph — see V28 for currency requirement).
*Falsifier*: every store has documented RPO, RTO, backup type(s), and PITR flag; priority sequence is consistent with the current versioned dependency graph; D2 document cites the graph version number.

**D3 · Backup design**
Per store: select backup type (full/incremental/differential/WAL-log-based) and cadence such that cadence + p99_backup_duration ≤ RPO_stated; for stores with RPO < 15 min, enable continuous WAL/log shipping to the backup store; schedule full vs. incremental rotation so that restore-assembly time from the oldest permitted chain ≤ RTO; set cross-region replication cadence such that secondary backup freshness ≤ RPO; bound backup I/O to prevent SLA degradation during peak load; establish migration-backup coordination procedure for schema changes that mandates logging the exact WAL LSN / commit timestamp of each DDL change as a named catalog anchor, so that PITR restores crossing a migration boundary can correctly target the pre- or post-migration schema without ambiguity.

Additional backup design requirements:
- *Snapshot consistency classification*: for stores backed up via storage-level or VM snapshots rather than DB-native mechanisms, classify the snapshot type as crash-consistent or application-consistent in the backup spec; document the restore path for each type — for crash-consistent snapshots, specify the crash-recovery procedure and the engines/versions for which this is valid; for application-consistent snapshots, document the quiesce mechanism (freeze/thaw, VSS writer, DB flush hook) and its operational preconditions.
- *CDC connector offset state backup*: for every CDC pipeline in scope (D1), back up the connector's offset/cursor state (schema-history topic, internal-offsets topic, task checkpoint file) on a cadence aligned to the WAL backup schedule; each cursor backup is timestamped against the source WAL LSN at the moment of capture so that, at restore time, the cursor can be aligned to the WAL LSN corresponding to the DB restore point T1.
- *Backup job retry idempotency*: the backup job implementation must ensure that if a job fails midway and is retried (by scheduler or operator), the outcome is exactly one valid, complete artifact per backup window registered in the catalog; partial artifacts must be atomically removed from the catalog before or during retry so that no dangling partial entries remain; if a retry produces a second artifact for the same window, the catalog must resolve to the valid complete entry and remove the superseded one before marking the window closed.

*Falsifier*: formula audit passes for every store; WAL lag < RPO for low-RPO stores; restore-assembly time from oldest chain ≤ RTO; cross-region backup age ≤ RPO at simulated primary failure; no SLA breach during backup-under-peak test; migration-backup coordination runbook exists AND every DDL change has a logged LSN/commit timestamp as a named catalog anchor (verified: given migration at LSN L, restore to L−1 yields pre-migration schema, restore to L+1 yields post-migration schema, both confirmed in drill); for every snapshot-based store, backup-type classification exists (crash-consistent or application-consistent) and corresponding restore path is documented; CDC cursor state backup exists and is timestamped against WAL LSN; on backup job retry, catalog contains exactly one valid, complete artifact per backup window with no dangling partial entries.

**D4 · Retention policy**
Define storage tiers (hot/warm/cold) with storage classes and benchmarked restore times per tier; set per-store per-tier retention durations such that min_retention ≥ RPO + operational_response_buffer; track compliance/legal retention floors separately (GDPR, HIPAA, SOX, etc.) — policy ≥ compliance floor; additionally, for each data class with a data-residency jurisdiction constraint, document the permitted backup storage regions for all copies (primary backup, cross-region replica, cold-tier archive) and verify compliance quarterly — policy must not place a residency-constrained data class in a non-compliant region at any tier; implement automated expiry with dependency awareness (must not expire a base backup that anchors a live incremental chain; chain must be sealed or deletion blocked); define tiered promotion schedule (hot→warm→cold) without breaking restore paths.
*Falsifier*: retention floor audit passes; attempt to expire a base backup with live dependents — blocked; restore from cold-tier backup succeeds within documented cold-restore RTO; compliance floor is met for every data class; backup count per store per tier matches expected floor; for each data class with a residency obligation, backup storage regions for all copies are listed and verified against applicable regulation — no non-compliant copy exists; quarterly residency audit record present.

**D5 · Restore and failover runbook**
Per failure scenario (single-store, multi-store, region-wide, total-loss / no-replica-available, table-/collection-level surgical recovery, KMS-service-unavailable, mid-restore interruption/abort, partial failover with concurrent live writes): document step-by-step restore or failover procedure.

Additional scenario specifications:
- *KMS-unavailable*: explicit bootstrap procedure — restore KMS infrastructure from its own backup → verify key retrieval → decrypt data backups — before any encrypted store recovery begins; dedicated drill exercises this full path.
- *Restore-abort/interrupt*: if a restore is interrupted midway (network drop, storage failure, operator error), the procedure must return the DB to a known recoverable state (either original pre-restore state, or the restore is checkpointed and resumable from a consistent point); procedure is documented and tested; restart must be idempotent.
- *Partial failover*: when one region/store is down and another is live and accepting writes, the runbook specifies a catch-up replication phase before cutover — the restored side must reach ≤ RPO lag from live before cutover is completed without write loss.

General runbook requirements: specify recovery priority sequence (KMS/secrets → config stores → primary DB → application tier → secondary stores); provide a failover-vs-restore decision rule (replica promotion for speed vs. backup restore for zero data loss from backup point); cover replica promotion steps (stop replication, verify lag, promote, redirect writes, update DNS/LB, notify app tier); reroute all read endpoints (read replicas, read-only DNS records, CDN-cached query layers) to the new topology, not only the write endpoint; set DNS TTL ≤ RTO and application connection-pool drain sequence with a documented maximum drain timeout — if drain does not complete within this timeout, treat the situation as a drain failure with explicit handling in the runbook; include post-restore validation checklist (row counts, last-write timestamps, cross-store consistency, application smoke test); define RACI for failure declaration, restore initiation, cutover approval, and stakeholder notification.
*Falsifier*: runbook is version-controlled and drill log shows successful execution of every scenario type within the current drill cycle; decision tree covers both replica-promotion and cold-restore paths; no-replica-available path exists in runbook; KMS-unavailable path with dedicated drill completion record exists; restore-abort procedure is tested (interrupt at 50% → system returns to recoverable state); partial-failover drill shows catch-up replication phase and zero write loss, completed within RTO; read-endpoint rerouting verified within RTO after promotion drill; post-restore validation checklist is in the runbook and was completed in the last drill; connection-pool drain timeout is documented in runbook and drain-failure handling procedure exists.

**D6 · Integrity and freshness check system**
After every backup job: verify completion (non-zero, structurally valid artifact); compute and store checksum (SHA-256 or equivalent); verify checksum before marking backup usable; confirm size > 0 AND record count > 0 (for structured stores), with the following exception: a legitimately empty store (newly provisioned, pre-population, or genuinely empty by design) generates a baseline "intentionally empty" attestation stored in the catalog; the record-count check accepts a zero-record artifact only when this attestation exists and was created within the last backup cycle; a store without an attestation that produces a zero-record artifact triggers the standard rejection alert; additionally, compare the artifact's record count against a rolling historical baseline — an artifact that passes non-zero and checksum checks but represents an anomalous shrinkage (configurable threshold, e.g., < 50% of the rolling N-period median for that store) must trigger an anomaly-detection alert before the artifact is marked usable (see V24). Periodically: sample-restore a random set of records from backup and compare against known state (catches correct-checksum but corrupt content); validate incremental chain pointer after every incremental write (base backup exists and is accessible); scan backup catalog (referenced files exist, checksums match, recovery times correct); validate that the escrowed encryption key can decrypt a backup created before the most recent key rotation. Continuously: monitor backup age per store (alert threshold = RPO − response_buffer); monitor WAL/log shipping lag (alert threshold ≤ RPO/2); monitor cross-region replication freshness (secondary backup age ≤ RPO); monitor replication lag when backups are sourced from a read replica. Enforce NTP synchronization on all backup hosts as a monitored prerequisite.
*Falsifier*: corrupt a backup byte → checksum detects it; produce a zero-byte artifact → rejected with alert; provision an empty store → attestation generated and stored; produce zero-record artifact without attestation → standard rejection alert fires; delete a base backup → chain validator detects broken link within one cycle; corrupt catalog entry → scan flags it within one scan cycle; restore from pre-rotation backup using escrowed key only (primary excluded) → succeeds; stop backup job → freshness alert fires before RPO elapses; pause WAL shipping → lag alert fires before RPO/2 elapsed; pause cross-region replication → freshness alert fires before RPO; backup from a lagging replica → effective-RPO alert fires; inject artifact with correct checksum and non-zero record count but only 10% of prior period's row count → anomaly-detection alert fires before artifact is marked usable.

**D7 · Monitoring and alerting system**
Emit alerts (each with an enforceable response-time SLA) for: backup job failure or invalid artifact (immediate); backup freshness breach — fires at RPO − response_buffer, not at RPO; WAL lag exceeding RPO/2; storage utilization at 75% and 90% (at 100%, backup job fails noisily, not silently); backup count per store per tier below floor; cross-region backup freshness beyond RPO; catalog integrity scan findings; backup schedule drift (actual start times logged; deviation beyond threshold alerts); retention expiry job failure or overdue completion (expiry must complete within its scheduled window to prevent accumulation reaching the 90% alert threshold before the next expiry run); backup artifact size anomaly (see V24 and D6). Monitoring system itself has a watchdog (dead-man's switch fires if no heartbeat within RPO window).
*Falsifier*: kill backup job → alert fires within 5 min; stop backup → freshness alert fires while RPO is still achievable; fill storage to 90% → alert fires; delete one backup → count-floor alert fires before next scheduled backup; pause replication → freshness alert fires in time; corrupt catalog entry → alert fires within one scan cycle; let jobs slip → schedule-drift alert fires; kill monitoring system → watchdog fires within RPO; let expiry job run overdue → alert fires before storage accumulation reaches 90%; inject anomalous-size artifact → anomaly alert fires before artifact is marked usable.

**D8 · Restore drill program**
Calendar-enforced mandatory drill frequency per criticality tier (e.g., Tier-1: quarterly; Tier-2: semi-annual); maximum elapsed time between drills is a hard gate, not a target — missed drill is a formal incident. Each drill cycle covers: full-estate restore (at least annually), single-store, table-level, region-failover, KMS-unavailable, partial-failover, and — for each in-scope SaaS system with production RPO/RTO obligations — a full SaaS export round-trip (export → clean-tenant import → verification of row count, referential integrity, binary attachments, and a sampled record set including API-only metadata not always present in export schema); a missing SaaS round-trip drill is treated identically to a missing drill for any other Tier-1 store. Drills run in an isolated environment version-locked to current production spec (same OS/DB version, hardware tier). Drills have objective pass/fail criteria: restore ≤ RTO, data within RPO, smoke tests pass. Per-step timing is logged; total is compared to RTO. Drill procedure uses the identical document and version as the real recovery runbook. Credential validity is pre-checked at drill start (expired credential is a drill blocker). Findings are tracked to closure — runbook version is bumped before a finding is closed; next drill cites the updated version.
*Falsifier*: drill log shows all scenario types exercised within cycle (including KMS-unavailable, partial-failover, and SaaS round-trip for each in-scope SaaS system); drill environment spec verified against current prod spec before each drill; drill report shows objective pass/fail verdict; timing log shows per-step times summing ≤ RTO; drill cites runbook version matching real runbook; credential pre-check step present in drill log; missed drill triggers formal incident; no finding older than one drill cycle without a resolution ticket and runbook version commit; SaaS round-trip drill record includes export→import→verification evidence for each in-scope SaaS system.

**D9 · Backup catalog backup and recovery**
The backup catalog is itself a critical data store; its loss or corruption coincident with a primary failure blocks all recovery. Requirements: the catalog is backed up on a cadence such that catalog RPO ≤ the primary data stores' shortest RPO; catalog backups are stored independently of the primary catalog service (not co-located); a catalog-reconstruction procedure from raw artifact metadata exists as an alternative recovery path (scan stored artifacts, rebuild LSN/timestamp index); the reconstruction procedure is timed; both the catalog-backup path and the reconstruction path are exercised in the drill program.
*Falsifier*: simulate catalog loss coincident with primary failure; recovery via catalog backup OR full reconstruction from artifact metadata completes within RTO; the assembled restore set from either path matches what the live catalog would have returned; both paths are present in the drill log.

## Dep — Cross-Component Dependency Seams

**Dep1 · WAL/log shipping → backup catalog → PITR restore path**
Log segments are deposited by the shipping agent; catalog records LSN and timestamp; PITR restore queries catalog to assemble the correct sequence. If the catalog lags, missequences, or drops a segment, PITR silently produces a gap without erroring.
*Falsifier*: restore to an arbitrary timestamp T within the log-shipping window; verify record state matches a known snapshot taken at exactly T.

**Dep2 · Base full backup integrity → incremental chain restorability**
All incrementals reference a base full backup. Silent corruption of the base makes every dependent unrestorable — the chain appears valid in the catalog but cannot be assembled.
*Falsifier*: corrupt the base full backup checksum; verify that a restore attempt fails with an explicit error, not silent data corruption.

**Dep3 · Retention engine → backup chain dependency check**
Retention policy may expire a full backup that still anchors an active incremental chain, eliminating the only restore path for all dependents.
*Falsifier*: configure retention to target a base backup with live dependents; verify deletion is blocked or the chain is explicitly sealed before the base is removed.

**Dep4 · Integrity check path = restore read path**
If the integrity check validates an artifact at storage path A but the restore process reads from path B (a stale copy, a different replica, or a redirected mount), the check provides no assurance.
*Falsifier*: corrupt a backup byte after integrity check passes; trigger restore from the same declared path; verify the mismatch is detected before restore completes.

**Dep5 · Alert threshold + on-call response time → RPO budget**
Setting the freshness alert threshold at RPO (not RPO − response_buffer) means human response time plus re-backup duration consumes the entire remaining window; RPO is breached before corrective action can complete.
*Falsifier*: verify alert_threshold + median_on_call_response_time + p99_backup_duration ≤ RPO for every store.

**Dep6 · DB restore point → encryption key version → decryptability**
A DB restored to time T1 was encrypted under the key version active at T1. If key rotation since T1 has not updated the escrow, the backup is unreadable. Applies across all rotation events since backup creation.
*Falsifier*: restore from a backup created before the most recent key rotation event, using only the escrowed key (primary key deliberately excluded from the test environment); all records are readable.

**Dep7 · DB restore point → cache state → cross-store consistency**
Cache is restored to T2 > T1 (or not invalidated); DB is restored to T1. The cache holds stale-future entries for rows rolled back in the DB restore; application reads return wrong data with no error.
*Falsifier*: post-restore runbook mandates cache invalidation; smoke test reads a record known to differ between T1 and T2 — cache returns the T1 value, not the T2 value.

**Dep8 · Replica promotion → DNS/LB TTL → application write connectivity**
After replica promotion, DNS TTL too high or load-balancer rule not updated; clients continue directing writes to the dead primary address; writes are lost or rejected.
*Falsifier*: time from promotion command to first successful application write through the new primary endpoint; must be ≤ RTO.

**Dep9 · DB restore point → message queue consumer offsets → replay correctness**
DB is restored to T1; Kafka/RabbitMQ consumer offsets remain at T2 > T1; replay re-processes transactions already committed before T1, producing duplicates.
*Falsifier*: restore scenario with active queue shows zero double-processing of records committed before T1; consumer-offset rollback procedure exists and is exercised in drill.

**Dep10 · DB restore point → object store version → referential integrity**
DB is restored to T1; some DB rows reference object keys written between T1 and T2 that do not exist in the T1 object store, leaving dangling foreign-key references.
*Falsifier*: post-restore referential integrity check between all DB foreign keys referencing object store keys and the T1 object store key listing; zero dangling references.

**Dep11 · Infrastructure provisioning → backup inventory gate**
A new data store is deployed to production without being added to the backup inventory; no backup job ever runs; the gap is discovered only at recovery time.
*Falsifier*: provisioning pipeline has a hard gate — a store cannot be promoted to production until it appears in the backup inventory with a verified successful first backup.

**Dep12 · Drill environment spec → runbook applicability**
Drill runs on a lower-spec or different-version environment; the procedure appears to succeed; the real production restore fails or behaves differently due to hardware, OS, or DB version mismatch.
*Falsifier*: drill environment spec is compared against current production spec before every drill; any discrepancy is a drill finding, not a silent skip.

**Dep13 · Drill finding registry → runbook version → next drill validity**
A drill surfaces a procedural gap; the gap is not tracked; the next drill uses the same flawed runbook; gaps accumulate silently across drill cycles.
*Falsifier*: finding registry requires a runbook version bump before the finding can be closed; the subsequent drill log cites the updated runbook version.

**Dep14 · Backup sourced from read replica → replication lag → effective RPO**
Backup is taken from a read replica; replica lag is nonzero at backup time; effective RPO = RPO_stated + lag; this breach is not surfaced by normal freshness checks (which measure backup age, not effective data age from the primary).
*Falsifier*: replica lag is measured at each backup run when backup source is a replica; if lag makes effective RPO impossible, alert fires; backup is sourced from a lagged replica only when lag ≤ RPO − cadence.

**Dep15 · Replica lag at promotion → unacknowledged transaction loss**
Replica promoted to primary at nonzero lag; the last N seconds of committed primary transactions are permanently lost; the application assumes zero data loss without any audit.
*Falsifier*: post-failover transaction audit compares last committed transaction ID on the old primary (from crash or WAL logs) against the promoted replica's last applied transaction; the delta is explicitly documented and either accepted via a data-loss approval process or reprocessed.

**Dep16 · Replica promotion → read endpoint rerouting → stale reads**
D5/Dep8 cover write-endpoint rerouting after replica promotion; read traffic directed to read-replica endpoints, read-only DNS records, or CDN-cached query layers is not automatically rerouted; clients silently read stale or unavailable data from the old topology while writes succeed against the new primary.
*Falsifier*: after a replica-promotion drill, measure time until all declared read endpoints (read replicas, read-only DNS records, CDN purge if applicable) are serving correct data from the new topology; must be ≤ RTO. Distinct falsifier from Dep8 (write connectivity): a write test passes while reads still fail.

**Dep17 · Backup agent credential rotation → job continuity**
When IAM roles, service-account keys, or storage-access tokens used by backup agents are rotated for security hygiene, backup agents may silently fail if their credential cache is not updated in lockstep; D7 fires a job-failure alert only after the credential has expired and one backup window has already been missed.
*Falsifier*: a pre-rotation checklist mandates updating all backup agents before the old credential is revoked; simulate a credential rotation event and verify zero backup jobs fail during the rotation window.

**Dep18 · CDC connector cursor state → DB restore point → CDC event duplication/gap**
CDC pipelines (Debezium, DMS, Kafka Connect source connectors) maintain their own offset/cursor metadata — schema-history topics, internal-offsets topics, task checkpoint files — independently of both the source DB WAL and consumer-side queue offsets (Dep9 addresses the consumer side). When the DB is restored to T1, a CDC connector resuming from a stale cursor representing a pre-T1 position re-emits events already committed before T1 (duplicates); a connector restored to a cursor position past T1 skips the events in [cursor, T1] (gaps). D3 requires CDC cursor backups timestamped against WAL LSN; this seam is what fails when that backup is absent or misaligned.
*Falsifier*: in a restore drill with an active CDC pipeline, verify that the CDC connector's cursor/offset is restored or reset to the WAL LSN corresponding to DB restore point T1; post-restore CDC replay for window [T1, T1+δ] produces zero duplicate events and zero skipped events. Distinct from Dep9: Dep9 = consumer-group offset rollback (Kafka consumer side); Dep18 = producer-side CDC connector cursor alignment to DB restore point.

**Dep19 · Backup job partial failure → catalog partial registration → PITR assembly ambiguity**
If a backup job fails midway and retries, two catalog pathologies arise: (a) a partial artifact is partially registered in the catalog before the retry, leaving a dangling entry that PITR assembly may select over the complete artifact from the successful retry; (b) a successful retry produces a second entry for the same backup window, creating ambiguity in restore-set assembly. D5 specifies restore-abort handling on the recovery side; this is the backup-execution-side equivalent. D3 mandates idempotent retry behavior; this seam is what fails when that guarantee is absent.
*Falsifier*: simulate backup job failure at 50% completion followed by automatic retry; verify catalog contains exactly one valid, complete artifact for that backup window with no dangling partial entries; artifact passes all D6 integrity checks; PITR query for that window returns the correct artifact unambiguously.

**Dep20 · Application connection-pool drain → old primary endpoint → write loss during failover**
D5 specifies a connection-pool drain sequence as a failover step, and Dep8 verifies write connectivity to the new primary (time from promotion to first successful write ≤ RTO). These are not equivalent: Dep8 passes the moment the new primary accepts one write; it does not verify that the application tier has drained connections to the dead primary. If a long-running query or stuck transaction holds a connection to the old endpoint after DNS has been updated, application instances continue directing writes to the old endpoint address and those writes are silently lost or rejected.
*Falsifier*: failover drill measures time from DNS update to zero active connections at the old primary endpoint (application-tier level, not DB level); this interval must be ≤ the connection-pool drain timeout specified in the D5 runbook; a stuck long-running query on the old endpoint is a drill finding requiring explicit runbook handling. Distinct from Dep8: Dep8 tests new-primary write availability; Dep20 tests old-primary connection drain completion.

**V10 · Regime self-consistency** — All parameters are internally consistent: cadence + p99_backup_duration ≤ RPO; min_retention ≥ RPO + operational_response_buffer; cold-tier restore time ≤ RTO if cold restore is a valid path; drill frequency ≤ maximum tolerable runbook drift interval. **V13 · Backup schedule adherence** — Actual backup start times are logged and compared to scheduled times; deviation beyond a defined threshold fires an alert. Schedule drift cannot accumulate silently into an RPO violation.

**V17 · PITR restorability for low-RPO stores** — For any store declared PITR-capable (RPO < 15 min), a restore to an arbitrary minute within the log-shipping window produces a system state that matches the authoritative record state at exactly that minute.

**V18 · Encryption key escrow currency** — The key rotation procedure mandates an escrow update as an in-line step; the updated escrow is verified by the next scheduled key-escrow validation drill (restore using only the escrowed key, primary key excluded from test environment).
*Falsifier*: rotate a key; verify escrow update is in the rotation procedure record; next key-escrow drill succeeds using only the escrowed key. Distinct from Dep6: Dep6 is the runtime seam; V18 is the process predicate that keeps Dep6 healthy.

**V19 · DB engine upgrade restore-drill gate** — A major-version DB engine upgrade (which may change WAL format, backup compression, or tool API) is not declared production-stable until a blocking restore drill from the first backup produced post-upgrade completes successfully; no such upgrade is approved without a drill completion record.
*Falsifier*: policy record shows a major-version upgrade was declared production-stable without a corresponding post-upgrade restore drill completion record; or: the first backup after upgrade is unrestorable (format change uncaught). Distinct from D8 scheduled drill: this is a triggered gate on upgrade events, not calendar-cadence.

**V20 · Network bandwidth as hard RTO input** — For every store, the regime document contains the formula ceil(data_volume / minimum_restore_network_bandwidth) and verifies that this transfer-time floor ≤ RTO minus all non-transfer restore steps; a store cannot have a committed RTO that is physically impossible given available WAN bandwidth.
*Falsifier*: regime document is missing the bandwidth-formula section for any store; OR the formula is present and the computed transfer floor exceeds (RTO − non-transfer step sum) for any store. Distinct from V2: V2 is drill-measured timing; V20 is a documented analytical bound that must hold before any drill is attempted.

**V21 · In-transit encryption of backup streams** — Backup data is encrypted in transit across all channels (WAL shipping streams, cross-region object-storage copy, backup agent → storage API, catalog sync); TLS version ≥ 1.2 enforced and audited on each channel.
*Falsifier*: packet capture during a backup job on each declared channel shows no plaintext backup data; TLS version audit confirms ≥ 1.2 on all channels. Distinct from V18/Dep6: those govern at-rest key escrow; V21 governs in-transit protection.

**V22 · Schema migration PITR boundary integrity** — For every DDL change event, the WAL LSN / commit timestamp is logged as a named catalog anchor; a PITR restore targeting LSN L−1 produces the pre-migration schema and targeting L+1 produces the post-migration schema, without DDL duplication or omission.
*Falsifier*: given a named migration anchor at LSN L, restore to L−1 and verify pre-migration schema; restore to L+1 and verify post-migration schema — both confirmed in a drill. Distinct from V17: V17 tests arbitrary-minute data accuracy; V22 tests DDL-boundary schema correctness at migration seams.

**V23 · Expiry job cadence vs. storage accumulation bound** — The retention expiry job runs frequently enough that, at the maximum backup accumulation rate, storage utilization cannot reach the 90% alert threshold between consecutive expiry runs; the formula max_accumulation_rate × expiry_run_interval ≤ (90% − steady_state_utilization) × total_capacity is documented in the regime and verified; the expiry job is monitored for overdue completion (alert fires if it has not completed within its scheduled window).
*Falsifier*: regime document is missing the accumulation-bound formula; OR formula is present but violated given current accumulation rate and expiry interval; OR let the expiry job run overdue — overdue alert does not fire. Distinct from D4 (which sets expiry policy) and D7 (which alerts at 75%/90%): V23 is the decidable bound proving the two will never collide under normal operation.

**V24 · Backup artifact size anomaly detection** — A backup artifact that passes all standard D6 integrity checks (non-zero size, valid checksum, non-zero record count) but represents an anomalous shrinkage relative to historical baselines for the same store (e.g., < 50% of the rolling N-period median row count) is not marked usable until an anomaly-detection alert has fired and been resolved; silent partial-dataset certifications are not permitted.
*Falsifier*: inject a backup artifact that passes all D6 checks but contains only 10% of the prior backup's row count for the same store; an anomaly-detection alert fires before the artifact is marked usable. Distinct from D6 (which checks non-zero count and checksum validity, not baseline deviation).

**V25 · Infrastructure DR handoff SLA as hard composite RTO input** — Total recovery time = infra_ready_time + data_restore_time. The regime document records the composite inequality infra_DR_SLA + p99_data_restore_time ≤ RTO for each failure scenario; the cross-referenced infrastructure DR runbook (N6) has a documented completion SLA satisfying this inequality; a joint drill measures both phases end-to-end against the stated RTO. An undocumented infra DR SLA or a violated composite inequality means the data recovery RTO is physically unachievable even when the data regime is fully compliant.
*Falsifier*: the composite inequality is absent from the regime document for any failure scenario; OR the infra DR runbook has no documented SLA; OR a joint drill shows combined time exceeds RTO. Distinct from V2 (which measures data-restore timing only) and N6 (which excludes the infra layer but does not bound the handoff seam).

**V26 · Snapshot consistency classification per store** — For every store backed up via storage-level or VM snapshots rather than DB-native mechanisms, the backup specification classifies the snapshot type (crash-consistent or application-consistent); if crash-consistent, a drill confirms crash-recovery completes and yields a consistent, queryable state within RTO for the specific DB engine and version in use; if application-consistent, the quiesce mechanism (freeze/thaw, VSS writer, DB flush hook) is documented and exercised in the drill.
*Falsifier*: any snapshot-based store lacks a type classification in the regime document; OR a crash-consistent store's drill shows crash-recovery fails to produce a consistent state within RTO; OR an application-consistent store's quiesce mechanism is undocumented or not exercised in the drill. Distinct from V2 (RTO compliance) and V6 (restore correctness): V26 requires per-type classification evidence and mechanism documentation, not just timing.

**V27 · Data residency compliance for backup storage locations** — For each data class with a data-residency jurisdiction constraint, backup storage regions for all copies (primary backup, cross-region replica, cold-tier archive) are listed in the regime document and verified against applicable regulation; no backup copy for a residency-constrained data class resides in a non-compliant region at any tier; a quarterly audit confirms current compliance.
*Falsifier*: regime document is missing the residency-constraint section for any data class with a jurisdiction obligation; OR a backup copy for a residency-constrained class resides in a non-compliant region; OR the last quarterly residency audit record is absent. Distinct from D4 (which tracks retention duration floors): V27 governs geographic placement constraints independently of retention duration.

**V28 · Store dependency graph currency** — The store dependency graph (used by D2 for priority ordering and D5 for recovery sequencing) is a versioned artifact; any in-scope infrastructure change (new store onboarded, inter-store dependency modified, store decommissioned) triggers a mandatory graph review with a version bump before the change is approved in production; D2 and D5 documents cite the current graph version number; an audit of the graph version date against the last infrastructure-change date shows zero gap.
*Falsifier*: D2 or D5 cites a graph version that predates the last infrastructure change; OR an infrastructure change was approved without a corresponding graph version bump; OR no version number is present on the dependency graph artifact.

**V29 · Multi-person authorization for immutability policy modification** — V9 protects backup artifacts from deletion or overwrite by production-level credentials. The immutability policy itself (Object Lock bucket configuration, WORM retention settings, retention-lock period) is additionally protected: the set of principals authorized to modify these settings is smaller than the set of principals with production write access; any modification to immutability configuration requires at minimum two-person authorization or an out-of-band approval workflow with a persistent audit trail; a single-actor attempt to modify the policy is blocked or raises an immediate alert.
*Falsifier*: attempt a single-actor modification of backup-storage immutability configuration using a production-privileged account — operation is blocked or alert fires; the authorization policy document shows the authorized-modifiers set is strictly smaller than the production-write-access set. Distinct from V9 (artifact-level protection): V29 governs policy-level protection against immutability bypass.

## N — Declared Scope Exclusions

**N1 · Logical / application-level data corruption** — A bug that writes semantically wrong values for weeks; backup faithfully preserves the corrupted data. Out of scope (backup fidelity ≠ data quality). Back in scope only if the regime explicitly commits to a PITR + data-quality-checkpoint recovery path and defines falsifiable criteria for it.
*Why safely out*: distinguishing "correct" from "incorrect" application-level data requires domain-specific quality checks that are the application's responsibility, not the backup regime's.

**N2 · Active-active replication infrastructure design** — Active-active is an architectural choice, not a backup. The replication infrastructure design is out of scope. Where active-active serves as the failover mechanism for a specific store, the regime must document it as such and verify tested RPO/RTO for that path.
*Why safely out*: the regime governs recoverability policy, not the topology that achieves it.

**N3 · Full security / ransomware incident response playbook** — The complete incident response is a security concern. Backup immutability (Object Lock, WORM, air-gap) and audit of immutability configuration are in scope. Cross-reference to the security incident runbook is required.
*Why safely out*: incident response spans far beyond data recovery; immutability is the data-recovery-relevant boundary.

**N4 · Application binary / deployment rollback** — Rollback of deployment artifacts is a CI/CD concern. This regime covers data state rollback only. The regime document explicitly delimits: "this regime restores data state, not application binaries."
*Why safely out*: binary rollback and data-state rollback are orthogonal; conflating them creates confusion about ownership and procedure.

**N5 · Development and staging environments (without prod data)** — Out of scope unless an environment holds a copy of production data (e.g., prod-clone staging), in which case that data is in scope regardless of environment label.
*Why safely out*: non-prod data loss carries no production RPO/RTO obligation; the regime document lists all in-scope environments explicitly.

**N6 · Compute, network, and orchestration layer rebuild** — Restoring the infrastructure layer (VMs, Kubernetes, networking) is an infrastructure DR concern. This regime assumes infrastructure is available or is being restored by a separate, cross-referenced runbook. The restore runbook has an explicit prerequisite: "infrastructure layer is operational." The composite recovery time inequality (infra_DR_SLA + p99_data_restore_time ≤ RTO) is documented in the data regime (V25) even though the infra layer itself is excluded.
*Why safely out*: data recovery and infrastructure recovery have separate ownership, tooling, and timelines; the regime document cross-references the infrastructure DR runbook.
