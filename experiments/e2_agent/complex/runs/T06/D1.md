## D — Subtasks / Components

**D1 · Scope definition**
Enumerate all production data stores (OLTP DBs, OLAP/warehouse, caches, message queues, object stores, file systems, search indices, secrets managers, config stores, audit/event logs, session stores); classify each as authoritative state or derived/reconstructable (derived stores still require a documented rebuild path with timed estimate); assign a business-criticality tier (drives RPO/RTO targets); declare which environments are in scope (any environment running prod data is in, regardless of label); document ephemeral/transient state disposition (acceptable loss or idempotency design — no silent assumption of zero loss).
*Falsifier*: diff inventory against live infrastructure — zero unregistered stores; every store has a tier, a state/derived classification, and — if derived — a timed rebuild procedure ≤ its RTO; ephemeral-state section exists with an explicit ruling per item.

**D2 · RPO/RTO target assignment**
For each store (keyed to its criticality tier), specify: maximum tolerable data age (RPO) in time units; maximum tolerable restore/failover duration (RTO) per failure scenario; PITR requirement flag for stores with RPO < 15 min; recovery tier priority ordering for multi-store failure (derived from store dependency graph).
*Falsifier*: every store has documented RPO, RTO, backup type(s), and PITR flag; priority sequence is consistent with the dependency graph.

**D3 · Backup design**
Per store: select backup type (full/incremental/differential/WAL-log-based) and cadence such that cadence + p99_backup_duration ≤ RPO_stated; for stores with RPO < 15 min, enable continuous WAL/log shipping to the backup store; schedule full vs. incremental rotation so that restore-assembly time from the oldest permitted chain ≤ RTO; set cross-region replication cadence such that secondary backup freshness ≤ RPO; bound backup I/O to prevent SLA degradation during peak load; establish migration-backup coordination procedure for schema changes.
*Falsifier*: formula audit passes for every store; WAL lag < RPO for low-RPO stores; restore-assembly time from oldest chain ≤ RTO; cross-region backup age ≤ RPO at simulated primary failure; no SLA breach during backup-under-peak test; migration-backup coordination runbook exists.

**D4 · Retention policy**
Define storage tiers (hot/warm/cold) with storage classes and benchmarked restore times per tier; set per-store per-tier retention durations such that min_retention ≥ RPO + operational_response_buffer; track compliance/legal retention floors separately (GDPR, HIPAA, SOX, etc.) — policy ≥ compliance floor; implement automated expiry with dependency awareness (must not expire a base backup that anchors a live incremental chain; chain must be sealed or deletion blocked); define tiered promotion schedule (hot→warm→cold) without breaking restore paths.
*Falsifier*: retention floor audit passes; attempt to expire a base backup with live dependents — blocked; restore from cold-tier backup succeeds within documented cold-restore RTO; compliance floor is met for every data class; backup count per store per tier matches expected floor.

**D5 · Restore and failover runbook**
Per failure scenario (single-store, multi-store, region-wide, total-loss / no-replica-available, table-/collection-level surgical recovery): document step-by-step restore or failover procedure; specify recovery priority sequence (secrets/KMS → config stores → primary DB → application tier → secondary stores); provide a failover-vs-restore decision rule (replica promotion for speed vs. backup restore for zero data loss from backup point); cover replica promotion steps (stop replication, verify lag, promote, redirect writes, update DNS/LB, notify app tier); set DNS TTL ≤ RTO and application connection-pool drain sequence; include post-restore validation checklist (row counts, last-write timestamps, cross-store consistency, application smoke test); define RACI for failure declaration, restore initiation, cutover approval, and stakeholder notification.
*Falsifier*: runbook is version-controlled and drill log shows successful execution of every scenario type within the current drill cycle; decision tree covers both replica-promotion and cold-restore paths; no-replica-available path exists in runbook; post-restore validation checklist is in the runbook and was completed in the last drill.

**D6 · Integrity and freshness check system**
After every backup job: verify completion (non-zero, structurally valid artifact); compute and store checksum (SHA-256 or equivalent); verify checksum before marking backup usable; confirm size > 0 AND record count > 0 (for structured stores). Periodically: sample-restore a random set of records from backup and compare against known state (catches correct-checksum but corrupt content); validate incremental chain pointer after every incremental write (base backup exists and is accessible); scan backup catalog (referenced files exist, checksums match, recovery times correct); validate that the escrowed encryption key can decrypt a backup created before the most recent key rotation. Continuously: monitor backup age per store (alert threshold = RPO − response_buffer); monitor WAL/log shipping lag (alert threshold ≤ RPO/2); monitor cross-region replication freshness (secondary backup age ≤ RPO); monitor replication lag when backups are sourced from a read replica. Enforce NTP synchronization on all backup hosts as a monitored prerequisite.
*Falsifier*: corrupt a backup byte → checksum detects it; produce a zero-byte artifact → rejected with alert; delete a base backup → chain validator detects broken link within one cycle; corrupt catalog entry → scan flags it within one scan cycle; restore from pre-rotation backup using escrowed key only (primary excluded) → succeeds; stop backup job → freshness alert fires before RPO elapses; pause WAL shipping → lag alert fires before RPO/2 elapsed; pause cross-region replication → freshness alert fires before RPO; backup from a lagging replica → effective-RPO alert fires.

**D7 · Monitoring and alerting system**
Emit alerts (each with an enforceable response-time SLA) for: backup job failure or invalid artifact (immediate); backup freshness breach — fires at RPO − response_buffer, not at RPO; WAL lag exceeding RPO/2; storage utilization at 75% and 90% (at 100%, backup job fails noisily, not silently); backup count per store per tier below floor; cross-region backup freshness beyond RPO; catalog integrity scan findings; backup schedule drift (actual start times logged; deviation beyond threshold alerts). Monitoring system itself has a watchdog (dead-man's switch fires if no heartbeat within RPO window).
*Falsifier*: kill backup job → alert fires within 5 min; stop backup → freshness alert fires while RPO is still achievable; fill storage to 90% → alert fires; delete one backup → count-floor alert fires before next scheduled backup; pause replication → freshness alert fires in time; corrupt catalog entry → alert fires within one scan cycle; let jobs slip → schedule-drift alert fires; kill monitoring system → watchdog fires within RPO.

**D8 · Restore drill program**
Calendar-enforced mandatory drill frequency per criticality tier (e.g., Tier-1: quarterly; Tier-2: semi-annual); maximum elapsed time between drills is a hard gate, not a target — missed drill is a formal incident. Each drill cycle covers: full-estate restore (at least annually), single-store, table-level, and region-failover scenarios. Drills run in an isolated environment version-locked to current production spec (same OS/DB version, hardware tier). Drills have objective pass/fail criteria: restore ≤ RTO, data within RPO, smoke tests pass. Per-step timing is logged; total is compared to RTO. Drill procedure uses the identical document and version as the real recovery runbook. Credential validity is pre-checked at drill start (expired credential is a drill blocker). Findings are tracked to closure — runbook version is bumped before a finding is closed; next drill cites the updated version.
*Falsifier*: drill log shows all scenario types exercised within cycle; drill environment spec verified against current prod spec before each drill; drill report shows objective pass/fail verdict; timing log shows per-step times summing ≤ RTO; drill cites runbook version matching real runbook; credential pre-check step present in drill log; missed drill triggers formal incident; no finding older than one drill cycle without a resolution ticket and runbook version commit.

## Dep — Cross-Component Dependency Seams

**Dep1 · WAL/log shipping → backup catalog → PITR restore path**
Log segments are deposited by the shipping agent; catalog records LSN and timestamp; PITR restore queries catalog to assemble the correct sequence. If the catalog lags, missequences, or drops a segment, PITR silently produces a gap without erroring.
*Falsifier*: restore to an arbitrary timestamp T within the log-shipping window; verify record state matches a known snapshot taken at exactly T.

**Dep2 · Base full backup integrity → incremental chain restorability**
All incrementals reference a base full backup. Silent corruption of the base makes every dependent unrestorable — the chain appears valid in the catalog but cannot be assembled.
*Falsifier*: corrupt the base full backup checksum; verify that a restore attempt fails with an explicit error, not silent data corruption.

**Dep3 · Retention engine → backup chain dependency check**
Retention policy may expire a full backup that still anchors an active incremental chain, eliminating the only restore path for all dependents.
*Falsifier*: configure retention to target a base backup with live dependents; verify deletion is blocked or the chain is explicitly sealed before the base is removed.

**Dep4 · Integrity check path = restore read path**
If the integrity check validates an artifact at storage path A but the restore process reads from path B (a stale copy, a different replica, or a redirected mount), the check provides no assurance.
*Falsifier*: corrupt a backup byte after integrity check passes; trigger restore from the same declared path; verify the mismatch is detected before restore completes.

**Dep5 · Alert threshold + on-call response time → RPO budget**
Setting the freshness alert threshold at RPO (not RPO − response_buffer) means human response time plus re-backup duration consumes the entire remaining window; RPO is breached before corrective action can complete.
*Falsifier*: verify alert_threshold + median_on_call_response_time + p99_backup_duration ≤ RPO for every store.

**Dep6 · DB restore point → encryption key version → decryptability**
A DB restored to time T1 was encrypted under the key version active at T1. If key rotation since T1 has not updated the escrow, the backup is unreadable. Applies across all rotation events since backup creation.
*Falsifier*: restore from a backup created before the most recent key rotation event, using only the escrowed key (primary key deliberately excluded from the test environment); all records are readable. [Collapses XS6 + XS12 + EB11 — all share this truth-maker and falsifier.]

**Dep7 · DB restore point → cache state → cross-store consistency**
Cache is restored to T2 > T1 (or not invalidated); DB is restored to T1. The cache holds stale-future entries for rows rolled back in the DB restore; application reads return wrong data with no error.
*Falsifier*: post-restore runbook mandates cache invalidation; smoke test reads a record known to differ between T1 and T2 — cache returns the T1 value, not the T2 value.

**Dep8 · Replica promotion → DNS/LB TTL → application write connectivity**
After replica promotion, DNS TTL too high or load-balancer rule not updated; clients continue directing writes to the dead primary address; writes are lost or rejected.
*Falsifier*: time from promotion command to first successful application write through the new primary endpoint; must be ≤ RTO.

**Dep9 · DB restore point → message queue consumer offsets → replay correctness**
DB is restored to T1; Kafka/RabbitMQ consumer offsets remain at T2 > T1; replay re-processes transactions already committed before T1, producing duplicates.
*Falsifier*: restore scenario with active queue shows zero double-processing of records committed before T1; consumer-offset rollback procedure exists and is exercised in drill.

**Dep10 · DB restore point → object store version → referential integrity**
DB is restored to T1; some DB rows reference object keys written between T1 and T2 that do not exist in the T1 object store, leaving dangling foreign-key references.
*Falsifier*: post-restore referential integrity check between all DB foreign keys referencing object store keys and the T1 object store key listing; zero dangling references.

**Dep11 · Infrastructure provisioning → backup inventory gate**
A new data store is deployed to production without being added to the backup inventory; no backup job ever runs; the gap is discovered only at recovery time.
*Falsifier*: provisioning pipeline has a hard gate — a store cannot be promoted to production until it appears in the backup inventory with a verified successful first backup.

**Dep12 · Drill environment spec → runbook applicability**
Drill runs on a lower-spec or different-version environment; the procedure appears to succeed; the real production restore fails or behaves differently due to hardware, OS, or DB version mismatch.
*Falsifier*: drill environment spec is compared against current production spec before every drill; any discrepancy is a drill finding, not a silent skip. [Collapses XS15 + DR3 + EB9.]

**Dep13 · Drill finding registry → runbook version → next drill validity**
A drill surfaces a procedural gap; the gap is not tracked; the next drill uses the same flawed runbook; gaps accumulate silently across drill cycles.
*Falsifier*: finding registry requires a runbook version bump before the finding can be closed; the subsequent drill log cites the updated runbook version. [Collapses XS13 + DR6 + DR7.]

**Dep14 · Backup sourced from read replica → replication lag → effective RPO**
Backup is taken from a read replica; replica lag is nonzero at backup time; effective RPO = RPO_stated + lag; this breach is not surfaced by normal freshness checks (which measure backup age, not effective data age from the primary).
*Falsifier*: replica lag is measured at each backup run when backup source is a replica; if lag makes effective RPO impossible, alert fires; backup is sourced from a lagged replica only when lag ≤ RPO − cadence. [SM2 — distinct from IF6/WAL lag and from Dep15.]

**Dep15 · Replica lag at promotion → unacknowledged transaction loss**
Replica promoted to primary at nonzero lag; the last N seconds of committed primary transactions are permanently lost; the application assumes zero data loss without any audit.
*Falsifier*: post-failover transaction audit compares last committed transaction ID on the old primary (from crash or WAL logs) against the promoted replica's last applied transaction; the delta is explicitly documented and either accepted via a data-loss approval process or reprocessed. [EB12 — distinct falsifier from Dep14: Dep14 is backup-quality, Dep15 is failover-loss acknowledgment.]

## V — Criteria (Decidable Predicates over the Produced Result)

**V1 · RPO formula compliance** — For every store: cadence + p99_backup_duration ≤ RPO_stated. Automated weekly audit; any violation is an incident. [GI1 + BC1 + XS11 — all same truth-maker.]
*Falsifier*: automated formula audit shows violation for any store.

**V2 · RTO formula compliance** — Sum of per-step restore/failover timings for each defined failure scenario ≤ RTO_stated. Measured in every drill.
*Falsifier*: drill timing log sum exceeds RTO for any scenario.

**V3 · Backup storage failure-domain independence** — After simulated primary-region loss, backups are fully accessible from the secondary region using only secondary-region credentials; no primary-region credential, network, or service is required.
*Falsifier*: simulate primary-region outage; attempt backup restore from secondary region without any primary-region credential; succeeds.

**V4 · No silent backup pipeline failure** — Any failure of any backup pipeline component (agent, network, storage, catalog) fires an alert before RPO − response_buffer elapses. The monitoring system itself has a watchdog that fires if the monitoring heartbeat is absent for > RPO.
*Falsifier*: kill each pipeline component in sequence; alert fires within RPO − response_buffer each time; kill monitoring system; watchdog fires within RPO. [GI4 + SM8.]

**V5 · Monotonic inventory coverage** — At all times, every data store in production is covered by the backup regime. Weekly diff of live infrastructure inventory against backup inventory returns zero gap. New stores cannot enter a coverage gap (enforced by Dep11 provisioning gate).
*Falsifier*: diff shows an uncovered store that has persisted beyond the defined grace period. [GI5 + SC1.]

**V6 · Restore correctness** — A restored system matches the pre-failure authoritative state on a sampled set of records. Injected-data test: known data written immediately before a simulated failure; post-restore verification finds all injected records present and uncorrupted.
*Falsifier*: injected record is absent or corrupted after restore. [GI6 + RF9 + IF3.]

**V7 · Catalog queryability** — Given any target recovery time T, the backup catalog identifies the correct backup set (full + incrementals + WAL segments) within the time budget allocated for catalog lookup in the RTO.
*Falsifier*: time catalog query for an arbitrary T; exceeds allocated lookup budget.

**V8 · Retention floor** — At any moment, at least one complete restore chain (full backup + incrementals + WAL segments) to a point within RPO of now exists per store and has not been expired.
*Falsifier*: audit: earliest usable restore point for any store is older than RPO before now. [GI8 + RT2.]

**V9 · Backup immutability** — Backups cannot be modified or deleted by any actor whose credentials could be compromised along with the production environment. Object Lock / WORM / air-gap enforced; immutability configuration is audited.
*Falsifier*: attempt to delete or overwrite a backup artifact using a production IAM role; operation is denied. [GI9 + SM7 + SB3 boundary.]

**V10 · Regime self-consistency** — All parameters are internally consistent: cadence + p99_backup_duration ≤ RPO; min_retention ≥ RPO + operational_response_buffer; cold-tier restore time ≤ RTO if cold restore is a valid path; drill frequency ≤ maximum tolerable runbook drift interval. No parameter combination makes another target impossible.
*Falsifier*: formal consistency check finds any contradiction among the above inequalities. [GI10.]

**V11 · Backup freshness alert threshold** — The alert for backup age fires at RPO − response_buffer, not at RPO itself, ensuring human response time and re-backup duration fit within the remaining RPO window.
*Falsifier*: stop the backup job; alert fires while a complete new backup can still finish before RPO elapses. [IF4 + MA2. Distinct falsifier from V12.]

**V12 · WAL lag alert threshold** — The alert for WAL/log shipping lag fires when lag reaches ≤ RPO/2, providing sufficient margin for corrective action.
*Falsifier*: pause WAL shipping; alert fires before lag reaches RPO/2. [IF6 + MA3. Distinct falsifier from V11: different subsystem, different threshold value.]

**V13 · Backup schedule adherence** — Actual backup start times are logged and compared to scheduled times; deviation beyond a defined threshold fires an alert. Schedule drift cannot accumulate silently into an RPO violation.
*Falsifier*: allow jobs to slip without component failure; schedule-drift alert fires before cumulative drift reaches the RPO − cadence margin. [SM10 — not covered by V4, which tests component kills, not timing drift.]

**V14 · Drill schedule enforcement** — A missed drill (beyond the maximum elapsed time for its tier) triggers a formal incident with a risk-acceptance process, not silent deferral. Last drill date is tracked in a registry.
*Falsifier*: simulate a missed drill; formal incident is raised; no silent skip occurs. [DR1 + EB3.]

**V15 · RPO/RTO target revision triggers regime review** — Any change to RPO or RTO targets for any store triggers a mandatory review and re-verification of backup cadence, retention policy, and drill schedule before the new target takes effect.
*Falsifier*: simulate an SLA change; the change management process blocks the new SLA effective date until the regime review is documented and signed off. [EB6 — distinct from all other V items.]

**V16 · Clock synchronization** — NTP synchronization is a monitored prerequisite on all backup hosts; clock skew beyond threshold fires an alert. Catalog timestamps used for PITR are trusted only when sync is current.
*Falsifier*: induce clock skew on a backup host; alert fires; PITR restore referencing timestamps from that host period is flagged as unreliable. [EB8 — distinct falsifier: skew does not stop jobs or lag WAL; it silently corrupts PITR windows.]

**V17 · PITR restorability for low-RPO stores** — For any store declared PITR-capable (RPO < 15 min), a restore to an arbitrary minute within the log-shipping window produces a system state that matches the authoritative record state at exactly that minute.
*Falsifier*: restore to an arbitrary minute T within the window; verify exact record state matches a known reference snapshot taken at T. [DP4 — distinct from V6: V6 tests pre-failure-point correctness; V17 tests arbitrary-minute precision across the full PITR window.]

**V18 · Encryption key escrow currency** — The key rotation procedure mandates an escrow update as an in-line step; the updated escrow is verified by the next scheduled key-escrow validation drill (restore using only the escrowed key, primary key excluded from test environment).
*Falsifier*: rotate a key; verify escrow update is in the rotation procedure record; next key-escrow drill succeeds using only the escrowed key. [EB11 + IF9 criterion layer — distinct from Dep6: Dep6 is the runtime seam; V18 is the process predicate that keeps Dep6 healthy.]

## N — Declared Scope Exclusions

**N1 · Logical / application-level data corruption** — A bug that writes semantically wrong values for weeks; backup faithfully preserves the corrupted data. Out of scope (backup fidelity ≠ data quality). Back in scope only if the regime explicitly commits to a PITR + data-quality-checkpoint recovery path and defines falsifiable criteria for it.
*Why safely out*: distinguishing "correct" from "incorrect" application-level data requires domain-specific quality checks that are the application's responsibility, not the backup regime's.

**N2 · Active-active replication infrastructure design** — Active-active is an architectural choice, not a backup. The replication infrastructure design is out of scope. Where active-active serves as the failover mechanism for a specific store, the regime must document it as such and verify tested RPO/RTO for that path.
*Why safely out*: the regime governs recoverability policy, not the topology that achieves it.

**N3 · Full security / ransomware incident response playbook** — The complete incident response is a security concern. Backup immutability (Object Lock, WORM, air-gap) and audit of immutability configuration are in scope. Cross-reference to the security incident runbook is required.
*Why safely out*: incident response spans far beyond data recovery; immutability is the data-recovery-relevant boundary.

**N4 · Application binary / deployment rollback** — Rollback of deployment artifacts is a CI/CD concern. This regime covers data state rollback only. The regime document explicitly delimits: "this regime restores data state, not application binaries."
*Why safely out*: binary rollback and data-state rollback are orthogonal; conflating them creates confusion about ownership and procedure.

**N5 · Development and staging environments (without prod data)** — Out of scope unless an environment holds a copy of production data (e.g., prod-clone staging), in which case that data is in scope regardless of environment label.
*Why safely out*: non-prod data loss carries no production RPO/RTO obligation; the regime document lists all in-scope environments explicitly.

**N6 · Compute, network, and orchestration layer rebuild** — Restoring the infrastructure layer (VMs, Kubernetes, networking) is an infrastructure DR concern. This regime assumes infrastructure is available or is being restored by a separate, cross-referenced runbook. The restore runbook has an explicit prerequisite: "infrastructure layer is operational."
*Why safely out*: data recovery and infrastructure recovery have separate ownership, tooling, and timelines; the regime document cross-references the infrastructure DR runbook.
