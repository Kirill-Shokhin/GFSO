## D — Subtasks / Components

**D.1 Entry data model + state machine**
Each entry carries: key, value, creation timestamp, TTL, last-access timestamp, dirty flag, version counter. State machine: absent → loading → present-fresh → present-stale → evicting.
*Falsifier*: omitting the dirty flag causes write-back to silently drop unflushable entries on eviction.

**D.2 Loading/population placeholder**
On a cache miss the entry moves to a "loading" placeholder before the backing read; other threads block on the same placeholder rather than each issuing their own backing read. The unblock mechanism must be explicit (condition variable, future/promise, or monitor) so that waiting readers are immediately signaled when the load completes or errors out — spin-polling is not acceptable.
*Falsifier*: load completes, placeholder replaced by real entry; blocked readers are never signaled and spin or sleep indefinitely rather than returning the loaded value. *(S2-2 folded)*

**D.3 Read path**
Lookup key → check existence → check expiry → acquire read lock → return value. Non-blocking for concurrent readers when no write is in progress.
*Falsifier*: global write lock on every read → serialised throughput, not concurrent.

**D.4 Write path**
Acquire write lock → check capacity → evict if needed → insert/update entry → set dirty or flush → release lock. Atomic with respect to readers.
*Falsifier*: reader sees the new key but not the new value (partial write visible).

**D.5 Eviction engine**
Selects and removes the victim entry per the chosen policy; callable both inline (on-write) and by the background sweeper.
*Falsifier*: eviction only on the write path means expired-but-not-written entries are never reclaimed (phantom fullness).

**D.6 TTL/expiry sweeper**
Background worker that periodically scans and removes expired entries without waiting for a read or write to trigger lazy expiry.
*Falsifier*: lazy-only expiry lets expired entries accumulate and exhaust capacity even when no writes arrive.

**D.7 Persistence adapter**
Abstraction over the backing store covering both directions: write operations (write-through: synchronous put before ack; write-back: enqueue to flush queue) and read operations (cache-miss load: issue read to backing store, apply timeout and retry policy, surface errors uniformly). All backing-store I/O passes through this component so that error handling, retry policy, timeout, and schema change impact only one path.
*Falsifier (write-only adapter)*: cache miss calls the backing store directly outside the adapter abstraction → error handling, retry policy, and timeout differ between the read and write paths; a backing-store schema change breaks only one path silently. *(S2-1 folded)*

**D.8 Write-back flush queue**
Ordered, bounded queue of dirty entries awaiting flush; implements back-pressure when the backing store is slow. Must perform per-key coalescing so that N writes to the same key between two flush cycles produce one flush entry (the latest version), not N entries.
*Falsifier*: unbounded queue allows dirty entries to accumulate in memory, defeating the cache's memory bound.

**D.9 Invalidation handler (receive side)**
Receives invalidation signals (local or remote) and removes or marks stale the specified entries.
*Falsifier*: absent handler → stale entries persist after an authoritative update elsewhere.

**D.10 Shard manager** *(merges items 6 + 19 from search_1)*
Owns the fixed (or explicitly versioned) shard count, the deterministic key → shard hash function, and the per-shard lock. Routes every key operation to exactly one shard.
*Falsifier*: non-deterministic routing sends reads and writes for the same key to different shards → two authoritative copies with no reconciliation.

**D.11 Background flush worker** *(merges items 20 + 58-flush from search_1)*
Periodically drains the write-back flush queue to the backing store; must be restartable and surface errors — it must not silently exit on the first failure.
*Falsifier*: silent exit on first backing-store error → all subsequent dirty entries remain unflushable indefinitely.

**D.12 Bulk / sweep-all operations** *(new — S2-5)*
Handles operations that span ALL shards: cache.clear(), capacity resize, and multi-key get. Acquires all shard locks in a globally consistent total order (same order as V.11) before mutating any shard; drains or coordinates with the flush queue before releasing index state on clear.
*Falsifier*: cache.clear() acquires shard locks in arbitrary order; concurrent cross-shard eviction or resize acquires them in a different order → deadlock. Or: clear() wipes the index without draining the flush queue → flush worker later writes already-cleared entries back to the backing store.

**D.13 Invalidation emitter (send side)** *(new — H3-1)*
Constructs and dispatches invalidation signals to peer cache nodes after a write. Must specify: which write events trigger emission (write-through completion, write-back flush confirmation, or both), the channel (queue, pub/sub, RPC), and the payload (key + version). Distinct from D.9, which handles the receiving side.
*Falsifier*: write-through completes; no emit step is implemented; peer nodes receive no signal and continue serving the old value indefinitely — Dep.7's requirement is stated but can never be satisfied without this component.

## Dep — Cross-Component Dependency Seams

**Dep.1 Write path → Eviction engine**
Eviction must complete and the victim must be fully removed (and flushed if dirty) before the new entry is inserted; the sequence must be atomic at the shard level.
*Falsifier*: insert before eviction completes → transient capacity breach; or new entry overwrites victim's slot before dirty flush → data loss.

**Dep.2 TTL expiry check → Read path** *(merges items 10 + 31 from search_1)*
The expiry check and the value return must occur within the same lock window; the lock must not be dropped between the check and the return.
*Falsifier*: expiry check passes, lock dropped, entry evicted, value returned is a dangling pointer / use-after-free; or entry appears fresh but expired between two lock windows.

**Dep.3 Write-back flush ↔ Eviction engine** *(merges items 9 + 32 + 57 from search_1)*
Evicting a dirty entry requires a synchronous flush before removal from the index; if flush fails the entry must not be removed; the dirty bit is cleared only after confirmed flush success.
*Falsifier*: dirty entry removed from index, flush then fails silently → data permanently lost with no error surfaced to the original writer.

**Dep.4 Invalidation handler → Read path**
An invalidation racing an in-flight read must not allow the read to return a value that was invalidated before the read's lock was acquired.
*Falsifier*: read begins, invalidation removes entry, read returns value from its local snapshot → stale value delivered despite invalidation.

**Dep.5 Shard manager → Lock protocol (cross-shard)**
A cross-shard operation must acquire both shard locks before mutating either shard; partial acquisition is forbidden.
*Falsifier*: shard A locked, entry removed; before shard B locked, another thread reads the key → key appears absent in both shards.

**Dep.6 Eviction engine ↔ TTL sweeper**
The eviction engine and the TTL sweeper may target the same entry simultaneously; only one must succeed in removing it; double-removal must not corrupt the capacity counter.
*Falsifier*: both remove the entry, decrement capacity counter twice → counter goes negative, allowing more entries than the limit.

**Dep.7 Write-through → Peer invalidation**
After a write-through to the backing store, all peer cache nodes must receive an invalidation before they serve reads for the updated key.
*Falsifier*: write-through completes, peer nodes still serve the old value → stale reads despite a durable write.

**Dep.8 Write-back flush queue ↔ Capacity bound**
Dirty entries in the flush queue count toward the capacity limit; only flushed-and-acknowledged entries may be reclaimed.
*Falsifier*: capacity computed from index only (not queue) → in-flight entries not counted → actual memory usage exceeds declared limit.

**Dep.9 Loading placeholder ↔ Invalidation handler**
An invalidation arriving while an entry is in the "loading" state must cause the completed load to be discarded rather than inserted.
*Falsifier*: invalidation received and marked for removal, load completes and inserts the stale value → invalidation silently reverted.

**Dep.10 Write path ↔ TTL (TTL reset policy on write)**
A write to an existing key must have an explicitly defined TTL behavior: either reset to full TTL or preserve the remaining TTL; the choice must be consistent across all callers.
*Falsifier*: reset when it should not → entries live longer than SLA; preserve when it should not → freshly inserted values expire immediately.

**Dep.11 Write-back flush ↔ Invalidation handler**
A dirty entry that receives an invalidation while queued for flush must not be flushed; the invalidation supersedes the write, or the flush must pass a version check before writing to the backing store.
*Falsifier*: invalidation removes entry from index, flush worker then writes the old value to the backing store → backing store silently reverted to stale state.

**Dep.12 Read path ↔ Write-back persistence (on miss)**
A cache miss triggers a load from the backing store; the loaded value must be inserted under the same lock that prevents a concurrent write from being overwritten by the load.
*Falsifier*: backing load starts; concurrent write updates the key; load completes and inserts old value, overwriting the newer write.

**Dep.13 Eviction engine ↔ Invalidation handler**
Concurrent eviction and invalidation of the same entry must be idempotent; double-removal must not corrupt the capacity counter or index.
*Falsifier*: both remove the entry; capacity counter decremented twice → index becomes inconsistent.

**Dep.14 Shard manager ↔ TTL sweeper**
The sweeper acquires the shard lock per-entry (or per-batch); it must not hold the lock for the entire scan of a shard.
*Falsifier*: sweeper holds shard lock for full scan → all reads and writes to that shard blocked for O(n) time.

**Dep.15 Eviction engine ↔ Read path (value lifetime)**
If an entry is evicted while a reader holds a reference to its value, the value buffer must remain valid for the reader's lifetime (copy semantics or reference counting).
*Falsifier*: eviction frees the underlying buffer; reader dereferences freed memory → crash or corrupt data.

**Dep.16 Read path → Eviction engine (metadata update)** *(new — S2-6)*
On every cache hit, the read path must update the entry's access metadata (last-access timestamp for LRU, frequency counter for LFU) atomically inside the shard lock, before releasing it.
*Falsifier*: last-access updated after the shard lock is released; eviction engine reads stale metadata and evicts a recently accessed entry; hit rate drops under concurrent read load with no error surfaced.

**Dep.17 Write path → Eviction engine (metadata refresh on update)** *(new — S2-7)*
Writing to an existing key must refresh its position in the eviction order (move to MRU tail for LRU; increment or reset counter for LFU) inside the shard lock at write time. Distinct from Dep.16 which covers the read-hit path.
*Falsifier*: LRU cache; key is written repeatedly; last-access not updated on write → key sits at the LRU tail and is evicted on the next capacity pressure despite being actively written.

**Dep.18 Flush worker ↔ Shutdown sequencer** *(new — S2-9)*
The shutdown signal must reach the flush worker, the worker must drain the queue completely, and the main thread must wait (join/await) for that drain before releasing resources or exiting.
*Falsifier*: shutdown closes the queue (worker can no longer dequeue) then terminates the worker thread → worker exits immediately without draining; dirty entries silently lost despite V.25 requiring flush completeness.

**Dep.19 TTL sweeper → Loading placeholder (skip rule)** *(new — S2-10)*
The sweeper must skip entries whose state is "loading" even if their creation timestamp exceeds the TTL; only entries in a completed state are eligible for expiry removal.
*Falsifier*: sweeper timestamps a loading placeholder as expired and removes it; the in-flight backing load completes and inserts the value into a vacated slot outside the shard index → capacity counter not decremented on removal; new entry not counted in capacity; effective capacity drifts above limit.

**Dep.20 Read path → TTL expiry deadline reset (sliding TTL)** *(new — H3-2)*
When sliding TTL is in effect, a cache hit must atomically reset the entry's expiry deadline (not merely its last-access timestamp) inside the shard lock before releasing it. The sweeper (D.6) reads the expiry deadline independently; without this seam the two components are uncoordinated.
*Falsifier*: sliding TTL configured; read hit updates last-access (satisfying Dep.16) but does not reset the expiry timestamp; sweeper runs, finds the timestamp past deadline, and evicts an actively-accessed entry; caller receives a spurious cache miss with no error — hit rate silently degrades under read-heavy workload.

**Dep.21 Shard lock scope during dirty eviction flush** *(new — H3-3)*
When evicting a dirty entry, the backing-store I/O (flush) must not execute while the shard lock is held, because I/O latency under lock serializes the entire shard. But releasing the lock before flush creates a limbo window: the entry is absent from the index but not yet in the backing store. The protocol must explicitly handle this window — e.g., mark the entry as "evicting-dirty" and make it visible but read-only to concurrent threads during the window, or insert a sentinel that redirects concurrent misses to the in-progress flush result.
*Falsifier*: shard lock released before flush completes; concurrent miss reader goes to the backing store, gets the pre-write value, and inserts it as a fresh cache entry; flush then writes the new value to the backing store; cache holds the old version while the backing store has the new one — cache and backing store silently diverge until the stale cache entry expires or is next evicted. (Distinct from Dep.3, whose falsifier is data loss on flush failure, not divergence via a concurrent miss during the flush window.)

**Dep.22 Write path ↔ Flush queue (saturation protocol)** *(new — H3-5)*
The write path must declare a concrete response when the flush queue is at capacity: (a) block the calling thread (risks deadlock if the caller holds a shard lock that the flush worker needs to dequeue), (b) return an error to the caller (changes the write API contract), or (c) force an inline synchronous flush (risks holding the shard lock during backing-store I/O, conflicting with Dep.21). Each option has a distinct failure mode; the choice must be explicit and consistent.
*Falsifier*: backing store slow; flush queue fills to capacity; write path blocks the calling thread while that thread holds a shard lock; flush worker needs to acquire the same shard lock to progress → deadlock; system hangs with no timeout or error recovery signal.

**Dep.23 Shard lock release during miss load I/O** *(new — H3-6)*
On a cache miss, the shard lock must be released before the backing-store I/O begins (after the loading placeholder is installed); it must be re-acquired after the load completes to insert the result or handle failure. This release-I/O-re-acquire protocol is distinct from the race Dep.12 describes (concurrent write arriving during the I/O window).
*Falsifier*: cache miss; shard lock held while backing-store read is in flight; 50 ms backing-store latency; all other threads targeting that shard block for 50 ms per miss; under moderate miss rate, shard throughput degrades to single-thread serialization — indistinguishable from a global lock, detectable only under realistic miss-rate load.

## V — Criteria

**V.1 Capacity unit uniformity**
The capacity limit is expressed in a single unit (entry count or byte budget) applied uniformly across all paths.
*Falsifier*: mixing count and byte limits in different paths allows silent capacity breach.

**V.2 Eviction policy identity**
Exactly one eviction policy (LRU, LFU, CLOCK, FIFO, or TTL-first) is chosen and consistently applied to every eviction decision.
*Falsifier*: two code paths using different policies produce non-deterministic capacity behavior under load.

**V.3 TTL semantics uniformity**
TTL is defined as either fixed (from insertion) or sliding (reset on read) and the choice is uniform across all entries.
*Falsifier*: mixed semantics → entries expire at unpredictable times, breaking the staleness SLA.

**V.4 Write mode global policy**
The persistence mode (write-through or write-back) is a single global policy with a well-defined ack point.
*Falsifier*: per-entry mode mixing → durability guarantees cannot be reasoned about.

**V.5 Entry state transition atomicity**
All state transitions in the entry state machine are atomic from other threads' perspectives; no thread observes an entry in a partial-transition state.
*Falsifier*: thread observes entry mid-transition (e.g., value set but TTL not yet written).

**V.6 Version ordering on flush** *(merges items 11 + 64 from search_1)*
Each write increments a monotonic version counter; flushes must compare versions before writing to the backing store so that an older flush cannot revert a newer one.
*Falsifier*: two concurrent writes to the same key — slower write flushes after faster one, silently reverting the newer value; or flush writes version N after version N+1 has already been flushed to the backing store.

**V.7 Capacity: no transient breach**
At no point does the number (or total byte size) of entries exceed the declared limit, even transiently between eviction and insertion.
*Falsifier*: insert-then-evict ordering allows one extra entry to exist momentarily, violating a hard limit.

**V.8 No-lost-write: concurrent writes serialize**
Concurrent writes to the same key resolve to exactly one winner; the losing write is either rejected or explicitly superseded — no partial field interleaving is observable.
*Falsifier*: two writers both succeed; later reader sees an arbitrary interleaving of partial field updates.

**V.9 Read-your-writes**
A thread that writes a key and then reads it sees its own write, not a prior value or a stale cache entry.
*Falsifier*: write goes to shard A's write buffer; read hits shard A's read path before the buffer is applied → stale read.

**V.10 Bounded staleness (TTL)**
No entry is returned to a caller after its TTL has elapsed; at most one sweeper-interval tolerance is acceptable only if explicitly declared.
*Falsifier*: expired entry returned because the expiry check uses wall clock but the entry timestamp was set with a different clock source.

**V.11 Deadlock freedom: multi-lock acquisition order**
Any operation acquiring multiple locks (cross-shard move, flush + eviction, bulk clear, etc.) acquires them in a globally consistent total order.
*Falsifier*: shard A → shard B in one path and B → A in another → classic deadlock under concurrent cross-shard operations.

**V.12 Durability invariant (write-through)**
A successful write-through ack implies the value is in the backing store; a crash after the ack must not lose the entry.
*Falsifier*: cache updated and ack sent before the backing-store write completes → crash loses the write.

**V.13 Crash-safe dirty bound (write-back)**
Dirty entries × max entry size must not exceed available process memory; flush must be triggered before that bound is reached.
*Falsifier*: flush only on eviction with a slow backing store allows dirty entries to fill all memory.

**V.14 Liveness of background workers** *(merges items 28 + 58-sweeper from search_1)*
The sweeper and flush worker are not starveable by high-throughput read/write operations and do not exit on transient errors.
*Falsifier*: sweeper holds a low-priority lock never granted under write load → expired entries and dirty data accumulate forever.

**V.15 Consistent shard routing** *(merges items 29 + 59 from search_1)*
All threads agree on the shard topology at any moment; shard-count changes require a coordinated transition; no thread uses a cached shard-map from before the transition.
*Falsifier*: one thread rehashes while another is mid-operation → key routed to wrong shard during transition; or thread uses stale shard-map post-resize → key appears absent in the old shard, causing spurious backing-store load or duplicate copy.

**V.16 Write-through: cache–backing-store divergence on write failure**
If the backing-store write fails after the cache is updated, the cache must either roll back or surface the failure; silent divergence is not acceptable.
*Falsifier*: backing-store write fails, cache shows new value, no rollback → future eviction causes reads to return the old backing-store value without error.

**V.17 Invalidation reliability**
The invalidation delivery path must either guarantee delivery or provide a re-sync / TTL-bounded fallback so that stale values do not persist indefinitely after a dropped message.
*Falsifier*: invalidation dropped (network partition, queue overflow) → receiving nodes serve stale values indefinitely with no timeout or re-sync mechanism.

**V.18 Capacity counter accuracy**
The capacity counter accounts for all live data including metadata overhead (key length, timestamps, pointers), not just payload bytes.
*Falsifier*: OOM kill despite capacity appearing below the declared limit; detected only post-mortem.

**V.19 Lock re-entrancy safety**
No component may acquire a shard lock it already holds; the call graph must not permit recursive lock acquisition on the same shard.
*Falsifier*: indirect call chain acquires shard lock A twice → deadlock that only manifests at runtime, not in code review.

**V.20 Loading placeholder cleanup on error and timeout** *(S2-14 folded)*
A failed backing load must remove the loading placeholder and unblock waiting readers with an error; no residual placeholder may remain in the index. Additionally, a maximum loading duration must be declared; if the backing store neither responds nor errors within that duration, the placeholder must be evicted and all waiting readers unblocked with a timeout error.
*Falsifier (error path)*: failed load leaves placeholder in index → all subsequent readers for that key block indefinitely.
*Falsifier (hung backing store)*: backing store hangs (TCP connection open, no data); loading placeholder stays in the index forever; all readers for that key block indefinitely with no timeout mechanism.

**V.21 Approximate eviction accuracy declaration**
If an approximate eviction policy (sampled LRU, CLOCK, etc.) is used, the implementation must declare the accuracy bound; under load the eviction-order degradation must not silently reduce the hit rate beyond that declared bound.
*Falsifier*: hit rate drops under load with no error or metric surfaced; only detectable post-mortem via monitoring.

**V.22 Capacity = 1 correctness**
With a single-entry cache, every write evicts the current occupant; the evict-then-insert sequence must not leave the cache empty after the write and must not deadlock.
*Falsifier*: eviction cascade removes the newly inserted entry, leaving the cache empty while the insert returned success.

**V.23 TTL = 0 or negative rejection**
A TTL of zero or negative must be rejected at insert time or treated as immediate expiry (entry never stored or immediately evicted).
*Falsifier*: TTL=0 entry stored, read returns it before the sweeper runs → effective TTL is the sweeper interval, not zero.

**V.24 Null / zero-length value (negative caching)**
A null or zero-length value must be representable and distinguishable from a cache miss; it is a valid cached result.
*Falsifier*: null value treated as absent → every read for a null-valued key triggers a backing-store load (miss stampede).

**V.25 Shutdown flush completeness**
The write-back cache must flush all dirty entries before process exit; the shutdown sequence must not skip the flush.
*Falsifier*: process exits, dirty entries lost, backing store out of date with no error logged.

**V.26 Hot-key / shard hotspot**
Under key-skewed access, throughput must not degrade to single-shard serialization beyond a declared tolerance; the design must account for hot-key scenarios.
*Falsifier*: throughput scales linearly with shard count in tests but degrades to single-shard throughput in production due to a hot key.

**V.27 Clock skew (multi-node TTL)**
TTL expiry across nodes must not rely on synchronized wall clocks without declaring a divergence tolerance; unsynchronized clocks cause inconsistent expiry.
*Falsifier*: entry expires on node A before node B due to clock skew; node B serves a stale value after node A has already rejected it.

**V.28 Hash collision key distinctness**
Two distinct keys mapping to the same shard slot must be stored and retrieved independently; hash equality must not be treated as key equality.
*Falsifier*: key2 lookup returns key1's value because hash equality is treated as key equality.

**V.29 Invalidation storm / thundering herd**
Mass cache invalidation must not produce O(N) simultaneous backing-store reads; the fill path must include rate-limiting, jitter, or coalescing.
*Falsifier*: cache flushed, all threads simultaneously miss all keys, backing store receives O(N) simultaneous reads and collapses.

**V.30 Entry size exceeds shard capacity**
A single entry whose byte size exceeds one shard's byte limit must be rejected cleanly at insert time, not admitted and then immediately evicted in a loop.
*Falsifier*: oversized entry inserted, immediately evicted; insert returns success but the value is unretrievable.

**V.31 Reinsert of just-evicted key**
A key evicted in the same operation must be immediately re-insertable; eviction must leave no residual bookkeeping ("ghost" entry) that blocks re-insertion.
*Falsifier*: evicted key still present in eviction bookkeeping → second insert fails or creates a duplicate.

**V.32 Write-back flush partial failure handling**
A partial batch flush where some entries succeed and others fail must clear the dirty flag only for successful entries; failed entries must remain dirty and be retried individually.
*Falsifier*: all-or-nothing retry re-flushes already-committed entries → duplicate writes or overwriting of newer backing-store state.

**V.33 Capacity accounting scope declared** *(new — S2-3)*
The implementation must explicitly declare whether the capacity limit is enforced per-shard or globally; both options have distinct failure modes that must be acknowledged.
*Falsifier (per-shard)*: hot shard hits its per-shard limit and evicts while cold shards have free slots → effective cache size is a fraction of the declared limit under key skew.
*Falsifier (global)*: global counter is a shared mutable integer updated on every insert/evict under high write load → counter becomes a serialization bottleneck or drifts under concurrent increment/decrement without CAS.

**V.34 LFU frequency counter decay** *(new — S2-4)*
If LFU is the chosen eviction policy, frequency counters must decay (age) over time so that a historical access burst does not permanently dominate the eviction order.
*Falsifier*: LFU mode, startup burst inflates counters to 10^6; new entries with counter=1 are always evicted first; cache never adapts to a changed access pattern; hit rate collapses under workload shift with no error surfaced.

**V.35 Write-back flush queue per-key coalescing** *(new — S2-8)*
N writes to the same key between two flush cycles must produce exactly one flush entry (the latest version); the queue must not grow proportionally to write rate for a hot key.
*Falsifier*: hot key updated 10^6 times between flush cycles; queue stores 10^6 entries; queue memory limit reached and back-pressure fires even though backing-store state needs only one write; or flush worker issues 10^6 redundant writes under load.

**V.36 Value serializability gate (write-back)** *(new — S2-11)*
In write-back mode, a value that cannot be serialized for the backing store must be rejected at insert time, not admitted and then silently stuck in the flush queue.
*Falsifier*: application inserts a value containing a live file handle; insert succeeds, dirty flag set; flush worker encounters serialization error on every retry; dirty entry occupies its slot indefinitely; capacity reclamation blocked; no error surfaced to the original caller.

**V.37 Backing-store degraded mode policy** *(new — S2-12)*
The required behavior when the backing store is unreachable must be explicitly declared: fail-writes, serve-reads-only, queue-indefinitely (write-back), or other. Silence is not an acceptable policy.
*Falsifier*: backing store goes down; write-through cache rejects all writes with no declared policy; callers receive errors with no degraded-read-only mode; or write-back queue fills to back-pressure limit and all writes block indefinitely — both behaviors are silent without an explicit policy decision.

**V.38 Write-through operation order** *(new — S2-13)*
The write-through implementation must declare which write completes first — backing-store or local cache — and must handle the failure mode of the first write succeeding but the second failing without silent divergence.
*Falsifier (backing-store-first)*: backing-store write succeeds; local cache update fails (e.g., hash-table resize OOM); cache still holds the old value; next read triggers a backing-store load that returns the new value — cache and backing store transiently diverge with no error surfaced to the caller.
*Falsifier (cache-first, already in V.16)*: backing-store write fails after cache is updated → covered by V.16; this criterion is distinct in addressing the opposite ordering.

**V.39 Lock granularity within a shard — throughput floor declaration** *(new — S2-15)*
If a single lock is used per shard, the implementation must declare the expected throughput floor under many-distinct-key concurrent writes to the same shard and confirm it meets the concurrency requirement. Per-entry locking within a shard is an alternative; the choice must be explicit.
*Falsifier*: shard contains 10,000 entries for 10,000 distinct keys; 100 threads each writing a different key in that shard serialize on the single shard lock → write throughput scales as 1/N with thread count rather than 1/shard-count; only detectable under realistic write load.

**V.40 Out-of-order invalidation version filtering** *(new — H3-4)*
Invalidation signals must carry the version of the write that triggered them; the invalidation handler must reject a signal whose version is older than the current entry's version counter. If two invalidations for the same key arrive out of order (I2 before I1, where W1 < W2), the late-arriving I1 must not remove or stale the value written by W2.
*Falsifier*: two rapid writes to the same key emit invalidations I1 (version 1) and I2 (version 2); I2 is processed first, cache re-populated; I1 arrives late with no version check, removes the current-version-2 entry; subsequent reads miss and load version 1 from the backing store with no error or metric surfaced — cache silently regresses to an older state.

## N — Scope Exclusions

**N.1 Distributed consensus (Raft/Paxos)**
Out of scope: strong consistency across nodes requires a consensus protocol, a full subsystem. Pulled back in only if the requirement is "all nodes agree on every write before ack."
*Why safely out*: task specifies an in-memory store with sharding, not a replicated state machine.

**N.2 Write-ahead log / crash recovery**
Out of scope for write-back unless the durability SLA requires recovery after crash; if required, a WAL or journal must be explicitly designed as a separate subsystem.
*Why safely out*: an in-memory cache is understood to be volatile; durability is delegated to the backing store.

**N.3 Network protocol between shards/nodes**
Out of scope if sharding is within a single process (thread-per-shard). Pulled in if nodes are separate processes or machines.
*Why safely out*: task does not specify distributed deployment; "nodes" may mean CPU cores.

**N.4 Cache warming / pre-loading**
Out of scope: pre-populating the cache on startup is an operational concern, not a correctness mechanism.
*Why safely out*: does not affect the correctness of read/write/evict/invalidate paths.

**N.5 Authentication / access control**
Out of scope: no per-key ACL or caller identity requirement is stated.
*Why safely out*: task is about internal store logic, not multi-tenant isolation.

**N.6 Observability / metrics**
Out of scope as a delivered feature, but hit rate, eviction rate, and dirty-queue depth are required instrumentation points for verifying other criteria.
*Why safely out*: metrics are not part of the cache logic; they belong in the test/monitoring harness.

**N.7 Read-repair / multi-writer mode** *(new — S2-16)*
Out of scope if the system operates in single-writer mode (only the local cache writes to the backing store). If multi-writer mode is in scope (multiple processes or nodes writing to the backing store), read-repair — detecting on a cache hit that the backing store holds a newer value — must be explicitly included. The task says "many threads or nodes" which does not rule out multi-writer; this exclusion is safe only under the single-writer assumption, which must be declared.
*Why safely out (conditional)*: single-writer assumption is the default for an in-memory cache with a persistence adapter; pull in explicitly if external writers are confirmed in scope.
