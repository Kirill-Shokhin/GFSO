# T05 — Canonical Basis D1

---

## D — Components (separable pieces of work to design)

**D1. SLO specification** — Define per-endpoint SLIs (precise "good event" semantics: status-code range, latency threshold per tier, exclusion of health-check traffic); p50/p99/p999 latency targets per endpoint class; error-rate target enumerating all error classes (5xx, timeouts, circuit-open responses, partial-content failures); error-budget arithmetic (shared, verified formula); window type (rolling vs calendar) with documented rationale.

**D2. Burn-rate alerting design** — Define fast-burn (1 h window, ~14× rate) and slow-burn (6 h window, ~6× rate) alert pairs; predictive/trend alert (projected exhaustion within X hours); real-time burn rate as a continuously tracked metric (not computed only at alert time); graduated error-budget depletion gates at defined thresholds (e.g., 50%, 75%, 90%) triggering governance responses.

**D3. Signal instrumentation** — Instrument: request latency histograms (histogram type, not summaries, sufficient bucket resolution); error rate per endpoint (4xx vs 5xx separated, retriable vs non-retriable); RPS/QPS (including silent drop as failure signal); saturation signals (CPU, memory, thread pool, fd, connection-pool depth per instance); per-downstream-dependency p99 + error rate; queue depth and consumer lag; cache hit rate per tier; circuit breaker state (open/closed/half-open per dependency); synthetic/canary probes (external, realistic requests, scheduled); DNS resolution time + failure rate; TLS certificate days-to-expiry; LB queue depth and connection rejections; GC/runtime pause duration and frequency; upstream traffic shape (payload size, batch size, streaming mix); node/host-level health (CPU steal, disk I/O latency, memory pressure); autoscaler headroom (replica count vs max ceiling); error budget burn rate (real-time).

**D4. Alert configuration** — Multi-window burn-rate alerts (fast + slow, per D2); per-dependency degradation thresholds that fire before service SLO alert fires; saturation leading-indicator thresholds (70–80% of ceiling, tuned per resource type); alert severity tiers (page / ticket / informational) with correct categorization; hysteresis/flap suppression (persist N windows before fire, clear M windows before resolve); maintenance-window suppression narrowly scoped to affected components only; alert ownership and routing to on-call rotation; alert-to-runbook linkage for every actionable alert; escalation timeout in alerting system (primary non-ack → secondary → incident commander); synthetic probe thresholds (consecutive failures, not single miss).

**D5. Load shedding mechanism** — Admission control at ingress/gateway layer; request prioritization by business criticality (high-priority shed last); graceful degradation responses (stale/reduced content, with observability for degraded-mode rate); backpressure signaling (429/Retry-After with correct semantics); health-check/readiness-probe traffic explicitly exempted from shedding; activation threshold (trigger condition tuned to avoid premature or late activation); per-client/per-tenant fairness (token bucket or fair queue); controlled overload queuing (bounded depth + measurable wait) vs hard rejection at ceiling; dependency-directed shedding (shed requests requiring a degraded dependency before they consume resources reaching the point of failure).

**D6. Autoscaling configuration** — HPA metric selection driven by the signal causally closest to SLO breach (request latency, RPS, queue depth — not CPU alone for I/O-bound services); asymmetric cooldowns (scale-up fast: 30–60 s; scale-down slow: 5–10 min); scale ceiling set to respect downstream limits (DB connections, dependency rate limits); scale floor ≥ 2 for HA (no single-instance cold-start risk); pod warm-up with readiness probe gated on warm state (not just process start); pre-scaling for known predictable spikes; node autoscaler buffer (spare node capacity or pre-provisioning to avoid Pending pods); autoscaler polling interval and metric aggregation window short enough to react before SLO breach; VPA/HPA conflict resolution (not both active simultaneously without coordination); connection pool sizing co-designed with max replica count; autoscaling observability (scale events logged, ceiling-hit alert distinct from normal scaling).

**D7. Failover and resilience layer** — Per-dependency independent circuit breakers with documented open/half-open/close thresholds; timeout hierarchy (per-hop: parent timeout > child timeout + network RTT); retry budget (per-request and per-time-window ceiling); exponential backoff with full jitter on retries; bulkhead isolation (separate thread pools/connection pools/semaphores per dependency); fallback strategy per dependency (tested in drills, with own SLI); multi-region/AZ failover procedure (automated where possible, regularly tested); connection draining on failover/restart (in-flight requests complete or timeout before LB removal); cascading failure detection with chokepoint (multiple simultaneous dependency failures detectable as correlated, not independent); idempotency or deduplication keys for non-idempotent operations to make retries safe; active-active vs active-passive topology explicitly chosen and documented with consistency tradeoffs.

**D8. Escalation and incident management** — 24/7 on-call rotation with no gaps (primary/secondary/incident commander roles explicit); escalation timeout enforcement in alerting system (not just process); runbook currency (reviewed and updated after each incident); incident declaration thresholds (explicit P1/P2 criteria, e.g., >X% budget burned in Y hours); customer-facing status page update triggered at declaration; war room / incident bridge pre-defined; post-incident review triggered automatically for P1/P2 or budget-gate breach; error budget exhaustion governance enforced in CI/CD pipeline (not policy-document only); role separation between incident mitigation and customer communication.

## Dep — Cross-component dependency seams

**Dep1. Load shedding → Autoscaler signal** — Shedding reduces accepted RPS; if HPA uses RPS as its scaling signal, shedding causes scale-down exactly when capacity is most needed. *Breaks: capacity removed during overload; shed lifted; service immediately overloaded with fewer replicas.*

**Dep2. Autoscaler scale-out → Latency SLO (cold start)** — New pods have higher latency until JIT cache warms, caches populate, pools fill; p99 spikes during scale-out even though capacity is increasing. *Breaks: alert fires on symptom of scale-out, not genuine degradation; responder acts on wrong cause.*

**Dep3. Circuit breaker open → Error budget** — Fast-fail (503/fallback) responses from open circuits consume error budget; protecting latency SLO can accelerate error-budget depletion simultaneously. *Breaks: team celebrates latency stability while error-rate SLO breaches unnoticed.*

**Dep4. Retry amplification → Dependency overload** — Client retries multiply effective RPS to a degraded dependency; amplification can push a partially degraded dependency into full failure. *Breaks: partial failure becomes total failure under retry amplification.*

**Dep5. Autoscaler scale-out → DB connection pool** (merges Group 5 "Scale-out ↔ connection pool" and Group 8 "Autoscaling ↔ DB connection pool") — Each new replica opens N connections; if HPA_max × N > DB max_connections, scale-out itself causes connection exhaustion. *Breaks: scale-out triggers a second, self-inflicted DB failure.*

**Dep6. Cache miss thundering herd → DB/origin** — After cache flush, restart, or failover, all concurrent requests miss and simultaneously hit DB/origin; spike proportional to request concurrency. *Breaks: cache failover triggers DB overload and latency SLO breach.*

**Dep7. Maintenance alert suppression → Concurrent failure visibility** — Broad suppression scoped to a component masks simultaneous unrelated failures that start during the suppression window. *Breaks: independent incident starts during maintenance window; detected only by customer reports.*

**Dep8. Per-replica bulkhead state → LB routing** — Bulkheads limit threads per replica; LB has no visibility into per-replica bulkhead utilization; routes to already-exhausted instances. *Breaks: fraction of requests slow-fail immediately while remaining capacity is idle.*

**Dep9. Parent timeout < child timeout + RTT** (merges Group 6 "Timeout hierarchy" falsifier and Group 8 "Timeout cascade") — Parent times out and retries while child is still processing first request; 2× load per request under moderate traffic. *Breaks: cascade from timeout-mismatch under otherwise manageable load.*

**Dep10. Graceful degradation responses → SLI accounting** — HTTP-200 degraded responses (stale data, reduced content) counted as "good" in SLI; latency and content SLO violations invisible in error budget. *Breaks: hours of real user impact with budget showing healthy.*

**Dep11. Shed requests → SLO accounting** (distinct from Dep10: different HTTP semantics, different falsifier) — Shed (429) requests excluded from SLI denominator; reported availability exceeds actual user-experienced availability. *Breaks: budget appears healthy while significant user-facing error rate exists.*

**Dep12. Pre-scaling action → Error budget** — Pre-scaling deployment or configuration change itself introduces errors; the act of preparing for a spike burns budget before the load arrives. *Breaks: mitigation consumes budget before the load it was meant to handle.*

**Dep13. Scale-event noise suppression → Genuine saturation visibility** — Saturation alerts suppressed during scale-out to reduce noise; genuine saturation occurring simultaneously is also suppressed. *Breaks: OOM kills or memory pressure during scale-out go undetected.*

**Dep14. Failover traffic → Destination-region autoscaler** — Traffic rerouted to failover region may exceed pre-provisioned capacity; failover region autoscaler starts cold and scale-out takes minutes. *Breaks: latency SLO breaches in failover region during an otherwise successful failover.*

**Dep15. Circuit half-open probe → LB routing** — Each replica has independent circuit state; LB may route the half-open probe to a different replica than the open-circuit ones; circuit never closes on those replicas. *Breaks: majority of traffic continues fast-failing after the underlying dependency recovers.*

**Dep16. Error budget gate → Deployment pipeline enforcement** — Budget-threshold deployment freeze exists as policy only, not enforced in CI/CD; bypassed under pressure during incidents. *Breaks: engineer manually deploys during incident; new failure; budget hits zero.*

**Dep17. Incident commander role → Status-page communication** — If mitigation and customer communication are the same person, status updates lag while engineer is heads-down on mitigation. *Breaks: extended customer-facing silence during active incident; support ticket flood duplicates response effort.*

## V — Criteria (decidable predicates over the produced design)

**V1. SLI unambiguity** — Given the same metric data, any two engineers reach the same pass/fail verdict for each SLO. *Falsifier: ambiguous "good request" definition.*

**V2. Per-endpoint SLO isolation** — A breach on a low-volume critical endpoint triggers an alert even when aggregate metrics are within target. *Falsifier: checkout p99 doubles; aggregate p99 unchanged; no alert.*

**V3. Slow-burn coverage** — A sustained error rate at 2–3× background level triggers an alert before budget is fully exhausted. *Falsifier: 15-day slow drain to 0% with no page.*

**V4. Latency SLO survives successful failover** — Cross-region latency overhead is explicitly modeled; if failover adds latency that breaches the SLO, this is documented as an accepted consequence with a defined threshold. *Falsifier: failover succeeds; latency SLO breaches; team unaware this was expected.*

**V5. Metric collection failure is detectable** — Loss of telemetry itself triggers an alert (absence of data ≠ good data). *Falsifier: scrape fails; dashboard shows last-known-good; outage runs undetected.*

**V6. Short-duration spike is explicitly handled** — The design explicitly addresses bursts shorter than scale-out time; documented reliance on pre-provisioning + load shedding, not reactive autoscaling. *Falsifier: 30-second burst always breaches SLO; autoscaling assumed but cannot respond in time.*

**V7. Partial dependency failure is detectable** — Per-dependency, per-endpoint signals exist such that degradation of a subset of a dependency's endpoints fires an alert. *Falsifier: DB read replica degraded; aggregate DB error rate below threshold; no alert.*

**V8. Circuit breaker stuck open is detectable** — An alert fires if any circuit remains open longer than a defined duration after the dependency's own health metric recovers. *Falsifier: DB recovers; circuit stays open 2 hours; service in fallback; no alert.*

**V9. Traffic shape change without volume change is handled** — The autoscaling or shedding signal is not volume-only; shape changes that increase per-request processing time trigger a response before SLO breach. *Falsifier: payload 3× larger; RPS unchanged; CPU-based HPA blind; pool exhaustion.*

**V10. Test/staging traffic excluded from SLI** — Synthetic test traffic does not dilute error rates or inflate the SLI denominator. *Falsifier: load test against production; real user error rate masked.*

**V11. Health-check traffic is never shed** — Load-shedding logic explicitly exempts health-check and readiness-probe requests from all shedding tiers. *Falsifier: health check hits rate limit; LB marks instance unhealthy; fleet shrinks; cascade.*

**V12. Runbook mitigation cost is documented** — Each runbook step that itself burns error budget (e.g., rolling restart) has its error cost quantified and noted. *Falsifier: rolling restart causes 503 spike; responder unaware the mitigation itself has a cost.*

**V13. SLO targets reviewed on a defined cadence** — Review schedule and trigger conditions are specified; stale targets are not acceptable. *Falsifier: targets set at launch, never revised; avoidable user pain normalized.*

**V14. Autoscaler ceiling-hit generates a distinct alert** — Autoscaler reaching max_replicas under continued traffic growth fires a signal distinct from normal scaling activity. *Falsifier: HPA at max for hours; nobody paged; first signal is SLO breach.*

**V15. Alert rule validity is tested before deployment** — New alert rules are validated (correct metric name, correct threshold unit, correct condition polarity) before going live. *Falsifier: alert deployed with inverted condition; silenced immediately; real condition never fires.*

## N — Scope exclusions

**N1. Deployment orchestration tooling** — Canary/blue-green deployment mechanics and rollback tooling are out. *In-scope pull-back*: deployment freeze enforced in CI/CD at budget thresholds, and the effect of any deployment on SLO, are in scope.

**N2. Data durability and backup/restore** — RPO, backup mechanics, and data recovery procedures are out. *In-scope pull-back*: cold-start latency/error impact from a service restart triggered by data loss is in scope.

**N3. Security incident response (non-volumetric)** — Authentication failures, credential compromise, and non-volumetric attacks are out. *In-scope pull-back*: admission control and shedding responses to volumetric DDoS that affect the operating regime are in scope.

**N4. Client-side behavior** — Browser-side retry logic and client error handling are out. CDN configuration (TTL, error pass-through) directly determines user-perceived SLO and is in scope; CDN misconfiguration serving stale 503s is an operating-regime failure mode.

**N5. Long-horizon capacity planning** — Multi-quarter demand forecasting and hardware procurement are out. *In-scope pull-back*: the scale ceiling and minimum pre-provisioned capacity values that bound autoscaling behavior, and their review cadence, are in scope.

**N6. Correctness / data quality SLO** — Whether the service returns correct results is out of scope for this operating regime (latency + error-budget only). Requests returning incorrect data without an HTTP error are a declared SLI gap; the design must explicitly mark this boundary. *In-scope pull-back*: if correctness failures manifest as latency anomalies (e.g., fallback path is detectably faster or slower), they become in scope as a latency signal.
