## D — Components / Subtasks

**D1. Lexer** — converts raw source bytes into a typed token stream with source locations.

**D2. Parser** — converts token stream into a fully-typed, location-annotated AST.

**D3. Name / Scope Resolver** — resolves every identifier-use to a unique declaration; builds and closes the symbol table; enforces scoping rules.

**D4. Type Checker** — annotates every expression node with a concrete type; enforces all type rules; produces the typed AST.

**D5. IR Lowering** — translates the typed AST into a typed intermediate representation with explicit control flow.

**D6. Code Generator** — translates IR into target output (assembly / bytecode); enforces calling convention and stack layout.

**D7. Driver (orchestration layer)** — sequences all phases in order, threads representations between them, accumulates all diagnostics, and suppresses output artifacts on error.

**D8. IR Verifier** — standalone checker that validates all IR well-formedness rules independently of the front-end; runs after lowering and before code generation.

## Dep — Cross-Component Dependency Seams

**Dep1. Lexer → Parser · byte-complete token stream**
Every source byte is accounted for by exactly one token or an explicitly discarded whitespace/comment span. *Breaks if absent: parser silently accepts a shorter token stream, producing a different program with no error.*

**Dep2. Lexer → Parser · monotonic position ordering**
Tokens appear in strictly non-decreasing start-byte-offset order. *Breaks if absent: parser misattributes source locations for all subsequent tokens silently.*

**Dep3. Parser → Name Resolver · scope-boundary fidelity**
Every AST construct that opens a new scope (block, function body, for-init) is represented by an explicit scope-boundary node; the set of such nodes exactly matches the language's scoping rules. *Breaks if absent: name resolution collapses distinct scopes, causing wrong-scope bindings with no error.*

**Dep4. Parser → Name Resolver · declaration vs use distinction**
The AST distinguishes declaration nodes from use nodes; name resolution never treats a use as a declaration or vice versa. *Breaks if absent: use-before-decl errors are either missed or spuriously emitted.*

**Dep5. Name Resolver → Type Checker · resolution complete before type checking**
The type checker is not called until resolution has completed and every identifier-use node has a valid declaration link. *Breaks if absent: type checker performs lookups against an incomplete symbol table and produces wrong types silently.*

**Dep6. Name Resolver → Type Checker · symbol table completeness**
The symbol table passed to the type checker contains every declared name in the program, including forward-declared functions. *Breaks if absent: type checker cannot find names declared later and produces spurious "not found" errors.*

**Dep7. Type Checker → IR Lowering · no unresolved type variables**
The typed AST passed to IR lowering has no nodes with an "inferred but not yet resolved" type marker; all type inference has converged. *Breaks if absent: IR lowering emits instructions with null or wrong types, producing silent code-generation errors.*

**Dep8. Type Checker → IR Lowering · explicit coercions in typed AST**
Every implicit numeric widening or coercion applied by the type checker is represented as an explicit coerce node in the typed AST; IR lowering translates it to an explicit IR instruction. *Breaks if absent: IR silently omits a widening (e.g., sign-extension vs. zero-extension) producing wrong values.*

**Dep9. IR Lowering → Code Generator · use-def dominance**
In the IR's CFG, every use of a value is dominated by its definition; code generation assumes this invariant without re-checking. *Breaks if absent: code gen reads an undefined or stale register/slot, producing wrong values or crashes.*

**Dep10. IR Lowering → Code Generator · call-site / callee-signature agreement**
The number and types of arguments at every call-site in the IR exactly match the callee's IR-level parameter list; code gen trusts this without re-checking. *Breaks if absent: argument is read from wrong register/stack slot, producing wrong values or crashes.*

**Dep11. Type Checker → IR Lowering → Code Generator · error-sentinel propagation**
The error sentinel type is recognized by IR lowering (suppresses instruction emission) and must not cause code gen to encounter a missing operand or internal error. *Breaks if absent: one type error deep in an expression causes spurious IR or code-gen crashes downstream.*

**Dep12. Name Resolver → Code Generator · symbol-name consistency**
The code generator reads all symbol names from the symbol table populated by name resolution; it does not re-derive names from source text. *Breaks if absent: emitted symbol names diverge from what name resolution established, causing linker mismatches.*

**Dep13. IR Verifier → Code Generator · verified-IR guarantee**
*(source: S1)*
The IR Verifier (D8) produces a pass/fail verdict certifying the structural invariants (use-def dominance, type completeness, CFG terminator coverage, call-site agreement) that code gen trusts without re-checking; code gen is only invoked on verifier-passed IR. *Breaks if absent: verifier is structurally disconnected from code gen — removing it does not break any named invariant, so the guarantee it provides is invisible and untestable.*

**Dep14. Name Resolver → IR Lowering · symbol identity handoff**
*(source: S2)*
IR lowering reads all symbol names and unique identifiers for function-call targets and global variable operands from the resolver's symbol table; it does not re-derive them from source text. *Breaks if absent: a rename applied by the resolver leaves IR operands carrying pre-rename source text, causing linker mismatches that are not caught until code gen or link time.*

**Dep15. Parser → Type Checker · type-annotation AST nodes**
*(source: S3)*
Every type-annotation position in the AST (variable declaration type, parameter type, return type, struct field type) is parsed into a distinct, structured type-annotation node — not a raw string or identifier token — so the type checker can resolve and compare it against the type environment. *Breaks if absent: `fn f(x: MyStruct)` stores the parameter type as a raw identifier string; the type checker silently substitutes the wrong type with no error.*

**Dep16. Type Checker → IR Lowering · struct field layout**
*(source: S4)*
The type checker computes and attaches to each struct type the ordered list of fields with their resolved types and integer offsets; IR lowering reads this layout to emit correct field-access instructions without re-deriving offsets. *Breaks if absent: IR lowering uses field index 0 for what is field index 2, producing wrong memory access with no error at lowering time.*

## V — Criteria

### Lexer

**V1. Token taxonomy complete**
Every token class (keyword, identifier, integer literal, float literal, string literal, boolean literal, operator, punctuation, EOF) is enumerated with its pattern; no class is absent or mis-classified.
*Falsifier: feed source with each class; any mis-classification or absent class → wrong token stream.*

**V2. Maximal-munch rule**
The lexer always consumes the longest prefix matching any token pattern.
*Falsifier: `!=` tokenizes as one NEQ, not `!` + `=`; likewise `<=`, `++`, `->`, etc.*

**V3. Keyword priority over identifier**
Reserved words match before the identifier rule at equal length.
*Falsifier: `return_value` → IDENT; `return` → KW_RETURN (not treated as identifier prefix).*

**V4. String escape sequences correct**
Recognized escapes (`\n`, `\t`, `\\`, `\"`, `\uXXXX`) decode to the correct code-point; unrecognized escapes produce a diagnostic.
*Falsifier: `"\n"` string value contains byte 0x0A, not backslash-n.*

**V5. Numeric literal overflow → diagnostic**
An integer or float literal outside the target type's representable range produces a diagnostic at lex/parse time; no silent truncation or wrap.
*Falsifier: `99999999999999999999` → lex/parse error; `let x: i32 = 3000000000;` → range error.*

**V6. EOF sentinel**
Lexer emits exactly one EOF token as the final element and returns the same EOF token on any subsequent call.
*Falsifier: call lexer twice past EOF; must return same EOF, not crash or new token.*

**V7. Comment handling**
Line and block comments are silently consumed; an unterminated block comment (reaches EOF) produces a diagnostic.
*Falsifier: `/* comment without closing` → "unterminated comment" error, not silent truncation.*

**V8. Byte completeness**
Every source byte is consumed by exactly one token or explicitly accounted for as whitespace/comment; no byte is skipped silently.
*Falsifier: sum of all token byte-spans plus whitespace spans equals source byte length.*

**V9. Unterminated string → diagnostic**
A string literal reaching EOF without a closing delimiter produces exactly one diagnostic on the opening delimiter's line; no tokens are emitted past the EOF.
*Falsifier: `"hello` → exactly one "unterminated string" error.*

**V10. Invalid character → diagnostic and resume**
A source character outside the allowed set produces a diagnostic with its exact source position; the lexer resumes on the next character and produces correct surrounding tokens.
*Falsifier: byte 0x01 in source → diagnostic citing its column; tokens before and after are correct.*

**V59. Source encoding contract**
*(source: M7)*
The lexer enforces a single declared source encoding (e.g., UTF-8); every input byte sequence is classified as a valid codepoint, an invalid-encoding sequence (→ one diagnostic), or ASCII whitespace/punctuation. The "allowed character set" referenced by V10 and identifier rules is defined relative to this encoding; the behavior is platform-independent.
*Falsifier: feed a valid UTF-8 two-byte sequence (e.g., U+00E9 é); compiler behaves consistently — either accepts it as an identifier character or produces exactly one "invalid character" diagnostic, not a crash or platform-dependent result.*

### Parser

**V11. Grammar unambiguous**
The grammar is unambiguous (or ambiguity is explicitly resolved via precedence/associativity declarations); every valid program has exactly one parse tree.
*Falsifier: dangling-else `if a if b s1 else s2` → single deterministic AST.*

**V12. Operator precedence and associativity complete**
All binary and unary operators have defined precedence levels and associativity; the table is complete.
*Falsifier: `a + b * c` → `b*c` nested under `+`; `8 - 3 - 2` evaluates to `3` (left-assoc), not `7`.*

**V13. Full grammar coverage with typed AST nodes**
Every syntactic construct has a parsing rule and maps to a distinct typed AST node; no construct falls through to a generic catch-all.
*Falsifier: walk AST for any valid program; every node is an instance of a typed node class, never a generic untyped node.*

**V14. Parser error recovery**
On a syntax error the parser synchronizes (e.g., at the next statement or closing brace) and continues to surface additional errors.
*Falsifier: file with syntax errors in three separate functions → all three functions' errors appear in diagnostics.*

**V15. Every AST node carries non-null, accurate source location**
Every AST node produced by the parser carries the source location of its primary token; parenthesized expressions carry the location of the outer parenthesis, not just the inner expression.
*Falsifier: walk every node of a parsed AST; assert none has a null/zero location; error inside `(expr)` cites a position inside the parens.*

**V16. Short-circuit operators distinct from bitwise operators in AST**
`&&` and `||` are distinct AST node types from bitwise `&` and `|`.
*Falsifier: AST for `a && b` is not the same node type as AST for `a & b`.*

### Name / Scope Resolution

**V17. Unique declaration per scope; duplicates at any scope level → redecl error**
Two declarations of the same name in the same scope (including top-level) produce a "redeclaration" error; shadowing in a child scope is allowed (or forbidden) per the language spec, consistently.
*Falsifier: `let x = 1; let x = 2;` in same block → one redecl error; two `fn foo()` at top level → one redecl error.*

**V18. Use-before-declaration error, including self-referential initializer**
A name used textually before its declaration in the same scope produces a diagnostic; a variable that references itself in its own initializer is also diagnosed.
*Falsifier: `print(x); let x = 1;` → "use before declaration"; `let x = x + 1;` → error, not silently unresolved.*

**V19. Forward reference for functions supported via pre-scan**
Functions may be called before their textual definition; the resolution pass does at least a pre-scan for function names before resolving bodies, enabling mutual and self recursion.
*Falsifier: mutually recursive `f` and `g` with `f` defined first → successful compilation; `fn fact(n: int) → int { return n * fact(n-1); }` → successful compilation without infinite loop.*

**V20. Built-in names in outermost scope**
Primitive type names (`int`, `bool`, `float`, `string`) and any built-in functions are installed in the outermost scope before user code is resolved.
*Falsifier: use `int` as a type in user code without declaring it → compilation succeeds.*

**V21. Every name-use carries correct declaration link**
After resolution, every identifier-use AST node carries an unambiguous, non-null reference to its correct declaration, even under shadowing and with many similarly-named identifiers.
*Falsifier: walk all identifier-use nodes; none has a null declaration pointer; in `{ let x=1; { let x=2; print(x); } }`, the inner `print(x)` resolves to the inner `x`.*

**V22. Shadow of a built-in name → defined behavior**
A user declaration that shadows a built-in name (e.g., `let int = 5;`) produces a defined, consistent outcome — either a clear error or silent shadowing per spec; never a crash or undefined behavior.
*Falsifier: `let int = 5;` → one of: compiler error with message, or accepted with consistent semantics.*

**V60. Forward reference for user-defined types**
*(source: M2)*
Type definitions (structs, type aliases) are pre-scanned so that a definition referencing a type declared later in the file resolves correctly; the result is either successful compilation or a well-formed "unknown type" error, never a crash or silent wrong-type binding.
*Falsifier: `struct B { a: A }; struct A { x: int }` → compiles successfully (or produces a defined "unknown type" error, not a crash).*

### Type Checker

**V23. Every expression node has a concrete type after type checking**
After type checking, every expression node carries a concrete type; no "pending" or "unknown" markers remain except the error sentinel.
*Falsifier: walk all expression nodes post-type-check; assert each has a non-null, non-pending type.*

**V24. Error sentinel propagates without cascade; single error per root cause**
When a sub-expression has a type error, its type is set to the error sentinel; operations on the sentinel propagate it without emitting additional errors; one root-cause defect produces O(1) diagnostics, not O(n).
*Falsifier: `1 + "hello" + 2` → exactly one error (the int+string), not a second error on the outer `+`; remove a widely-used type definition → one root-cause error, not one per use.*

**V25. Operator type rules enforced; wrong-typed and void-return operands rejected**
Every operator has an explicit type signature; applying it to wrong-typed operands, including void-return function results, produces exactly one diagnostic.
*Falsifier: `true + 1` → type error; `1 + f()` where `f` is void → type error.*

**V26. Return type matches declared type; non-void missing-return path → diagnostic**
Every return statement's expression type must be assignable to the enclosing function's declared return type; a non-void function with a path that has no return produces a "missing return" error.
*Falsifier: `fn f() -> int { if cond { return 1; } }` → "missing return" error.*

**V27. Void function must not return a value**
`return expr;` in a void function is a type error.
*Falsifier: `fn f() { return 1; }` → type error.*

**V28. Call arity and parameter types checked**
A function call must have the same number of arguments as the callee's parameter list, and each argument's type must match the corresponding parameter type.
*Falsifier: call a two-parameter function with one argument → arity error.*

**V29. Non-function value called as function → diagnostic**
Calling a non-function value as a function produces a "not callable" type error.
*Falsifier: `let x = 1; x(2);` → type error.*

**V30. Invalid struct field access → diagnostic**
Accessing a field on a non-struct type, or a nonexistent field on a struct type, produces a type error.
*Falsifier: `let x: int = 0; x.field;` → type error.*

**V31. Directly self-containing struct rejected**
A struct that directly contains itself as a value (not via pointer) is rejected with an "infinite size" error.
*Falsifier: `struct Node { next: Node }` without pointer → "infinite size" error.*

**V32. Assignment RHS type assignable to LHS declared type**
The right-hand side of an assignment must have a type assignable to the left-hand side's declared type (per the assignability relation defined by V65).
*Falsifier: `let x: bool = 42;` → type error.*

**V33. Condition must be bool; no implicit truthiness**
The condition of `if`, `while`, `for` must be of type `bool`; other types are rejected.
*Falsifier: `if 1 { ... }` → type error on condition.*

**V61. Mutual struct infinite-size rejection**
*(source: M1)*
Mutually recursive value-type structs (a cycle of structs each containing the other as a value field, not via pointer) are rejected with an "infinite size" or "cyclic type" error.
*Falsifier: `struct A { b: B }; struct B { a: A }` → "infinite size" or "cyclic type" error.*

**V62. Array element and index type rules**
*(source: M3; resolves W1 for arrays)*
(a) An array-index expression requires an integer-typed index — non-integer index → type error. (b) An array literal requires all elements to be of the same type — heterogeneous literal → type error. (c) The type of `a[i]` where `a: T[]` is `T`.
*Falsifier: `a["key"]` → type error; `[1, "two", 3]` → type error; `let x: int = arr[0]` where `arr: int[]` → type-checks cleanly.*

**V63. Pointer dereference type rules**
*(source: M4; resolves W1 for pointers)*
(a) Dereferencing a non-pointer type is a type error. (b) The type of `*p` where `p: *T` is `T`. (c) Taking the address of an expression `&e` where `e: T` produces type `*T`.
*Falsifier: `let x: int = 0; let y = *x;` → type error (deref of non-pointer); `let p: *int = ...; let v: int = *p;` → type-checks cleanly.*

**V64. Lvalue validity on assignment left-hand side**
*(source: M5)*
The left-hand side of an assignment must be a valid lvalue (variable, array element, pointer dereference, struct field access); assigning to a function-call result, a literal, or a type name produces a "not an lvalue" error — not a type-mismatch error.
*Falsifier: `f() = 5;` → "not an lvalue" error; `42 = x;` → "not an lvalue" error.*

**V65. Numeric assignability / implicit widening rule**
*(source: M9)*
The type checker defines an explicit assignability relation: which (source-type, target-type) pairs are assignable without an explicit cast, and which require an explicit coercion node in the typed AST. The relation is deterministic and covers all primitive type pairs; "assignable" in V32 refers to this relation.
*Falsifier: `let x: float = 1;` — must either succeed (with an implicit int→float coerce node present in the typed AST per Dep8) or fail with a type error; the same expression produces the same outcome across compiler runs.*

**V69. Type environment (struct layouts) built before function body type-checking**
*(source: S3-1)*
The type checker resolves all struct and type-alias definitions to their complete field lists and layouts in a first pass before type-checking any function body or expression. A function defined textually before a struct it uses must type-check successfully once the full type environment is available.
*Falsifier: `fn f() -> S { let v: S; v.x } struct S { x: int }` → type-checks successfully; `S`'s field layout is available when `f`'s body is checked regardless of textual order.*

**V70. Pointer-recursive struct layout terminates**
*(source: S3-2)*
When computing struct field offsets and sizes (Dep16), pointer types are treated as opaque fixed-size units; the layout algorithm does not recursively expand the pointed-to type. A struct with a pointer-to-self field is valid and its layout computation terminates. (V31/V61 handle value-type cycles by rejection; this criterion handles valid pointer cycles.)
*Falsifier: `struct Node { next: *Node; val: int }` → type-checker computes Node's size as `pointer_size + int_size` without hanging or stack-overflowing.*

### IR Lowering

**V34. Every AST construct has a defined IR translation**
Every expression and statement form in the language has a lowering rule; no construct falls through to "unimplemented."
*Falsifier: program exercising every language construct → IR lowering completes without "unimplemented" error.*

**V35. Short-circuit operators lower to conditional branches**
`&&` and `||` lower to conditional branches so the right-hand side is not evaluated when unnecessary; not bitwise operations.
*Falsifier: `f() && g()` where `f()` returns false → IR contains a call to `g` only on the true branch.*

**V36. Temporaries unique per subexpression**
Every temporary introduced during lowering has a unique name/ID; no two subexpressions share a temporary.
*Falsifier: lower `(a+b)*(a+b)` → two distinct temporaries for the two `a+b` subexpressions.*

**V37. Every IR operand has explicit non-null type**
Every value and operand in the IR carries an explicit type; no operand has a null or implicit type.
*Falsifier: inspect every IR instruction; every operand has a non-null type field.*

**V38. CFG completeness: every path ends at a terminator**
Every function's IR has a CFG where every basic block is reachable from the entry block and every path through the function ends at a return or explicit "unreachable" instruction.
*Falsifier: lower a function with two branches; both branches have a terminator instruction.*

**V39. Error-typed AST nodes produce no IR instructions**
Any AST node annotated with the error sentinel must not produce IR instructions.
*Falsifier: introduce a type error; inspect the IR; no instructions correspond to the errored subexpression.*

**V66. Dead code after `return` closes the current basic block**
*(source: M6)*
When a `return` statement appears in the middle of a statement list, IR lowering closes the current basic block at the `return` instruction; subsequent statements in the same syntactic block produce no IR instructions (they are unreachable and must not appear in the same block).
*Falsifier: lower `{ return 1; x = 2; }` → the basic block containing `return 1` has that as its sole terminator; no instruction for `x = 2` appears in that block.*

### Code Generator

**V40. Every IR instruction has a defined code-gen translation**
Every instruction in the IR has a translation to target output; no instruction falls through to "unimplemented."
*Falsifier: program exercising every IR instruction type → code gen completes without error.*

**V41. Calling convention conformance**
Function calls and function prologues/epilogues follow the target's calling convention (argument passing order, register/stack layout, return value location).
*Falsifier: call a function returning a value; caller reads return value from the correct register/stack slot.*

**V42. Stack frame: locals at non-overlapping unique frame slots**
Local variables are allocated at correct stack offsets; no two locals share a frame slot.
*Falsifier: function with several locals → each has a unique, non-overlapping frame slot in generated code.*

**V43. Generated output parseable by target assembler/runtime**
The generated code (assembly, bytecode) is parseable and accepted by the target assembler/runtime without errors.
*Falsifier: pipe generated output through target assembler → succeeds with no errors.*

**V71. External symbol import declarations emitted**
*(source: S3-3)*
For every symbol referenced but not defined in the current compilation unit (built-in functions, runtime functions such as `print` or `malloc`), the code generator emits the appropriate external/import declaration in the output format (e.g., `.extern print` in assembly, an import entry in an object format). N3 excludes the runtime library implementation; this criterion covers the code-gen contract that makes the assembled output link-ready. Distinct from V43: a program with no external calls can satisfy V43 without testing this criterion.
*Falsifier: compile a program calling `print`; pipe generated output through the target assembler; assembler does not produce an "undefined symbol" error for `print`.*

**V72. CFG traversal visits every reachable basic block exactly once**
*(source: S3-4)*
The code generator's CFG traversal emits instructions for every reachable basic block — no block skipped, none emitted more than once. V38 guarantees every block has a terminator; V40 guarantees every instruction has a translation; neither guarantees the traversal algorithm visits all blocks exactly once (e.g., a depth-first traversal that mis-tracks visited nodes could skip a back-edge target or duplicate a block with multiple predecessors).
*Falsifier: compile a function with a loop (back-edge in the CFG); generated output contains instructions for both the loop-header block and the loop-body block; neither block's instructions appear twice.*

### Pipeline / Global

**V44. Source location continuity throughout the pipeline**
Source locations flow from token → AST node → IR instruction → diagnostic message without any stage setting a location to null, zero, or synthesized-without-propagation.
*Falsifier: any compiler diagnostic that omits a source location is a violation; an error on a synthesized IR node must still cite the originating source line.*

**V45. Type-safety preservation: IR introduces no type-unsafe operations**
The type invariants established by the type checker are preserved in the IR and generated code; the IR must not introduce casts or reinterpretations absent from the source.
*Falsifier: compile a well-typed program; every IR cast/reinterpret instruction corresponds to an explicit cast in the source.*

**V46. Meaning preservation: AST semantics equal IR semantics**
The semantics of the program in the AST equal the semantics of the generated IR; lowering is meaning-preserving and does not elide calls with side effects.
*Falsifier: run the same program through an AST interpreter and through the full pipeline; outputs agree; `f();` where `f` has a side effect → IR contains a call instruction for `f`.*

**V47. Argument evaluation order specified and enforced**
The language specifies argument evaluation order; IR lowering emits call arguments in that order consistently.
*Falsifier: write a test where left-to-right and right-to-left produce different values with side effects; IR uses the specified order.*

**V48. Phase ordering enforced; no backward dependencies**
Phases execute in fixed order: lex → parse → resolve → typecheck → lower → codegen; no phase reads the output of a later phase.
*Falsifier: inject a dependency from type checker back into parser → build fails or produces wrong result.*

**V49. Error accumulation: each phase exhausts its diagnosable errors**
Each phase collects all errors it can diagnose before passing control to the next phase; the pipeline continues through subsequent phases even when prior phases had errors.
*Falsifier: file with three distinct parse errors → diagnostic list contains all three, not just the first.*

**V50. No output artifact produced when any error exists**
If any phase emits at least one error (severity = error, per V67), no final output artifact (IR file, object file, executable) is produced.
*Falsifier: program with a type error → output directory contains no object file.*

**V51. No phase discards errors; driver list equals union of all phase lists**
Errors emitted by any phase are never silently discarded; the driver's final diagnostic list is a superset of every phase's emitted errors.
*Falsifier: count errors emitted by each phase; sum across phases; compare to driver's final count — must be equal.*

**V52. Determinism: identical source → identical output**
Given identical source input, the pipeline produces bit-identical output across runs.
*Falsifier: compile the same file twice; diff the IR or object output — must be identical (modulo declared embedded timestamps, if any).*

**V53. Unique symbol identity throughout the pipeline**
Each declared symbol (variable, function, type) has a globally unique ID from name resolution through code generation; no two declarations share an ID.
*Falsifier: compile two functions both named `f` in different scopes → IDs in symbol table are distinct; error if language forbids it.*

**V54. Type representation schema: distinct nodes and equality rules**
Every type in the language (primitive, struct, array, pointer, function type, error sentinel) is represented as a distinct node in the type language; type identity and structural equality rules are explicitly defined.
*Falsifier: `type A { x: int }` and `type B { x: int }` are distinguishable under nominal typing — not equal.*

**V55. Deep nesting (expressions): clean outcome or diagnostic; no crash**
A deeply nested expression (e.g., 10,000 levels of parentheses) either compiles correctly or produces a clean "nesting too deep" diagnostic; the compiler never crashes.
*Falsifier: generate deeply nested expression programmatically; run compiler; expect success or a clean diagnostic, never a stack overflow.*

**V73. Deep nesting (control structures): clean outcome or diagnostic; no crash**
*(source: S3-5)*
A deeply nested sequence of control structures (e.g., 1,000 nested `if` or `while` blocks) either compiles correctly or produces a clean "nesting too deep" diagnostic; the compiler never crashes. Distinct from V55: the syntactic form is different (statements, not expression groupings) and the recursion paths through the recursive-descent parser and IR-lowering pass are different.
*Falsifier: generate a program with 1,000 nested `if (true) { ... }` structures; run compiler; expect success or a clean "nesting too deep" diagnostic, never a stack overflow crash.*

**V56. EOF-unclosed delimiter → diagnostic citing opener; no crash**
A source file ending inside an unclosed block produces a diagnostic citing the unclosed delimiter's position; the compiler does not crash.
*Falsifier: `fn f() {` → "missing `}`" diagnostic with the line of the opening brace.*

**V57. Empty and whitespace-only source → zero errors, empty valid module**
A file with zero bytes or only whitespace produces zero tokens (plus EOF), a valid empty AST, no name-resolution or type errors, and an empty but valid IR module.
*Falsifier: compile an empty file and a file of 1000 spaces; expect success with zero diagnostics and an empty IR module.*

**V58. Zero-field struct → defined behavior**
A struct type with no fields is either accepted with a defined size (0 or 1 per ABI spec) or rejected by a defined rule; the outcome is consistent and the compiler does not crash.
*Falsifier: `struct Empty {}` → defined outcome (accepted or error), not crash or undefined behavior.*

**V67. Diagnostic severity taxonomy**
*(source: M8)*
The pipeline defines at least two severity levels — error and warning — with explicit rules for which conditions produce each. V50's suppression of output artifacts applies only to error-severity diagnostics. All phases emit diagnostics with their severity attached; the driver propagates severity without downgrading or upgrading.
*Falsifier: program with one unused-variable warning and no errors → output artifact is produced; program with one type error → no output artifact. A warning mis-classified as an error would wrongly suppress the artifact.*

**V68. Diagnostic deduplication: same (location, code) pair emitted at most once**
*(source: M10)*
A single root-cause defect that is visited multiple times during a single compiler pass (e.g., a shared sub-expression visited by two parent checks) produces at most one diagnostic with a given (source-location, error-code) pair; duplicates are suppressed before the driver's final diagnostic list is formed.
*Falsifier: one undeclared name used in an expression visited twice during type checking → exactly one "undeclared name" diagnostic in the output, not two.*

**V74. Diagnostic output ordered by source location**
*(source: S3-7)*
The driver's final diagnostic list is sorted by source location (file, line, column) before output; a diagnostic at an earlier line appears before one at a later line regardless of which phase emitted each. V51 ensures no diagnostic is discarded; V68 deduplicates; neither specifies order.
*Falsifier: source file with a parse error at line 10 and a type error at line 5 → the driver's final diagnostic output presents the line-5 diagnostic before the line-10 diagnostic.*

## N — Scope Exclusions

**N1. Optimization passes** — constant folding, dead-code elimination, inlining, loop transformations belong to the middle-end optimizer, not the front-end.
*Why safe: the task specifies lowering to IR, not optimizing it; re-include only if "produce optimized IR" is added.*

**N2. Linking** — resolving cross-translation-unit references, library symbol resolution, and relocation belong to the linker.
*Why safe: front-end produces a single module's IR/object; re-include if multi-file compilation is required.*

**N3. Runtime library implementation** — the implementation of built-in functions (e.g., `print`, `malloc`) is out of scope; the front-end generates calls to them by name and emits import declarations (V71). (Built-in names themselves are in scope via V20.)
*Why safe: implementation is a separate library; re-include if "implement a complete runtime" is added.*

**N4. Garbage collector implementation** — the GC algorithm and collector are out of scope; GC-root annotation in the IR may be required if the language is GC'd but the collector is not.
*Why safe: GC is a runtime concern; annotation requirement stays in scope.*

**N5. Target-specific ABI detail** — full register-assignment rules per type on specific ISAs are out of scope; abstract-level calling convention is in scope (V41).
*Why safe: ABI is backend/platform-specific; re-include if "targeting a specific ISA" is added.*

**N6. Debug information format** — DWARF, PDB, and other debug-info wire formats are out of scope; source-location threading in the IR (V44) is the prerequisite and remains in scope.
*Why safe: format is toolchain-specific; source-location threading is in scope.*

**N7. Macro / metaprogramming system** — macro expansion, compile-time code generation, and template instantiation are out of scope for a "small statically-typed language" without macros.
*Why safe: task description does not mention macros; re-include if the language spec adds them.*

**N8. Separate compilation / module system** — importing symbols from other compiled units is out of scope; single-file or single-module compilation is assumed.
*Why safe: task does not specify multi-file; re-include if "module system" or "imports" are required.*

**N9. Mutability / const distinction**
*(source: W2)*
Whether the language distinguishes mutable variables from immutable constants (`const` vs `let`) is not specified by the task. This decomposition treats all declared variables as mutable (V32 governs assignment type-checking). If a `const`/immutability distinction is added to the language spec, a criterion — "assignment to a const variable → type error" — and IR representation impact (value vs. memory slot) must be re-included.
*Why safe: task is silent on mutability; re-include if the language spec defines immutable bindings.*

**N10. Global variable initializer ordering**
*(source: S3-6)*
If the language restricts global variable initializers to compile-time constants, initialization order is irrelevant and entirely out of scope. If the language permits expression initializers on globals (e.g., `let b: int = a + 1;` at file scope), the IR must capture a dependency ordering for global initializers and the code generator must emit initialization code that respects it. This decomposition assumes constant-only global initializers; re-include the ordering requirement if expression-initializers on globals are specified.
*Why safe: task does not specify global initializer semantics; re-include with explicit ordering V and IR constraint if non-constant global initializers are added.*

**N11. Generic / parametric types**
*(source: S3-8)*
Generics and parametric polymorphism are out of scope for the stated "small statically-typed language." If added, every phase from name resolution (type-parameter scoping) through type checking (type argument substitution, unification) through IR lowering (monomorphization or boxing) requires substantial additional machinery not covered by this decomposition.
*Why safe: task says "small" language with no mention of generics; re-include if the language spec adds parametric types.*
