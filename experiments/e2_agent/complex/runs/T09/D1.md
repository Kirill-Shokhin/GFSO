# T09 — Canonical Decomposition D1 (first audit pass)

Task: Design the access-control logic for a multi-tenant SaaS — principal/role/permission model, tenant
isolation, resource hierarchy & permission inheritance, delegation/impersonation, API-key & service-account
scoping, and the audit trail. Rules must guarantee no principal ever reaches a resource outside its grants or
its tenant.

**Merges applied from search_1:**
- C3 (scope-reduction on grant creation) → V-H5 (same truth-maker: can't grant more than you hold).
- I1 (empty grant set → deny everything) → V-H3 (same truth-maker: deny-by-default on absent grant).
- J6 (async audit write after response → crash = unlogged) → V-H4 (same truth-maker: audit write must
  be durable before the response is final; H4's architectural enforcement already specifies sync + typed
  decision object).

All G items → Dep (cross-component seams). All K items → N (scope exclusions).

---

## D — Components (separable design tasks)

D1. **Principal & identity model** — define principal types (user, service account, support agent), stable
unique immutable IDs, deactivation state.

D2. **Role model** — define role structure (named, versioned permission set), tenant-scoped vs. platform-
global, built-in immutability, custom-role mutability with versioned changelog, circular-inclusion detection.

D3. **Permission & grant model** — define permission atomicity, grant record structure (principal,
role-or-permission, resource scope, optional expiry), effective-permission evaluation algorithm (union,
deny precedence, wildcard expansion, hierarchy walk), expiry enforcement, and concurrent-write safety.

D4. **Tenant isolation layer** — design tenant-namespaced resource IDs, boundary enforcement at API and
storage layers (token-derived tenant context, ORM-level predicate), cross-tenant sharing protocol, platform-
operator access governance, and offboarding cascade.

D5. **Resource hierarchy** — enumerate hierarchy levels and valid grant anchors, define the walk-up
inheritance algorithm, reparent semantics, maximum depth constraint, and circular-parent detection.

D6. **Delegation / impersonation mechanism** — delegation record lifecycle (creation, scope constraints,
bounded expiry, post-creation narrowing only), impersonation token issuance, chain-depth limit, revocation
with SLA, and support-staff break-glass procedure.

D7. **API key & service account subsystem** — service account as first-class principal, API key lifecycle
(creation with explicit scope declaration, rotation with grace window, revocation with SLA propagation),
resource binding, and key-secret non-returnability.

D8. **Audit trail subsystem** — audit record structure (minimum required fields), append-only immutability,
tamper-evidence (hash chain or signing), synchronous fail-secure write, access control (who may read/export),
retention policy, and export capability.

## Dep — Cross-component dependency seams

Dep1. **AuthN → permission evaluator** — principal identity and tenant context must arrive via tamper-proof
signed token claims; the evaluator rejects any caller-supplied header that would override them.
*Breaks if:* evaluator trusts `X-Principal-Id` or `X-Tenant-Id` HTTP header → caller impersonates any
principal or tenant.

Dep2. **Grant store → permission evaluator** — evaluator reads grants from a consistent snapshot; a partial
grant-removal must not be visible to concurrent evaluations.
*Breaks if:* role removal is half-committed; half the replicas still allow the access that should be denied.

Dep3. **Resource hierarchy cache → permission evaluator** — hierarchy cache must be invalidated on reparent
before any evaluation using the moved resource.
*Breaks if:* resource reparented from project A to project B is still evaluated against the old hierarchy,
producing an incorrect allow or deny.

Dep4. **Delegation record store → token issuer** — the token issuer verifies the delegation record via a
strong-consistent read before minting an impersonation token; a stale replica showing a deleted record is not
accepted.
*Breaks if:* delegation is revoked, but the issuer reads a lagging replica and mints a new token.

Dep5. **Key-revocation event → principal-resolution cache** — revocation must invalidate the key-to-principal
cache entry at all nodes within the defined SLA; no node may accept a revoked key past that window.
*Breaks if:* revoked API key is still resolved to a valid principal for 10 min due to a stale cache.

Dep6. **Permission evaluator → audit writer** — the authorization decision and matched grant ID must be
passed atomically to the audit writer; if the write fails, the request is blocked (fail-secure).
*Breaks if:* audit writer is unavailable → evaluator returns allow and the request succeeds with no record.

Dep7. **Offboarding workflow → tenant-deletion step** — all keys, sessions, and grants must be revoked
before the tenant record is marked deleted; the ordering is enforced, not best-effort.
*Breaks if:* tenant record is marked deleted first; in the cleanup window, the tenant's API keys still
authenticate.

Dep8. **Role mutation → session manager** — when a role's permission set changes, principals holding active
sessions with that role have effective permissions refreshed within a bounded window or are forced to
re-authenticate.
*Breaks if:* write permission removed from a role; a session holder continues writing for the rest of their
session lifetime with no re-evaluation.

Dep9. **Resource creation → inheritance engine** — inherited grants must be fully applied before the creation
response is returned to the caller; no window where the resource is accessible to its creator but not to
principals who should inherit parent grants.
*Breaks if:* parent-level admin cannot access a newly created resource for 2 s while async propagation runs.

Dep10. **Impersonation token issuer → audit writer** — the real principal ID must be embedded in the
impersonation token (or looked up from the delegation record at request time) so the audit writer always has
both actor IDs available.
*Breaks if:* the token carries only the impersonated principal's ID; the real actor is hidden from the audit
log.

Dep11. **Cross-tenant grant use → both-tenant audit logs** — when a cross-tenant grant is exercised, the
audit record must appear in both the source and the target tenant's logs.
*Breaks if:* a principal from tenant A accesses a shared resource in tenant B; only tenant B's log has a
record, hiding the event from tenant A's admin.

## V — Criteria (decidable predicates over the produced result)

### Identity & principal

V1. Principal IDs are stable, immutable, and never reused after deletion.
*Falsifier: deleted user re-created with the same ID silently inherits prior grants.*

V2. A deactivated principal is denied all access immediately; their grants are preserved for audit but are
inactive.
*Falsifier: a deactivated user's API key still authenticates after account suspension.*

### Role model

V3. Custom roles are tenant-scoped; a tenant's custom role permission list is not visible to another tenant's
role editor.
*Falsifier: tenant A's custom role leaks its permission list to tenant B's role editor.*

V4. Built-in (platform-defined) roles are immutable; custom roles are mutable with a versioned changelog.
*Falsifier: mutating a built-in role silently changes the effective permissions of all holders.*

V5. A grant references a specific role version; role updates do not retroactively change grantee permissions
without an explicit re-grant or version bump.
*Falsifier: admin narrows a role expecting immediate effect, but all grantees keep the old permission set
indefinitely.*

V6. Assigning a role whose permission set is empty is a no-op; the principal gains no access and no
exception is raised.
*Falsifier: assigning an empty role throws an unhandled exception or grants unexpected default access.*

V7. Circular role inclusion is detected at role-definition time and rejected.
*Falsifier: role A includes role B includes role A; the evaluator enters an infinite loop.*

### Permission & grant model

V8. Each permission names exactly one action on one resource type; no coarse action implies a finer one
unless explicitly listed.
*Falsifier: a `write` permission silently includes `delete`, granting more than intended.*

V9. The grant store — not any derived cache — is the authoritative source for access decisions.
*Falsifier: access is decided from a derived cache that has drifted from the grant store.*

V10. Effective permissions = union of all matching grants; deny entries override allows with defined
precedence; resolution is deterministic across replicas.
*Falsifier: conflicting grants from two roles resolve non-deterministically, producing different answers per
replica.*

V11. Wildcard grants expand only over resource types explicitly enumerated at grant-creation time; a new
resource type added later is not covered without a new or updated grant.
*Falsifier: wildcard grant covers a new resource type added after the grant, exceeding original intent.*

V12. An explicit deny at any resource level overrides an allow at the same or any ancestor level; the deny-
wins rule is defined and holds across every level pair in the hierarchy.
*Falsifier: deny on parent does not block an allow on a child because precedence is undefined.*

V13. The maximum permission a principal can grant is bounded by what they themselves hold at the same or
broader scope; enforced in the grant-creation handler, not only in documentation.
*Falsifier: a viewer-role holder calls create-grant with role=owner and it succeeds.*

V14. Every grant has a creation timestamp, creator principal ID, and reason; grants cannot appear or
disappear without a corresponding audit record.
*Falsifier: a grant disappears from the grant store with no revocation record in the audit log.*

V15. A time-bound grant that has expired is denied, including for in-flight requests evaluated after the
expiry timestamp.
*Falsifier: a grant expired 10 s ago; a client session that started before expiry continues to act on it.*

V16. A grant on a non-existent resource either fails or creates a pending grant that activates only when a
resource with the exact same ID and type is created.
*Falsifier: a pending grant on resource ID `X` activates when any resource with ID `X` is created, regardless
of type.*

V17. Concurrent grant modifications targeting the same principal both persist without either overwriting the
other.
*Falsifier: second concurrent write silently overwrites the first, leaving the principal with only one of the
two intended grants.*

V18. A bulk grant-assignment either fully succeeds or fully rolls back; partial application is not permitted.
*Falsifier: a bulk role-assignment partially applies (7 of 10 principals get the role); the operation returns
success; 3 principals are silently skipped.*

### Tenant isolation

V19. All resource IDs are namespaced by tenant ID at the storage layer; a bare resource ID cannot be
resolved without a tenant context.
*Falsifier: a GET /resources/{id} call without tenant context resolves the resource and returns data.*

V20. Tenant context is derived from the authenticated token, not from a caller-supplied header; every
authorization check is bounded to that tenant.
*Falsifier: a caller supplies `X-Tenant-Id: other-tenant` and gains access to that tenant's resources.*

V21. Every query on tenant-owned tables carries a `tenant_id` predicate enforced at ORM/query-builder level,
not only in business logic.
*Falsifier: a query omitting the predicate returns rows from all tenants to the first requester.*

V22. Tenant A cannot discover the existence, name, member count, or resource list of tenant B.
*Falsifier: the list-tenants API returns all tenants to any authenticated user.*

V23. Cross-tenant resource sharing requires an explicit bilateral grant approved by both tenant owners.
*Falsifier: any tenant admin can make a resource accessible to another tenant unilaterally.*

V24. On tenant offboarding, all API keys, grants, delegations, and active sessions are revoked before the
tenant record is marked deleted.
*Falsifier: a deleted tenant's API key continues to authenticate for hours after deletion.*

V25. Platform operators who can access any tenant hold a distinct, audited role; every cross-tenant access is
audit-logged with a stated reason.
*Falsifier: an ops engineer reads a tenant's data with no audit-log entry because their internal role bypasses
logging.*

V26. Tenant IDs and resource IDs are non-guessable; sequential enumeration is not a valid discovery path.
*Falsifier: tenant IDs are sequential integers; guessing ±1 reveals other tenants' existence.*

V27. For any authorization evaluation, the grant set considered is bounded to the tenant derived from the
authenticated token; no grant from another tenant influences the outcome.
*Falsifier: a grant in tenant B matches a permission check for a resource in tenant A because the evaluator
queries grants across all tenants.*

### Resource hierarchy & inheritance

V28. A child resource inherits all grants of its parent; inheritance flows downward only; a newly created
child receives applicable parent-level grants.
*Falsifier: a resource created under a project does not receive the project-level viewer grant.*

V29. A grant on a child resource cannot confer permissions that the granting principal does not hold on the
parent.
*Falsifier: a project-editor can grant project-owner on a sub-resource to a third party, escalating
privilege.*

V30. The concrete hierarchy levels are enumerated; each level is defined as a valid or invalid grant anchor.
*Falsifier: permissions applied at a level that cannot own grants cause undefined behavior.*

V31. The walk-up inheritance algorithm is defined for every level pair and traverses to the root without
early termination.
*Falsifier: a deeply nested resource does not inherit an organization-level admin grant because the walk stops
early.*

V32. Grants can be pinned to a specific resource instance; type-level grants cover all current and future
instances of that type within scope.
*Falsifier: a grant intended for a single dataset covers all datasets of the tenant because instance pinning
was not enforced.*

V33. Moving a resource to a new parent recalculates inherited grants; existing instance-level grants require
explicit reconfirmation.
*Falsifier: resource moved from project A to project B silently retains all project-A inherited grants.*

V34. The permission evaluator resolves hierarchy traversal at the maximum permitted nesting depth without
timeout or stack overflow.
*Falsifier: a 10-level-deep resource causes a 30 s evaluation timeout under normal load.*

V35. Circular parent chains are detected and rejected at resource-creation time.
*Falsifier: a project set as its own grandparent causes infinite recursion in the hierarchy walker.*

V36. Resource creation at a depth exceeding the defined maximum nesting depth is rejected at creation time.
*Falsifier: a client creates a 50-level-deep hierarchy; the evaluator times out or overflows on every request
to that branch.*

### Delegation / impersonation

V37. Impersonation is allowed only when an active delegation record (delegator, target, scope, expiry) exists.
*Falsifier: a support agent can impersonate any user without any record existing.*

V38. An impersonation token's effective permissions equal the intersection of the target's current grants and
the declared delegation scope; it cannot exceed either.
*Falsifier: a support agent acting as a user obtains permissions the user does not hold.*

V39. Every delegation record has a non-null, bounded expiry timestamp; null-expiry delegations are rejected
at creation.
*Falsifier: a delegation record with `expiry = null` is accepted.*

V40. Every action taken under impersonation records both the real principal and the impersonated principal in
the audit log.
*Falsifier: the audit log records only the impersonated identity, hiding who actually acted.*

V41. A delegated token cannot itself be used to create a further delegation; chain depth is capped at one
hop.
*Falsifier: an impersonation token is accepted as input to a create-delegation call, enabling chained
impersonation.*

V42. Delegation revocation invalidates all derived tokens within a bounded latency SLA.
*Falsifier: delegation revoked in the grant store but an existing derived token remains valid until its
embedded expiry.*

V43. A principal cannot create a delegation targeting itself with a broader scope than it currently holds.
*Falsifier: a user creates a delegation to themselves with `scope = *`, obtaining effective owner access.*

V44. Support-staff impersonation requires either explicit tenant-owner consent recorded in the system, or a
documented break-glass procedure with dual approval; both paths produce audit records.
*Falsifier: a support ticket causes an impersonation token to be minted with no notification or record visible
to the tenant owner.*

V45. A delegation record's scope cannot be widened after creation; only narrowed or revoked.
*Falsifier: a delegation record is updated to add new resource types after creation, silently expanding
access.*

### API key & service account

V46. An API key is a credential that authenticates to its owning principal; key effective permissions =
principal's current grants ∩ the key's declared scope restriction.
*Falsifier: an API key is granted permissions directly, bypassing the owning principal's grant set.*

V47. An API key's scope restriction cannot expand beyond the owning principal's effective permissions at key-
creation time.
*Falsifier: an API key is created with a scope that includes a permission the owner does not hold.*

V48. An API key is permanently bound to the tenant in which it was created; it cannot authenticate in another
tenant.
*Falsifier: an API key created in tenant A is accepted in an API call scoped to tenant B.*

V49. A resource-bound API key is rejected for any request outside its declared resource set.
*Falsifier: an API key created with `dataset:D1:read` can also read dataset D2 because the binding is not
enforced.*

V50. A service account is a first-class principal with its own stable ID, its own role grants, and its own
audit trail; it is not a shared credential.
*Falsifier: multiple services share a single user's credentials, making action attribution impossible.*

V51. When a human must act as a service account, they obtain a short-lived impersonation token via the
delegation mechanism; the SA's raw long-lived key is not distributed to engineers.
*Falsifier: the SA's long-lived key is distributed to engineers for ad-hoc debugging access.*

V52. Key rotation produces a new key while the old key remains valid for a configurable grace window; the old
key is revoked after that window.
*Falsifier: rotation immediately invalidates the old key, breaking live integrations with no migration path.*

V53. A revoked API key is rejected by all nodes within a defined SLA; no cache may serve the key past that
window.
*Falsifier: a revoked API key is accepted for 5+ minutes because the auth cache has no invalidation path.*

V54. The raw API key value is shown only once at creation; subsequent list or get calls return only a masked
form.
*Falsifier: the GET /api-keys/{id} endpoint returns the full raw key value.*

V55. A service account from tenant A cannot be granted a role in tenant B without an explicit cross-tenant
sharing arrangement per V23.
*Falsifier: tenant B's admin endpoint accepts a foreign service-account ID and assigns it a role without any
cross-tenant approval.*

V56. Creating an API key with no scope restriction either fails or requires an explicit full-scope declaration
with confirmation; there is no silent full-scope default.
*Falsifier: a key created with no `scope` field defaults to the owner's full permissions silently.*

V57. The list-api-keys endpoint returns only keys owned by the calling principal, or (for admins) only keys
within their tenant.
*Falsifier: a tenant member can list API keys created by other members of the same tenant.*

### Audit trail

V58. Audit records are append-only; no principal — including tenant admins and platform operators — can
modify or delete them.
*Falsifier: a DELETE /audit/{id} call succeeds for a tenant admin.*

V59. Both allow and deny authorization decisions are recorded in the audit log.
*Falsifier: all successful reads are unlogged; a data-exfiltration event is invisible.*

V60. Every audit record contains: `timestamp` (UTC, monotonic), `principal_id`, `real_principal_id` (if
impersonation), `tenant_id`, `resource_id`, `action`, `decision`, `grant_id`, `ip`, `user_agent`.
*Falsifier: an audit record contains no `grant_id`; it is impossible to reconstruct why an action was
allowed.*

V61. Audit records are hash-chained or signed; any modification or deletion is detectable offline.
*Falsifier: audit records are updated directly in the DB with no detection mechanism.*

V62. A tenant admin can read (not write or delete) audit records for their own tenant only; a platform
operator can read all; no principal can write directly.
*Falsifier: a tenant admin reads another tenant's audit records by supplying a different tenant filter
parameter.*

V63. A minimum audit retention period is defined; records are not garbage-collected before it; changes to
the retention policy are themselves audit-logged.
*Falsifier: a nightly cleanup job deletes records older than 30 days regardless of the configured retention
policy.*

V64. Tenant admins can export their tenant's audit log in a standard machine-readable format (CEF, JSON-ND);
the export itself is logged.
*Falsifier: there is no export endpoint; tenants can only browse logs via the UI, making SIEM integration
impossible.*

V65. Role assignments, role mutations, delegation creation/revocation, and API key creation/revocation are
audit-logged with before-and-after state.
*Falsifier: a role assignment is performed; the audit log contains no record of the grant change.*

V66. If an audit write fails, the associated request is denied (fail-secure) and an operational alert fires;
the failure is never silently swallowed.
*Falsifier: the audit service is down; all API calls continue to succeed with no log records and no alert.*

### System-wide invariants

V67. No finite sequence of valid API calls allows a principal to acquire effective permissions exceeding those
explicitly granted to it.
*Falsifier: a principal with `role:grant-viewer` can chain two calls to assign `role:owner` to themselves.*

V68. An absent grant means deny; the evaluator never defaults to allow on an unmatched resource or principal.
*Falsifier: a new resource type is deployed; before any grants are defined, any authenticated principal can
access it.*

V69. No permission evaluation completes without a durable audit record; the evaluator returns a typed
decision object that the caller must pass to the audit writer before acting on the result (enforced
architecturally; this also prohibits async-after-response write patterns).
*Falsifier: a code path skips the decision object and acts directly on a local boolean; that action is never
logged — or: the process is killed between response dispatch and an async write, leaving the action unlogged.*

V70. Revoking a principal's access (role removal, key revocation, delegation revocation) terminates all
derived permissions and active tokens within a defined SLA; no derived credential outlives its source grant.
*Falsifier: a service-account role is removed; the SA's existing JWT continues to work until its `exp`
claim.*

### Boundary & failure-mode criteria

V71. Token expiry checks accept a bounded, documented clock-skew tolerance; tokens beyond that tolerance are
rejected regardless.
*Falsifier: a validator with a 10-min slow clock accepts tokens that expired long ago.*

V72. A tenant with zero members is not accessible to any platform operator without an explicit break-glass
grant.
*Falsifier: a tenant with zero members is readable by any platform operator because the "no members" state is
treated as unprotected.*

V73. Resource ID matching in the permission evaluator is exact; no prefix-match algorithm that would grant
access to a resource sharing only a prefix with the granted resource.
*Falsifier: resources `proj:A` and `proj:AB` are created; a grant for `proj:A` matches `proj:AB`.*

V74. Internal service-to-service calls must enforce tenant context; "trusted internal" status does not exempt
a call from the `tenant_id` predicate.
*Falsifier: an internal endpoint fetching resources by ID does not enforce `tenant_id`; calling it with any
valid resource ID returns the data.*

V75. A delegation-scope restriction claim in the impersonation token is enforced by every downstream service,
not only at the entry point.
*Falsifier: a delegation scoped to `dataset:read` allows write access when the token is used against a
microservice that ignores the scope claim.*

V76. An unrecognized action string is denied, not allowed by default.
*Falsifier: a new action type is deployed; a principal with no grants for it gains access because the
evaluator treats unknown actions as unconstrained.*

V77. An unauthenticated request (nil or anonymous principal) cannot reach the permission evaluator; the
authentication layer rejects it before any grant lookup occurs.
*Falsifier: a request with no `Authorization` header reaches the evaluator and is granted access to public-
wildcard-scoped resources.*

## N — Scope exclusions

N1. **Authentication mechanism** (OIDC, SAML, password hash, WebAuthn) — the AuthZ layer consumes a
verified, signed principal-identity assertion; credential verification is out of scope. *Pulled back in if
the AuthZ layer also issues tokens or performs credential validation directly.*

N2. **Rate limiting / abuse prevention** — per-principal or per-tenant rate limits are an operational
control, not an access-control rule. *Pulled back in if rate limits function as a security boundary (e.g.,
consecutive-deny lockout gates access itself).*

N3. **Data encryption at rest / customer-managed keys** — storage-level encryption and key management are
separate from logical access control. *Pulled back in if key possession equals data access and the key scope
is functionally a grant primitive.*

N4. **Frontend / UI access control** — hiding or disabling UI elements based on role is a UX concern, not a
security control. *Pulled back in if the UI is the only enforcement point for a permission (no API-layer
check exists), at which point it becomes an in-scope security gap.*

N5. **Billing / subscription entitlements** — plan-based feature gating is a separate entitlement layer.
*Pulled back in if entitlement checks must compose with permission-grant checks in the same evaluation chain.*
