## D — Components

1. **Ingestion & schema validation** — reads raw data, enforces schema contract (column names, dtypes, nullability, allowed ranges, label presence); emits a validated, versioned dataset or hard failure. *Falsifier: a column with wrong dtype or absent label passes ingestion.*

2. **Feature transforms** — applies stateful (fit-then-transform) and stateless operations; must be serializable; fit state must be persisted as a versioned artifact. *Falsifier: fit is called on the full dataset before splitting.*

3. **Train/val/test split** — partitions validated data into three non-overlapping, non-contaminated sets; respects temporal order for time-series data; stratifies for classification. *Falsifier: test rows appear in the training partition.*

4. **Training** — consumes train partition + fitted transform artifact; produces serialized model artifact (weights, architecture, framework version); detects and aborts on numerical divergence. *Falsifier: training completes and registers a model when loss is NaN.*

5. **Offline evaluation** — evaluates model on test partition only; reports primary and secondary metrics (including per-class for imbalanced data); writes a persisted, versioned report linked to dataset and split versions. *Falsifier: evaluation runs on val partition and is reported as test-set performance.*

6. **Model registry/versioning** — stores model artifact + fitted transform artifact + hyperparameters/architecture config + schema version + evaluation report as a single versioned bundle; supports promotion state machine (candidate → validated → production → retired) with rollback support (re-promotion from retired or validated back to production), retirement, and retrieval by version tag. *Falsifier: registry stores model weights but not the associated transform artifact.*

7. **Serving transform path** — loads the exact frozen transform artifact from the registry for the deployed model version; applies it to incoming requests; output must be byte-identical to training-time transform for the same input. *Falsifier: serving re-fits or re-initializes the transformer on incoming data.*

8. **Online inference** — loads model from registry, applies serving transforms, validates incoming request schema, returns prediction; handles single-sample and batch requests. *Falsifier: online endpoint returns a prediction for a request missing a required feature column without error.*

9. **Monitoring** — tracks input feature distribution, prediction distribution, and (when labels arrive with correct lag handling) accuracy metrics; compares against stored training-time reference distributions; emits alerts on significant drift, on stale models, and on zero traffic. *Falsifier: monitoring reports "healthy" when input distribution has shifted substantially.*

10. **Shadow/canary deployment** — routes a defined fraction of production traffic to a newly promoted candidate in parallel with the current production model; compares offline and online metrics empirically; required to verify that the offline score predicts online behavior (explicit task requirement). *Falsifier: offline AUC is 0.94; production AUC is 0.62; no mechanism exists to detect the gap prior to full rollout.*

## Dep — Cross-component dependency seams

1. **Split → Transform fit** (leakage): transform fitting must happen strictly after splitting and must receive only training-partition rows; any code path that passes test or val rows to fit() introduces leakage invisible to the training loss. *Falsifier: move fit() to before split; offline accuracy improves suspiciously without model change.*

2. **Transform fit → Registry** (artifact identity): the transform artifact passed to training must be the exact object persisted in the registry; a separately re-fitted transform at serving time will differ even if the code is identical. *Falsifier: retrain without saving the artifact; serving uses a new re-fitted transform; predictions silently differ.*

3. **Training → Registry** (eval gate): a model artifact may enter the registry only after a valid evaluation report is attached; the report is a required field of the registry entry. *Falsifier: a model artifact is registered with an empty evaluation report.*

4. **Registry → Serving transform path** (version match): the serving path must load the transform artifact bundled with the deployed model version, not the latest artifact in the registry. *Falsifier: deploy model v1; update registry with v2 transform; serving silently uses v2 transform with v1 model.*

5. **Serving transform path → Online inference** (feature contract): transforms must emit features in the exact column order and dtype the model expects; any reordering or coercion applied at training must be replicated identically at serving. *Falsifier: swap two feature columns in the serving path; linear/NN model silently produces wrong predictions.*

6. **Online inference → Monitoring** (durable logging): every inference request and its prediction must be durably logged before the response is returned; logging failure must be detectable; log completeness must survive queue saturation. *Falsifier: saturate or kill the logging sink; predictions are served with no log entries; monitoring reports healthy.*

7. **Monitoring → Retraining trigger** (actionable alert loop): drift alerts must propagate to an actionable trigger that initiates a new pipeline run; without this connection, monitoring is decorative. *Falsifier: inject synthetic drift; no retraining trigger fires.*

8. **Offline evaluation → Model promotion decision** (promotion gate): promotion logic must compare the candidate model's report against the current production model's report using a defined threshold; a degraded candidate must not be promotable. *Falsifier: a candidate with lower test AUC than production is successfully promoted.*

9. **Ingestion schema → Training schema** (schema evolution): if the ingestion schema is updated (new or renamed column), the training pipeline must detect the mismatch and fail or re-derive the schema rather than silently training on a stale schema. *Falsifier: rename a column in raw data; training succeeds on the old schema; serving fails.*

10. **Split → Offline evaluation** (correct partition): evaluation must use the test partition, not val; the partition identity must be recorded in the evaluation report. *Falsifier: evaluation report does not record which partition was used; val set used for early stopping is reported as test performance.*

11. **Offline evaluation → Online monitoring** (metric proxy validity): the metric evaluated offline must be a valid proxy for the metric monitored online; mismatched evaluation windows or feature distributions make the offline score uninformative as a predictor of online behavior. *Falsifier: offline AUC 0.95; online AUC 0.60 in first week with no concept drift.*

12. **Transform fit → Offline evaluation** (inference-mode application): the fitted transform artifact must be applied in transform-only mode (no refit) to val and test partitions before evaluation; evaluating raw features against a model trained on transformed features silently distorts metrics. *Falsifier: skip transform application to test partition; offline metric appears better than it should, then collapses in production.*

13. **Split → Training** (training loop data boundary): the model's forward/backward pass must consume strictly training-partition rows; unlike Dep-1 (which covers fit() on transforms), this covers the training loop itself receiving val or test rows during gradient updates — a separate leakage path. *Falsifier: pass full dataset to the training loop and rely on transform-fit guard alone; model sees test rows during weight updates; offline metric is inflated.*

14. **Registry → Serving** (hot-swap/reload SLA): after a new model version is promoted to production, the serving endpoint must detect and reload it within a defined SLA; absent this, the old model serves forever post-promotion with no alert. *Falsifier: promote v2 to production; serving endpoint continues returning v1 predictions indefinitely with no error or alert.*

15. **Ingestion → Split** (validated-output-only): split must receive the post-validated, versioned dataset emitted by ingestion; any code path that reads raw data directly bypasses schema enforcement and can feed schema-violating or unlabeled rows into partitions. *Falsifier: wire split to read directly from the raw file path instead of ingestion output; a row with a missing label enters the training partition; training completes without error.*

## V — Criteria

### Spanning invariants

1. **No test contamination** — no fit() call anywhere in the pipeline receives test-partition rows, directly or indirectly; verified by tracing all fit() call sites to their input indices. *Falsifier: trace fit() calls; any that receive test indices.*

2. **Transform reproducibility across environments** — given the same fitted artifact and same input, transform output is byte-identical in dev, staging, and production. *Falsifier: apply same input in two environments with same artifact; outputs differ.*

3. **Schema consistency end-to-end** — the feature schema (column names, dtypes, order) at ingestion, training, evaluation, and serving is identical; schema hashes match at all pipeline stages. *Falsifier: log schema hash at each stage; hashes differ.*

4. **Version bundle atomicity** — model artifact and its associated transform artifact are always retrieved and deployed together; no code path loads one without the other. *Falsifier: a code path loads model v2 with transform v1 without raising an error.*

5. **Offline metric traceability** — every promoted model's evaluation report is traceable to the exact dataset version (by hash) and split indices used; the original offline number is reproducible. *Falsifier: re-running evaluation on a different data snapshot produces a different number; the original is unrecoverable.*

6. **Label distribution preservation across splits** — class frequencies in val and test partitions approximate the overall distribution within a defined tolerance. *Falsifier: 90/10 imbalance dataset produces a test set with 50/50 distribution.*

7. **Serving label exclusion** — the label column is never present in the serving feature vector; its absence is enforced at the serving endpoint, not assumed. *Falsifier: serving endpoint accepts and uses the label column from the request as a feature.*

8. **Stale model alert** — a production endpoint serving a model older than a defined staleness threshold triggers a monitoring alert. *Falsifier: model is 30 days old; no alert fires.*

### Artifact and lifecycle criteria

9. **Transform artifact persistence** — the fitted transform artifact includes the fit parameters (scaler means, encoder mappings, etc.), not merely the transform code or spec. *Falsifier: pipeline stores only transform code; a separately instantiated transformer produces different outputs on the same input.*

10. **Split reproducibility** — split indices are persisted; re-running the split on a modified dataset is detectable rather than silently producing different assignments. *Falsifier: re-run split after silent row addition; train/test assignments change undetected.*

11. **Pipeline run identity** — each pipeline execution has a unique run ID that links the data snapshot, transform artifact, model artifact, and evaluation report; lineage is traceable across runs. *Falsifier: two runs produce artifacts with no shared lineage identifier.*

12. **Data version/hash per run** — the exact dataset used in each run is identified by content hash or immutable snapshot reference; silent dataset mutations are detectable. *Falsifier: retrain on "same" dataset that was silently appended; registry claims same dataset version.*

13. **Model promotion state machine** — models move through defined states (candidate → validated → production → retired); only validated models may serve production traffic. *Falsifier: a candidate model with no evaluation report is set to production.*

14. **Transform fit frozen** — the transform artifact's fit state is frozen after initial fit on the training partition; any subsequent refit must produce and register a new versioned artifact. *Falsifier: adding training data triggers a silent re-fit without issuing a new versioned transform artifact.*

### Boundary-state criteria

15. **Empty batch rejection** — zero-row input to ingestion produces a hard failure, not a zero-row or trivially-trained model. *Falsifier: pass empty CSV; pipeline completes and registers a model.*

16. **All-null feature column policy** — a column with 100% missing values is rejected or handled by an explicit documented policy (drop, constant impute); it must not silently produce NaN-filled features. *Falsifier: all-null column passes ingestion; model trains with NaN inputs.*

17. **Unseen categorical at serving** — the categorical encoder has an explicit, configured policy (error / unknown token / frequency-based fallback) for categories not seen during training. *Falsifier: serving receives an unseen category; encoder raises an unhandled exception or silently maps it to an existing class.*

18. **Single-class training batch detection** — if only one class is present after splitting/filtering, training detects this and aborts with a clear error. *Falsifier: training completes on a single-class dataset; classifier predicts 100% one class with no alert.*

19. **Per-class metrics for imbalanced data** — evaluation reports per-class precision, recall, and F1 in addition to aggregate metrics; aggregate accuracy alone is insufficient for imbalanced datasets. *Falsifier: 99/1 class imbalance; evaluation report shows only 99% accuracy.*

20. **Serving-time request schema validation** — the serving endpoint validates incoming request feature columns (names, count, dtype) against the trained model schema before calling the transform or model. *Falsifier: add or remove a feature column in the serving request; inference silently drops or ignores it.*

21. **Training divergence detection** — training must detect NaN or inf loss and abort, not register a corrupt model artifact. *Falsifier: inject NaN features; training completes; model produces NaN predictions in production.*

22. **Zero serving traffic detection** — monitoring distinguishes "no requests received" (traffic alert) from "predictions are healthy" (accuracy/drift alert); zero traffic is not silently reported as healthy. *Falsifier: traffic drops to zero; monitoring reports "healthy" because no anomalous predictions observed.*

23. **Duplicate row deduplication before split** — rows duplicated across the train/test boundary cause artificial metric inflation; a deduplication policy is applied before splitting. *Falsifier: duplicate every row; offline AUC improves noticeably with no model change.*

24. **Dtype consistency across train and serve** — dtype coercions (float32 ↔ float64) between training and serving must not shift predictions beyond a defined tolerance for any model type. *Falsifier: train with float64, serve with float32; predictions differ beyond tolerance.*

25. **Single-sample and batch inference** — transforms and model forward pass handle both single-row and large-batch inputs without shape errors or silent broadcasting bugs. *Falsifier: send a single-row request; transform raises a shape error expecting 2D input.*

26. **Zero-variance feature column detection** — a constant feature column is caught at validation or transform fit; StandardScaler division by zero must not silently produce NaN/inf features. *Falsifier: constant column passes through; scaler divides by zero silently.*

### Failure-mode-as-criterion

27. **Non-positive log-transform input validation** — transforms with logarithm operations must validate that inputs are strictly positive; log(0) or log(negative) must not silently propagate NaN or −∞ through the model. *Falsifier: inject zero or negative values into a log-transformed feature; inspect model output for NaN.*

28. **Target leakage detection** — features that are derived from or correlated with the label only at training time (post-event signals) are identified and excluded; feature availability at inference time must be verified against feature availability at training time. *Falsifier: compare feature availability at training vs inference; any feature unavailable at inference is a leak.*

29. **Output distribution monitoring coverage** — monitoring covers both input feature distribution AND prediction output distribution; input stability alone does not detect concept drift. *Falsifier: inject synthetic concept drift (same inputs, shifted labels); monitoring does not alert because inputs are stable.*

30. **Logging durability under load** — the inference-to-monitoring logging path must be durable under high traffic; queue overflow must be detectable and must fire an alert; silent log entry drops must not go undetected. *Falsifier: saturate logging endpoint; entries dropped silently; no alert fired.*

31. **Accuracy monitoring label-arrival lag** — ground-truth label arrival is delayed after prediction; accuracy metrics must not be computed until labels arrive; prediction timestamps must be recorded to enable label matching. *Falsifier: accuracy metric computed at prediction time using stale or zero label set; reports fabricated 0% or incorrect values.*

32. **Monitoring reference distribution** — the input and output distributions from training (or a representative baseline window) are stored and versioned alongside the model; drift detection requires a reference distribution to compare against. *Falsifier: deploy with no reference distribution stored; drift monitor reports "no drift" always.*

33. **Model artifact integrity on load** — the checksum or hash of the serialized model artifact is validated when loaded from the registry; a silently corrupted file raises a detectable error rather than producing garbage predictions. *Falsifier: corrupt 4 bytes of the model file in the registry; serving loads without error and returns numerically wrong predictions.*

34. **Prediction output range validity** — model output is constrained to a domain-valid range (probabilities in [0, 1], regression within defined bounds); out-of-range values are enforced or logged before the response is returned. *Falsifier: a numerical edge case produces a probability of 1.7; the serving endpoint returns it without error; downstream consumers treat it as valid.*

35. **Serving latency SLA** — the combined serving-transform + model forward-pass must complete within a defined per-request time budget; the budget is specified and an enforcement or alert point exists. *Falsifier: deploy a transform that loads from disk on every request; p99 latency is 10 s; no SLA violation is raised.*

36. **Transform artifact thread-safety at serving** — the in-memory loaded transform artifact is safe for concurrent requests; mutable internal state must not corrupt outputs under simultaneous access. *Falsifier: send 100 simultaneous requests; a fraction of responses contain wrong feature values with no error logged.*

37. **Out-of-distribution input handling** — feature values at serving that fall outside a defined range relative to the training distribution must be flagged, clipped, or rejected; unconstrained extrapolation must not silently corrupt model output. *Falsifier: send a numeric feature value of 10⁶ (training max was 100); scaler outputs a 10 000 σ value; model predicts extreme nonsense; monitoring does not alert.*

38. **Partial batch failure semantics** — when one sample in a multi-sample batch request fails transform validation or schema check, the failure policy (fail-all vs. return-partial-with-error) is defined and enforced consistently. *Falsifier: send a 100-row batch where row 42 has a missing required column; the entire batch is silently dropped with a 500 error; caller cannot identify which rows failed.*

39. **Training hyperparameter and config versioning** — model hyperparameters and architecture configuration are persisted as part of the versioned registry bundle linked to the model artifact; training is reproducible given the same data and transform. *Falsifier: re-train with identical data and transform; model produces different behavior because learning rate and depth used originally are unrecorded.*

40. **Retraining data freshness on drift trigger** — when a drift-triggered retraining run fires (Dep-7), the new pipeline execution must ingest fresh or updated data; reusing the same frozen historical snapshot cannot address concept drift. *Falsifier: drift trigger fires; retraining runs on the same frozen snapshot; trained model is identical to the drifted one; alert fires again immediately.*

41. **Point-in-time correctness for temporal features** — features computed from historical windows (rolling counts, running averages, cumulative statistics) must use only data available at the exact prediction timestamp; using a window that bleeds future rows is time-leakage distinct from target leakage (V-28) and transform-fit leakage (Dep-1). *Falsifier: compute a 7-day rolling average using rows from day T+1 through T+7; offline AUC is 0.97; online AUC is 0.55.*

42. **Model rollback reachability** — the registry state machine supports re-promoting a previously-production or validated model back to production without re-registering; a "retired" state with no re-promotion path leaves operators without a rollback path during incidents. *Falsifier: v2 is promoted and causes a production incident; operator attempts rollback to v1; registry has no rollback operation; v1's state is "retired" with no path back to production.*

43. **Monitoring reference window recency** — the reference distribution used for drift detection is derived from a specified, recent data window (e.g., last N days or a dedicated calibration window), not the full training history; a broad historical reference can absorb recent distributional shifts and suppress valid drift alerts. *Falsifier: training data spans 3 years; reference is the full 3-year distribution; deployment distribution matches only the last 3 months; drift monitor always reports "no drift" because the broad reference absorbs the shift.*

## N — Scope exclusions

1. **Hyperparameter optimization (HPO)** — excluded unless the task requires production-grade competitive model performance; if included, HPO must use the val set only and must complete before test evaluation. *Why out: pipeline logic design does not depend on the HPO mechanism; it is an internal concern of the training component.*

2. **Online / continual learning** — excluded; the pipeline is batch-trained; the served model does not update weights from online traffic. *Why out: weight updates from traffic require a different architecture; in scope only if concept drift response requires online learning.*

3. **Data labeling / annotation** — excluded; the pipeline starts from already-labeled data; annotation is upstream of ingestion. *Why out: active learning and human-in-the-loop labeling are separate systems.*

4. **Distributed training** — excluded; training is a black box to the pipeline logic; parallelism is an internal concern of the training component. *Why out: multi-node training does not change pipeline seams unless artifact format or versioning is affected.*

5. **Multi-model production routing (A/B testing)** — excluded; simultaneous routing of live traffic across multiple competing models requires a separate routing and evaluation layer. Shadow/canary deployment is **in scope** and required by the task (D-10) as the mechanism for verifying offline→online score correlation. *Why out: only multi-model production routing is excluded; single-candidate shadow verification is a distinct, required mechanism.*

6. **Feature store** — excluded unless online feature freshness or cross-model feature reuse is required; this pipeline defines and computes features inline. *Why out: a feature store is needed only if features are shared across models or pre-computed for latency requirements beyond this scope.*

7. **Explainability (SHAP, LIME)** — excluded; a separate concern from pipeline correctness. *Why out: per-prediction explanations do not affect the correctness of the prediction pipeline; added only if regulatory or audit requirements mandate it.*

8. **Data pipeline orchestration / scheduling** — excluded; the task asks for stage logic and connections, not a scheduler specification. *Why out: orchestration tools are infrastructure; the logical design is independent of the scheduler.*
