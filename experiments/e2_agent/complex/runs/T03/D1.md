# T03 — Canonical Basis (Audit Pass 1)

Source: `search_1.md` (first pass — reduce to basis).

## D — Subtasks

**D.1 Expand-phase design** — specify DDL to add new schema objects (table, columns, indexes, deferred/unenforced FK constraints) without altering or dropping old ones; includes lock-safe execution strategy (e.g., `CREATE INDEX CONCURRENTLY`, statement-timeout guards on `ALTER TABLE`).
*Falsifier: any DDL that drops or renames an old object, or that enforces a constraint old-version code cannot satisfy, or that takes unguarded locks blocking live queries.*
Collapses: D-1, C-1, C-12, S-12, E-8.

**D.2 Dual-write design** — specify how every mutating operation writes to both old and new schema; covers ALL write entry points (service layer, background jobs, admin scripts, event consumers); includes error-surfacing strategy (failures must not be silently swallowed).
*Falsifier: any write path that reaches old schema and skips new schema, or that catches and suppresses new-schema write failures.*
Collapses: D-3, C-3, E-6, F-1, F-4, G-6 (implementation side).

**D.3 Backfill design** — specify the bulk-copy job: chunked and resumable (cursor/watermark persisted durably), rate-limited, idempotent (upsert / `INSERT … ON CONFLICT DO UPDATE`), monotonic (latest-write-wins conflict resolution against concurrent dual-writes), covering all rows including soft-deleted/archived.
*Falsifier: any pre-dual-write row absent from new schema after backfill; backfill overwriting a newer dual-written value; crash restarting from row 0; backfill saturating DB I/O.*
Collapses: D-4, C-4, C-5, C-6, C-7, G-3, G-7, E-3, E-9, F-6.

**D.4 Read-path switch design** — specify the runtime flag (gradual rollout, per-region or global), gate conditions for enabling it (backfill verified + dark-launch soak), and the path to revert without a new deploy.
*Falsifier: reads hitting new schema before backfill is verified complete; flag with no cut-back path short of a redeploy.*
Collapses: D-5, C-8, L-6.

**D.5 Contract-phase design** — specify DDL to drop old schema objects and enforce remaining constraints; define conditions that must all hold before execution: read-switch confirmed on all nodes, all in-flight queries against old schema drained.
*Falsifier: old column/table dropped while any deployed node still reads or writes it, or while a slow query against it is in flight.*
Collapses: D-2, C-2, S-6.

**D.6 Post-migration cleanup design** — specify removal of dual-write shims, migration helpers, old ORM models, and temporary indexes in both application code and DB; define the deployment coupling between contract DDL and cleanup deploy.
*Falsifier: cleanup runs before contract phase completes; migration scaffolding remains in the codebase indefinitely; contract DDL rolled back after cleanup code already removed the old write path.*
Collapses: D-10, S-10, F-7 (index-removal side), F-8.

**D.7 Per-phase rollback design** — specify, for every phase, a tested reversal procedure (DDL reversal + data disposition); includes dry-run requirement; explicitly addresses disposition of new-schema rows orphaned if dual-write phase is rolled back.
*Falsifier: any phase with no written, tested rollback procedure; rollback procedure that discards writes made in that phase.*
Collapses: D-8, C-9, G-8, S-7, F-7 (rollback-path side).

**D.8 Phase state-machine design** — specify the legal phase sequence (Baseline → Expand → Dual-write+Backfill → Read-switch → Contract → Cleanup), the gate condition for each transition, the persistent state record (single, atomic, transactional write per transition), and idempotency of phase-entry operations.
*Falsifier: phase advanced while gate condition is unverified; phase state stored only in memory or config; re-applying a phase entry raises an error or corrupts data; partial transitions visible to some nodes.*
Collapses: D-6, D-9, L-1, L-2, L-3.

**D.9 App-version compatibility window design** — specify which (app-version, schema-version) pairs are simultaneously valid during rolling deploys; define the drain-check procedure to verify all live instances are on a compatible version before each phase advance; covers multi-region/multi-DC global gate evaluation.
*Falsifier: a phase transition that makes any currently-deployed app version unable to read or write; phase gate evaluated per-region rather than globally.*
Collapses: D-7, L-4, E-10.

**D.10 Migration observability design** — specify dedicated metrics (dual-write error rate, backfill lag, new-schema vs old-schema row-count parity, read-path flag state), alerting thresholds, and the operator runbook (phase-by-phase procedure with verification queries, expected outputs, go/no-go criteria, rollback triggers).
*Falsifier: phase advances with no observable difference in metrics between a successful and a failed migration; migration executed ad-hoc without documented go/no-go checks.*
Collapses: C-10, C-11.

**D.11 Data reconciliation job design** — specify a continuous or periodic job that compares old and new schema row-by-row during the dual-write phase; provides the detection mechanism for silent dual-write failures that neither D.2's error surfacing nor D.3's completion check catches.
*Falsifier: divergence between old and new schema accumulates during dual-write and is only discovered at read-switch.*
Collapses: B-3, F-2 (detection side).

## Dep — Dependency Seams

**Dep.1 D.2 → D.3** (sequencing): dual-write must be active on 100% of nodes before backfill starts; any write to old schema occurring before dual-write is universal is missed by both dual-write and backfill.
*Breaks if: backfill starts while any pod still writes old-only; rolling deploy of dual-write code is in progress.*
Collapses: S-1, S-11, E-4.

**Dep.2 D.2 ↔ D.3** (conflict protocol): when backfill and dual-write touch the same row concurrently, the upsert must pick the winner by `updated_at` timestamp (latest-write-wins), not by wall-clock write-arrival order.
*Breaks if: backfill clobbers a newer dual-written value because the backfill SQL arrived later in wall time.*
Collapses: S-3, G-3 (mechanism side).

**Dep.3 D.3 → D.4** (verification gate): backfill completion must be verified against the primary database before the read-path switch proceeds; a replica-based completion check is insufficient due to replication lag.
*Breaks if: backfill job exits 0 but counted rows from a lagging replica; migration state machine advances to read-switch anyway.*
Collapses: S-2, S-8.

**Dep.4 D.9 → D.4** (version gate): the read-path flag may be enabled only for app versions confirmed capable of deserializing new-schema responses; enabling it globally while old-version pods are live causes deserialization errors.
*Breaks if: flag enabled globally; old-version pods receive new-schema response shape and throw errors.*
Collapses: S-4.

**Dep.5 D.1 → D.9** (constraint schedule): expand DDL must not enforce FKs or NOT NULL constraints that old-version app code cannot satisfy; the constraint enforcement schedule is determined by the compatibility window design.
*Breaks if: expand DDL adds enforced FK; old-version INSERT into old table fails with FK violation.*
Collapses: S-5, C-12 (ordering side).

**Dep.6 D.4 → D.5** (read-switch prerequisite): contract DDL may not execute until the read-path switch is confirmed complete on all nodes and all in-flight queries against old schema have drained.
*Breaks if: contract DDL drops old column while a slow query still references it.*
Collapses: S-6.

**Dep.7 D.2 → D.7** (rollback state): rollback from the dual-write phase requires an explicit decision about rows already written to new schema; the rollback design cannot be specified without knowing dual-write data state.
*Breaks if: rollback re-enables old-only writes but leaves new-schema rows in place, causing confusion on next attempt.*
Collapses: S-7.

**Dep.8 D.8 → D.4** (state/flag consistency): the migration state record and the read-path feature flag must agree; if the state record says "read-switch complete" but the flag service disagrees, behavior is undefined.
*Breaks if: migration state says Phase=Contract, flag service still routes 100% of traffic to old schema.*
Collapses: S-9.

**Dep.9 D.5 → D.6** (deployment coupling): the cleanup deploy (removing old-schema ORM models, dual-write shims, and compatibility code) must be coupled to the contract DDL deployment; cleaning code before DDL leaves no rollback path; rolling back DDL after code removal causes runtime errors.
*Breaks if: application code cleaned of dual-write shim, DDL rollback attempted, old write path no longer exists in code.*
Collapses: S-10, F-8 (ordering side).

**Dep.10 D.2 → D.11** (reconciler activation): the reconciliation job is meaningful only while dual-write is active; it must be running during the entire dual-write window, not only at backfill completion, because silent failures accumulate continuously.
*Breaks if: reconciler runs only as a one-shot post-backfill check; divergence from an early dual-write failure goes undetected until read-switch.*
Collapses: B-3 (timing side), F-1 (detection mechanism).

## V — Criteria

**V.1 No downtime** — at every instant during the migration, the service can serve reads and writes; no phase step requires stopping ingestion or blocking queries.
*Falsifier: any step that takes an unguarded table lock blocking all queries, or requires quiescing writes.*

**V.2 No data loss** — every write committed to old schema during the migration window is reflected in new schema before contract phase completes.
*Falsifier: a committed old-schema write has no corresponding new-schema row at contract time.*

**V.3 Monotonicity** — backfill must not overwrite a row already written by dual-write with a stale value; conflict resolution always applies latest-write-wins, keyed on `updated_at` or equivalent.
*Falsifier: backfill clobbers a newer dual-written value.*

**V.4 Intra-request read consistency** — within a single request or transaction, reads must not mix old-schema and new-schema responses.
*Falsifier: load-balanced request with partial flag rollout returns inconsistent aggregates within one response.*

**V.5 Schema backward compatibility at every phase boundary** — at each phase boundary, the schema state is readable and writable by both version N and version N−1 application code simultaneously.
*Falsifier: schema state at any phase boundary causes version N−1 to error on read or write.*

**V.6 Dual-write error visibility** — a new-schema write failure must be surfaced (raised or alarmed), not silently swallowed; old-schema write must not succeed while a new-schema write failure goes undetected.
*Falsifier: new-schema write fails with a caught exception logged only; divergence accumulates without alert.*

**V.7 Backfill completeness** — all rows in old schema at dual-write-start (including soft-deleted and archived rows) are present in new schema after backfill completes; verified by count or checksum comparison against the primary.
*Falsifier: any pre-dual-write row absent from new schema; completion declared based on replica row counts while primary has additional rows.*
Collapses: L-5, F-2, F-6.

**V.8 Full reversibility until cleanup** — until contract phase is committed and cleanup is complete, every phase transition can be reversed to the Baseline state without data loss.
*Falsifier: any phase that destroys old-schema data with no recovery path.*

**V.9 Phase-entry idempotency** — re-applying the DDL or application step for any given phase is a no-op; no error or data corruption on re-run (IF NOT EXISTS, upsert semantics throughout).
*Falsifier: applying expand DDL twice raises an error or corrupts data.*

**V.10 Atomic phase commitment** — a phase transition is a single, transactional write to the migration state record; no partial transitions where some nodes observe the new phase and others the old.
*Falsifier: phase state updated via a sequence of independent config changes, leaving nodes in split-brain.*

**V.11 Dark-launch soak criterion** — before the read-switch gate closes, the new-schema write path must have sustained real traffic for a defined minimum duration or traffic volume; the gate must not be satisfiable immediately after backfill completion.
*Falsifier: read-path flag enabled immediately after backfill with no soak period.*

**V.12 NULL policy enforced** — the split operation has an explicit, tested policy for NULLs in the original column (null FK, sentinel row, or error); no NULL silently produces an FK violation or is dropped from new schema.
*Falsifier: NULL in source column silently causes FK violation or disappears from new schema.*

**V.13 Empty-table correctness** — the backfill procedure handles zero-row tables without error; count/checksum completion check passes on empty tables.
*Falsifier: backfill job fails or count-check errors on a table with zero rows.*

**V.14 WAL/log retention sufficiency** — for large tables where backfill spans multiple days, WAL retention settings and replication slot horizons are configured to outlast the backfill window.
*Falsifier: WAL truncated before backfill finishes, preventing rollback or breaking replication.*

**V.15 Gap-free coverage across expand-to-dual-write window** — no write occurring after the expand DDL and before dual-write is universally deployed is left uncaptured; if such a gap is unavoidable, an explicit gap-backfill pass covers those rows.
*Falsifier: a row inserted in this window is absent from new schema at read-switch.*

**V.16 Cascade-delete semantics preserved** — FK relationships and CASCADE DELETE behavior of the old schema are reproduced correctly in the new schema; if old FK was ON DELETE CASCADE, new FK is also ON DELETE CASCADE.
*Falsifier: delete on parent row cascades correctly in old schema but leaves orphan rows in new table.*

**V.17 All write paths covered** — dual-write hooks are applied to every write entry point: service layer, background jobs, admin scripts, event consumers; no secondary path writes old-schema-only.
*Falsifier: a nightly ETL job inserts rows into old schema; those rows are never reflected in new schema.*

**V.18 Migration tooling separation** — expand and contract DDLs are in separate, sequentially numbered migration files; the migration tool cannot apply them atomically in a single step that skips the intermediate stable state.
*Falsifier: migration tool refuses to apply partial migrations, forcing expand and contract in one step.*

**V.19 Index-build gate** — required indexes on new schema are built (`CONCURRENTLY` or equivalent) and their completion is verified as an explicit gate before the read-path switch.
*Falsifier: index build skipped; read-switch causes full-table scans degrading performance.*

**V.20 Backfill progress durability** — backfill progress (cursor or watermark) is persisted to a durable store; a job crash resumes from the last committed chunk, not from row 0.
*Falsifier: crash at 90% completion restarts from row 1.*

**V.21 Global phase-gate evaluation** — in multi-region/multi-DC deployments, phase gate conditions are evaluated globally across all regions; a single region's readiness does not permit a global phase advance.
*Falsifier: region A completes read-switch, region B still on old version; contract DDL drops old column globally, breaking region B.*

**V.22 External FK migration completeness** — all FKs from other tables pointing to the column being split are migrated as part of the procedure; no FK in any sibling table points to a dropped column after contract.
*Falsifier: contract DDL drops old column; FK from sibling table now references a non-existent column.*

**V.23 No join-completeness dependency during backfill** — no executing query may depend on join completeness between old and new schema during the backfill phase; such queries are either deferred or rewritten.
*Falsifier: reporting query joins old and new table during backfill, returns incorrect aggregates feeding a live dashboard.*

**V.24 Staging validation at production scale** — the full procedure is validated on a staging environment with production-scale data before live execution.
*Falsifier: procedure passes on 10k-row staging, backfill job times out on 500M-row production.*

**V.25 Read-path flag observability** — the flag service has an observable default/fallback behavior; a flag service outage must not silently leave reads on old schema without detection.
*Falsifier: flag service outage causes silent fallback to old schema; migration appears complete while reads never switched.*

**V.26 Constraint pre-validation** — before contract DDL enforces NOT NULL or UNIQUE constraints on new schema, a scan confirms no existing rows violate them.
*Falsifier: contract DDL fails with a constraint violation, requiring manual data repair under live traffic.*

**V.27 Cleanup does not destroy rollback path** — before any cleanup action removes an artifact (index, helper table, shim), the rollback query plan is verified to not depend on it, or the removal is deferred until rollback is declared impossible.
*Falsifier: cleanup drops a temporary index that was the only efficient path for a rollback query; rollback takes hours instead of seconds.*

## N — Scope Exclusions

**N.1 XA/2PC distributed transactions** — out by default; compensating dual-write + reconciler is used instead. Pulled back in only if old and new schemas reside on different database servers.
*(B-1)*

**N.2 Online schema change tools (OSC)** — pt-online-schema-change, gh-ost, and equivalents are not mandated; the procedure must work without them. Decision is per-table based on lock-sensitivity and table size.
*(B-2)*

**N.3 DB-trigger implementation of dual-write** — the default design uses application-layer dual-write; the trigger option is documented with tradeoffs but not the baseline. Pulled back in if multiple heterogeneous services write to old schema independently.
*(B-4)*

**N.4 Read-replica DDL propagation** — DDL assumed to propagate to replicas automatically via standard replication; replica parity not explicitly managed. Pulled back in if replica lag is high or replicas have diverged.
*(B-5)*

**N.5 Business-logic constraint implementation details** — domain-specific rules introduced by the split (e.g., cardinality invariants) are enumerated as requirements to enforce in new schema, but their implementation details are out of scope.
*(B-6)*
