## Task `T` (verbatim, PLAN §3 T09)

> Design the access-control logic for a multi-tenant SaaS: the principal/role/permission model, tenant
> isolation, resource hierarchy & permission inheritance, delegation/impersonation (e.g. support acting as a
> user), API-key & service-account scoping, and the audit trail. Specify the rules so that no principal can
> ever reach a resource outside its grants or its tenant.

**Shape.** Layered authorization: a request traverses **layers** — **authentication** (who is the
principal) → **tenant-context establishment** (which tenant, verified) → **policy decision** (does this
principal's roles/permissions grant this action on this resource) → **enforcement** at **every layer**
(API/gateway, application/service, **data/row**) → cross-cutting **delegation/impersonation**,
**service-account/API-key scoping**, and **audit**. The defining content is the **isolation invariant** (no
principal ever reaches a resource outside its grants *or its tenant*) and the **cross-layer escalation
seams** — leaks created *by interaction* between layers (inheritance × delegation × tenant boundary,
app-layer check vs data-layer row filter, tenant inferred from client input). The hard items are the
**conjunction**: isolation holds only if *every* layer enforces and *every* seam composes. Achievement
goal: a correct rule-set that *terminates* in a designed authz model — not a maintenance regime.

**Single meta-level.** This is a **design decomposition** of an authorization model — the components,
seams, invariants, and rules of *building a correct authz model* — at one level. It is NOT a hierarchy of
delegated org sub-projects (E3), and it is **ABOUT authorization but is not itself the org-authority
plane**: the *who-approves-this-design* question (security review sign-off, change control on policy
edits) is the orthogonal authority plane (see §3) and earns no `D`/`Dep`/`V` credit. Every criterion is a
predicate on the *designed model's* correctness (e.g. "a request whose token-tenant ≠ URL-tenant is
rejected"), not a self-report that a component was built. (Consequence: the OPERATIONAL failure modes
{FM-5,6,7} — runtime/execution-time modes — are mostly out of scope for this static single-meta-level
decomposition; see §7.)

## 1. Subtasks `D` — the authorization sub-systems / passes

> `D` = the children of the decomposition (canon §2.2: `D: T → P(T)`, a DAG).

Each subtask is a **separable part of the authz model** with its own pass/fail criterion on its
*behavior*, not a self-report ("RBAC implemented"). A decomposition covers a `D` iff it names a part with the
same role, however worded.

| # | Name | What it requires | Truth-maker (covered iff the decomposition names…) |
|---|---|---|---|
| **D1** | **Authentication↔authorization boundary (principal establishment)** | Establish the **verified principal** (user / service account / API key) as the *input* to authorization — and **draw the boundary**: authentication answers *who*, authorization answers *what they may do*. Authorization decisions are made on the **authenticated identity**, never on an unverified/claimed identity. AuthN mechanism itself (password/OIDC/SAML) is consumed, not built (→ N1). | …a principal model that distinguishes *who you are* (authenticated identity) from *what you may do* (authz), and feeds the **verified** identity into the decision. Credit "identify the principal first," "authn vs authz separation," "principal = user / service account / API key." |
| **D2** | **Tenant-context establishment & propagation** | Derive a **verified tenant context** for every request from a trusted source (the token/session claim, NOT client-controlled input like a URL/header/body), and **propagate it through every layer** (API → service → data) so each layer knows the tenant. The tenant context is a first-class, request-scoped, verified value. | …that every request carries an established, **verified** tenant identity derived from a trusted source and carried through all layers. Credit "establish the tenant on each request," "tenant scope from the token, propagated to the DB." **The spine of the whole task** — without it nothing else can isolate. |
| **D3** | **Policy model (roles / permissions — RBAC and/or ABAC)** | A model binding principals → roles → permissions (RBAC), and/or attribute/condition rules (ABAC), defining the *grammar of grants*: what permissions exist, how roles aggregate them, how a grant is expressed. Roles/grants are **tenant-scoped** (a role exists within a tenant, except declared cross-tenant admin → D6). | …a role/permission (or attribute-policy) model defining the vocabulary of grants and how principals acquire them. Credit "RBAC roles & permissions," "ABAC policies," "map users to roles to permissions." |
| **D4** | **Policy Decision Point (PDP) — the authorization decision** | A **single, well-defined evaluation** that, given (principal, action, resource, context), returns **permit/deny** by evaluating the policy model (D3) against the request — *centralized logic*, so the decision is consistent wherever it is asked. Resolves precedence (deny-overrides / explicit precedence, V-I2) and default-deny (V-I3). | …a defined decision function/point that evaluates grants and returns allow/deny for a (who, what, which-resource) tuple. Credit "central policy engine / decision point," "the function that decides permit or deny," "evaluate the request against the policy." **Distinct from D5** (D4 = *decides*; D5 = *enforces the decision*). |
| **D5** | **Policy Enforcement Points (PEPs) at EVERY layer** | The decision (D4) is **enforced** wherever a resource can be reached: API/gateway, application/service, **and the data layer** (row-level / query-scoping). Enforcement is **not only at the edge** — every layer that can return data re-checks (or provably inherits) the decision. The data layer's tenant/row filter is a PEP, not an afterthought. | …that the allow/deny is enforced at **multiple layers**, explicitly including the **data layer** (every query scoped by tenant/grant), not just at the API edge. Credit "enforce in the API and in the service and in the DB," "every query filters by tenant," "defense in depth / enforce at every layer." **The most load-bearing component** for isolation (ties to V-I4, V-F1). |
| **D6** | **Resource ownership & hierarchy / permission inheritance** | A model of **resource ownership** (each resource belongs to a tenant, and to an owner/org/project) and a **hierarchy** (org → project → resource) with **permission inheritance** rules (a grant at a parent node flows to children) — *and* the precedence between an inherited allow and an explicit deny (V-I2). Defines what "outside its grants" means structurally. | …a resource hierarchy with ownership and inheritance of permissions down the tree (grant at org/project flows to child resources), with a rule for inherited-vs-explicit precedence. Credit "resources belong to a tenant/org/project," "permissions inherit down the hierarchy," "ownership model." |
| **D7** | **Role/permission administration (grant lifecycle)** | The **administration surface**: who may create roles, assign/revoke grants, invite users, manage API keys — and the meta-rule that **administering grants is itself an authorized action bounded by the tenant** (a tenant admin administers *only their tenant*; no-privilege-escalation-via-admin, V-I5/V-F2). Grant changes take effect predictably (no stale-cache allow). | …that there is an administration model for managing roles/grants/keys, and that this administration is itself authorization-bounded (a tenant admin cannot grant outside their tenant or escalate themselves). Credit "role/grant management," "admin assigns permissions, scoped to their tenant," "who can change permissions." |

> **Note on `D` vs `Dep`/`V`.** D4 (PDP, *decide*) and D5 (PEP, *enforce*) are deliberately split: an agent
> can name "a policy engine" (D4) and silently assume one edge check enforces it, missing that enforcement
> must recur at the data layer (D5/V-I4). **Delegation/impersonation, service-account/API-key scoping, and
> audit** are listed by PLAN in the task statement; here **delegation** and **service-account scoping**
> surface as *cross-layer seams* (Dep5, Dep6) and *boundary-state criteria* (V-E2) rather than standalone
> components — they are properties *of* D1/D3/D4 under interaction, and the hard content is the seam, not a
> parts-list box (PLAN §1.3 rule 1, avoid `D`/`Dep` double-count). **Audit** is component-like but its real
> requirement is the *every-access-audited invariant* (V-I7) plus its *gap* failure (V-F5); it is scored
> there, not duplicated as a thin D8.

## 2. Dependencies `Dep` — cross-layer dependencies as explicit, separately-falsifiable `Dep` edges

> `Dep` = the canon primitive (§2.2): an acyclic relation on `T × T`; `(tₐ, tᵦ) ∈ Dep` iff `criteria(tᵦ)`
> references the output of `tₐ` (with coherence `deadline(tₐ) < deadline(tᵦ)`). **Each `Dep` edge is a
> criterion of a child that references a sibling's output — the glue** — and carries its **own** falsifying
> truth-maker (the anti-mock condition), not "these layers relate" prose.

**The most important and most-forgotten category — and the defining content of this task** (PLAN: "rich in
cross-layer escalation seams"). Each seam is a REAL edge: the *output of one named layer/component feeds
the input/decision of another*, and the edge carries its **own** falsifying criterion — a concrete leak /
IDOR / escalation path that opens if the edge is dropped (Constitution Ст. II.5 anti-mock). The shared
artifact is named for each (a tenant-id, a decision, a row filter, an impersonation token). A seam is
covered iff the decomposition names the **same pair** and the **same thing that leaks** if the edge is
absent/violated. T09's seams are **cross-layer tenant-isolation seams**: the leak is an objectively
identifiable cross-tenant / escalation path, not a nominal "these relate" pair.

| # | Name | Pair (source → consumer) | What the edge requires (shared artifact) | Truth-maker (covered iff named with its leak) |
|---|---|---|---|---|
| **Dep1** | **AuthN identity → AuthZ tenant-scoping (decide on the verified identity)** | D1 → D4 | The PDP must decide on the **authenticated** principal and its **verified** tenant, not on a claimed/spoofable identity. Shared artifact = the verified principal+tenant passed into the decision. If authz reads a client-supplied "I am user X / tenant Y," it authorizes the wrong identity. | …that the decision is made on the *verified* identity from authn, not a claimed one. Falsifier = authz check on the wrong/spoofed identity (**V-F4**'s seam face). Credit "decide on the authenticated user, never a client-asserted one." |
| **Dep2** | **Tenant-context propagated through EVERY layer (API → service → data)** | D2 → {D5 at API, service, data} | The verified tenant-id established at the edge must **reach every downstream layer**, especially the **data layer**, so the row filter / query scope uses it. Shared artifact = the request-scoped tenant-id. **A single layer that drops the tenant-id** (a service call that forgets to pass it, a query built without the tenant predicate) opens a cross-tenant read. | …that the tenant context is threaded through *all* layers down to the data query — and that **any layer dropping it is a leak**. Falsifier = a query/handler missing the tenant filter → IDOR / cross-tenant row. **The single hardest, most-forgotten seam** (objectively identifiable: a tenant-id absent at one layer). Shared artifact = the permit/deny decision. A divergent or skipped PEP = a path that returns data the PDP would have denied. | …that *every* code path reaching a resource goes through (or provably inherits) the decision — no unguarded endpoint/DAO/export. Falsifier = a resource path with no authz check. Credit "every endpoint enforces the policy," "no resource path skips the check." **Distinct from Dep2** (Dep2 = the *tenant-id* reaches the data layer; Dep3 = the *decision* is consulted at every PEP — different artifact). |

Shared artifact = the *same* (principal,tenant,resource) authorization, evaluated consistently at both layers. Divergence = a row the app would hide is reachable through a query the data layer didn't scope. | …that the app-level check and the DB-level filter must be **consistent** — the DB does not rely solely on the app having filtered, and an app deny is not undone by an unscoped query. Falsifier = app-allows-but-data-leaks (or app-denies-but-data-returns). **Hard cross-layer seam** — the defense-in-depth consistency edge. Credit "the DB must enforce tenant scoping itself, consistent with the app," "don't trust the app layer to have filtered." |
| **Dep5** | **Delegation / impersonation ↔ tenant boundary (support acting as a user)** | D1/D4 (impersonation) ↔ D2 (tenant boundary) | When a principal **acts as** another (support impersonating a user, on-behalf-of, admin assume-user), the **effective** authorization is the **intersection / bounded** set — and the impersonation must **not cross a tenant boundary** unless explicitly a declared cross-tenant role. Shared artifact = the *effective* principal+tenant under impersonation. Naive impersonation that adopts the target's full grants *or* lets cross-tenant support read arbitrary tenants = escalation. | …that impersonation/delegation produces a **bounded effective identity that respects the tenant boundary** (support acting as a user does not thereby reach other tenants, and the delegated scope is the intersection, not a union/elevation). Falsifier = delegation crossing a tenant boundary or granting more than both parties hold. **A signature escalation seam of this task** (PLAN: inheritance × delegation × tenant-boundary). Credit "impersonation is scoped to the target's tenant and bounded by least of the two grants." |

Shared artifact = the key/SA's scoped grant set. A key treated as "full access" or untied to a tenant = a non-human escalation path. | …that API keys / service accounts are **scoped (tenant + permissions)** and the decision enforces that scope as an upper bound. Falsifier = a key reaching beyond its issued tenant/permissions. **Distinct from Dep5** (Dep5 = a human acting as another; Dep6 = a non-human credential's static scope). Credit "API keys are scoped to a tenant and a permission set," "a service account can't exceed its grant." |
| **Dep7** | **Inherited permission ↔ explicit deny precedence (hierarchy × policy)** | D6 (inheritance) ↔ D4 (precedence) | When a permission is **inherited** down the resource hierarchy (grant at org → child project), and an **explicit deny** exists at a child (or vice-versa), the PDP must apply a **defined precedence** (V-I2). Shared artifact = the resolved effective permission at the resource node. An inherited allow that silently **overrides an explicit deny** (or an undefined conflict) is an escalation. | …that inheritance and explicit grants/denies compose by a **stated precedence rule** so an inherited allow cannot quietly override a deny. Falsifier = an inherited grant defeats an explicit deny / undefined conflict resolution. Credit "deny overrides inherited allow (or a stated precedence)," "resolve conflicts between inherited and explicit permissions." **The inheritance×policy escalation seam.** |
| **Dep8** | **Resource move / re-parent ↔ inherited grants recomputed** | D6 (hierarchy mutation) → D4 (effective grants) | When a resource is **moved** to a new parent/owner/tenant, its **inherited (and tenant-scoped) permissions must be recomputed**; stale inherited grants from the old parent must not persist. Shared artifact = the resource's effective grant set after re-parenting. A moved resource that keeps old-parent grants (or old-tenant visibility) leaks across the new boundary. | …that moving/re-parenting a resource recomputes its inherited grants and tenant scope (no stale grants from the old location). Falsifier = a moved resource still accessible under old-parent/old-tenant grants. **Easily-forgotten mutation seam.** Credit "when a resource moves, recompute who can see it." | **Dep9** | **Grant change → effective decision (no stale-cache allow)** | D7 (admin revoke/grant) → D4/D5 (live decision) | A **revocation** (or grant) made via administration (D7) must take effect at the decision/enforcement points **promptly and consistently** — a cached role/permission/decision that still says "allow" after a revoke is a live leak. Shared artifact = the principal's current grant set vs the one the PDP/PEP uses. Stale authz cache = access after revocation. | …that revoking a grant actually removes access in a bounded, consistent way (no stale-cache / stale-token allow after revoke). Falsifier = access persists after revocation due to caching/long-lived token. Shared artifact = the cross-tenant grant and its scope. An over-broad or implicit cross-tenant role dissolves isolation for everyone. | …that any legitimate cross-tenant access (platform admin/support) is an **explicit, minimal, audited** role, distinct from tenant roles, and is the *only* sanctioned boundary crossing. > **Anti-mock note.** Each `Dep` references a concrete *shared artifact* whose absence/violation is an
> **objectively identifiable leak** (a tenant-id missing at a layer → a returnable cross-tenant row; an
> impersonation token spanning tenants → a reachable foreign resource), not a nominal "these relate" pair.
> None collapse onto each other: different layer-pair OR different artifact OR different falsifier ⇒ distinct
> seam (PLAN §1.3 rule 1). In particular **Dep2** (the *tenant-id* must reach the data layer) ≠ **Dep3** (the
> *decision* must be consulted at every PEP) ≠ **Dep4** (app and data layers must *agree*) — three different
> shared artifacts on the same API↔service↔data spine, three different falsifiers (missing filter · unguarded
> path · inconsistent layers). **Dep5** (human impersonation) ≠ **Dep6** (non-human key scope) ≠ **Dep10**
> (standing cross-tenant role) ≠ **Dep11** (one user's *active* tenant among several memberships) — four
> distinct boundary/identity mechanisms (acting-as-another · static credential scope · standing cross-tenant
> role · active-tenant pinning). **Dep7** (inheritance vs explicit-deny precedence, *within* a tenant) ≠
> **Dep8** (re-parent *mutation* recomputes grants) ≠ **Dep12** (inheritance *halts at the tenant root* — a
> *static* boundary rule) — three distinct inheritance concerns (intra-tenant conflict · mutation ·
> tenant-boundary). **Dep9** (a *principal's grant data* is current after revoke) ≠ **Dep13** (the *policy
> version* is coherent *across all PEPs* after a rule edit) — single-subject freshness vs distributed
> multi-PEP coherence.

> **FM mapping for `Dep`.** A forgotten/violated `Dep` edge is an **FM-1** defect (a spanning integration
> criterion — the glue — not written / not covered; §4.2 FM-1 insufficiency, §18.10 *hole-i*) when it is a
> coverage hole, and an **FM-2** defect (criteria of two children incompatible / a relational defect at fixed
> composition; §4.2 FM-2) for the two-sided / shared-artifact seams whose breakage is a mutual-satisfiability
> conflict (Dep4 app↔data consistency, Dep5 impersonation↔tenant-boundary, Dep7 inheritance↔deny precedence,
> Dep12 inheritance↔tenant-boundary, Dep13 policy-version coherence across PEPs). The §7 FM table records
> this. Per one-defect-one-place, a seam's failure is scored **here as a `Dep` item**, never re-listed as a
> separate criterion.

## 3. Authority / control — ORTHOGONAL PLANE (`Del`, NOT scored)

> **`Del` is the canon "who" axis** (§2.3: `Del: T → A`, exactly one agent per task) — **orthogonal** to the
> decomposition plane `{D, Dep, V}` and **NOT scored** as a decomposition item. This is a plane-separation
> note, NOT a NEGLECTED exclusion, NOT a criterion, NOT a completeness hole.
> **Special care for T09:** the task is *about* authorization, which makes it tempting to conflate the
> **modeled** authority (the authz rules being designed) with the **process** authority (who approves the
> design). They are different planes.

The **modeled** authority — roles, grants, the PDP/PEP, tenant isolation — **IS** the decomposition (`D`/`Dep`/`V`
above): it is the *artifact being designed*, scored normally. What is **orthogonal** is the **process /
governance** authority over *this design*: who **approves** the policy model, security-review sign-off on the
authz design, change-control on who may edit production policies, segregation between the engineer who writes
the policy and the one who reviews it. That governance is a predicate on the **process/authority assignment**,
not on the produced authz model. An authz model can be perfectly correct (full tenant isolation, default-deny,
every layer enforcing, no escalation path) **and still** have been authored and merged by one person with no
review gate. In GFSO's primitives this is emergent from the **edges of the delegation hierarchy** (Issuer sets
the design criteria and validates `V`; Executor produces; `Del` assigns who; Issuer-validation ≠
self-validation) — structurally carried by the protocol, not a node *within* the decomposition.

**Consequences for scoring (scorer rules):**
- A decomposer is **NOT penalized** for failing to list "security review gate / change-control on policy
  edits / SoD between policy author and reviewer" as a decomposition item — there is no `D`/`Dep`/`V`/NEGLECTED
  slot it belongs in.
- **Force-fitting a process-approval gate into a Subtask or Criterion is a category error.** The
  *administration model inside the system* (who may assign grants, scoped to their tenant) **is** covered —
  that is **D7 / V-I5 / Dep9** (the modeled admin authority). The *human approval of the design itself* is the
  orthogonal authority plane and earns no `V`/`D` credit and loses none.

> **Scorer discriminator (modeled authority vs process authority):** "a tenant admin may assign roles only
> within their tenant" = **D7/V-I5** (the modeled authz rule, an artifact criterion) → score it. "a security
> architect must approve the policy model before it ships" = **process authority plane** → do not score as a
> category item, do not penalize its absence.

## 4. Criteria `V` — task predicates (former Invariants + Edge-cases + Failure-modes, COLLAPSED)

> `V` is **derived**: `V(t) = AND(criteria(t))` (§2.2, §3.1 Theorem 1). Every item below is a **predicate of
> the task** — a `criterion` whose conjunction is the validation. The former Invariants (parent-level
> spanning predicates), Edge-cases (boundary-state predicates) and Failure-modes (defect-coupling
> predicates) are **all criteria** and are collapsed here into one section. Each criterion keeps its
> verbatim text + truth-maker and carries an **FM tag**: which canon failure mode(s) it precludes (§4.2 /
> §4.6). The old I/E/F labels are retired — the FM tag replaces them. (Item ids keep an I-/E-/F- prefix
> purely for cross-reference traceability to `reference_buckets_v1.md`; they are NOT separate categories.)

**How to read the FM tag.** Per §4.2/§4.6: a **spanning/coverage predicate** a faithful decomposition must
carry (and whose omission is a coverage hole) precludes **FM-1** (Correspondence — joint sufficiency); a
predicate enforcing **mutual satisfiability** of children / cross-layer or precedence consistency precludes
**FM-2** (Consistency); a predicate guarding against an **insensitive / mockable / looks-secure-but-leaks**
check (a value that passes where reality fails) precludes **FM-3** (Verifiability, false-PASS); a predicate
enforcing **correct fail-propagation / complete mediation / no-bypass** precludes **FM-4** (Propagation).

### 4.1 Global correctness criteria (spanning predicates — the isolation invariant)

A spanning criterion is a parent-level predicate that **spans layers/components** — no single component
establishes it; it holds only if all are jointly correct (canon §2.2 joint sufficiency / §3.1).
Canonicalized by the *enforced predicate*, not by where it is checked (PLAN §1.3 rule 2). These are the
**defining rich content** of T09 (the goal `spec`: "no principal can ever reach a resource outside its grants
or its tenant").

| # | Name | Enforced predicate | FM tag (precludes) | Truth-maker (covered iff the decomposition asserts…) |
|---|---|---|---|---|
| **V-I1** | **Tenant isolation (NO cross-tenant access, ever)** | For **every** principal, action, resource, and layer: a principal of tenant A can never read, write, or even *observe the existence of* a resource of tenant B (no cross-tenant data access, no cross-tenant enumeration/inference). The conjunction over all layers and all access types. | **FM-1** (the headline spanning isolation predicate the `spec` names) | …that no principal ever reaches another tenant's data through *any* path (the defining isolation predicate). **The signature invariant of the task** — the goal `spec` restated. Credit "tenants are fully isolated; A never sees B's data by any route." |
| **V-I2** | **Deny-overrides-allow (or a stated, total precedence)** | Conflicts (inherited allow vs explicit deny, role-union conflicts, multiple matching policies) resolve by a **defined, total** precedence — canonically **deny overrides allow**, or an explicitly stated alternative — so no conflict is left undefined (an undefined conflict is a latent escalation). | **FM-2** (mutual satisfiability of conflicting grants — a defined total precedence) | …that grant/deny conflicts resolve by a stated precedence (deny-overrides, or an explicit total order), with no undefined conflict. Credit "explicit deny beats inherited allow," "a defined conflict-resolution / precedence rule." |
| **V-I3** | **Default-deny (closed by default)** | Absence of an explicit grant is **deny**, at every decision and every layer. No action is permitted because it was *not* explicitly forbidden; a new endpoint/resource/code path is denied until a grant exists. The fail-safe default. | **FM-1** (closed-world coverage: absence → deny, no unguarded path) | …that the system denies unless explicitly allowed (closed-world / default-deny), including unguarded new paths. Credit "default deny," "deny unless a grant exists," "fail closed." **Distinct from V-I2** (V-I2 = how *conflicts* resolve; V-I3 = how *absence* resolves). |
| **V-I4** | **Enforcement at every layer (no edge-only trust / complete mediation)** | The isolation/grant predicate is enforced at **every** layer that can reach a resource (API, service, **data**), so a bypass of one layer does not yield access — complete mediation, defense in depth. Not a single perimeter check. | **FM-4** (complete mediation: no layer left unmediated; no bypass path) | …that enforcement is **layered**, not edge-only — every access is mediated, the data layer included. Credit "enforce at every layer / defense in depth," "the DB enforces tenant scope even if the API is bypassed." **Distinct from D5** (D5 = the *components* that enforce; V-I4 = the cross-cutting *predicate* that no layer is unmediated) and from Dep3 (Dep3 = the *seam* decision→each PEP). |
| **V-I5** | **Least privilege / no privilege escalation (esp. across tenants)** | Every principal holds the **minimum** grants needed; **no operation lets a principal acquire grants it shouldn't** — neither horizontally (another tenant) nor vertically (admin powers), including via self-administration (D7), impersonation (Dep5), or key issuance (Dep6). Escalation paths are closed. | **FM-1** (spanning no-escalation coverage predicate across every grant-conferring path) | …that principals get least privilege and **cannot escalate** their own privileges (across tenants or to admin) through any feature. Credit "least privilege," "no privilege escalation," "a tenant admin can't grant themselves cross-tenant / platform powers." |
| **V-I6** | **Verified tenant context on every request** | **Every** authorized request carries a tenant context that is **established from a trusted source and verified** (token/session claim), never inferred from client-controlled input (URL, header, body, query param). No request is authorized without a verified tenant. | **FM-3** (an insensitive check that trusts a spoofable tenant source false-PASSes) | …that every request has a **verified** tenant context from a trusted source, never trusting a client-supplied tenant id. Credit "tenant comes from the verified token, not the URL/header," "every request is tenant-scoped before authz." **Tightly tied to V-F6** (tenant inferred from client input). |
| **V-I7** | **Every access decision is audited (complete, tamper-evident trail)** | Every authorization-relevant event — **permit and deny**, impersonation start/stop, grant change, key use — is recorded in an **append-only / tamper-evident** audit trail with principal, tenant, resource, action, decision, and (for impersonation) the *real* actor behind the assumed one. The trail is complete enough to reconstruct *who did what as whom*. | **FM-1** (the auditability half of the task — a spanning coverage predicate; detection back-channel tied to V-F5) | …that all access decisions (allows **and** denies), impersonations, and grant changes are logged in a complete, tamper-evident trail that records the real actor (incl. behind impersonation). Credit "audit every access incl. denials and impersonations, append-only, capturing the real principal." |

> **Criteria vs `D`/`Dep`.** V-I4 and Dep3/D5 are the same physical concern (enforce everywhere) seen as the
> cross-cutting *predicate* (V-I4) vs the *seam* decision→PEP (Dep3) vs the *components* doing it (D5) —
> counted once each, by category (PLAN §1.3 rule 2), not triple-counted. V-I1 (isolation) is the goal `spec`'s
> headline; omitting it leaves the core requirement uncovered. V-I2 (conflict precedence), V-I3 (absence→deny),
> and V-I6 (verified context) are genuinely distinct predicates — a model can satisfy any one and fail another.

### 4.2 Boundary-state criteria (former Edge-cases)

A boundary-state criterion is a boundary state a naive happy-path authz design silently mishandles — i.e. a
predicate the design must satisfy at the boundary, or the corresponding check is **insensitive** there
(passes a wrong result). Covered iff the decomposition names the same boundary condition and that it needs a
rule.

| # | Name | What it requires | FM tag (precludes) | Truth-maker (covered iff named) |
|---|---|---|---|---|
| **V-E1** | **Shared / global / cross-tenant resources** | Some resources are **not** tenant-private: platform-global config, shared reference data, a marketplace listing visible across tenants, a resource explicitly *shared* from tenant A to tenant B. The model needs an explicit notion of "global" / "shared with" — distinct from the default tenant-private — so isolation (V-I1) is not violated *and* legitimate sharing is possible. | **FM-3** (a happy-path isolation check insensitive to a legitimately-shared resource → false-FAIL, or a default-private gap → false-PASS) | …that some resources are global or explicitly shared across tenants, needing a deliberate rule distinct from default tenant-private (not an isolation hole). Credit "global/shared resources," "cross-tenant sharing as an explicit grant." |
| **V-E2** | **Support / platform-admin impersonation across the tenant boundary** | The concrete impersonation case: a support engineer (platform tenant) **acts as** a user inside a customer tenant. The design must define how the effective identity is scoped (Dep5/Dep10), that it is **time-bounded and consented/justified**, and that the audit records the **real** support actor behind the assumed user (V-I7). | **FM-3** (a happy-path check insensitive to the cross-boundary impersonation passes the wrong effective identity) | …the specific support-impersonates-customer-user case with a bounded, audited, time-limited mechanism that records the real actor. Credit "support can act as a user, scoped + audited + time-boxed." **The boundary-state face of Dep5/Dep10.** |
| **V-E3** | **Orphaned / re-parented / moved resource (inherited grant on a moved resource)** | A resource is **moved** to a new owner/project/tenant, or its parent/owner is **deleted** (orphaned). Credit "when a resource moves or its owner is deleted, fix its permissions." **Boundary-state face of seam Dep8.** |
| **V-E4** | **Tenant-in-URL (or header/body) vs tenant-in-token MISMATCH** | A request supplies a tenant id in a **client-controllable** place (URL path `/tenants/{id}/…`, header, body) that **disagrees** with the verified tenant in the token/session. The design must **reject the mismatch** (or always derive tenant from the token and ignore the client value) — never trust the client-supplied tenant. | **FM-3** (an insensitive check trusts the client-supplied tenant → cross-tenant false-PASS, the canonical IDOR) | …that a tenant id in the URL/header/body conflicting with the token must be rejected (or the token is authoritative). Credit "if the URL tenant ≠ the token tenant, deny," "never trust the tenant id from the path." **Tied to V-I6 / V-F6** — the canonical IDOR vector. |
| **V-E5** | **Background jobs / async / system context with no end-user** | A code path runs with **no interactive user** — a cron job, queue consumer, webhook handler, scheduled report, data pipeline. Credit "the nightly job / queue consumer must carry a tenant and a scoped identity, not run as root." **The most-forgotten edge** — happy-path authz reasons only about interactive requests. |
| **V-E6** | **Nested orgs / sub-tenants / tenant hierarchy** | Tenants are not always flat: an org with **sub-organizations / teams / child tenants** (enterprise with departments, reseller with sub-accounts). Isolation and inheritance must be defined across the **tenant hierarchy** — a parent-org admin may (by an *explicit* rule) see child orgs, but a sibling sub-tenant must not see another, and "tenant" boundary becomes a subtree, not a single id. | **FM-3** (a flat-tenant happy-path check is insensitive to the subtree boundary → sibling leak / wrong parent scope) | …that tenants can nest (sub-orgs/teams/child accounts) and isolation/inheritance must be defined across that hierarchy (parent-admin scope explicit, siblings isolated). | **V-E7** | **Wildcard / broad grants & role explosion** | Grants like `*` (all resources), an org-wide role, or a wildcard scope on an API key are **legitimate but dangerous** boundary inputs: the model must define how a wildcard interacts with tenant scope (a `*` is still **tenant-bounded**, never global) and with explicit deny (V-I2). A `*:*` that silently escapes the tenant boundary is the trap. | **FM-3** (a wildcard the check reads as tenant-escaping is an insensitive grant evaluation → false-PASS) | …that wildcard/broad grants (`*`, org-admin, full-scope key) are still **bounded by the tenant** and compose with deny precedence — a wildcard is not a tenant escape. Credit "a `*` permission is still tenant-scoped," "broad grants don't cross tenants." |
| **V-E8** | **Newly added resource type / endpoint (coverage at extension time)** | When a **new** resource type, endpoint, or field is added later, it must be **denied by default** (V-I3) and **explicitly brought under** the policy model & every PEP — not silently unguarded because no rule mentions it. The boundary state is *model extension*: the new path inherits enforcement, not an exemption. | **FM-3** (the extension-time boundary where a default-deny check is insensitive to an unguarded new path) | …that a newly added resource/endpoint is closed by default and must be explicitly added to the policy & enforcement, not left unguarded. Credit "a new endpoint defaults to deny until a grant covers it," "extending the system doesn't open a hole." **Distinct from V-I3** (V-I3 = the *predicate*; V-E8 = the *extension-time boundary* where it bites). |
| **V-E9** | **IDOR object-reference boundary (valid foreign-tenant id ⇒ not-found/deny)** | A request supplies a **syntactically valid object id that belongs to another tenant** (a guessed/enumerated/leaked-elsewhere identifier). The boundary state is *a well-formed reference into another tenant's space*. | **FM-3** (an insensitive post-dereference check returns the foreign object / leaks an existence oracle → false-PASS) | …that a valid-but-foreign object id resolves to **not-found/deny after an ownership re-check**, leaking no existence signal via enumeration. | **V-E10** | **Delegation / re-delegation chain (depth & loop bounded)** | When delegation/impersonation is **transitive** (A acts-as B, who acts-as C; or a delegated grant is re-delegated onward), the **chain is depth- and scope-bounded**: each hop's effective authority is **≤ the delegator's** (never amplifies along the chain), the chain **cannot loop**, and the **tenant boundary holds at every hop** (Dep5). Shared boundary state = a *multi-hop* effective identity, not a single hop. Naive transitive delegation that unions grants or recurses unbounded escalates. | **FM-3** (a single-hop happy-path check is insensitive to the multi-hop chain → amplification/loop passes) | …that a delegation/impersonation **chain** is bounded — each hop ≤ the delegator, no looping, no amplification, tenant boundary respected at every hop. Credit "re-delegation can't grant more than the delegator and can't chain unbounded/loop." **Extends Dep5** (Dep5 = a *single* hop's bound; V-E10 = the *transitive chain* depth/loop bound). |
| **V-E11** | **Tenant provisioning / first-principal bootstrap (scoped to the new tenant)** | **Creating a new tenant** T grants its **initial admin scoped to T only**. The bootstrap path — which by necessity creates the first grants when no admin yet exists — **cannot confer cross-tenant authority** or reach an existing tenant; it is the one provisioning act, still tenant-bounded. Boundary state = *the moment a tenant has no users yet and its first admin is minted*. A bootstrap that grants global/platform powers, or lets the creator retain reach into other tenants, opens a provisioning escalation. | **FM-3** (the no-admin-yet bootstrap boundary is insensitively handled → cross-tenant grant passes) | …that provisioning a tenant yields an admin **scoped only to that new tenant**, and the bootstrap cannot grant cross-tenant/platform authority. Credit "creating tenant T makes an admin of T only; bootstrapping can't escape the new tenant." **Distinct from D7** (D7 = the *steady-state* admin surface, already tenant-bounded; V-E11 = the *bootstrap boundary* where no admin yet exists). |
| **V-E12** | **Self-grant / reflexive escalation (no granting oneself authority)** | A principal **cannot grant itself** authority it does not already hold, nor **approve its own escalation** — the modeled self-grant rule. Where an escalation requires approval, a **distinct approver** is required (modeled separation-of-duty *inside the system*). Boundary state = *the grant subject and the grant actor are the same principal*. A self-grant loophole lets any admin bootstrap itself to higher privilege within the model. **In-scope (the modeled self-grant rule); distinct from the orthogonal process-authority plane** (who approves the *design* — see §3, which earns no credit). | **FM-3** (the reflexive grant-subject = grant-actor boundary is insensitively handled → self-escalation passes) | …that a principal cannot grant itself (or approve its own) escalation, and that elevation requires a distinct approver where applicable (modeled SoD). Credit "you can't grant yourself more than you have / approve your own escalation; a second approver is needed." **Refines V-I5/D7** (V-I5 = no-escalation predicate, D7 = admin bounded; V-E12 = the *reflexive self-grant* boundary specifically). |

### 4.3 Defect-coupling criteria (former Failure-modes — only those with NO `Dep` / invariant twin)

Phrased as **concrete coverable claims** (PLAN §1.3 rule 4), never adjectives. Each names a specific defect
coupling AND its resolution; covered iff the decomposition names the same coupling and a guard.
**One-defect-one-place (PLAN §1.3 rule 1):** a defect-coupling is kept ONLY if it has no `Dep`-seam / `V`-E /
`V`-I twin sharing the *same pair, falsifier, and fix*. The *missing-tenant-filter-at-one-layer* leak is
carried by **Dep2**; the *inherited-allow-overrides-deny* escalation by **Dep7/V-I2**;
*stale-cache-allow-after-revoke* by **Dep9** — those are NOT restated here. What remains are couplings with
**no twin**: the structural **single-missing-filter → IDOR** mechanism (V-F1, kept as the *mechanism+guard*
distinct from Dep2's enumeration), confused-deputy (V-F2), default-allow (V-F3 — distinct from V-I3's predicate
as a concrete misconfiguration coupling), authz-on-the-wrong-identity (V-F4), the audit *gap* (V-F5),
client-controlled-tenant-inference (V-F6), and the **checked-once-then-trusted handle / TOCTOU** temporal
coupling (V-F7 — distinct from Dep9's *input-freshness seam* as the *per-use re-validation* mechanism + guard).

| # | Name | FM tag (precludes) | What it requires (coupling + guard) | Truth-maker (covered iff named with a guard) |
|---|---|---|---|---|
| **V-F1** | **Single layer missing the tenant filter → leak / IDOR** | **FM-1** (a forgotten guard / coverage hole) | One query / handler / endpoint that **forgets the tenant predicate** returns another tenant's rows — even though every *other* layer is correct. The coupling: per-query correctness vs the global isolation invariant. Guard (a *mechanism*, beyond "be careful"): **make tenant-scoping structural, not per-query opt-in** — a mandatory query interceptor / row-level security (RLS) at the DB / ORM global scope / repository base class, so the filter cannot be omitted by forgetting. | …that a single un-scoped query is enough to leak (IDOR), AND a structural guard (DB row-level security, mandatory ORM/query filter, repo base class) makes the filter impossible to forget — not "remember to filter." **Distinct from Dep2** (Dep2 = the *seam* tenant-id-reaches-data-layer; V-F1 = the *single-omission-is-catastrophic* mechanism + the structural-enforcement guard). **The #1 real-world multi-tenant breach.** |
| **V-F2** | **Confused deputy** | **FM-3** false-PASS (a trusted intermediary acts with *its* authority on a caller's behalf) | A privileged component (a service, a shared internal API, an export job, a webhook with broad creds) performs an action **using its own elevated authority** on input from a less-privileged caller, **without re-checking the caller's grants** — so the caller reaches resources it could not directly. The coupling: the *source of truth* for tenant vs client controllability. | **V-F7** | **Checked-once-then-trusted handle / TOCTOU (authz cached across a privilege change)** | **FM-1** (a coverage hole in *time* — a guard not re-applied at use) | Authorization is decided **once** and then **trusted across subsequent uses**: a long-lived handle/session/cached decision obtained under the **old** grants keeps working **after a grant/role/policy change revokes it**, or the resource's **tenant/ownership mutates between the time-of-check and the time-of-use** (TOCTOU race) so the acted-on object no longer matches what was authorized. The coupling: a decision's validity window vs the mutability of grants/ownership during it. Guard: **re-evaluate authorization on each use** (no checked-once-then-trusted handle), and bind check-and-act so a tenant/ownership change between check and dereference **cannot** be raced into access. | …that authz must be **re-checked on each use, not cached across a privilege/grant change**, AND that a long-lived handle or a TOCTOU race (ownership/tenant mutating between check and use) is closed. Credit "don't trust a handle issued under old permissions — re-authorize each use," "close the check-then-use race." **Distinct from Dep9** (Dep9 = the *seam* revoke→live-decision, the *input freshness* artifact; V-F7 = the *checked-once-then-trusted / TOCTOU* coupling + per-use re-validation guard) and from V-F4 (V-F4 = *which* subject/object — check-X-act-on-Y; V-F7 = the *temporal* window — checked-then-trusted-across-change). |

> **Note on V-F5 and the operational axis.** V-F5 is the one criterion that names an OPERATIONAL failure mode
> (**FM-7 feedback** — a defect-detection back-channel) at design time — because the *task itself* (the audit

## 6. Hardest / most-easily-forgotten seams (flag for scorer)

> Not a category — a scorer pointer at the highest-signal `Dep` edges.

- **Dep2 — tenant-id propagated through EVERY layer down to the data query** (the isolation spine). The single
  most load-bearing and most-forgotten edge: a parts-list happily lists "RBAC" and "tenant isolation" as
  boxes but drops the requirement that the *tenant predicate is on every single query* — one handler/DAO/
  report/export that builds a query without it returns another tenant's rows (IDOR). A "magic-word"
  decomposition names isolation as a goal and never as a per-query, per-layer obligation. (Its structural-
  guard / single-omission-is-catastrophic face is **V-F1**.)
- **Dep4 — app-layer check ↔ data-layer row-filter consistency** (defense-in-depth that actually composes).
  Forgotten because the happy-path model assumes "the service checked, so the DB is safe" — but a second
  query path, a reporting view, or an over-trusting DAO that applies *no* filter turns one app-layer bug into
  a full-tenant exposure. The seam is that both layers must *independently and consistently* enforce.
- **Dep5 / V-E2 — delegation/impersonation bounded by the tenant boundary** (support acting as a user). The
  signature *escalation-by-interaction* seam: naive impersonation adopts the target's full grants or lets
  cross-tenant support read arbitrary tenants; the effective identity must be the *bounded intersection*,
  tenant-respecting, time-boxed, and audited with the *real* actor (V-I7). Inheritance × delegation ×
  tenant-boundary is exactly the PLAN-named hard interaction.
- **Dep7 / Dep12 — inheritance precedence & the tenant-boundary stop** (inheritance × policy, inheritance ×
  tenant). Dep7: inheritance is modeled as "grants flow down" with no thought to a child's explicit deny — an
  inherited allow silently overriding a deny is a clean escalation, an *undefined* conflict a latent one
  (V-I2). Dep12 (distinct): inheritance that does not **halt at the tenant root** — a nested node or a child
  role that imports/widens a *cross-tenant* grant — dissolves isolation through the hierarchy itself, a
  different falsifier from Dep7's same-tenant precedence and from Dep8's re-parent mutation.
- **Dep11 — multi-tenant user's active-tenant selection** (one user, several flat tenants). Forgotten because
  the happy-path model conflates "the user is in tenant X" with "this request is scoped to X" — but a user in
  {A,B} must have **exactly one server-pinned active tenant per request**, and membership in A must not
  ambiently widen a B-request's scope. The leak is **A-data bleeding while active=B**, or the active tenant
  taken from a client-controlled request value. Distinct from V-E6 (nested *hierarchy*) — this is *flat
  multi-membership* with active-tenant pinning, the one truly missing `Dep`-seam the audit surfaced.
- **V-E5 — background jobs / async with no end-user context.** *The most-forgotten edge-case.* Happy-path
  authz reasons only about interactive requests; the cron job, queue consumer, webhook handler, and scheduled
  report run with no user, and the lazy fix is an ambient super-user/no-tenant context that bypasses isolation
  entirely — they must carry an explicit tenant-scoped service-account principal (Dep6).

  *human approval of the design itself* (security-review sign-off, change-control on policy edits, SoD between
  policy author and reviewer) is a property of the process/authority, not a predicate over the produced authz
  model; it is emergent from the Issuer ≠ Executor-on-validation split (`Del` + delegation hierarchy) the GFSO
  protocol already guarantees structurally. **Scorer rule:** do **not** penalize a decomposition for omitting
  it as a `D`/`Dep`/`V`/NEGLECTED item, and do **not** award criterion-credit (nor deduct) for an agent who
  states "a security architect must approve the policy model." It is a correct statement in a different plane.
  Force-fitting it into a criterion is a category error (criterion = artifact predicate; design-approval =
  process/authority predicate). The *modeled* admin authority (a tenant admin assigns roles only within their
  tenant) IS scored — that is **D7/V-I5/Dep9**. See §3 above. This is plane-separation, **not** a NEGLECTED
  exclusion and **not** a completeness hole.
