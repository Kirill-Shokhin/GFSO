## Task `T` (verbatim, PLAN §3 T03)

> Design the *procedure and the invariants* to evolve a relational schema under a backward-incompatible
> change (e.g. split a column into a new table) on a live, high-traffic service with rolling deploys and no
> downtime: expand/contract phases, dual-write & backfill, read-path switch, app-version compatibility
> windows, the rollback path at each phase, and post-migration cleanup. **Design the migration logic, do not
> execute it.**

**Shape.** Layered: the change must hold simultaneously *across four layers* — **schema** (DDL state),
**application code** (the running binaries' read/write expectations), **data** (old vs new representation of
existing rows), and **deploy fleet** (a mix of old and new app versions during every rolling deploy). The
defining content is the **cross-layer compatibility invariant** (every old AND new app instance must work
against every *intermediate* schema state) and the **per-phase rollback** edge-cases. The phases are *ordered
in time* (expand → backfill → dual-write soak → read-switch → soak → contract); the ordering is the
rollback-safety spine.

**Achievement goal executed over time.** T03 is an ACHIEVEMENT goal — it *terminates* in the migrated schema
(the new representation live, the old structure dropped, every reference cleaned up). But it is an **ordered
process executed over live time**: each phase runs while the service keeps serving traffic, the underlying
data is *mutating under the migration* during backfill, and a defect found mid- or post-migration must route
through a *designed* rollback/abort path. This live-over-time character is why two OPERATIONAL failure modes
carry genuine design-time predicates here (unlike a purely static design reference): the rollback/reversibility
design is an FM-7 (feedback) predicate the task statement forces, and the dual-write-during-live-traffic /
state-changing-under-the-running-pass design is an FM-5 (currency) predicate (see §7).

**Single meta-level.** This decomposes the migration **logic** at one level: the procedure, its phases, the
invariants each phase must hold, and the rollback path. It does NOT spawn org sub-projects (coordinating the
deploy across teams, staffing on-call, building CI). Phases are passes of one design, not delegated
sub-projects (PLAN §3 T03 E3-check). **"Design, do not execute"** — every criterion is a predicate on the
*designed procedure's* correctness (e.g. "the rollback at phase k is defined and loses no committed data"),
not a self-report that a step ran.

## 1. Subtasks `D` — the migration phases / passes

> `D` = the children of the decomposition (canon §2.2: `D: T → P(T)`, a DAG).

Each subtask is a **phase**: a separable state of the migration with its own pass/fail criterion on its
*output state* (a schema+data+code configuration that is itself live-correct), not a self-report ("backfill
done"). The phases form the expand→contract skeleton. A decomposition covers a `D` iff it names a phase with
the same role in the sequence, however worded.

| # | Name | What it requires | Truth-maker (covered iff the decomposition names…) |
|---|---|---|---|
| **D1** | **Expand — additive schema change** | Apply only **additive, backward-compatible** DDL first: create the new table/column **nullable / with default**, add nothing that an old app instance can violate (no NOT NULL on new col, no dropped/renamed old col, no new FK old code can break). The old schema's surface is untouched. | …an *expand* / additive phase that adds the new structure non-destructively (nullable new column / new table) while leaving the old structure fully intact, so old code still runs. Credit "add the new column/table first, nullable," "additive migration," "expand phase." |
| **D2** | **Dual-write — write both old & new representations** | Deploy app code that, on every write, populates **both** the old and the new representation in the **same transaction**, so new writes are correct under either read path. Begins only after D1 is fully rolled out to the whole fleet. | …a phase where the application writes to both old and new schema simultaneously (keeping them in sync going forward). Credit "write to both," "dual-write," "shadow-write the new column." |
| **D3** | **Backfill — migrate existing rows** | Copy/transform all **pre-existing** rows from the old representation to the new one, in **bounded batches**, idempotently, without locking the table or blocking live traffic. Runs concurrently with live dual-writes. Batches are bounded by **key range with a size cap and adaptive throttle**, so uneven key distribution / hot rows / a few enormous rows do not turn one batch into a lock-or-latency spike. | …a backfill / data-migration phase that populates the new representation for historical rows in **throttled, bounded-key-range** batches without long locks. Credit "backfill old data," "batch-copy existing rows," "migrate historical data," "throttle / cap batch size so skewed or hot rows don't spike latency." |
| **D4** | **Read-path switch (cutover)** | Once new data is verified complete & consistent (backfill done AND dual-write soaked), switch reads to the **new** representation — ideally behind a flag/config so the switch is gradual and instantly reversible. Old representation is still written. | …a cutover phase that moves reads from the old to the new representation (flag-gated / gradual). Credit "switch reads to the new column," "cut over the read path," "flip reads to new table." |
| **D5** | **Contract — remove the old representation (and all references to it)** | After the new read path has **soaked** (no rollback expected) and dual-write to old is no longer needed, stop writing the old representation, then drop the old column/table and **every reference to the old structure** — not only the dual-write branch, but ORM models/mappings, views, reporting queries, old DTO fields, and downstream-consumer references (cf. Dep9). The first **destructive** step, deliberately last and separately deployed. | …a contract / cleanup phase that removes the old column/table **and purges every dangling reference** (dual-write code, ORM models, views, reports, DTOs, downstream refs) **after** the new path is proven. Credit "drop the old column," "contract phase," "remove dual-write / old schema," "clean up the ORM model / views / reports that still name the old column." |
| **D6** | **Constraint / index installation (online)** | Add the integrity the new schema ultimately needs — NOT NULL, FK, UNIQUE on the new column, supporting indexes — **online** and **only after** the data is fully backfilled and consistent (a NOT NULL/UNIQUE added before backfill completes fails or blocks). Validate constraints `NOT VALID` then `VALIDATE` style; build indexes `CONCURRENTLY`. | …that the final constraints/indexes on the new structure are added online and *after* backfill completes (you cannot make the new column NOT NULL until every row is populated). Credit "add the NOT NULL/FK/index after backfill, online/concurrently," "tighten constraints last." A decomposition that only "adds the column" (D1) and never tightens it to its target constraints has not covered D6. |
| **D7** | **Per-phase rollback procedure** | For **every** phase a defined, tested, forward-or-backward recovery that returns the system to a known-good state **without losing committed writes**. This is a design component (the rollback *plan* per phase), not merely an edge-case occurrence; its per-phase instances and their asymmetry are criteria (V-E1). | …that each phase has its own rollback/abort plan (not one global "roll back the migration"). Credit "rollback strategy per phase," "each step is reversible," "abort plan at every stage." The cross-cutting *reversibility invariant* is V-I4; the *concrete asymmetric rollbacks* are V-E1; this `D` is the design obligation that a rollback exists at each phase. |

> **Note on `D` vs criteria.** D7 is the *obligation* that a rollback procedure is designed per phase. The
> global **"every phase reversible"** correctness condition is the criterion **V-I4** (listed once under §4,
> not double-counted as a D7 internal check; canon §2.2 non-redundancy). The **concrete per-phase rollback
> boundary states** (what exactly is undone, and the irreversibility of D5) are **V-E1**. D6 (constraint
> tightening) is kept distinct from D1 (additive add): an agent can name "add column" and still miss that the
> column must *later* be tightened to NOT NULL/UNIQUE — different truth-maker, different failure if dropped.

## 2. Dependencies `Dep` — cross-subtask edges as explicit, separately-falsifiable `Dep` edges

> `Dep` = the canon primitive (§2.2): an acyclic relation on `T × T`; `(tₐ, tᵦ) ∈ Dep` iff `criteria(tᵦ)`
> references the output of `tₐ` (with coherence `deadline(tₐ) < deadline(tᵦ)`). **Each `Dep` edge is a
> criterion of a child that references a sibling's output — the glue** — and carries its **own** falsifying
> truth-maker (the anti-mock condition), not "the phases relate" prose.

**The most important and most-forgotten category.** Each seam is a REAL edge: the *output of one named
phase/layer feeds the input of another*, and the edge carries its **own** falsifying criterion — not "the
phases relate" prose (Constitution Ст. II.5 anti-mock). T03's seams are of two kinds: **(a) phase→phase
temporal ordering seams** (phase A must be *fully rolled out / soaked* before phase B, or a window opens where
data is lost or an app instance breaks) and **(b) layer-coupling seams** (the schema-version ↔ app-version
compatibility window across the rolling fleet). A seam is covered iff the decomposition names the **same
ordered pair** and the **same thing that breaks** if the edge is absent/violated.

| # | Name | Pair (source → consumer) | What the edge requires | Truth-maker (covered iff named with its breakage) |
|---|---|---|---|---|
| **Dep1** | **Expand fully deployed before dual-write** | D1 → D2 | The new column/table must exist on the DB **and** every app instance must tolerate it **before** any instance starts dual-writing; a dual-write issued against a schema that hasn't got the new column yet errors. | …that the additive schema change must be live (and the fleet aware of it) before dual-write begins. Ordering edge + the write-error it prevents. |
| **Dep2** | **Dual-write precedes backfill (no lost new writes)** | D2 → D3 | Dual-write must be active **before** backfill runs (or backfill+dual-write overlap correctly), so that rows written/updated *during* the backfill window are captured in the new representation. If backfill runs while writes still go only to the old column, concurrent writes during the backfill are silently lost from the new side. | …that dual-write must be on before/while backfilling, so writes occurring during backfill are not missed. **Hard, easily-forgotten seam** — the concurrent-write-during-backfill data-loss window. Credit "start dual-writing before backfilling," "backfill must account for rows changing during the copy." |
| **Dep3** | **Backfill complete & verified before read-switch** | D3 → D4 | Reads may switch to the new representation **only after** backfill is 100% complete AND a consistency check confirms old≡new for all rows; cutting over with an incomplete backfill serves wrong/empty data for un-backfilled rows. | …that reads switch only after backfill is finished and verified consistent. Ordering edge + the wrong-read it prevents. Credit "verify backfill before cutover," "old and new must match before flipping reads." |
| **Dep4** | **Constraints installed only after backfill** | D3 → D6 | A NOT NULL / UNIQUE / FK on the new column can be enabled **only after** every existing row has been backfilled to satisfy it; enabling it earlier fails the migration or rejects valid writes. | …that final constraints come after the data is fully populated. Distinct ordered pair (backfill→constraint) from Dep3 (backfill→read-switch). Credit "can't add NOT NULL until backfill done." |
| **Dep5** | **Old-write must persist until read-path has soaked** *(the rollback-safety spine — listed prominently)* | D4 ↔ D5 | The application must **keep writing the old representation** (dual-write stays on) **until the new read path has soaked long enough that rollback is no longer expected.** Stopping old-writes (or contracting) the moment reads flip destroys the rollback option: if reads-on-new then fails, you must fall back to reads-on-old, but old data written during the gap is now stale/missing. **This is the load-bearing seam of the whole migration.** | …that old writes must continue past the read-switch — through a soak window — and only stop once rollback is abandoned; flipping reads and immediately stopping old-writes (or contracting) is the classic data-loss trap. **The single hardest/most-forgotten seam.** Credit any statement that "keep writing the old column until you're sure you won't roll back," "don't drop old until new reads are proven," "soak before contract." |
| **Dep6** | **App-version ↔ schema-version compatibility window (rolling fleet)** | {D1,D5 schema state} ↔ deploy-fleet (old & new app instances) | During every rolling deploy, **both** the old and the new app version run **simultaneously** against the **single shared live schema**. Therefore every intermediate schema state must be **readable and writable by both** the pre-deploy and post-deploy code. The shared artifact is the *live schema as seen concurrently by a mixed-version fleet*; a step that is "backward-compatible" but not **forward-compatible** (old code breaks on a change new code made, or new code assumes structure not yet present) breaks half the fleet. | …that during rolling deploys old and new code share one schema, so each schema step must work for **both** versions (backward **and** forward compatible). The shared artifact = the live schema under a mixed-version fleet. **Hard layer-coupling seam.** Credit "old and new app versions must both work against every intermediate schema," "rolling deploy means mixed versions hit the same DB." |
| **Dep7** | **Dual-write atomicity (old & new stay consistent; cross-table for table splits)** | D2 internal write-path | Each dual-write must keep the old and new representations **mutually consistent** — both updated atomically (same transaction) or with a defined reconciliation — so the two never diverge. A non-atomic dual-write (write old, crash, new never written) silently diverges old↔new. **For the defining table-split case** (the running example: one logical write touches the parent row + the new child table), the parent+child write is **one transaction** and the FK keeps them consistent; a partial commit that lands the parent but not the child splits the entity. | …that the two writes in a dual-write must be atomic/consistent (same txn or reconciled), so old and new never drift apart — **including** the table-split case where one entity's write spans the parent table and the new child table and must commit together. Shared artifact = the row's old-vs-new value pair (or parent↔child pair). Credit "dual-write in one transaction," "keep old and new in sync," "split-out parent+child written atomically." **Distinct from Dep2** (Dep2 = ordering vs backfill; Dep7 = per-write atomicity old↔new). |
| **Dep8** | **Contract gated on no-old-readers / no-old-writers remaining** | D5 ← (D4 soak + fleet) | The old column/table may be dropped **only after** it is provably no longer read **and** no longer written by **any** instance — every app instance is on the new read path AND dual-write-to-old has been turned off and that turn-off is fully deployed. Dropping while a lagging instance still reads/writes old crashes that instance (de-facto downtime). | …that contract/drop happens only once nothing reads or writes the old structure anymore (all instances migrated). Ordering/gating edge + the crash it prevents. Distinct from Dep5 (Dep5 = *keep old-write for rollback*; Dep8 = *the drop is safe only when no old reader/writer remains*). |
| **Dep9** | **Downstream consumers compatible across the window** *(HIGH — senior-DBA differentiator)* | {schema state} → every non-app reader of the column (CDC/logical-replication stream, warehouse ETL, search indexer, cache populator, reporting jobs, other services) | The app's read/write paths are **not** the only consumers of the changed shape. Every **downstream** reader of the column — CDC / logical-decoding streams, warehouse ETL, search/index pipelines, cache builders, BI/reporting queries, sibling services reading the table directly — must tolerate **both** the old and the new shape across the whole window, and be sequenced (or schema-mapped) so that the additive change (D1), the cutover (D4), and especially the **contract drop (D5)** do not feed it a column that vanished or changed type. A consumer overlooked here breaks **after** contract, far from the migration, looking like an unrelated outage. The shared artifact = the column shape as seen by each external consumer. | …that consumers *other than the app* read this schema — CDC, ETL, search index, cache, reporting, other services — and each must handle old **and** new shapes across the window (and survive the contract drop). Credit any concrete "the search indexer / warehouse job / CDC stream / other service also reads this column and must be updated/sequenced before we drop it." **The single most substantive seam the parts-list of phases omits.** Distinct from Dep6 (Dep6 = the *app* mixed-version fleet; Dep9 = *non-app external consumers*). |
| **Dep10** | **All write paths dual-write; old-column writers frozen at contract** *(HIGH — senior-DBA differentiator)* | {every writer of the old representation} → D2 dual-write contract / D5 freeze | Dual-write (D2) must cover **every** path that writes the old representation, not just the main app's ORM code: **batch jobs, admin/back-office scripts, bulk imports/data loads, DB triggers, stored procedures, and sibling services** that write the table. A single writer left writing only-old diverges old↔new **silently, with no error**. Symmetrically, when old-writes are finally stopped (after the Dep5 soak), **every** such writer must be frozen / re-pointed — and the old column's write grants revoked — *before* contract, or a forgotten writer keeps resurrecting old data. The shared artifact = the complete set of writers of the old column. | …that the decomposition **enumerates non-app writers** (batch, admin tools, imports, triggers, stored procs, other services) and makes each dual-write, **and** freezes/revokes them before contract — not just "the app dual-writes." Credit "don't forget the nightly batch / admin script / trigger that writes this column," "revoke write access to the old column after stop-old-write." **#4 most-forgotten trap.** Distinct from Dep7 (Dep7 = *atomicity of the known* dual-write; Dep10 = *a writer you forgot exists* — different falsifier: a missing writer, not a torn write). Its silent-no-error detection face is **V-F4**. |

> **Anti-mock note.** Dep6, Dep7 reference a concrete *shared artifact* (the live schema seen by a mixed-version
> fleet; the row's old/new value pair) — a forgotten seam here is an objectively identifiable defect (an app
> instance throws, or old≠new), not a nominal pair. The ordering seams (Dep1–Dep5, Dep8) are falsified by a
> concrete *out-of-order* execution that yields lost/wrong data or a crashing instance. None collapse onto each
> other: different ordered pair OR different falsifier ⇒ distinct seam (canon §2.2 non-redundancy). In
> particular **Dep5** (keep old-write *for rollback safety*, gated on read-soak) and **Dep8** (drop is safe
> only when *no old reader/writer remains*) are different falsifiers on the same D4↔D5 region — Dep5 is the
> data-loss-on-rollback trap, Dep8 is the crash-a-lagging-instance trap — and are kept separate. **Dep9**
> (non-app *downstream* consumers) and **Dep10** (non-app *writers*) extend the coupling beyond the app: Dep6
> is the app's mixed-version fleet, Dep9 is everything else that *reads* the column (CDC/ETL/index/cache/other
> services), Dep10 is everything else that *writes* it (batch/admin/triggers/imports/other services) — three
> disjoint consumer/producer sets, three falsifiers (app instance throws · downstream consumer breaks after
> contract · forgotten writer diverges silently). Dep10 ≠ Dep7: Dep7 is a *torn* write on a known path, Dep10
> is a *whole path you forgot exists*.

> **FM mapping for `Dep`.** A forgotten/violated `Dep` edge is an **FM-1** defect (a spanning integration
> criterion — the glue — not written / not covered; §4.2 FM-1 insufficiency, §18.10 *hole-i*) when it is a
> coverage hole, and an **FM-2** defect (criteria of two children incompatible / a relational defect at fixed
> composition; §4.2 FM-2) for the two-sided / shared-artifact seams whose breakage is a mutual-satisfiability
> conflict (Dep6 mixed-fleet shared schema, Dep7 old↔new atomicity). The temporal-ordering seams additionally
> read onto **FM-5** to the extent they guard against *state changing under a running pass* across live time
> (Dep2 most directly — writes mutating during the backfill window — the live-over-time predicate; see §7).
> The §7 FM table records this. Per one-defect-one-place, a seam's failure is scored **here as a `Dep` item**,
> never re-listed as a separate criterion.

## 3. Authority `Del` — orthogonal note (NOT scored)

> **`Del` is the canon "who" axis** (§2.3: `Del: T → A`, exactly one agent per task) — **orthogonal** to the
> decomposition plane `{D, Dep, V}` and **NOT scored** as a decomposition item. This is a plane-separation
> note, NOT a NEGLECTED exclusion, NOT a criterion, NOT a completeness hole.

Operational *governance* of the migration — who **approves** each phase gate, change-management / CAB
sign-off, the on-call **authorization** to trigger a rollback, segregation between the engineer who writes the
migration and the one who runs it — is **NOT in the decomposition plane.** A migration procedure can be
perfectly correct (no data loss, no downtime, every phase reversible, compatibility matrix held) **and still**
have been authored and executed by the same person without an approval gate. Approval/SoD is a predicate on
the **process/authority assignment**, not on the produced procedure or on any phase node.

**Why authority is orthogonal (derived, not asserted).** A GFSO decomposition is graded on its
artifact-predicates and how the work splits ({D, Dep, V}) — predicates on *what must be true about the
produced artifact* and *how the work splits*. Approval / change-management / SoD is **not** a predicate over
the produced procedure: the migration logic can be entirely correct (no data loss, no downtime, every phase
reversible, the compatibility matrix held) **and still** have been authored and run by the same person with no
approval gate. In GFSO's primitives it is an emergent property of the **edges of the delegation hierarchy**:
the **Issuer** sets the phase-gate criteria and validates `V`; the **Executor** produces (`Del` assigns who,
and `V`-by-Issuer ≠ self-validation). It is emergent from `Del` + the delegation hierarchy, not a node
*within* the decomposition.

**Consequences for scoring (scorer rules):**
- A decomposer is **NOT penalized** for failing to list approval gates / change-management / SoD as a
  decomposition item — there is no `D`/`Dep`/`V`/NEGLECTED slot it belongs in.
- **Force-fitting "approval gate" into a subtask or criterion is a category error.** A *phase gate as a
  technical exit-condition* (backfill verified before cutover) **is** covered — that is **Dep3/V-I6**, the
  data/ordering criterion. The *human approval* of that gate is the orthogonal authority plane and earns no
  `V`/`D` credit and loses none.
- This is **plane-separation**, not a NEGLECTED scope-exclusion and not a completeness hole.

> **Scorer discriminator (technical gate vs authority gate):** "reads switch only after backfill is verified
> consistent" = **Dep3/V-I6** (a data/ordering criterion on the artifact) → score it. "a senior engineer must
> approve the cutover" = **authority plane** → do not score as a category item, do not penalize its absence.

## 4. Criteria `V` — task predicates (former Invariants + Edge-cases + Failure-modes, COLLAPSED)

> `V` is **derived**: `V(t) = AND(criteria(t))` (§2.2, §3.1 Theorem 1). Every item below is a **predicate of
> the task** — a `criterion` whose conjunction is the validation. The former Invariants (parent-level spanning
> predicates), Edge-cases (boundary-state predicates) and Failure-modes (defect-coupling predicates) are
> **all criteria** and are collapsed here into one section. Each criterion keeps its verbatim text +
> truth-maker and carries an **FM tag**: which canon failure mode(s) it precludes (§4.2 / §4.6). The old I/E/F
> labels are retired — the FM tag replaces them. (Item ids keep an I-/E-/F- prefix purely for cross-reference
> traceability to `reference_buckets_v1.md`; they are NOT separate categories.)

**How to read the FM tag.** Per §4.2/§4.6: a **spanning/coverage predicate** a faithful decomposition must
carry (and whose omission is a coverage hole) precludes **FM-1** (Correspondence — joint sufficiency); a
predicate enforcing **mutual satisfiability** of children / cross-layer consistency precludes **FM-2**
(Consistency); a predicate guarding against an **insensitive / mockable / looks-OK-but-wrong** check (a value
that passes where reality fails) precludes **FM-3** (Verifiability, false-PASS); a predicate enforcing
**correct fail-propagation / dependency-ordering** precludes **FM-4** (Propagation). Because T03 runs **over
live time**, two criteria additionally carry an OPERATIONAL tag the task statement forces: a predicate
guarding against **state changing under a running pass during live traffic** reads onto **FM-5** (Currency),
and a predicate demanding a **designed rollback/reopen channel for a defect found mid/post-migration** reads
onto **FM-7** (Feedback) — see §7.

### 4.1 Global correctness criteria (spanning predicates — the cross-layer constraint)

A spanning criterion is a parent-level predicate that **spans phases/layers** — no single phase establishes
it; it holds only if all phases are jointly correct (canon §2.2 joint sufficiency / §3.1). Canonicalized by
the *conserved quantity / enforced predicate*, not by where it is checked (one item per category). These are
the **defining rich content** of T03 (the goal `spec` says "design the procedure **and the invariants**").

| # | Name | Conserved quantity / predicate | FM tag (precludes) | Truth-maker (covered iff the decomposition asserts…) |
|---|---|---|---|---|
| **V-I1** | **No data loss** | No committed write is ever lost across the whole migration — every write that succeeds at time t is reflected in the representation that is authoritative at every later time, including across backfill, cutover, and any rollback. | **FM-1** (spanning conservation/joint-sufficiency predicate) | …that not one committed write may be lost at any phase (the conservation predicate over all writes). The defining safety invariant. |
| **V-I2** | **No downtime / continuous availability** | At no point is the service unable to read or write — no exclusive long lock, no window where the schema is mid-change and unusable, no instance that must stop to migrate. Reads and writes succeed throughout. | **FM-1** (spanning liveness/joint-sufficiency predicate) | …that the service stays fully available the whole time (no lock-induced or deploy-induced outage). The defining liveness invariant. **Locks counting as de-facto downtime is the coupling V-F1; here it is the predicate.** |
| **V-I3** | **Cross-layer compatibility (both app versions × every intermediate schema)** | At **every** intermediate state, **both** the old and the new app version can read **and** write correctly against the **current** schema. This is the conjunction over (app-version ∈ {old,new}) × (operation ∈ {read,write}) × (every intermediate schema state). The matrix must hold *jointly*, not phase-by-phase in isolation. | **FM-2** (mutual satisfiability across the mixed-version fleet — children's read/write criteria must be jointly satisfiable on one shared schema) | …that every intermediate schema is fully usable by **both** app versions for **both** reads and writes — the compatibility *matrix* holds throughout. **The signature invariant of this task.** Distinct from Dep6: Dep6 is the *seam* (the shared live schema under a mixed fleet); V-I3 is the *global predicate* that the whole sequence preserves the compatibility matrix. Credit "every step keeps both versions working." |
| **V-I4** | **Every phase reversible (rollback loses no new-schema data)** | From **any** phase, the system can return to a known-good prior state, AND a rollback never loses data written under the new schema (a rollback that reverts the schema must preserve or re-derive writes that happened post-switch). Reversibility is monotone *until* the deliberate point of no return (contract). | **FM-7** (the designed-reversibility/feedback predicate the task forces: a defect mid/post-migration must route through a controlled rollback channel without losing data) + FM-1 (no-loss-on-rollback coverage) | …that the procedure is reversible at each phase **and** that rolling back does not discard data written in the meantime. **The rollback-safety invariant.** Distinct from D7 (the *obligation to design* a per-phase rollback) and V-E1 (the *concrete asymmetric* rollbacks): V-I4 is the cross-cutting predicate "reversible + no new-data-loss-on-rollback." Credit "you can roll back any step without losing data written after the switch." |
| **V-I5** | **Backfill idempotency & old≡new consistency** | The backfill is **idempotent** (re-running after a crash produces the same result, no double-application) AND at completion the new representation is **provably equal/consistent** with the old for every row. Both legs: safe-to-rerun AND verified-equal. | **FM-3** (verified-equal leg = a check that must be sensitive to real old≠new divergence) + FM-1 (idempotency = non-redundancy / no double-application) | …that backfill can be re-run safely (idempotent) **and** that old and new are checked equal before relying on new. Credit "backfill is idempotent / resumable," AND "verify new matches old." Two legs; an agent asserting only "re-runnable" covers the idempotency leg but not the consistency-verification leg. |
| **V-I6** | **Monotonic phase progression on observable guards (no skipped / re-ordered phase)** | The phases execute in their dependency order and a later phase is entered **only when** the prior phase's exit condition (fully deployed / soaked / verified) holds for the **entire** fleet; no phase is skipped and none overlaps in a way that violates a seam. The migration advances as a state machine with guarded transitions, and **each guard is a measurable, recorded signal** — replication lag, old↔new divergence count, backfill %, error rate — observed and logged *before* the transition, not asserted. The migration advances on an observed number, not on "looks done." | **FM-4** (dependency-ordering / fail-propagation: a later phase must not proceed until the prior phase's guard is met) | …that the phases proceed in strict guarded order (no flipping reads before backfill, no contract before soak), advancing only when the whole fleet has reached the prior phase, **and that each gate is gated on a measured/logged signal** (lag, divergence, backfill %, error rate) rather than a self-report. Spans Dep1–Dep5, Dep8. **Distinct from the individual seams** (each Dep is one edge; V-I6 is the global "the procedure is a guarded ordered state machine advancing on observable signals"). Credit "each transition is gated on a recorded metric (lag/divergence/percent), not on assertion." |

> **Criteria vs D/Dep.** V-I3 and Dep6 are the same physical concern (mixed-version fleet on one schema) seen
> as *predicate* (V-I3) vs *edge* (Dep6) — kept once each, by category (canon §2.2 non-redundancy), not
> double-counted. V-I4 (reversibility predicate) is distinct from D7 (design-a-rollback obligation) and V-E1
> (the concrete asymmetric per-phase undo). V-I1 (no data loss) is the goal `spec`'s first half; V-I2 (no
> downtime) is its second half (Constitution Ст. II.1.b: criteria jointly sufficient for `spec`) — omitting
> either leaves a core requirement uncovered.

### 4.2 Boundary-state criteria (former Edge-cases)

A boundary-state criterion is a boundary input/state that a naive happy-path design silently mishandles —
i.e. a predicate the design must satisfy at the boundary, or the corresponding check is **insensitive** there
(passes a wrong result). Covered iff the decomposition names the same boundary condition and that it needs a
rule.

| # | Name | What it requires | FM tag (precludes) | Truth-maker (covered iff named) |
|---|---|---|---|---|
| **V-E1** | **Per-phase rollback asymmetry (irreversible after contract)** | The *concrete* rollback at each phase differs, and rollback becomes **impossible** once contract (D5) drops the old structure — so the design must define exactly what is undone at expand / dual-write / backfill / read-switch, and mark the post-contract point-of-no-return. Pre-contract rollbacks are cheap; the read-switch rollback must restore reads-to-old *and* reconcile any gap; post-contract there is no rollback, only roll-forward. | **FM-7** (the concrete asymmetric instances of the designed-rollback/feedback channel — what is undone per phase, and the point of no return) | …that the rollback action is **different at each phase** and that after the old structure is dropped you can no longer roll back (only forward-fix). Credit "rollback at expand = drop new col; at cutover = flip reads back; after contract = no going back." The concrete asymmetry, not just "reversible" (which is V-I4). |
| **V-E2** | **Partial-failure mid-backfill (crash / resume)** | The backfill process dies halfway: on restart it must resume without re-doing completed rows incorrectly and without skipping rows — checkpointing / watermark / WHERE-not-yet-migrated, leaning on V-I5 idempotency. | **FM-3** (a happy-path "backfill ran" check is insensitive to a half-done run — must detect the partial state and resume correctly) | …a backfill that crashes partway and must resume safely (checkpoint / resumable / idempotent restart). Credit "backfill must be resumable after a crash," "track progress so a restart doesn't double-process or skip." |
| **V-E3** | **Long-running transaction spanning the schema change** | A transaction (or a long analytical query / report) open *across* a DDL change can see an inconsistent or locked schema, or hold locks that block the DDL. The design must bound DDL lock time (lock-timeout + retry) and account for in-flight long txns. | **FM-3** (a happy-path DDL step is insensitive to an in-flight long txn — blocks or sees an inconsistent schema) | …that long-running transactions/queries open during a DDL step are a hazard (they block the change or see an inconsistent schema), needing a lock-timeout/retry or a low-lock DDL approach. Credit "watch for long transactions during DDL," "set a lock timeout so a long query doesn't block / get blocked." |
| **V-E4** | **Large-table lock avoidance (online DDL)** | On a high-traffic large table, naive DDL (rewrite, ACCESS EXCLUSIVE lock, full-table index build) takes a lock long enough to **be** an outage. The design must use online/concurrent DDL (`ADD COLUMN` nullable = metadata-only, `CREATE INDEX CONCURRENTLY`, `ADD CONSTRAINT ... NOT VALID` then `VALIDATE`, batched backfill) so no step holds a blocking lock. | **FM-3** (a naive "DDL applied" check is insensitive to the lock it held — the change *is* the outage while passing) | …that on a large/busy table the DDL itself must avoid a long exclusive lock (use metadata-only adds, concurrent index builds, NOT VALID→VALIDATE), or the "schema change" is itself the downtime. Credit "add the column without a table rewrite," "build the index concurrently," "avoid the full-table lock." **Distinct from V-E3** (V-E3 = a *long txn* collides with DDL; V-E4 = the *DDL operation itself* takes a blocking lock). |
| **V-E5** | **Concurrent writes during backfill (live mutation of source rows)** | While backfill copies historical rows, live traffic is **mutating** some of those same rows. The backfill must not overwrite a fresher dual-written value with a stale old-value copy (e.g. backfill only-if-null, or order so dual-write wins). Closely tied to Dep2/Dep7 but here as the *boundary state*: a row updated *between* the backfill read and write. | **FM-5** (state changing under the running pass during live traffic — the row mutates *during* the backfill, the canonical over-live-time currency boundary) + FM-3 (a stale-copy clobber passes silently) | …that rows changing *during* the backfill (concurrent writes) must not be clobbered by a stale backfill copy (backfill must not overwrite newer dual-written data). Credit "backfill must not overwrite live updates," "only backfill rows the app hasn't already populated." **The boundary-state face of the Dep2 seam** — covered if either the seam-as-ordering OR this row-level race is named with its fix. |
| **V-E6** | **Replica lag during read-switch** | When reads switch to the new representation but some replicas haven't yet received the backfilled/dual-written data (replication lag), a read served from a lagging replica returns stale/empty new-column data. The design must account for read-replica lag before/at cutover (wait for replicas caught up, or read-your-writes routing). | **FM-3** (a "new data ready" check is insensitive to replica lag — a lagging replica serves stale/empty new data that passes) | …that read replicas may lag behind the primary, so a cutover/read of the new column on a lagging replica can be stale/empty — the design must wait for or route around replica lag. Credit "account for replication lag before flipping reads," "lagging replica returns stale new data." |
| **V-E7** | **In-flight writes at the instant reads flip** | At the exact moment of the read-path switch, writes are in flight under the old read assumptions; the flip must be atomic per-request / flag-evaluated consistently so no request reads-new while its own just-committed write only landed old. Tie-in to read-your-writes consistency at the cutover boundary. | **FM-3** (the cutover instant is a boundary an atomic-looking flip check is insensitive to — a request reads-new while its own write only hit old) | …that the read-switch instant is a boundary where a request might read the new path but its own write only hit the old path (read-after-write at cutover), needing the switch to be consistent/atomic per request. Credit "ensure read-your-writes across the cutover," "the flip must not strand a just-committed write." **Distinct from V-E6** (V-E6 = replica lag; V-E7 = the cutover *instant* read-after-write). |
| **V-E8** | **Un-coercible / dirty legacy data at backfill** | Existing rows may not cleanly transform into the new representation: a column-type tightening (text→int, naive→tz timestamp, a split that assumes a parseable format) hits legacy rows that **don't coerce** (malformed, out-of-range, NULL where the new shape forbids it). The backfill must **surface and quarantine** the un-coercible rows (dead-letter / exception table / report) and continue, rather than abort the whole run or silently write garbage; and new code must tolerate a still-NULL/un-migrated value until its row is resolved. | **FM-3** (a happy-path backfill is insensitive to un-coercible rows — aborts the run or silently writes garbage) | …that some historical rows won't convert to the new shape (dirty/malformed/un-coercible data) and the backfill must isolate those rows (quarantine / flag for manual fix) instead of aborting or writing wrong values. Credit "handle rows that fail the type conversion," "quarantine bad legacy data, don't let it kill the backfill." **Distinct from V-F3** (V-F3 = the verification *check lying* about completeness; V-E8 = the *data itself* refusing to coerce) and from V-E2 (V-E2 = process crash/resume; V-E8 = a data-content boundary). |

### 4.3 Defect-coupling criteria (former Failure-modes — only those with NO `Dep` twin)

Phrased as **concrete coverable claims** (never adjectives). Each names a specific defect coupling AND its
resolution; covered iff the decomposition names the same coupling and a guard. **One-defect-one-place:** a
defect-coupling is kept here ONLY if it has no `Dep`-edge / boundary twin. A coupling that shares the *same
ordered pair, same falsifier, and same fix* as an existing `Dep` edge or boundary criterion is **not** a
separate item — the seam/edge already carries it. The dual-write-divergence defect is carried by **Dep7**; the
lost-write-during-backfill defect by **Dep2/V-E5**; the rollback-loses-new-data defect by **V-I4**; they are
**not** restated here. What remains are couplings with **no twin**: a "backward-compatible" step that is not
*forward*-compatible (V-F2), the in-scope false-PASS residual (V-F3), the lock-is-de-facto-downtime coupling
phrased as a *guard requirement* rather than the V-I2 predicate (V-F1), the **silent** divergence of a
*forgotten* writer (V-F4 — the no-error detection face of seam Dep10, kept because its falsifier is "diverges
with no signal," not the Dep10 enumeration obligation), and the **tooling/runtime-schema** false-completeness
coupling (V-F5).

| # | Name | FM tag (precludes) | What it requires (coupling + guard) | Truth-maker (covered iff named with a guard) |
|---|---|---|---|---|
| **V-F1** | **Lock = de-facto downtime** | **FM-2 / FM-5** (a step's own action breaks the availability criterion of the live-running system) | A migration step that is "correct" in isolation acquires a lock (DDL exclusive lock, long backfill transaction, index build) that **blocks live traffic** → the migration *is* the outage even though no instance crashed. The coupling: correctness-of-the-step vs the no-downtime invariant. Guard: bounded lock time + online/concurrent/batched operations (named as a *mechanism*, not just "be careful"). | …that an internally-correct step can still cause an outage by holding a lock, AND a concrete guard (lock-timeout, batching, concurrent/online DDL) prevents it. **Distinct from V-I2** (V-I2 = the availability *predicate*; V-F1 = the *coupling* "a correct step holds a blocking lock" + the mechanism that breaks it). Distinct from V-E4 (V-E4 = the *boundary* of a large table's DDL; V-F1 = the general coupling lock↔availability across any step incl. long backfill txn). |
| **V-F2** | **"Backward-compatible" step that isn't (forward-incompat / hidden breaking change)** | **FM-3** false-PASS (a change *believed* safe is not) | A step labeled backward-compatible silently breaks the *other* version: e.g. adding a column with a default triggers a table rewrite (lock); a "compatible" enum/type change old code can't parse; renaming via a view old code still writes through; a new NOT NULL the old insert path violates. The coupling: a change asserted safe for the mixed fleet is in fact not. Guard: prove the change is **both** backward- and forward-compatible for every running version (test old binary against new schema and vice-versa). | …that a step *assumed* backward-compatible can actually break one of the running versions (a hidden breaking change), AND that each step must be verified safe for **both** old and new code, not assumed. Credit any concrete "we thought this was safe but old/new code breaks on it" with a verify-both-versions guard. **Mirrors the GFSO faithfulness residual** (a believed-safe edge that the domain refutes) — hardest to articulate. |
| **V-F3** | **Cutover false-PASS (consistency check that passes on incomplete data)** | **FM-3** false-PASS | The pre-cutover consistency check (old≡new) reports OK while the new representation is actually wrong/incomplete — e.g. it samples rows instead of checking all, or runs before dual-write caught the tail of concurrent writes — and reads flip onto bad data. "Backfill reported done" ≠ "new data is correct." Guard: a verification that actually covers all rows / is independent of the backfill's own success flag. | …that the "new data is ready" check can pass while data is still wrong (a false green on the cutover gate), AND a guard stronger than the backfill's self-report (full/independent verification) is needed before flipping reads. **No `Dep` twin** — distinct from Dep3 (Dep3 = the ordering *that* verification gates cutover; V-F3 = the verification itself lying). |
| **V-F4** | **Forgotten-writer divergence is silent (no error)** | **FM-3** false-PASS (a missed writer produces *no* signal) | A write path missed by dual-write (the Dep10 enumeration gap) does not raise an error — it just writes old-only, so old↔new silently diverge with **nothing failing**. The danger is the *silence*: without active detection a missed writer is invisible until a wrong read surfaces much later. Guard (a *mechanism*, beyond Dep10's "enumerate them"): **actively detect** unexpected old-only mutations — a periodic old↔new divergence scan, CDC-monitor on the old column, and **revoking write grants** on the old column after stop-old-write so any forgotten writer *fails loudly* instead of diverging quietly. | …that a forgotten writer corrupts the migration **without any error**, AND a concrete detection mechanism (divergence scan / CDC-monitor / revoke-grant-so-it-errors) is named — not just "make all writers dual-write." **Distinct from Dep10** (Dep10 = the *obligation* to enumerate/freeze all writers; V-F4 = the *silent-no-signal* failure mode + active-detection guard). Distinct from Dep7 (torn write on a known path, which *can* be caught in-txn). |
| **V-F5** | **Tooling / runtime-schema false-completeness (CONCURRENTLY-INVALID, stale pool/ORM, env skew)** | **FM-3** false-completeness | The migration tool or runtime *believes* the schema is in a state it is not: a `CREATE INDEX CONCURRENTLY` that failed leaves an **INVALID** index the tool records as "applied"; cached **prepared statements / connection-pool plans** still reference the old column shape and throw mid-traffic after the `ALTER`; a compiled **ORM model / migration-history** drifts from the live schema; **environments are skewed** (staging ≠ prod) so a step that "passed" elsewhere mis-fires. The coupling: a later step trusts a tool/runtime's bookkeeping that does not match physical reality. Guard: verify **object state independently** of the tool's success flag (is the index actually `VALID`? is the constraint actually `VALIDATED`? does the live schema match the ORM/pool?), **refresh/invalidate cached plans & ORM metadata** after DDL, and make each step **re-assertable at runtime** against actual preconditions (env-agnostic, idempotent precondition checks) rather than assumed-from-a-prior-run. | …that the tool's / runtime's notion of "done" can diverge from the real schema (INVALID index marked done, stale prepared-statement/pool plan, ORM drift, staging↔prod skew), AND a guard that checks actual object state / refreshes caches / re-asserts preconditions at runtime is named. Credit "verify the index is really VALID, not just that the tool said so," "reset the connection pool / prepared statements after the DDL," "assert preconditions at runtime so env drift can't bite." **Distinct from V-F2** (V-F2 = a *schema change* breaks running *code*; V-F5 = the *tool/runtime's own state-tracking* lies about what the schema is). |

> **Note on the operational axis (V-E5, V-I4, V-E1, V-F1).** Unlike a purely static design reference, T03 runs
> **over live time**, so a handful of criteria name OPERATIONAL failure modes at design time — because the
> *task itself* forces the predicate. **V-E5** (concurrent writes during backfill) names **FM-5** (currency):
> the source data is *changing under the running backfill*, the canonical over-live-time currency boundary;
> **V-F1** reads partly onto FM-5 for the same reason (a live lock degrades the running system). **V-I4** and
> **V-E1** name **FM-7** (feedback): the task statement's explicit "rollback path at each phase" forces a
> *designed* reversibility/reopen channel for a defect found mid/post-migration. These do **not** make the
> static reference responsible for the full runtime FM-5/FM-7 behaviour (live spec-drift re-derivation,
> escalation signalling) — those remain protocol-layer (§6); only the design-time predicate the task forces is
> carried (see §7).

## 5. NEGLECTED — declared scope-exclusions (each with its `predictability_verdict`, STD-1/2/3)

> Canon §5.1 STD-1: a decomposition **without** NEGLECTED is incomplete by definition — the auditable "no
> silent skip" record. Each entry carries a **`predictability_verdict`** (STD-2 §5.2: predictability is
> presumed; the *declarer* bears the burden of proving safe-to-skip) and an `invalidation_condition` (when the
> exclusion flips in-scope). Only assumptions whose **omission would otherwise be a foreseeable defect**
> (FM-1.b, §5.2 / §4.2: a predictable external risk left without a mitigating child) — assessed-and-declared-
> skipped, not a dumping ground.

| # | Excluded assumption | `predictability_verdict` (why safely excluded) | Truth-maker (covered iff the decomposition declares…) |
|---|---|---|---|
| **N1** | **Replication lag is bounded / replicas eventually catch up** | The design *consumes* a replication topology whose lag is bounded and recoverable; building/repairing replication is platform scope. Declared boundary: the cutover **waits for** replicas (V-E6 handles the in-window lag), but a permanently-broken replica is an infra failure, not a migration-logic defect. Predictable S-regularity: replica lag exists → mitigated *in-window* by V-E6; unbounded replica failure → named external dependency. Invalidation: replication permanently broken / unbounded lag → migration must pause. | …that replication is assumed to function with bounded lag (the migration waits for it but does not fix replication itself). |
| **N2** | **No competing schema change / no "schema change during an incident"** | The migration assumes it is the **only** schema change in flight and is **not** run concurrently with an active outage/incident on the same tables. Two overlapping migrations or a migration during an incident interact unpredictably. Declared boundary: serializing migrations and not migrating mid-incident is an operational policy, foreseeable to exclude. Invalidation: a second migration touches the same tables, or an incident is open → defer. | …that no other concurrent schema change is in flight and the migration is not run during an active incident (one migration at a time). |
| **N3** | **Application can be deployed in the required ordered, rolling steps** | The procedure assumes the app can ship in the needed sequence (expand-aware code → dual-write code → read-switch flag → contract code) via rolling deploys, and that an old version is never pinned forever. Declared boundary: the CD pipeline / deploy mechanism delivering these ordered rollouts is platform scope, not migration logic. Predictable: rolling deploy is standard → the *logic* assumes it; building the pipeline is upstream. Invalidation: a client/version cannot be upgraded (e.g. mobile app pinned to old API) → the compatibility window must extend indefinitely / different strategy. | …that the application can be rolled out in the required ordered code stages (and old versions are eventually retired), with the deploy pipeline itself out of scope. |
| **N4** | **DB engine supports online/transactional DDL (or the chosen low-lock equivalents)** | The plan assumes the target engine offers the online-DDL primitives it relies on — transactional DDL, `CREATE INDEX CONCURRENTLY`, metadata-only `ADD COLUMN`, `NOT VALID`/`VALIDATE`, or an external tool (gh-ost/pt-osc) where the native engine lacks them. Declared boundary: which engine and which low-lock mechanism is an input; if absent, the lock-avoidance (V-E4/V-F1) strategy changes. Invalidation: engine lacks online DDL and no OSC tool available → a maintenance-window approach is forced (violating no-downtime) → re-scope. | …that the database engine provides the online/low-lock DDL capabilities the plan uses (or an OSC tool stands in), and that this engine capability is an assumed input. |
| **N5** | **The set of downstream consumers is enumerable** *(twin assumption of seam Dep9)* | Dep9 makes each downstream consumer (CDC/ETL/index/cache/reporting/other services) compatible across the window — which **presupposes** the full set of such consumers is **knowable** (a maintained inventory of who reads this table). Declared boundary: discovering an unknown, undocumented consumer of the column is an *organizational/observability* gap, not a migration-logic defect; the logic assumes the consumer list is complete. Invalidation: a hidden consumer (an undocumented service / ad-hoc replica / shadow ETL) reads the column → it breaks at contract and the inventory must be fixed first. | …that the set of downstream consumers of the schema is assumed enumerable/known (the migration sequences the *known* consumers; an undocumented hidden reader is an inventory gap, not a design flaw). |
| **N6** | **A tested backup / PITR exists as the past-contract safety net** | The design's irreversibility ack at contract (V-E1) implicitly leans on a **tested point-in-time-recovery / backup** existing for a catastrophe *after* the point of no return. Declared boundary: *building and testing* DR/PITR is platform scope; the migration *consumes* it as the last-resort recovery past D5. Invalidation: no working PITR/backup → the post-contract irreversibility (V-E1) has no floor and the contract step must be deferred / re-planned. | …that a tested backup/PITR is assumed available for catastrophic recovery past the contract point (designing DR itself is out of scope). Omitting this makes a post-contract data catastrophe look like a migration-design failure rather than a missing DR precondition. |
| **N7** | **Single logical primary; multi-primary / sharded conflict resolution out of scope** | The procedure assumes writes converge on a **single logical primary** so dual-write atomicity (Dep7) and ordering hold. Declared boundary: multi-primary / active-active / sharded topologies introduce cross-node write-conflict resolution that is a different problem; the migration logic assumes one authoritative write target. Invalidation: a multi-primary / sharded cluster → conflict-resolution and per-shard sequencing must be designed separately. | …that there is a single logical primary (multi-primary/sharded conflict resolution is excluded). Distinct from N4 (N4 = engine *DDL capability*; N7 = write *topology*). |

> **N-discipline (STD-1/2/3).** Each N is an assumption whose *failure* would otherwise surface as a defect
> (e.g. omitting N1 makes a stale-replica read look like a migration bug; omitting N3 makes an un-upgradable
> client look like a compatibility-design failure; omitting N4 makes a forced lock look like careless DDL;
> omitting N5 makes a hidden-consumer break at contract look like a migration bug; omitting N6 makes a
> post-contract catastrophe look like a migration-design failure; omitting N7 makes a multi-primary
> write-conflict look like a dual-write defect). Each carries a `predictability_verdict` and an invalidation
> trigger (the input under which the exclusion flips in-scope). This is a *bounded* list of foreseeable
> misattributions, not an open-ended "anything could be assumed" dumping ground: "no triggers on the table"
> stays OUT (trigger writers are handled inside Dep10, not a new exclusion); the **single-primary** and
> **enumerable-downstream** assumptions are *declared* (N7, N5) because their omission is exactly such a
> foreseeable misattribution. N is capped to assumptions whose omission is a *foreseeable misattribution* of an
> external/platform failure to the migration logic.

## 6. Hardest / most-easily-forgotten seams (flag for scorer)

> Not a category — a scorer pointer at the highest-signal `Dep` edges.

- **Dep5 — old-write must persist until the read path has soaked** (the rollback-safety spine). The single most
  load-bearing and most-forgotten edge: a parts-list happily lists "cutover" and "cleanup" but drops the
  *soak window* between them, and the moment old-writes stop while rollback is still possible, a rollback
  loses every write made in the gap. A "magic-word" decomposition almost never names this.
- **Dep2 — dual-write must precede/overlap backfill** (concurrent-write-during-backfill data loss). The window
  where rows written during the backfill are lost from the new side unless dual-write is already on — forgotten
  because the happy-path mental model is "copy the data, then start writing both."
- **Dep6 / V-I3 — app-version ↔ schema-version compatibility across the rolling fleet.** The whole *reason*
  expand/contract exists, yet a parts-list names the phases as components and silently drops the *forward*-
  compatibility half (old code must survive what new code does to the schema). This is the layered task's
  defining edge.
- **Dep8 — contract is safe only when no instance still reads/writes old.** Forgotten because "drop the old
  column" looks atomic; in a rolling fleet a single lagging instance still on the old path crashes on the drop.
- **Dep9 — non-app downstream consumers (CDC/ETL/index/cache/other services) survive the window & the drop.**
  *The senior-DBA differentiator.* A phase parts-list reasons only about the app; the warehouse ETL, the search
  indexer, the CDC stream, the cache builder, and sibling services that read the column are dropped from the
  model and break *after* contract, looking like an unrelated outage.
- **Dep10 — every writer dual-writes, then is frozen/revoked before contract.** *The senior-DBA differentiator.*
  The nightly batch job, the admin back-office script, a DB trigger, a bulk import, or a sibling service that
  still writes only-old diverges silently with no error; the #4 most-forgotten trap.

## Appendix — settled adjudications carried over (scorer must apply; verbatim from `reference_buckets_v1.md`)

- **V-E7 (read-after-write at the cutover instant) vs V-E6 (replica lag) — SEPARATE, keep both.** V-E6 =
  *spatial* staleness (a lagging *replica* returns stale/empty new-col → wait-for-replica / RYW routing); V-E7
  = *temporal* atomicity (at the flag-flip instant a request reads-new while its *own* write only hit old, even
  on a fully caught-up single-node primary → per-request consistent flip). A zero-replica DB still has V-E7 and
  not V-E6 — proof they don't collapse. **Scorer rule:** credit V-E6 for any "lagging replica returns stale new
  data"; credit V-E7 for any "a request must not read-new while its own write only landed old"; naming one does
  **not** earn the other.
- **D7 (per-phase rollback subtask) vs V-I4 (reversibility invariant) vs V-E1 (concrete asymmetry) — three
  legit truth-makers, anti-double-penalty rule.** Distinct falsifiers: D7 = "no per-phase abort plan exists at
  all"; V-I4 = "a rollback discards post-switch writes"; V-E1 = "treats all phase rollbacks alike / thinks
  contract is reversible." **Scorer rule:** one rich paragraph — "each phase has a rollback; reversible at every
  step until contract = point-of-no-return; the read-switch rollback restores old reads and loses no
  post-switch write" — earns **all three (D7 + V-I4 + V-E1)** by meaning. A bare generic "every step is
  reversible" with no per-phase plan and no asymmetry earns **V-I4 only**. Score by which falsifiers the text
  defuses, not by counting the word "rollback."
- **V-F1 (lock=de-facto-downtime) vs V-I2 (no downtime) vs V-E4 (large-table lock) — three legit views, do NOT
  merge.** V-I2 = the *predicate* (any outage from any cause); V-E4 = the *large-table-DDL boundary* (the DDL
  op itself takes a blocking lock → metadata-only add / CONCURRENTLY / NOT VALID→VALIDATE); V-F1 = the *general
  coupling+mechanism* (any internally-correct step's lock = outage, **incl. the long backfill txn and
  lock-queueing behind a long reader**, guarded by lock-timeout + retry + online/batched). **Scorer rule:** a
  decomposition that only says "no downtime" (V-I2) but never explains *how a lock sneaks one in* has **not**
  earned V-E4 or V-F1; the two hard mechanism-level insights are what distinguish a senior decomposition.
- **Authority / control — ORTHOGONAL AUTHORITY PLANE, not scored as a decomposition item.** Approval gates /
  change-management / SoD (the engineer who writes the migration ≠ the one who runs it) is a property of the
  process/authority, not a predicate over the produced procedure; it is emergent from the Issuer ≠
  Executor-on-validation split (`Del` + delegation hierarchy) the GFSO protocol already guarantees
  structurally. **Scorer rule:** do **not** penalize a decomposition for omitting approval/SoD as a
  `D`/`Dep`/`V`/NEGLECTED item, and do **not** award criterion-credit (nor deduct) for an agent who states "a
  senior engineer must approve the cutover" — it is a correct statement in a different plane. A *technical*
  phase gate ("reads switch only after backfill is verified consistent") **is** in-plane (Dep3/V-I6) and **is**
  scored; the *human approval* of that gate is orthogonal. Force-fitting an approval gate into a subtask or
  criterion is a category error. See §3 authority-plane section above. This is plane-separation, **not** a
  NEGLECTED exclusion and **not** a completeness hole.
