## Task `T` (verbatim, PLAN §3 T02)

> Design the end-to-end logic of a supervised-model pipeline from raw labeled data to a served
> prediction endpoint: ingestion & schema validation, feature transforms, train/val/test split, training,
> offline evaluation, model registry/versioning, the serving transform path, online inference, and
> monitoring. Specify how the stages connect so the *served* model is correct and the offline score predicts
> online behavior.

**Shape.** Chained pipeline: raw data → ingestion → features → split → train → eval → registry →
serving-transform → inference → monitoring, with a **feedback edge** (monitoring → retrain). The
load-bearing content is the **seam structure** (`Dep` — each stage's output is the next stage's input, each
edge individually falsifiable), not the stage list. The two headline correctness properties — **no leakage**
and **train/serve parity** — are global invariant criteria no single stage can establish. Achievement goal:
a correct connective design that *terminates* in a served endpoint whose offline score predicts online
behavior — not a maintenance regime (the live serving/monitoring loop is in scope as *design of the
connective logic*, not as an ops rotation; cf. N3).

**Borderline static-vs-operational.** T02 is nominally an **achievement** task (design the pipeline) yet it
has genuine **runtime aspects** — serving, monitoring, retraining, distribution-drift — that the task
statement itself ("the offline score predicts online behavior") forces into the *design*. Unlike a
purely-static decomposition (cf. T04/T08), several **OPERATIONAL** failure modes therefore carry real
**design-time** predicates: FM-5 currency (the design must specify a drift/retrain trigger so a stale model
is caught), FM-7 feedback (the design must specify the prediction-logging → delayed-label → monitoring loop
and a defect→retrain/rollback channel), FM-6 feasibility (the design must handle cold-start / can't-yet-
train). These are NOT N/A-static here (see §7) — they are carried by named criteria/seams.

**Single meta-level.** This decomposes the pipeline **logic** at one level: the stages and the contracts
between them. It does NOT spawn sub-projects (build the feature platform, staff an ML-ops team, procure
GPUs). Components are passes of one design, not org units or infra builds.

## 1. Subtasks `D` — the pipeline stages / passes

> `D` = the children of the decomposition (canon §2.2: `D: T → P(T)`, a DAG).

Each subtask is a **pass**: a separable stage with its own pass/fail criterion on its *output artifact*
(a validated dataset, a fitted transformer, a trained model, a registered version, a served response), not
a self-report ("training done"). The richness of T02 is in the **edges between** these stages (`Dep`), so
`D` is deliberately the saturated, recall-friendly backbone; the discriminating content lives in `Dep` and
the criteria.

| # | Name | What it requires | Truth-maker (covered iff the decomposition names…) |
|---|---|---|---|
| **D1** | **Ingestion & schema validation** | Raw labeled data is read and validated against an explicit schema (types, ranges, nullability, allowed categories, label presence) before anything downstream consumes it; non-conforming rows are rejected/quarantined **with counts surfaced**, never silently coerced **and never silently dropped** (a silent drop biases the surviving training set). | …an ingest pass that validates incoming raw data against a declared schema/contract and rejects or quarantines violations **with the dropped/quarantined volume counted/surfaced, not silently lost**. Credit "data validation," "schema check on input," "great-expectations-style gate," however worded; the silent-drop guard is covered by any "quarantine with counts / log how many rows were rejected / don't silently discard rows." |
| **D2** | **Feature transforms (transformation logic)** | The logic that turns validated raw fields into model features (encoding, scaling, imputation, aggregation, embedding) is defined **once as a reusable transform**, parameterized by statistics fitted on data. | …a feature-engineering/transform pass producing model features from raw fields. Credit "feature engineering," "preprocessing," "build features," "transform pipeline." (The *single-definition / reuse* property is the Dep1 seam truth-maker, not restated here.) |
| **D3** | **Train / val / test split** | The dataset is partitioned into training, validation, and test (or CV folds) by a defined, reproducible rule appropriate to the data (random, grouped, or temporal). | …a split pass that partitions data into train/validation/test (or CV). Credit "split the data," "hold out a test set," "cross-validation folds." (The *leakage-free* and *fit-on-train-only* properties are Dep2/Dep3 seams, scored there.) |
| **D4** | **Model training** | A model is fit on the training partition to a defined objective, with hyperparameter selection driven by the validation partition (not the test set). | …a training pass that fits a model on the train split with validation-driven tuning. Credit "train the model," "fit," "hyperparameter search on val." |
| **D5** | **Offline evaluation** | The trained model is scored on the held-out test partition against defined metrics (and slices/segments), under the **same** transform path it will be served with, producing the offline performance estimate. | …an offline-evaluation pass that measures the model on held-out data against named metrics. Credit "evaluate on test set," "offline metrics," "compute AUC/accuracy/RMSE on holdout." (The *eval-uses-serving-transform* property is Dep9; *eval↔monitoring metric alignment* is Dep11.) |
| **D6** | **Model registry / versioning** | The model artifact **plus its fitted transform/preprocessor plus its training/eval metadata** is registered as an immutable, addressable version (lineage: which data, code, hyperparameters, metrics produced it). | …a registry/versioning pass that stores the model as a named, immutable version with its lineage. Credit "model registry," "version the model," "store artifact + metadata," "MLflow/model store." (Co-versioning of the *preprocessor with the model* is the Dep5 seam.) |
| **D7** | **Serving transform path** | The production transform that converts an incoming raw request into model-input features at inference time — the **same transformation** as D2, applied online. | …a serving-side feature/transform pass that prepares raw requests into features at inference time. Credit "serving preprocessing," "online feature computation," "request→features." (Identity with the training transform is the Dep1 skew seam — the headline content — scored there.) |
| **D8** | **Online inference / serving endpoint** | The registered model is loaded and exposed as a prediction endpoint that, given a transformed request, returns a prediction (with the binding of *which* model version is serving made explicit). | …an inference/serving pass that loads a model version and returns predictions over an endpoint. Credit "serve predictions," "inference endpoint," "load model and predict." (Version→endpoint binding is the Dep6 seam.) |
| **D9** | **Monitoring** | The live system continuously observes input distributions, prediction distributions, and (when labels arrive) realized performance, against the offline baseline, raising signals on drift/degradation. | …a monitoring pass observing production inputs/predictions/performance over time. Credit "monitor in production," "drift detection," "track live metrics," "alert on degradation." (Metric-definition match to eval is Dep11; drift→retrain trigger is Dep14.) |
| **D10** | **Online pre-promotion validation (shadow / canary / champion-challenger)** | Before a candidate that passed the offline gate (Dep9/Dep14) takes full production traffic, it is exposed to **mirrored or partial live traffic** (shadow scoring, canary slice, or champion-vs-challenger) and compared to the incumbent on the **live** metric — so the residual "offline passed but online behaves differently" case is caught **before** full cutover, not after. The pass artifact is the online comparison verdict (candidate ≥ champion on the live metric over the canary window), gating the full promotion. | …an online validation pass between offline-gate and full promotion: a candidate gets shadow/mirrored or canary/partial live traffic and is compared to the current production model on the live metric before full cutover. Credit "shadow deployment," "canary release," "champion/challenger," "A/B the new model before full rollout," "compare candidate to incumbent on live traffic first." (Carried as a subtask, not excluded, because the task explicitly stresses *offline score predicts online behavior* — this pass is the standard mechanism that de-risks the residual offline↔online gap that Dep9 alone cannot guarantee. Distinct from D9 monitoring of the *live* model: D10 validates a *candidate* against the *incumbent* pre-promotion; D9 watches the *promoted* model over time.) |

> **Note on `D` granularity.** Ingestion (D1) and feature transforms (D2) are kept distinct because their
> truth-makers differ (conform-to-schema vs produce-features) and an agent can cover one without the other.
> D2 (offline transform) and D7 (online transform) are listed as **two** subtasks on purpose: the whole
> train/serve-skew problem is precisely that these are two implementations of one logic — collapsing them
> into one item would erase the headline seam (Dep1). An agent who names a single "preprocessing" stage and
> *explicitly* asserts it is shared by train and serve covers D2, D7 **and** Dep1 in one stroke (credit all
> three); an agent who names "preprocessing" only on the training side has D2 but not D7/Dep1.

## 2. Dependencies `Dep` — cross-component dependencies as explicit, separately-falsifiable `Dep` edges

> `Dep` = the canon primitive (§2.2): an acyclic relation on `T × T`; `(tₐ, tᵦ) ∈ Dep` iff `criteria(tᵦ)`
> references the output of `tₐ` (with coherence `deadline(tₐ) < deadline(tᵦ)`). **Each `Dep` edge is a
> criterion of a child that references a sibling's output — the glue** — and carries its **own** falsifying
> truth-maker (the anti-mock condition), not "these stages relate" prose.

**The dominant and most-forgotten category for T02.** Each seam is a REAL edge: the *output of one named
stage feeds the input of another*, and the edge carries its **own** falsifying criterion — not "these
stages relate" prose (Constitution Ст. II.5 anti-mock). A seam is covered iff the decomposition names the
**same ordered pair** and the **same thing that breaks** if the edge is absent/violated. T02's seams are
of two kinds: **(a) data/contract seams** (the artifact one stage emits must satisfy a contract the
consumer relies on) and **(b) parity/identity seams** (two stages must use the *same* logic or the *same*
fitted statistics, or results diverge). The parity seams are the hardest and most-forgotten.

| # | Name | Pair (source → consumer) | What the edge requires | Truth-maker (covered iff named with its breakage) |
|---|---|---|---|---|
| **Dep1** | **Train/serve transform skew** *(headline seam — listed first)* | D2 ↔ D7 | The offline (training) feature transform and the online (serving) feature transform must be **the same logic applied the same way** — same code path or a shared/exported transformer, AND using the **training-fitted** statistics (means, vocabularies, bins), not re-fitted online. If the two diverge, the model sees a different feature distribution in production than it was trained on and silently mispredicts despite a good offline score. | …that the *training* and *serving* feature transforms must be identical (shared code / exported transformer) and use the *same fitted parameters*; a divergence = the model gets different features in prod → silent degradation. **The single most-forgotten ML seam — credit any "train/serve skew," "reuse the same preprocessing in production," "feature parity," "don't re-implement features for serving."** |
| **Dep2** | **No-leakage across the split** | D3 ↔ {D2, D4, D5} | Information from validation/test must not reach training: the split must precede any data-dependent fitting/selection, and no feature, target-derived value, or duplicate row may cross from test into train. Violation inflates the offline score above true generalization. | …that train/val/test must be isolated so test information never informs training (no peeking); a leak inflates offline metrics. Credit "avoid data leakage," "no information from test in train," "split before fitting." **Distinct from Dep3** (Dep2 = isolation between partitions; Dep3 = transforms fitted only on the train slice). |
| **Dep3** | **Transforms fitted on train only** | D3 → D2 (and D2→D5) | Any data-dependent transform statistic (scaler mean/std, imputation value, encoder vocabulary, target encoding, feature selection) must be **fit on the training partition only** and then *applied* to val/test/serving — never fit on the full dataset. Fitting on all data leaks val/test statistics into features. | …that transform statistics are computed on the *training* fold and merely applied to val/test/serving — not fit on the whole dataset. Credit "fit preprocessing on train, transform val/test," "no scaler/encoder fit on full data." **Distinct from Dep2** (target/row isolation) and from Dep1 (train↔serve identity): Dep3 is *fit-scope discipline within training*. |
| **Dep4** | **Label join / alignment correctness** | D1 → {D3, D4, D5} | Each example is joined to the **correct** label, and (for time-series / event data) the label reflects the outcome as of the right time — no label belonging to a different entity/time is attached. A mis-join silently trains on wrong targets. | …that features and labels are correctly aligned per example (right entity, right time), not mis-joined. Credit "join labels correctly," "align target to example," "label-feature key integrity." |
| **Dep5** | **Model ↔ preprocessor co-versioning** | D2 → D6 ← D8 | The registered version must bundle the model artifact **with the exact fitted transformer** that produced its training features, so that serving loads a *matched* (model, preprocessor) pair. A model loaded with a mismatched/newer preprocessor produces wrong features. | …that the fitted preprocessor/transformer is versioned and shipped *together with* the model (matched pair), so serving never pairs a model with the wrong transform. Credit "version preprocessing with the model," "bundle transformer in the artifact," "model+transform are one deployable." **Distinct from Dep1** (Dep1 = same logic train vs serve; Dep5 = the *fitted artifact* travels with the model through the registry). |
| **Dep6** | **Registry version ↔ serving binding** | D6 → D8 | The serving endpoint must load a **specific, addressable** model version from the registry, and which version is live must be explicit and controllable (promotion/rollback). An ambiguous or stale binding serves an unintended model. | …that serving loads an explicit registered version and the live-version binding is controlled (promote/rollback). Credit "serving pins a model version," "deploy a specific registry version," "rollback to prior version." |
| **Dep7** | **Ingestion schema ↔ inference schema (request contract)** | D1 ↔ D8 | The schema the model was trained against and the schema of incoming **inference requests** must agree (same fields, types, encodings, allowed categories). A request field that drifts/renames/changes units relative to training is silently mis-featurized. | …that production request inputs are validated against the *same* schema/contract the training data used; a drift between training schema and request schema is a defect. Credit "validate inference inputs," "request schema matches training schema," "reject/handle out-of-contract requests at serve time." **Distinct from D1** (D1 validates *training* data; Dep7 is the *training-schema = serving-schema* agreement). |
| **Dep8** | **Offline/online feature-source parity (feature store consistency)** | D2/D7 shared feature source | When features are read from a precomputed store/cache (not computed inline), the **offline** values used in training and the **online** values served at inference for the same entity must be equal as-of the prediction time — same source, same freshness semantics. A store whose offline and online halves disagree reintroduces skew even when the transform code is identical. | …that any feature store/cache used offline and online must return consistent values for the same entity (one source of truth for feature values), not two stores that drift. Credit "offline/online feature store consistency," "same feature values in training and serving," "single feature source." **Distinct from Dep1** (Dep1 = identical transform *code*; Dep8 = identical *materialized feature values* from a shared store). Score only if a precomputed feature source is in the design; otherwise N/A (not a hole). |
| **Dep9** | **Eval uses the serving transform path** | D7 → D5 | Offline evaluation must run the model through the **same** transform path used in serving (Dep1), not a notebook-only transform, or the reported offline score does not estimate online behavior. This is the seam that makes "offline score predicts online" *mean* something. | …that the offline evaluation is computed over the production/serving transform path, so the offline number reflects what serving will do. Credit "evaluate using the serving preprocessing," "eval mirrors inference path." **Distinct from D5** (D5 = scoring on holdout; Dep9 = scoring *through the serving transform*). Directly discharges the task clause "offline score predicts online behavior." |
| **Dep10** | **Point-in-time / temporal correctness (no future leakage)** | D1 → D2/D3 | For any time-ordered data, features for an example must be computed using **only** information available at or before that example's timestamp; the split must respect time order; no future aggregate (e.g. a forward-looking average) enters a past example. Train-on-future is leakage that disappears in production. | …that features and the split respect time-ordering — no future information in past examples, temporal split for temporal data. Credit "point-in-time correctness," "no look-ahead," "time-based split," "as-of feature computation." **Distinct from Dep2/Dep3**: Dep10 is the *temporal* axis of leakage specifically (a random split can pass Dep2 and still leak across time). Score only for time-ordered data; for IID data this folds into Dep2 (don't double-penalize). |
| **Dep11** | **Eval metric ↔ monitoring metric alignment** | D5 ↔ D9 | The metric and slicing computed in offline evaluation and the metric tracked in production monitoring must be the **same definition** (same target, same population, same computation), so an online drop is comparable to the offline baseline. Two different metric definitions make "monitoring vs eval" meaningless. | …that monitoring tracks the *same* metric/definition as offline eval, against the offline baseline, so online and offline numbers are comparable. Credit "monitor the same metric we evaluated on," "compare production performance to the offline baseline." **Distinct from D9** (D9 = monitoring exists; Dep11 = its metric *matches* eval's). |
| **Dep12** | **Prediction logging → delayed-label join (online ground truth)** | D8 → D9 | To measure live performance, production predictions must be **logged with the keys/timestamp** needed to later join the **delayed true labels** when they arrive, reconstructing online ground truth. Without this join, monitoring can only watch input/score drift, never realized accuracy. | …that predictions are logged so that arriving ground-truth labels can be joined back to compute live performance (delayed-label feedback). Credit "log predictions and join labels later," "ground-truth feedback loop," "wait for labels to measure live accuracy." **Distinct from Dep11** (Dep11 = metric *definition* match; Dep12 = the *mechanism* that obtains online labels at all). |
| **Dep13** | **Training data ↔ eval data provenance (same generation, disjoint rows)** | D1 → {D4, D5} | The train and eval partitions must come from the **same data-generating process/version** (same ingestion contract, same population) yet be **row-disjoint** — eval must be representative of what training saw, not a differently-sourced or overlapping set. Mismatched provenance makes the offline score un-interpretable. | …that the evaluation set is drawn from the same population/snapshot as training but is disjoint from it (representative + non-overlapping). Credit "test set from the same distribution, held out," "no row overlap, same source." **Distinct from Dep2** (Dep2 = no information leakage; Dep13 = same-provenance + disjointness so the score is a *valid estimate*). |
| **Dep14** | **Monitoring → retrain/promote trigger** | D9 → D4/D6 | A defined condition on monitoring signals (drift / performance drop past a threshold) must feed back to a **retrain-or-roll-back** decision, closing the loop — and a freshly trained candidate must pass the *same* eval gate (D5/Dep9) before promotion (Dep6). Without this edge, monitoring is a dashboard that observes decay but never corrects it. | …that monitoring signals feed a retrain/rollback decision, and a retrained model re-enters through the same eval+registry gate before promotion. Credit "trigger retraining on drift," "monitoring closes the loop to retrain/rollback," "promote only after re-eval." (The feedback edge of the chain.) |

> **Anti-mock note.** Every `Dep` references a concrete shared artifact or identity: Dep1/Dep8 the *transform
> logic / feature values*, Dep5 the *(model, preprocessor) pair*, Dep6 the *registered version*, Dep7 the
> *request schema*, Dep4/Dep12 the *label join key*, Dep11 the *metric definition*. A forgotten seam here is
> an objectively identifiable production defect (skew, leaked score, mismatched model), not a nominal pair.
> None collapse: different ordered pair OR different falsifier ⇒ distinct seam (PLAN §1.3 rule 1). In
> particular the four leakage-adjacent seams are deliberately separated by falsifier — Dep2 (partition
> isolation), Dep3 (fit-on-train-only), Dep10 (temporal/look-ahead), Dep13 (same-provenance disjointness) —
> each breaks a *different* way; an agent covering one has not automatically covered the others.

> **FM mapping for `Dep`.** A forgotten/violated `Dep` edge is an **FM-1** defect (a spanning integration
> criterion — the glue — not written / not covered; §4.2 FM-1 insufficiency, §18.10 *hole-i*) when it is a
> coverage hole, and an **FM-2** defect (criteria of two children incompatible / a relational defect at
> fixed composition; §4.2 FM-2) for the two-sided / parity / shared-artifact seams whose breakage is a
> mutual-satisfiability conflict (Dep1, Dep5, Dep7, Dep8, Dep11). The two feedback-loop seams additionally
> touch the **operational** axis: Dep12 (prediction-logging → delayed-label) is the **FM-7** online-feedback
> mechanism and Dep14 (monitoring → retrain/rollback) is the **FM-5**/**FM-7** loop-closing channel that
> refreshes a stale model — design-time predicates the task forces, see §7. The §7 FM table records this.
> Per one-defect-one-place, a seam's failure is scored **here as a `Dep` item**, never re-listed as a
> separate criterion.

## 3. Authority `Del` — orthogonal note (NOT scored)

> **`Del` is the canon "who" axis** (§2.3: `Del: T → A`, exactly one agent per task) — **orthogonal** to the
> decomposition plane `{D, Dep, V}` and **NOT scored** as a decomposition item. This is a plane-separation
> note, NOT a NEGLECTED exclusion, NOT a criterion, NOT a completeness hole.

A real ML pipeline carries control/governance requirements — model-promotion **approval** (a human signs
off before a model goes to production), **separation of duties** (the person who trains is not the sole
person who promotes), **audit of who deployed which version**. These are **authority/control predicates on
the process**, not predicates on the produced artifact, and they live in the **ORTHOGONAL AUTHORITY
PLANE**, not in the decomposition plane.

**Why authority is orthogonal (derived, not asserted).** A GFSO decomposition is graded on its
artifact-predicates and how the work splits ({D, Dep, V}) — predicates on *what must be true about the
produced pipeline* and *how the work splits*. "An approver must sign off before promotion" is **not** a
predicate over the served model: a model can be leakage-free, train/serve-parity-correct, reproducible, and
version-pinned **and still** have been trained and promoted by the same person without review.
Promotion-approval is therefore a property of the **process / authority assignment** (Constitution Ст.
II.14: Issuer sets/validates criteria, Executor produces; self-validation — one context that both trains
and signs off — violates the **Issuer ≠ Executor-on-validation** separation the protocol already guarantees
structurally, emergent from `Del`). It is **not** a node *within* the decomposition.

**Consequences for scoring (scorer rules):**
- A decomposer is **NOT penalized** for failing to list promotion-approval / segregation-of-duties as a
  decomposition item. There is no `D`/`Dep`/`V`/NEGLECTED slot it belongs in.
- **Force-fitting "approval gate" into a criterion is a category error.** A criterion is a predicate on the
  produced artifact (no leakage, train/serve parity); an approval gate is a predicate on the
  *process/authority that produced it*. An agent who writes "require human sign-off before deploy" earns no
  criterion-credit and loses none — it is a correct statement in a different plane.
- This is **plane-separation**, not a NEGLECTED exclusion (it is *carried structurally by the
  Issuer/Executor split*) and not a completeness hole (nothing is missing from the decomposition).

> **Note — the *eval gate* IS in-plane; the *approval* is not.** The requirement that a model must pass the
> offline eval threshold before promotion (Dep14/Dep9/Dep6) is an *artifact predicate* (a property of the
> model) and lives in the decomposition plane. The requirement that a *person* approves the promotion is an
> *authority predicate* and lives in the orthogonal plane. An agent naming "promote only if eval passes"
> covers Dep14 (in-plane); an agent naming "a reviewer must approve" earns the plane-separated treatment (no
> penalty, no criterion-credit).

## 4. Criteria `V` — task predicates (former Invariants + Edge-cases + Failure-modes, COLLAPSED)

> `V` is **derived**: `V(t) = AND(criteria(t))` (§2.2, §3.1 Theorem 1). Every item below is a **predicate of
> the task** — a `criterion` whose conjunction is the validation. The former Invariants (pipeline-level
> spanning predicates), Edge-cases (boundary-state predicates) and Failure-modes (defect-coupling
> predicates) are **all criteria** and are collapsed here into one section. Each criterion keeps its
> verbatim text + truth-maker and carries an **FM tag**: which canon failure mode(s) it precludes (§4.2 /
> §4.3 / §4.6). The old I/E/F labels are retired — the FM tag replaces them. (Item ids keep an I-/E-/F-
> prefix purely for cross-reference traceability to `reference_buckets_v1.md`; they are NOT separate
> categories.)

**How to read the FM tag.** Per §4.2/§4.3/§4.6: a **spanning/coverage predicate** a faithful decomposition
must carry (and whose omission is a coverage hole) precludes **FM-1** (Correspondence — joint sufficiency); a
predicate enforcing **mutual satisfiability** of children / train↔serve parity precludes **FM-2**
(Consistency); a predicate guarding against an **insensitive / mockable / good-aggregate-but-wrong** check
(a value that passes where reality fails) precludes **FM-3** (Verifiability, false-PASS); a predicate
enforcing **correct fail-propagation / dependency-gating / atomicity** precludes **FM-4** (Propagation).
Because T02 has runtime aspects the task forces into the design, the **operational** axis is also reachable
at design time: a predicate guarding **distribution/data drift → stale model** precludes **FM-5**
(Currency); a predicate guarding a **not-yet-trainable / cold-start** state precludes **FM-6** (Feasibility);
a predicate guarding the **post-deployment detect→report→retrain channel** precludes **FM-7** (Feedback).

### 4.1 Pipeline-wide spanning criteria (former Invariants)

A spanning criterion is a pipeline-level predicate that **spans stages** — no single stage can establish it;
it holds only if the stages are jointly correct (canon §2.2 joint sufficiency / §3.1). Canonicalized by the
*enforced predicate*, not by where it is checked (PLAN §1.3 rule 2).

| # | Name | Enforced predicate | FM tag (precludes) | Truth-maker (covered iff the decomposition asserts…) |
|---|---|---|---|---|
| **V-I1** | **No leakage (the offline score is an honest estimate)** | No information from the evaluation/future/target reaches the model or the feature statistics during training; the offline metric therefore equals (in expectation) true generalization. Spans Dep2, Dep3, Dep10, Dep13. | **FM-1** (spanning no-leakage coverage predicate) | …that the whole pipeline is leakage-free so the offline score is an honest generalization estimate (not just one local "split before fit"). The *global* honesty-of-the-score predicate. Credit "no leakage end-to-end," "offline metric is unbiased." |
| **V-I2** | **Train/serve parity (the served model = the evaluated model)** | The exact (model, transform, feature-source) that was evaluated offline is what runs in production: same transform logic (Dep1), same fitted artifact (Dep5), same feature values (Dep8), same model version (Dep6). Spans Dep1, Dep5, Dep6, Dep8, Dep9. | **FM-2** (mutual satisfiability: served and evaluated artifacts must match across the offline↔online boundary) | …that what is served is identical to what was evaluated — model, preprocessing, and features all match between offline and online. The *global* parity predicate that makes "offline predicts online" hold (the task's central requirement). Credit "what you evaluate is what you serve," "no train/serve gap end-to-end." |
| **V-I3** | **Reproducible / deterministic pipeline** | Re-running the pipeline from the same data + code + config + seeds yields the same split, the same model (or a controlled-variance one), the same metrics — and every produced model has full lineage (data version, code version, hyperparameters). Spans D3, D4, D6. | **FM-1** (the reproducibility/lineage half of `spec` — a spanning predicate no single pass owns) | …that the pipeline is reproducible: fixed seeds/config → same split and model, with recorded lineage. Credit "set the random seed," "deterministic split," "track data+code+params for each run," "reproducible training." |
| **V-I4** | **Schema/contract consistency end-to-end** | One data contract (fields, types, units, encodings, allowed categories) is enforced *consistently* at ingestion, in features, and at the inference request boundary — the same schema governs training and serving. Spans D1, Dep7. | **FM-2** (one consistent contract across data-touching stages = mutual consistency) | …that a single consistent schema/contract governs the data from ingestion through serving requests (training schema = serving schema). Credit "one schema enforced everywhere," "input contract consistent train and serve." **Distinct from Dep7** (Dep7 = the *specific* ingestion↔inference edge; V-I4 = the global single-contract predicate spanning all data-touching stages). |
| **V-I5** | **Version pinning / artifact immutability** | Every produced artifact (dataset snapshot, model, preprocessor, metric report) is immutable and addressable by version; serving and eval always refer to a pinned version, never "latest" that can shift underneath them. Spans D6, Dep5, Dep6. | **FM-1** (a spanning coverage predicate: every produced artifact addressable/immutable) | …that artifacts are immutable and version-pinned (no mutable "latest" silently changing what's served/evaluated). Credit "pin the model version," "immutable artifacts," "addressable dataset/model versions." **Distinct from V-I3** (V-I3 = re-running yields the same thing; V-I5 = a produced thing never changes after the fact). |
| **V-I6** | **Calibration / decision-threshold parity** | Any post-model decision logic (probability calibration, classification threshold, business rules) used to turn scores into actions is **fixed at eval time and carried unchanged to serving** — the threshold/calibration evaluated offline is the one applied online. Spans D5, D7/D8. | **FM-2** (post-score decision parity across offline↔online — mutual consistency) | …that the decision threshold / calibration is set during evaluation and applied identically in serving (not re-chosen or defaulted to 0.5 in prod). Credit "carry the calibrated threshold to serving," "same decision cutoff offline and online," "calibrate then freeze." **Distinct from V-I2**: V-I2 is feature/model parity; V-I6 is *post-score decision* parity — an agent can get features identical yet apply a different threshold in prod. |
| **V-I7** | **Fail-closed staging (no advance on a failed/empty upstream)** | Every stage runs **only** on its upstream's PASS artifact: a failed data-quality gate, an empty/degenerate output, or a failed eval/parity gate **blocks** the downstream stage rather than letting it proceed on bad or absent input (training does not start on un-gated/empty data; eval does not run on an unfit model; promotion does not occur on a failed gate). The pipeline's default on any gate failure is *stop*, not *pass through*. Spans D1→D4, D4→D5, D5/Dep9→D6, Dep14. | **FM-4** (propagation: any recorded fail must block dependents — the global gate-on-every-upstream predicate) | …that the pipeline gates each stage on its predecessor's success and **fails closed** — a failed/empty upstream stops the downstream stage instead of advancing on bad data. Credit "don't train on data that failed validation," "stop the pipeline if a stage fails," "gate every stage on the previous one's pass," "fail closed / no silent pass-through." **Distinct from Dep14** (Dep14 = the *eval→promote* gate specifically; V-I7 = the *global* gate-on-every-upstream predicate) and from **D1** (D1 = ingest *rejects* bad rows; V-I7 = a *failed gate halts the next stage* across the whole chain). |
| **V-I8** | **Crash / resume atomicity (no half-written artifact, no half-promoted model)** | A run that fails partway must leave **no half-written dataset, no half-trained-but-registered model, no half-promoted version**: each produced artifact appears **atomically or not at all**, and a re-run resumes from a consistent checkpoint without corrupting reproducibility or lineage. The *logical* guarantee — partial work is never observable as a completed artifact — is a design predicate, not just an orchestration detail. Spans D4, D6, D8. | **FM-4** (propagation/atomicity: a failed run must not emit a visible partial artifact downstream) | …that a partial/interrupted run must not leave a corrupt or half-promoted artifact — artifacts commit atomically (all-or-nothing) and runs are resumable/idempotent on retry. Credit "no half-written model/dataset," "atomic publish of the artifact," "resume from checkpoint without corruption," "a crashed run doesn't promote a partial model." **Distinct from V-I5** (V-I5 = a *committed* artifact never mutates afterward; V-I8 = a *failed* run never produces a visible partial artifact in the first place). The *engine* that retries (Airflow/Kubeflow) is N3; the *predicate* that the artifact is atomic is in-plane here. |
| **V-I9** | **Atomic model+transform hot-swap under concurrency** | A version change in serving is **atomic with respect to the (model, transform) pair**: under live traffic, no in-flight request may see a half-swapped state — e.g. the new model weights with the old transform, or vice versa — and a retrain finishing mid-traffic swaps the whole matched pair cleanly. The swap is a single observable transition, not a window in which serving mixes versions. Spans D6→D8, D7, Dep5, Dep6. | **FM-4** (propagation/atomicity of the runtime version transition under concurrency) | …that switching the live model version is atomic and swaps the *model and its transform together*, so no request ever mixes a new model with an old transform (or vice versa) during a concurrent swap. Credit "atomic model swap," "no half-swapped serving state," "hot-swap the model+preprocessor as one unit," "no request sees a mismatched (model, transform) during deploy/retrain." **Distinct from Dep6** (Dep6 = serving *binds a specific version*; V-I9 = *the transition between versions is atomic under concurrency*) and from **Dep5** (Dep5 = the matched pair is *co-versioned in the registry*; V-I9 = the *runtime swap* of that pair is atomic). A half-swap silently mis-predicts — exactly the parity class the task centers on. |

> **Criteria vs the seams.** V-I1/V-I2 are the *global* predicates the leakage-seams (Dep2/Dep3/Dep10/Dep13)
> and parity-seams (Dep1/Dep5/Dep6/Dep8/Dep9) jointly establish; they are listed once in **§4 Criteria**, not
> double-counted as the seams that compose them (PLAN §1.3 rule 2). An agent who names the four leakage seams
> *and* states the global "the score is honest end-to-end" earns both the `Dep`-credits and V-I1; an agent who
> states only the global invariant without any mechanism earns V-I1 but none of Dep2/Dep3/Dep10/Dep13.

### 4.2 Boundary-state criteria (former Edge-cases)

A boundary-state criterion is a boundary input/state a naive happy-path pipeline silently mishandles — i.e. a
predicate the design must satisfy at the boundary, or the corresponding check is **insensitive** there
(passes a wrong result). Covered iff the decomposition names the same boundary condition and that it needs a
rule.

| # | Name | What it requires | FM tag (precludes) | Truth-maker (covered iff named) |
|---|---|---|---|---|
| **V-E1** | **Unseen category / out-of-vocabulary at serving** | A categorical value (or token) appears at inference that was absent from the training vocabulary; the transform must have a defined rule (reserved unknown bucket / fallback), not crash or one-hot to all-zeros silently. | **FM-3** (insensitive transform silently mis-features the OOV value, passes wrong) | …the unseen-category / OOV boundary at serving and a defined handling (unknown bucket / fallback), not a crash. Credit "handle new categories at inference," "OOV token." |
| **V-E2** | **Missing / null / malformed feature at inference** | A required field is missing, null, or out-of-range in a live request; serving must apply the *same* imputation/rejection rule as training, not a different default. | **FM-3** (a serve-time check insensitive to missing/malformed input applies a different default → false result) | …missing/null/malformed inputs at serve time and that they're handled with the training-consistent rule. Credit "handle missing features in production," "impute or reject at inference." |
| **V-E3** | **Class imbalance / rare-target stratification** | A skewed label distribution requires stratified splitting and metric choice (e.g. PR-AUC over accuracy) so a model that predicts the majority class isn't falsely scored as good. | **FM-3** (an accuracy check insensitive to skew false-PASSes a majority-class predictor) | …class imbalance and that the split/metric must account for it (stratify, appropriate metric). Credit "imbalanced classes," "stratified split," "don't use accuracy on skewed data." |
| **V-E4** | **Cold start / empty or insufficient training data** | At first deployment (or for a new segment) there may be too little data to train; the design needs a fallback (baseline model, default prediction, hold serving) rather than shipping an unfit model. | **FM-6** (Feasibility: the model is *not-yet-determinable* — there is not enough information to train; needs a declared fallback) | …the cold-start / insufficient-data boundary and a fallback, not serving an untrained/garbage model. Credit "cold start," "not enough data → fallback/baseline." |
| **V-E5** | **Empty / degenerate batch & feature-distribution boundaries** | Edge inputs — an empty inference batch, a constant/zero-variance feature column, a single-row group — must not divide-by-zero in normalization or crash the transform; defined behavior required. | **FM-3** (a happy-path transform insensitive to a degenerate-numeric boundary crashes / divides by zero instead of handling it) | …degenerate numeric boundaries (zero-variance feature, empty batch, single example) and that the transform handles them. Credit "constant column / zero-variance," "empty batch," "avoid divide-by-zero in scaling." |

### 4.3 Defect-coupling criteria (former Failure-modes — only those with NO `Dep` twin)

Phrased as **concrete coverable claims** (PLAN §1.3 rule 4), never adjectives. **One-defect-one-place (PLAN
§1.3 rule 1):** a defect-coupling is kept here ONLY if it has no `Dep`-seam twin — *the PLAN's explicit
reference-builder warning for T02 is "do not double-count an F-item that is the negation of an X-seam."* The
two headline ML defects — **train/serve skew** and **leakage** — are the *negations of seams Dep1 and
Dep2/Dep3/Dep10/Dep13* and are therefore scored **on those seams, NOT duplicated here**. What remains are the
failure couplings with **no seam twin**: a *time-evolution* failure (silent drift past a still-good offline
score, FM-5), a *false-PASS* failure (a good aggregate metric hiding a broken segment, FM-3), a
*feedback-channel* gap (a detected production defect with no path back to retrain/rollback, FM-7), and an
*endogenous-signal* failure (the served model contaminating its own future training labels, FM-3). Each maps
to a canon §4 FM class. None is the negation of a `Dep`-seam (skew/leakage/schema-drift stay on Dep1 /
Dep2·Dep3·Dep10·Dep13 / Dep7).

| # | Name | FM tag (precludes) | What it requires (coupling + guard) | Truth-maker (covered iff named with a guard) |
|---|---|---|---|---|
| **V-F1** | **Silent staleness — model decays while offline score stays green** | **FM-5** (currency / stale inputs) | The world's input/label distribution shifts *after* training (concept/data drift); the frozen model degrades in production while its **offline** score (computed once, on old data) stays good — the defect is invisible without live monitoring. **No seam twin** (it is not a wrong edge between two stages but the pipeline computing validation against stale data over time). Guard: continuous drift/performance monitoring against the live distribution (D9/Dep11/Dep12) with a refresh trigger (Dep14). | …that a deployed model silently degrades as the live distribution drifts even though its offline number is unchanged, AND that live monitoring + a refresh path is needed to catch it. Credit "model goes stale / concept drift," "offline score doesn't reflect current reality," "need to retrain as data shifts." |
| **V-F2** | **Good aggregate metric hides a broken segment (false-PASS)** | **FM-3** false-PASS | The headline offline metric passes while the model is badly wrong on an important slice (a rare class, a key cohort, a fairness-sensitive group); "AUC = 0.9 overall" does NOT prove per-segment correctness. **No `Dep` twin.** Guard: sliced/segmented evaluation + per-segment thresholds beyond the aggregate number. | …that a good overall metric can hide a broken subgroup, AND that per-slice/segment evaluation (not just the aggregate) is needed. Credit "evaluate per segment/slice," "check subgroup performance," "aggregate metric isn't enough." **Mirrors the GFSO faithfulness residual** — a passing check that doesn't reflect reality. |
| **V-F3** | **No channel from a detected production defect back to retrain/rollback** | **FM-7** (no feedback channel) | A defect found **in production** (drift alarm, bad predictions, a discovered leakage bug) has no controlled channel to reach the owners and trigger retrain/rollback/registry-update → the error persists, unbooked. **No `Dep` twin** (distinct from Dep14, which is the *automatic drift→retrain trigger*; V-F3 is the *human/operational feedback channel* for defects a metric didn't pre-define). Guard: an incident → rollback/retrain feedback path with an owner. | …that a production defect needs a controlled feedback/rollback channel to the model owner (not a silent persistent error), AND that this is more than the automated drift trigger. Credit "rollback path on bad model," "feedback loop for production issues," "owner can pull a bad model." |
| **V-F4** | **Feedback-loop bias — the model's own outputs contaminate future training labels** | **FM-3** (endogenous / self-fulfilling input — false-PASS variant: the retraining signal is corrupted by the model itself) | The deployed model's predictions **influence the data later used to retrain it** (a recommender's shown items shape which clicks occur; a fraud model's blocks shape which outcomes are ever observed); naive retraining on this endogenous data treats the model's own effect as ground truth and **amplifies its bias / makes labels self-fulfilling**, while every offline metric on that data still looks fine. **No `Dep` twin** — this is not a wrong edge between two stages but a corruption of the label-generating process *by the served model*, so it cannot be carried by Dep12 (which merely *collects* labels, assuming them honest) or Dep14 (which *closes* the loop, assuming the signal is clean). Guard: log exposure/propensity (what the model showed/did) to debias the retraining signal, OR declare-and-bound the assumption that serving does not influence labels. | …that the model's own predictions can bias the labels/data used for its retraining (self-fulfilling labels / feedback-loop bias), AND that this needs a guard — exposure/propensity logging to debias, or an explicit assumption that serving doesn't affect future labels. Credit "feedback loop bias," "the model influences its own training data," "self-fulfilling predictions," "log what we showed so retraining isn't biased." **Distinct from V-F1** (V-F1 = the world drifts *exogenously*; V-F4 = the *model itself* corrupts the future signal) and from Dep12/Dep14 (those assume an honest label signal; V-F4 is the case where that assumption fails). |

> **Note on the operational axis (the borderline difference vs a pure-static task).** Unlike a fully-static
> one-shot decomposition where the runtime FMs {FM-5,6,7} are mostly N/A-static (cf. T08), T02's task
> statement forces runtime concerns into the *design*, so the operational axis is **genuinely carried** by
> named criteria/seams: **FM-5 currency** by V-F1 (silent staleness) + the seam Dep14 (drift→retrain refresh)
> and Dep11/Dep12 (the live-vs-offline comparison that detects drift); **FM-6 feasibility** by V-E4
> (cold-start / not-yet-trainable → declared fallback); **FM-7 feedback** by V-F3 (defect→retrain/rollback
> channel) + the seam Dep12 (prediction-logging→delayed-label) + Dep14 (loop closes). §7 records the full
> mapping and explains why these are design-time predicates here, not the N/A-static they would be for a
> purely-static pipeline-on-paper.

> the exclusion flips in-scope). Only assumptions whose **omission would otherwise be a foreseeable defect**
> (FM-1.b, §5.2 / §4.2: a predictable external risk left without a mitigating child) — assessed-and-declared-

|---|---|---|---|
| **N1** | **Label quality / correctness is assumed (no label-noise modeling)** | The pipeline *consumes* labels as given; detecting/correcting mislabeled ground truth (annotation quality, label noise) is an upstream data-labeling function. Declared boundary: a wrong label is a named upstream dependency, not a pipeline-logic defect. Invalidation: if label noise is known-material, a label-cleaning/agreement child becomes in-scope. | …that label quality/correctness is assumed (label noise / annotation quality is upstream / out of scope). |
| **N2** | **Serving infrastructure, autoscaling, latency/throughput SLOs are out of scope** | The task is the *connective logic* (data→features→model→served correctness), not the serving infrastructure: autoscaling, GPU provisioning, latency budgets, and load balancing are an infra/ops concern. Declared boundary: the design specifies *what is served correctly*, not *how the box scales*. Invalidation: a hard latency budget that forces a model/feature simplification would pull a constraint in-scope. | …that serving infrastructure / autoscaling / latency-throughput SLOs are out of scope (infra, not pipeline logic). |
| **N3** | **Pipeline orchestration / scheduling engine is a fixed input** | *Which* orchestrator runs the DAG (Airflow / Kubeflow / step functions), retries, and scheduling cadence is a platform choice; the design specifies the *logical* stage order and contracts, not the orchestration engine. Declared boundary: orchestration is the carrier, not the logic. | …that the orchestration/scheduling tool is a given platform choice, out of scope (the design fixes logical order, not the engine). |

| **N5** | **Data security / privacy / PII governance & compliance are out of scope** | Access control, PII redaction, consent, and regulatory compliance for the training data are a data-governance function upstream of and orthogonal to pipeline correctness. Declared boundary: the pipeline assumes it is licensed to use the data as provided; mishandled PII is a governance defect, not a pipeline-logic defect. Invalidation: a compliance constraint that forbids a feature pulls it in-scope as a transform constraint. | …that data privacy/PII/security/compliance is assumed handled upstream / out of scope (governance, not pipeline logic). |
| **N6** | **Serving/training regime (batch vs streaming) is a declared assumption** | The contract changes materially with the regime: point-in-time semantics, feature freshness, idempotency, and the offline↔online parity surface differ between batch scoring and online/streaming serving. Declared boundary: leaving the regime *unstated* is the foreseeable misattribution this N closes — not the regime choice itself. Invalidation: an explicit ensemble/cascade requirement pulls per-member co-versioning and combined-decision parity in-scope. | …that the design assumes a single model / single task (not an ensemble, cascade, or multi-task system), so the binding/parity surface is single. Credit "single model," "one model one endpoint," "ensembles out of scope," or a design that is simply written for one model without claiming multi-model support. |

> **N-discipline (STD-1/2/3).** Each N is an assumption whose *failure* would otherwise be misattributed to
> the pipeline (omitting N1 makes "wrong predictions from bad labels" look like a training bug; omitting N2
> makes "endpoint too slow" look like a design hole; omitting N4 makes "should have picked a different
> model" look like a missing pass). Each carries a `predictability_verdict` and an invalidation trigger.
> This is a *bounded* list of foreseeable misattributions, not "anything could be assumed": e.g. "one cloud
> region," "Python is the language," **and a cost/budget ceiling** stay OUT (their failure is not a
> foreseeable *pipeline-logic* misattribution — a cost cap is an operating constraint, not a correctness
> predicate, exactly like N2's latency SLOs). N6 (regime) and N7 (single-model) *are* carried because an
> *undeclared* regime or an *assumed-but-unstated* single-model topology silently changes the parity/binding
> contract — a real misattribution surface — whereas a cost ceiling does not.

## 6. Hardest / most-easily-forgotten seams (flag for scorer)

> Not a category — a scorer pointer at the highest-signal `Dep` edges.

**Dep1** (train/serve transform skew — *the* canonical ML seam, and the one a stage-list never mentions
because both halves look like "preprocessing"), **Dep5** (the fitted preprocessor must travel with the model
through the registry — a model loaded with a mismatched transform mispredicts silently), **Dep9** (offline
eval must run through the *serving* transform path or the offline number is meaningless — the seam that
literally discharges "offline score predicts online"), and **Dep12** (predictions must be logged so delayed
true labels can be joined to measure live accuracy — without it monitoring is blind to realized
performance). These are the directed data/parity edges a parts-list ("ingest, features, split, train, eval,
registry, serve, monitor") names as stages but silently drops as *edges* — exactly where a "magic-word"
decomposition diverges from a faithful one.

## Appendix — settled adjudications carried over (scorer must apply; verbatim from `reference_buckets_v1.md`)

- **F-vs-`Dep` double-count (the PLAN's explicit T02 hazard) — RESOLVED by removal.** "Train/serve skew,"
  "leakage," and "schema drift" as *failure-modes* are the negations of Dep1, Dep2/Dep3/Dep10/Dep13, Dep7 and

  train/serve skew" maps to **Dep1 only** (it names the seam + its breakage) — it does not additionally earn
  a defect-coupling credit. No shared coverage credit across the `Dep`/`V-F` boundary.
- **D2/D7 collapse — credit either granularity.** An agent who writes one "preprocessing" stage *and*
  explicitly asserts it is reused at serving covers D2, D7 **and** Dep1; an agent who writes two stages
  covers D2 and D7 and (iff they assert identity) Dep1. Do not require the split; do not penalize it. Only
  the *assertion of shared/identical transform* earns Dep1.
- **Dep10 (temporal) vs Dep2/Dep3 — conditional, no double-penalty.** Dep10 is a distinct seam **for
  time-ordered data** (a random split passes Dep2/Dep3 yet leaks across time). For IID data with no temporal
  structure, Dep10 folds into Dep2 — **do not penalize an agent for omitting a temporal-split seam on data
  with no time axis.** Credit Dep10 whenever the agent raises point-in-time/look-ahead correctness; treat as
  N/A otherwise.
- **Dep8 (feature store) — conditional on design.** Dep8 is a real seam **only if** a precomputed feature
  store/cache is part of the design. If the agent's design computes features inline (no store), Dep8 is N/A
  and its omission is **not** a hole; if a store is present, offline/online value consistency is required.
- **Eval gate (in-plane) vs promotion approval (orthogonal plane).** "Promote only if the model passes the
  eval threshold" is an artifact predicate → **Dep14 (in-plane), credited.** "A human must approve the
  promotion" is an authority predicate → **orthogonal plane: no penalty for omission, no criterion-credit for
  inclusion.** Force-fitting an approval gate into a criterion is a category error (criterion = artifact
  predicate; approval = process/authority predicate). See the authority-plane section above.
- **V-I1/V-I2 (global invariants) vs the seams that compose them — credit independently.** Naming the
  composing seams (Dep2/Dep3/Dep10/Dep13 or Dep1/Dep5/Dep6/Dep8/Dep9) earns the `Dep`-credits; stating the
  *global* honest-score / parity predicate earns V-I1 / V-I2. An agent can have one without the other; they
  are not the same canonical item (PLAN §1.3 rule 2 — invariants canonicalize by the enforced predicate,
  seams by the adjacent pair).
- **D10 (online pre-promotion validation) — carried, credit any flavor.** Shadow scoring, canary slice, or
  champion/challenger all cover D10 (the truth-maker is *a candidate is compared to the incumbent on live
  traffic before full cutover*). It is **not** required for an agent to also have D9 — D10 (validate a
  *candidate* pre-promotion) and D9 (monitor the *promoted* model) are separate passes; credit each on its
  own truth-maker. An agent whose promotion is offline-gate-only and who *explicitly declares* online
  pre-promotion validation out of scope is not penalized for D10, but the carried-component framing is the
  faithful reference because the task stresses *offline predicts online*.
- **V-F4 (feedback-loop bias) vs Dep14/Dep12 — distinct, no shared credit.** "Trigger retraining on drift"
  (Dep14) and "log predictions for delayed labels" (Dep12) do **not** earn V-F4: both assume the label signal
  is honest. V-F4 is earned only by naming that the *model's own outputs bias the future training labels*
  (self-fulfilling labels) **and** a guard (exposure/propensity logging, or an explicit declare-and-bound).
  It is also not a twin of any `Dep`-seam (no static edge carries an endogenous-signal corruption), so it is
  a real defect-coupling criterion, scored once in §4.3.
