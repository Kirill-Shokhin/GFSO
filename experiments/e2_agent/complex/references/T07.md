## Task `T` (verbatim, PLAN §3 T07)

> Design the logic of a concurrent in-memory cache/store used by many threads or nodes:
> the read/write path, an eviction policy, per-entry TTL/expiry, write-through or write-back persistence
> backing, invalidation on update, and sharding/partitioning. Specify how these mechanisms interact so the
> store stays consistent and bounded under concurrent access.

**Shape.** Pairwise-dense: six mechanisms (read/write path, eviction, TTL, persistence, invalidation,
sharding) that genuinely **couple under concurrency**. The load-bearing content is the **cross-mechanism
interaction seams** and the **global consistency/boundedness invariants** that no single mechanism can
establish alone. Achievement goal: a correct, bounded design that *terminates* in a specified set of rules —
not a maintenance/viability regime.

**Defect-class (distinctness from T01, the other pairwise-dense task).** T01's coupling is
money-conservation over a sequential state-machine (value-conserving, deterministic order). T07's coupling is
**concurrency/consistency over shared mutable state** — interleaving-sensitive, race-bearing: the same seam
can be correct under one thread interleaving and broken under another. Every seam below must hold *under
arbitrary concurrent interleaving*, which is what makes them hard.

**Single meta-level.** This decomposes the **store's logic** at one level: the mechanisms and how they
interact. It does NOT spawn sub-projects (build the allocator, run a benchmark suite, operate a cluster).
Components are mechanisms of one design, not deliverables owned by different teams. (Consequence: the
OPERATIONAL failure modes {FM-5,6,7} — runtime/execution-time modes — are mostly out of scope for this
static single-meta-level decomposition; see §7.)

**Scope anchor (the `spec`).** The two halves of the goal `spec` are: (a) the store stays **consistent**
under concurrent access (no lost/torn/stale read or write, per-key coherence, durable flush) and (b) the
store stays **bounded** under concurrent access (eviction keeps memory within its bound, expired entries
don't leak). A decomposition is complete iff it covers both halves. **NOTE on the static/denotational
framing:** T07's *failures* manifest as runtime concurrency **races**, but the decomposition's criteria are
**static predicates** — invariants the concurrent design must satisfy (no-lost-update, no-torn-read,
no-stale-read, no-deadlock, memory-bound). These predicates are **denotational** {FM-1,2,3,4} (design-time,
determinable from the spec); the races are exactly what the static invariants **preclude**. Concurrency
correctness here is a static-invariant (denotational) matter — not an operational {FM-5,6,7} one (see §7).

## 1. Subtasks `D` — the cache mechanisms (the parts)

> `D` = the children of the decomposition (canon §2.2: `D: T → P(T)`, a DAG).

Each subtask is a separable **mechanism** with its own pass/fail criterion on its *output behaviour*
(what state the store is in after the mechanism runs), not a self-report ("locking added"). The concurrency
control is treated as ONE subtask (the mechanism that makes the others safe), not as a property smeared
across every other mechanism, to keep the design at one meta-level — its *interactions* with each other
mechanism are the `Dep`-seams.

| # | Name | What it requires | Truth-maker (covered iff the decomposition names…) |
|---|---|---|---|
| **D1** | **Storage / index (the map itself) + operation API** | The core key→value store: a hash map (or equivalent associative structure) holding entries; the get/put/delete operations and the in-memory representation of an entry (value + metadata: TTL, dirty bit, size, recency/frequency stats). Includes the **atomic compound-op contract** (D1a below): which read-modify-write operations the API exposes (`getOrLoad`/`computeIfAbsent`, `putIfAbsent`, `replace`/CAS, `getAndSet`) and the **stated atomicity of each** — the indivisible-RMW substrate that Dep12 (publication), Dep14 (delete-vs-load) and V-F1 (single-flight) all sit on. | …a key-value store / hash map and the basic get/put/delete operations over it. Credit "the underlying map," "the index," "store entries by key." The data structure that everything else operates on. |
| **D1a** | **Atomic compound-op API contract** | The set of compound (read-modify-write) operations the cache exposes and a **per-op atomicity guarantee**: `getOrLoad`/`computeIfAbsent` (loader runs at most once per key — ties to V-F1), `putIfAbsent`, `replace`/compare-and-swap, `getAndSet` — each stated to take effect atomically w.r.t. concurrent ops on the same key (no interleaving observes a half-applied compound op). | …that the cache offers compound atomic operations (computeIfAbsent / putIfAbsent / replace-CAS / getAndSet or equivalents) **with a stated per-op atomicity contract**, not just bare get/put/delete. Credit "atomic getOrCompute," "CAS / putIfAbsent is atomic." The RMW *atomicity* is the V-I1 predicate; this item is the *API surface contract* (which compound ops exist and that each is atomic). **Distinct from V-I1** (V-I1 = no-lost-update predicate; D1a = the named compound-op API the predicate applies to). |
| **D2** | **Concurrency control** | The mechanism that makes concurrent access safe: locking (coarse/fine-grained, per-bucket/per-shard, read-write locks), or lock-free/atomic operations (CAS), or single-writer schemes. Defines the **atomicity granularity** — what unit of operation is indivisible w.r.t. other threads. | …the synchronization mechanism (locks, RW-locks, sharded/striped locks, atomics/CAS, lock-free). Credit any concrete concurrency-control scheme. The mechanism that the no-lost-update / no-torn-read invariants (V-I1/V-I2) rest on. **Distinct from D7 sharding** (sharding partitions the keyspace for parallelism; D2 is the synchronization within whatever the unit is). |
| **D3** | **Eviction policy** | The policy that selects victims to remove when the store is over its capacity bound: LRU, LFU, FIFO, random, or a hybrid (e.g. segmented-LRU, 2Q, ARC, W-TinyLFU); maintains the recency/frequency bookkeeping (recency list / frequency counters) needed to pick a victim. | …an eviction policy (LRU/LFU/FIFO/etc.) that chooses what to remove when full, and the bookkeeping it maintains. Credit "evict least-recently-used," "evict on capacity." |
| **D4** | **TTL / expiration** | Per-entry time-to-live: each entry may carry an expiry time; expired entries are not served and are reclaimed. Requires BOTH the **passive** path (an expired entry is treated as absent on access — lazy expiry) AND an **active** path (a background sweeper / sampling reclaims expired entries that are never accessed), because lazy-only leaks memory for cold expired keys. | …per-entry TTL and that expired entries must not be served, **with** reclamation. Credit "entries expire after a TTL." The active-sweep half is scored at V-I6 (no-leak) / V-E5, not required to name D4 itself — but a design with only lazy expiry has covered D4's serve-path and missed the reclamation half. |
| **D5** | **Persistence backing (write-through / write-back)** | The optional backing store the cache fronts, and the write policy: **write-through** (every write goes synchronously to backing before ack) vs **write-back / write-behind** (writes buffered in cache, flushed asynchronously; entries carry a **dirty** bit). Defines what "committed" means and which entries are dirty. | …a backing store and the write policy (write-through vs write-back), and that write-back entries are dirty until flushed. Credit "persist to a backing store," "write-through / write-behind," "dirty entries flushed later." The mechanism that introduces the dirty-entry seams (Dep3, Dep4, V-I5). |
| **D6** | **Invalidation on update** | The mechanism that keeps a cached value from being served after it is superseded: on an update (or external change), the stale cached copy is invalidated/refreshed so no reader subsequently observes the old value as if current. Covers the local case AND, in a multi-node deployment, the cross-node propagation of invalidations. | …an invalidation/refresh-on-update mechanism that prevents serving a value after it has been superseded. Credit "invalidate on write," "evict stale entry on update," "publish invalidation to other nodes." The mechanism the no-stale-read invariant (V-I3) rests on. |
| **D7** | **Sharding / partitioning** | The keyspace is partitioned into shards (by hash of key) so independent shards can be accessed concurrently without a global lock; defines the shard-mapping function and the per-shard ownership of storage/locks/eviction/capacity. | …a partitioning of the keyspace into shards (hash-partitioned) for concurrency, and the shard-mapping function. Credit "shard by key hash," "stripe the map," "partition the keyspace." Enables parallelism; introduces the per-shard-vs-global seams (Dep7, Dep8, V-I4). |

> **Note on D2 vs the others.** Concurrency control (D2) is a *distinct subtask*, not a property folded
> into each of D1/D3/D4/D5/D6. It is listed once; its *interactions* with each other mechanism are the
> concurrency seams in **`Dep`** (e.g. evict-under-concurrent-read = Dep1, stats-under-concurrency = Dep6). An
> agent who says only "use locks everywhere" has named D2 but not the seams. D1a (the atomic compound-op API
> contract) is folded into D1 as a sub-contract rather than an 8th mechanism — its truth-maker (which compound
> ops exist and that each is atomic) is distinct from the V-I1 no-lost-update predicate.

## 2. Dependencies `Dep` — cross-mechanism interaction seams as explicit, separately-falsifiable `Dep` edges

> `Dep` = the canon primitive (§2.2): an acyclic relation on `T × T`; `(tₐ, tᵦ) ∈ Dep` iff `criteria(tᵦ)`
> references the output of `tₐ` (with coherence `deadline(tₐ) < deadline(tᵦ)`). **Each `Dep` edge is a
> criterion of a child that references a sibling's output — the glue** — and carries its **own** falsifying
> truth-maker (the anti-mock condition), not "these mechanisms relate" prose. **T07's seams are concurrency
> interaction seams:** two named mechanisms exchange a concrete shared artifact (an entry, a lock, a counter,
> the size accounting, the shard map) and the edge's falsifier is a concrete *thread interleaving* under
> which the cache returns a wrong result, loses data, or exceeds its bound.

**The dominant and most-forgotten category — the heart of T07.** Each seam is a REAL edge: two named
mechanisms exchange a concrete **shared artifact** (an entry, a lock, a counter, the size accounting, the
shard map) and the edge carries its **own** falsifying criterion — a concrete *thread interleaving* (or
ordering) under which the cache returns a wrong result, loses data, or exceeds its bound (Constitution
Ст. II.5 anti-mock). Not "these mechanisms relate" prose. A seam is covered iff the decomposition names the
**same mechanism pair** and the **same thing that breaks** (the race / the dropped write / the bound
violation) if the edge is mishandled. **One-defect-one-place:** each `Dep` is a coupling with its own
breakage; a defect-coupling criterion (§4.3) is kept only if it has NO `Dep`-twin.

| # | Name | Pair (mechanism ↔ mechanism) | What the edge requires | Truth-maker (covered iff named with its breakage) |
|---|---|---|---|---|
| **Dep1** | **Eviction under concurrent read/write (evict the entry someone is using)** | D3 ↔ D2/read-write path | A victim chosen by eviction may be concurrently read or written by another thread. Eviction must not free/remove an entry out from under an in-flight reader (use-after-free / null deref) or race with a concurrent writer that just re-touched it. | …that eviction races with concurrent access to the *same* entry, and that the victim must not be removed while a reader/writer holds it (no use-after-free / no removing a just-accessed entry). Shared artifact = the victim entry + its refcount/lock. **Hardest, most-forgotten seam.** |
| **Dep2** | **Eviction vs TTL ordering (expired-vs-evicted on a contended entry)** | D3 ↔ D4 | An entry can be simultaneously a TTL-expiry candidate and an eviction victim. The design must define which fires and reclaim the entry **exactly once** — not double-free (both paths reclaim it) and not leak (each assumes the other will). On a write-back dirty entry the order also decides whether a flush is owed (ties to Dep3). | …that TTL-expiry and eviction can target the same entry and must be reconciled so it is reclaimed exactly once (no double-free, no both-skip leak). Shared artifact = the entry's reclamation. Credit "an expired entry being evicted must not be freed twice." |
| **Dep3** | **Evicting a dirty (write-back) entry must flush, not drop** | D3 ↔ D5 | When the victim is a write-back entry whose dirty data has not yet been persisted, eviction must **flush it to the backing store before freeing it**, not silently drop it — otherwise the buffered write is lost. | …that evicting a dirty/unflushed entry must flush to backing first (not drop it); dropping a dirty victim loses the write. Shared artifact = the dirty entry's unpersisted value. **Classic forgotten seam** — the eviction policy and the write-back buffer are designed separately and the flush-on-evict edge is dropped. |
| **Dep4** | **TTL expiry of a dirty entry (don't lose / don't persist stale)** | D4 ↔ D5 | A write-back entry can reach its TTL before its dirty data is flushed. Expiry must not discard unflushed data (lost write); symmetrically, a flush must not persist an already-expired value as if current. The expiry path and the flush path share the dirty entry. | …that TTL expiry of an unflushed dirty entry must still flush (don't lose the write) and must not persist an expired value as live. Shared artifact = the dirty-and-expiring entry. **Easily-forgotten** — twins neither Dep2 (eviction) nor Dep3 (eviction); this is expiry-vs-flush. |
| **Dep5** | **Invalidation vs read (no stale read after a committed write)** | D6 ↔ read path / D2 | An update commits a new value; a concurrent or subsequent reader must not observe the *old* cached copy as current. The invalidation/refresh of the stale copy must be ordered w.r.t. the commit so no reader sees a value the write already superseded. | …that after a write commits, no reader may serve the pre-update cached value — invalidation/refresh is ordered against the commit. The shared artifact = the cached copy of the updated key + the commit point. **The defining consistency seam.** |
| **Dep6** | **Concurrency vs stats/metadata updates (atomic counters & recency bookkeeping)** | D2 ↔ {D3 bookkeeping, stats} | Hit/miss counters, size accounting, and the eviction policy's recency/frequency metadata are mutated on every access by many threads. These updates must be atomic / correctly synchronized or they drift (lost increments) and the eviction policy reads corrupt recency data (picks a wrong/garbage victim, or the recency list corrupts). | …that the shared counters and the eviction policy's recency/frequency bookkeeping are updated under concurrency and must be synchronized/atomic, or they drift / corrupt. Shared artifact = the hit/miss/size counters + the LRU/LFU metadata. **Distinct from V-I7 (stats-accuracy invariant):** Dep6 is the *concurrent update to the metadata the eviction policy reads*; V-I7 is the *observable counters being meaningful*. |
| **Dep7** | **Cost-aware sizing / memory accounting drives eviction (the trigger seam)** | D7-capacity / size accounting ↔ D3 | Eviction is *triggered* by a memory/entry-count bound being reached; the size accounting is the shared artifact that tells eviction when and how much to evict. The cost may be **per-entry bytes** (via a named size function — see N5), not just an entry count, and the trigger is a **loop that evicts until total cost is back under the bound** (one victim may not free enough). If accounting is wrong or not updated atomically with insert/evict, the store either evicts needlessly or **exceeds its bound**. (The oversized-value corner — a value whose cost exceeds total capacity, which would otherwise force an evict-everything loop — is the V-E7 boundary.) | …that a memory/count bound triggers eviction and that the size accounting is the shared signal between insert and evict (kept in sync so the bound is enforced), **including byte-cost (not just count) and evicting until back under the bound**. Shared artifact = the running size/count vs the capacity bound. **The seam that makes "bounded" actually hold.** |
| **Dep8** | **Sharding vs global capacity / eviction (per-shard vs global bound)** | D7 ↔ D3 + size accounting | With sharded storage, eviction and the capacity bound are usually **per-shard**. The design must reconcile per-shard eviction with the **global** memory bound: an uneven key distribution (hot shard) can blow one shard's budget while others sit empty, so either the bound is global (needs cross-shard accounting/coordination) or it is per-shard (and the global bound is the sum, with skew slack). | …that sharding makes eviction/capacity per-shard and this must be reconciled with the global memory bound (skew across shards, per-shard vs global budget). Shared artifact = the shard budgets vs the global bound. **Forgotten** — sharding is named for parallelism but its interaction with the *global* bound is dropped. |
| **Dep9** | **Cross-shard invalidation ordering / atomicity** | D6 ↔ D7 | When an invalidation must reach entries (or replicas of a key) on **other** shards/nodes, the cross-shard/cross-node propagation must be ordered/atomic enough that no shard serves a stale value after the update is acknowledged, and that two concurrent updates to the same key don't leave shards disagreeing. | …that invalidation crossing shard/node boundaries needs ordering (and handling of concurrent updates) so shards don't disagree / serve stale after ack. Shared artifact = the invalidation message + the per-shard copy. **Distinct from Dep5** (Dep5 is local invalidation-vs-read; Dep9 is the *cross-shard propagation* of it). |
| **Dep10** | **Get-under-eviction / get-under-expiry race (lookup vs reclaim of the same key)** | read path ↔ D3 + D4 | A `get` for key K can interleave with K's eviction or expiry: the reader may find the entry, then it is reclaimed before the value is returned (use-after-free), or the reader misses an entry that is being concurrently inserted. The lookup and the reclaim share the entry slot and must be ordered (hold a reference / hazard pointer / lock during the read). | …that a concurrent get and evict/expire of the *same* key race (the reader can be handed an entry that is being freed), and the lookup must pin/guard the entry. Shared artifact = the entry being read while concurrently reclaimed. **Distinct from Dep1** (Dep1 = eviction policy choosing a live victim generally; Dep10 = the specific get-vs-reclaim handoff of one key — the lookup side). Flag for scorer: if an agent collapses Dep1 and Dep10 into one "evict-while-in-use" point, credit one and note the other as a non-redundancy merge, not two holes. |
| **Dep11** | **Insert-into-full-store ordering (evict-then-insert vs insert-then-evict)** | read-write path ↔ D3 + Dep7 | A `put` into an at-capacity store must trigger eviction; the design must order evict-vs-insert so the store never *transiently* exceeds the bound by more than one entry under concurrent inserts, and two concurrent inserts into a full store don't both skip eviction (double over-fill) or both evict (over-evict). | …that inserting into a full store couples insert with eviction (evict to make room) and the ordering/atomicity of the two under concurrent inserts (don't over-fill, don't over-evict). Shared artifact = the one free slot. **Distinct from Dep7** (Dep7 = accounting *triggers* eviction; Dep11 = the *insert↔evict ordering* on the hot full-store path). |
| **Dep12** | **Write-through commit vs read visibility (read-your-writes / publication ordering)** | read-write path ↔ D2 ↔ D5 | A committed write must become visible to subsequent readers atomically with (or before) its acknowledgement — partial publication (value updated but metadata/index not, or backing acked before cache visible) lets a reader observe a torn or pre-commit state. The write path and the read path share the entry's publication point. | …that a write's new value and its metadata become visible to readers atomically at the commit/publish point (read-your-writes; no reader sees a half-updated entry). Shared artifact = the entry's publication / visibility point. **Distinct from Dep5** (Dep5 = *invalidating an old copy* on update; Dep12 = *publishing the new value* atomically so no torn/pre-commit read) and from Dep3/Dep4 (those are the dirty-flush seams). |
| **Dep13** | **Rehash / resize × concurrent ops (key-in-limbo during migration)** | D7 / D1 (bucket array, shard count) ↔ read-write path | When the bucket array grows/shrinks or the shard count changes, entries migrate between old and new tables. Concurrent ops during migration must resolve each key to **old-or-new (never *neither*)**: a `get` mid-migration must not miss a key that exists, a `set` to a bucket being moved must not be lost, and no reader may observe a partially-rebuilt table. Each key/bucket's routing transitions atomically (the old slot stays readable until the new one is published). | …that resizing/rehashing (or changing shard count) races with concurrent get/set, and a key being migrated must always be locatable in old-or-new (no key-in-limbo, no lost write on a moved bucket, no half-built-table read). Shared artifact = the entry mid-migration + the routing/table pointer. **Forgotten dynamic-resize seam** — the map is sized once on paper and the live-grow race is dropped. Establishes V-I10 (routing stability). |
| **Dep14** | **Delete × in-flight load-through → resurrection** | D1-delete ↔ D5 load-through path | A `getOrLoad(K)` reads `V` from the backing store; concurrently `delete(K)` (or an invalidation) commits; the loader then inserts `V` → the deleted/invalidated key **reappears stale** (resurrection). The load-completion must be conditional: CAS-on-version / generation guard so a load only installs if the key's generation is unchanged since the load began (or `delete` must cancel/invalidate in-flight loads). | …that a delete (or invalidation) racing an in-flight load-through can resurrect the deleted key, and the load must install conditionally (version/generation CAS) or be cancelled by the delete. Shared artifact = the key's generation/version across the load window. **Distinct from V-F1** (V-F1 = *deduping* concurrent loads of the same key; Dep14 = a *delete* racing one load and the loader writing back stale). **Silent** — every local check passes; the key just comes back. |

> **Anti-mock note.** Every `Dep` references a concrete *shared artifact* (an entry + its refcount, a lock,
> the dirty bit, the size counter, the LRU metadata, the shard map, a publication point) — a forgotten seam
> here is an objectively identifiable concurrency/correctness **bug** (a race that loses data, a
> use-after-free, a bound violation), not a nominal pair. None collapse onto each other: different mechanism
> pair OR different falsifier ⇒ distinct seam (PLAN §1.3 rule 1). In particular Dep2 (expired-vs-evicted
> reclamation) ≠ Dep3 (flush-dirty-on-evict) ≠ Dep4 (flush-dirty-on-expiry) — three different mechanism pairs
> with three different dropped artifacts; Dep5 (local stale-read) ≠ Dep9 (cross-shard invalidation) ≠ Dep12
> (atomic publish-new-value); Dep13 (rehash/resize migration race) and Dep14 (delete-vs-in-flight-load
> resurrection) are two further distinct pairs — Dep13's artifact is the entry mid-migration + the routing
> pointer, Dep14's is the key generation across a load window; neither collapses onto Dep1/Dep10 (reclaim) nor
> V-F1 (load dedupe).
> **The anti-mock filter excludes nominal pairs** that share no truth-maker: e.g. TTL × sharding (a per-entry
> timer does not couple with the partition function — each shard expires its own keys) and eviction ×
> invalidation-policy (independent unless they contend on the same entry, which is Dep1/Dep10) are NOT real
> seams and are correctly absent.

> **FM mapping for `Dep`.** A forgotten/violated `Dep` edge is an **FM-1** defect (a spanning integration
> criterion — the glue — not written / not covered; §4.2 FM-1 insufficiency, §18.10 *hole-i*) when it is a
> coverage hole, and an **FM-2** defect (criteria of two children incompatible / a relational defect at fixed
> composition; §4.2 FM-2) for the two-sided / shared-artifact seams whose breakage is a mutual-satisfiability
> conflict (Dep2 reclaim-exactly-once, Dep8 per-shard↔global budget, Dep9 cross-shard agreement, Dep12
> publish-vs-read-visibility agreement). The §7 FM table records this. Per one-defect-one-place, a seam's
> failure is scored **here as a `Dep` item**, never re-listed as a separate criterion.

## 3. Authority `Del` — orthogonal note (NOT scored)

> **`Del` is the canon "who" axis** (§2.3: `Del: T → A`, exactly one agent per task) — **orthogonal** to the
> decomposition plane `{D, Dep, V}` and **NOT scored** as a decomposition item. This is a plane-separation
> note, NOT a NEGLECTED exclusion, NOT a criterion, NOT a completeness hole.

Access control / authorization on the cache (who may read or evict a key), admission control as a *policy
approval*, or any segregation-of-duties over operations is **not** a predicate over the produced artifact (a
correct, bounded, consistent store) and is **not** a decomposition node. A cache can be perfectly race-free,
bounded, and consistent **and** have any authority model bolted on or absent. Authority is a property of the
**delegation/ownership edges** (GFSO Issuer/Executor split, emergent from `Del`), not a component, seam,
invariant, edge-case, failure-mode, or scope-exclusion.

**Why authority is orthogonal (derived, not asserted).** A GFSO decomposition is graded on its
artifact-predicates and how the work splits ({D, Dep, V}) — predicates on *what must be true about the
produced artifact* and *how the work splits*. Access-control / approval / SoD over operating the cache is
**not** a predicate over the artifact: a store can be race-free, bounded, consistent, and per-key coherent
**and still** have any authority model around it or none. In GFSO's primitives it is an emergent property of
the **edges of the delegation hierarchy**: the **Issuer** sets criteria and validates `V`; the **Executor**
produces (`Del` assigns who, and `V`-by-Issuer ≠ self-validation). It is emergent from `Del` + the delegation
hierarchy, not a node *within* the decomposition.

**Consequences for scoring (scorer rules):**
- A decomposer is **NOT penalized** for omitting any access-control / approval / SoD item — there is no
  decomposition slot it belongs in.
- **Force-fitting it into a criterion is a category error** (criterion = predicate on the produced store;
  authority = predicate on the process that operates it). An agent who adds "only authorized callers may
  evict" earns no criterion-credit and loses none — a correct statement in a different plane.
- This is **plane-separation**, not a NEGLECTED scope-exclusion and not a completeness hole.

> **NB (in-plane vs orthogonal).** *Admission control* in the sense of "decide whether a new entry is worth
> caching" — e.g. TinyLFU admission — IS in-plane, part of D3's eviction/admission policy; it is *not* the
> authority plane. Only authorization/approval/SoD over *operating the cache* is orthogonal.

## 4. Criteria `V` — task predicates (former Invariants + Edge-cases + Failure-modes, COLLAPSED)

> `V` is **derived**: `V(t) = AND(criteria(t))` (§2.2, §3.1 Theorem 1). Every item below is a **predicate of
> the task** — a `criterion` whose conjunction is the validation. The former Invariants (store-wide spanning
> predicates), Edge-cases (boundary-state predicates) and Failure-modes (defect-coupling predicates) are
> **all criteria** and are collapsed here into one section. Each criterion keeps its verbatim text +
> truth-maker and carries an **FM tag**: which canon failure mode(s) it precludes (§4.2 / §4.6). The old
> I/E/F labels are retired — the FM tag replaces them. (Item ids keep an I-/E-/F- prefix purely for
> cross-reference traceability to `reference_buckets_v1.md`; they are NOT separate categories.)

**How to read the FM tag.** Per §4.2/§4.6: a **spanning/coverage predicate** a faithful decomposition must
carry (and whose omission is a coverage hole) precludes **FM-1** (Correspondence — joint sufficiency); a
predicate enforcing **mutual satisfiability** of children / per-shard-vs-global or per-key-coherence
consistency precludes **FM-2** (Consistency); a predicate guarding against an **insensitive / mockable /
looks-OK-but-wrong** check (a value that passes where reality fails) precludes **FM-3** (Verifiability,
false-PASS); a predicate enforcing **correct fail-propagation / progress / termination of the rule**
precludes **FM-4** (Propagation).

**Why these concurrency predicates are DENOTATIONAL (not operational).** T07's failures *manifest* as
runtime races, but every criterion below is a **static invariant** the concurrent design must satisfy by
construction (a predicate over the design, determinable at design time). The race is what the static
invariant **precludes**; naming the invariant is a design-time act. Hence all eleven invariant criteria, all
the boundary criteria, and the defect-couplings preclude **denotational** FMs {FM-1,2,3,4} — not the
operational runtime modes {FM-5,6,7} (see §7).

### 4.1 Global correctness criteria (spanning predicates — former Invariants)

A spanning criterion is a store-wide predicate that **spans mechanisms** — no single mechanism establishes
it; it holds only if all the coupled mechanisms are jointly correct (canon §2.2 joint sufficiency / §3.1).
Canonicalized by the *conserved quantity / enforced predicate*, not by where it is checked (PLAN §1.3 rule
2). These are the binary correctness conditions the task asks for ("consistent and bounded").

| # | Name | Conserved quantity / predicate | FM tag (precludes) | Truth-maker (covered iff the decomposition asserts…) |
|---|---|---|---|---|
| **V-I1** | **No lost update** | Concurrent writes to the same key are serialized so every committed write is reflected; no write is silently overwritten/dropped by a racing write (read-modify-write is atomic where required). | **FM-1** (spanning write-safety joint-sufficiency predicate) | …that concurrent updates to a key must not lose a write (writes serialize / RMW is atomic). The defining write-safety invariant — spans D1, D2. Credit "no lost updates," "concurrent writes don't clobber each other." |
| **V-I2** | **No torn read / no torn write (atomic visibility)** | A reader never observes a partially-updated entry (half-written value, value updated but TTL/size metadata not); an entry's value+metadata transition atomically from one consistent state to the next. | **FM-1** (spanning atomic-visibility coverage predicate) | …that reads never see a partially-written/half-updated entry (no torn read; entry updates are atomically visible). **Distinct from V-I1** (V-I1 = no *lost* write; V-I2 = no *partial/torn* observation of a write). Spans D1, D2, Dep12. |
| **V-I3** | **No stale read after a committed write (consistency)** | Once a write commits, no subsequent read returns the pre-update value as current — the cache is consistent with the latest committed write (the store's stated consistency level is honoured). | **FM-1** (the "consistent" half of `spec`, spanning) | …that after a write commits, reads reflect it — no stale value served post-commit. The consistency invariant the task names. Spans D6, Dep5, Dep9. Credit "no stale reads," "reads see the latest committed write." |
| **V-I4** | **Memory / size bound never exceeded** | The store's total memory (or entry count) stays within its configured bound at all times, including transiently under concurrent inserts — eviction keeps it bounded; the bound is never (or only by ≤1 entry, by stated policy) exceeded. | **FM-1** (the "bounded" half of `spec`, spanning) | …that the store stays within its memory/count bound (bounded growth; eviction enforces it, including under concurrency). The "bounded" half of the goal `spec`. Spans D3, D7, Dep7, Dep8, Dep11. Credit "memory is bounded," "never exceeds capacity." |
| **V-I5** | **No lost write through the persistence path (dirty entries durably flushed before reclaim)** | Every dirty (write-back) entry's value reaches the backing store before the entry is reclaimed by *any* path (eviction, expiry, shutdown) — buffered writes are never dropped. | **FM-1** (spanning durable-flush coverage across every reclaim path) | …that a dirty/unflushed entry is always flushed before it is freed by eviction, expiry, or shutdown (no buffered write lost). Spans D5, Dep3, Dep4. **Distinct from V-I1** (V-I1 = no lost write *in memory* under a race; V-I5 = no lost write *to the backing store* via reclamation). Credit "write-back data is never dropped on eviction/expiry." |
| **V-I6** | **No memory leak from un-reclaimed expired entries** | Expired entries are eventually reclaimed even if never accessed again — the store does not accumulate dead (expired) entries that lazy-on-access expiry never touches; memory used by expired-but-cold keys is bounded. | **FM-1** (spanning no-leak coverage — the active-sweep half of "bounded") | …that expired entries that are never re-accessed are still reclaimed (active sweep / sampling), so expired-but-cold keys don't leak memory. **Distinct from V-I4** (V-I4 = live entries bounded by eviction; V-I6 = *expired* entries don't accumulate when lazy-expiry alone never sees them). Spans D4. Credit "background expiry of cold keys," "expired entries don't leak." |
| **V-I7** | **Stats / counters accurate under concurrency (no drift)** | Hit/miss/eviction/size counters are correct (no lost increments) under concurrent updates — the observable metrics and, critically, the *size accounting that drives eviction* (Dep7) do not drift from the true state. | **FM-1** (spanning counter-accuracy coverage; the size-accounting leg the bound rests on) | …that the counters (hits/misses/size/evictions) are accurate under concurrency — no drift from lost increments. **Distinct from Dep6** (Dep6 = the *concurrent-update mechanism* on the metadata; V-I7 = the *resulting numbers being correct*, which Dep7's bound-enforcement also depends on). Spans D2, Dep6, Dep7. |
| **V-I8** | **Deadlock freedom / liveness (progress)** | The locking/coordination scheme cannot deadlock (no lock-ordering cycle across mechanisms — e.g. acquiring an entry lock then a shard lock in one path and the reverse in another) and makes progress (no livelock/starvation under contention); every operation completes. | **FM-4** (liveness/progress — the rule terminates / makes progress under contention) | …that the concurrency scheme is deadlock-free (consistent lock ordering / lock-free) and makes progress under contention. The liveness invariant. Spans D2, D7, and every multi-lock seam (Dep1, Dep3, Dep9, Dep11). Credit "no deadlock," "consistent lock-acquisition order," "lock-free progress." **A predicate over the whole locking design**, not any one mechanism. |
| **V-I9** | **Single-key linearizability / coherence (one consistent value per key)** | At any point, all readers (and, in a multi-node deployment, all shards/replicas) agree on a single coherent value (or definite absence) for a key — operations on a key appear to take effect in a single total order; no two concurrent readers observe two different "current" values. | **FM-2** (per-key coherence — readers/shards mutually consistent on one value) | …that each key has one coherent value visible across all readers/shards (operations linearize per key; no split-brain on a key). **Distinct from V-I3** (V-I3 = not *stale* after a write; V-I9 = no *divergence* — two readers/shards never see two different current values at once). Spans D2, D6, D7, Dep9. Credit "per-key coherence," "all nodes agree on a key's value," "operations on a key are linearizable." |
| **V-I10** | **Routing stability / key-locatability (every live key has exactly one home)** | At all times — including *during* a rehash/resize or shard-count change — every live key is locatable by **exactly one** route (old table or new, one shard), never zero (in limbo) and never two (divergent homes). The mapping from key to its storage location is always resolvable to a single definite slot. | **FM-2** (one-route well-formedness — a key with two/zero homes is a structural inconsistency) | …that every present key is always findable by exactly one route, including mid-resize — no key in limbo, no two homes. **Distinct from V-I9** (V-I9 = one coherent *value* per key; V-I10 = one definite *location/route* per key — a key with two homes can't even be coherently invalidated). The predicate the rehash seam Dep13 establishes. Spans D1, D7, Dep13. Credit "no key is ever unreachable during resize," "a key maps to one bucket/shard at a time." |
| **V-I11** | **No read returns a value past its TTL (TTL-liveness)** | A `get` never returns an entry whose TTL has elapsed — an expired entry is observationally absent on every read path, whether or not it has been physically reclaimed yet. The serve-decision honours the expiry deadline at a single check-and-act point. | **FM-1** (spanning serve-correctness coverage — the "never-serve-expired" half of TTL) | …that a get never serves an expired value (expired = treated as a miss), as a store-wide predicate — not merely that "entries have a TTL." **Distinct from V-I6** (V-I6 = expired entries don't *leak memory*; V-I11 = expired entries are never *served*). The "served-correctly" half of TTL the way V-I4 is the "bounded" half. Spans D4, V-E2, Dep10. Credit "an expired entry is never returned," "reads past TTL miss." |

> **Criteria vs mechanisms.** The invariant criteria are *spanning predicates*; the seams (`Dep`) are the
> *mechanism couplings* that must be right for the predicate to hold. They are scored separately (PLAN §1.3
> rule 2): an agent asserting the *predicate* "no stale read" (V-I3) without naming the
> *invalidation-ordering seam* (Dep5) has covered V-I3 not Dep5, and vice versa. The invariant criteria
> canonicalize by the conserved quantity (lost-update ≠ torn-read ≠ stale-read ≠ bound ≠ durable-flush ≠
> no-expired-leak ≠ stats-accuracy ≠ deadlock-freedom ≠ per-key-coherence ≠ routing-stability ≠ ttl-liveness
> — eleven genuinely distinct predicates; a design can satisfy any subset and fail another).

### 4.2 Boundary-state criteria (former Edge-cases)

A boundary-state criterion is a boundary input/state that a naive happy-path design silently mishandles —
i.e. a predicate the design must satisfy at the boundary, or the corresponding check is **insensitive**
there (passes a wrong result). Covered iff the decomposition names the same boundary condition and that it
needs a rule.

| # | Name | What it requires | FM tag (precludes) | Truth-maker (covered iff named) |
|---|---|---|---|---|
| **V-E1** | **Concurrent get + evict of the same key** | A `get(K)` interleaving exactly with `evict(K)` — the reader must either see the value or a clean miss, never a freed/garbage entry. The boundary is the *simultaneous* access-and-reclaim of one key. | **FM-3** (a happy-path lookup is insensitive to a concurrent reclaim → returns a freed/garbage entry) | …the concurrent-get-and-evict-of-the-same-key boundary and that it must be made safe (pin/guard or clean miss). (This is the *boundary state*; the mechanism coupling is Dep1/Dep10 — credit V-E1 for naming the specific simultaneous-access scenario as a case to handle.) |
| **V-E2** | **TTL expiry mid-operation / at the instant of access** | An entry whose TTL elapses *during* a get or between the expiry check and the value return: the design must define whether it is served or treated as expired at a single decision point (no serve-then-expire-then-serve flapping; the check-and-act is atomic). | **FM-3** (a non-atomic check-and-serve is insensitive to the expiry crossing mid-access → flaps / serves wrong) | …the entry-expires-mid-operation boundary (TTL crosses during an access) and a single atomic check-and-serve decision. Credit "what if the entry expires exactly as it's read." |
| **V-E3** | **Full-cache insert (insert when nothing is evictable / all entries pinned)** | A `put` into a full store where eviction can find no victim (e.g. every entry is pinned/in-use, or all equally hot): the design must define the fallback (reject the insert, block, evict-anyway-by-policy), not spin or silently overwrite. | **FM-3** (a happy-path full-insert is insensitive to the no-victim corner → spins / silently overwrites) | …the can't-evict-on-full-insert boundary and a defined fallback (reject / block / forced policy), not an infinite retry. **Distinct from Dep11** (Dep11 = the normal full-insert evict ordering; V-E3 = the *no eligible victim* corner). |
| **V-E4** | **Hot-key contention (single key hammered by many threads)** | A single key under extreme concurrent read/write contention: the design must avoid serializing the whole store (or whole shard) on one hot key, lock convoy, or per-key starvation — and must not let the hot key's recency churn corrupt the eviction policy. | **FM-3** (a happy-path design is insensitive to extreme single-key contention → serializes / convoys / starves) | …the hot-key / single-key-contention boundary and that it must not serialize the store / starve / convoy. Credit "what if one key is extremely hot." |
| **V-E5** | **Mass / synchronized expiry (expiry storm)** | A large cohort of entries sharing the same TTL deadline expiring at once: the active sweep / reclamation must not stall the store (a stop-the-world expiry pass) or cause a thundering-herd of backing-store reloads. Includes the cold-expired-keys reclamation case (the active-sweep half of D4 / V-I6). | **FM-3** (a happy-path reclaim is insensitive to a synchronized expiry cohort → stalls / stampedes) | …the synchronized-mass-expiry boundary (many entries expire together) and that reclamation must be incremental / not stall, and/or the reload stampede it triggers. Credit "expiry storm," "many keys expire at once," "background reclaim must be incremental." |
| **V-E6** | **Clock skew / non-monotonic time for TTL** | TTL decisions depend on time; in a multi-node store, node clocks differ (skew), and even on one node a non-monotonic wall clock (NTP step backward) can make an entry expire early/late or "un-expire." The design must use a defined time source (monotonic clock / logical time / agreed reference) for TTL. | **FM-3** (a TTL check insensitive to clock skew / a backward step expires early/late, passes wrong) | …the clock-skew / non-monotonic-clock boundary for TTL and a defined time source (monotonic / logical / single reference). **Foreseeable, easily-forgotten** — listed in the §2.2 bar. Credit "clock skew across nodes affects TTL," "use a monotonic clock for expiry." |
| **V-E7** | **Oversized value (cost > total capacity)** | A `put` of a value whose byte-cost exceeds the *entire* store capacity: a naive evict-until-under-bound loop would evict everything and still not fit (or spin). The design must define a rule — reject the insert, or admit-and-bypass (don't cache), or a documented policy — never an evict-everything / infinite-retry loop. | **FM-3** (the evict-until-under-bound loop is insensitive to a can't-ever-fit value → evicts everything / spins) | …the value-larger-than-capacity boundary and a defined rule (reject / don't-cache / stated policy), not an unbounded eviction loop. **Distinct from V-E3** (V-E3 = nothing *evictable*; V-E7 = the *value itself* can't fit even an empty store). Ties to Dep7's cost-aware loop. Credit "what if a value is bigger than the whole cache." |
| **V-E8** | **Hash collision / key identity by equality** | Two distinct keys with the same hash must remain distinct entries: identity is decided by **equality**, not by hash alone. A naive map keyed on hash only would cross-evict or overwrite one key with another. The collision-resolution (chaining/probing) must use full key equality. | **FM-3** (a hash-only identity check is insensitive to a collision → cross-evicts / overwrites a distinct key) | …the hash-collision boundary and that equality (not hash) decides key identity (colliding keys don't overwrite / cross-evict each other). Credit "two keys can hash the same and must stay separate," "compare keys by equality on collision." |
| **V-E9** | **TTL-value boundary conventions** | Boundary TTL values — TTL = 0, negative, absent (eternal / no-expiry), TTL == now, and far-future — each need a **stated convention** (e.g. 0/negative = don't cache or immediate-expire; absent = never expires), not accidental behaviour from arithmetic. | **FM-3** (TTL arithmetic is insensitive to boundary values → accidental behaviour passes as correct) | …the TTL-value boundary cases (zero / negative / no-TTL / now / far-future) and a stated convention for each. **Distinct from V-E6** (V-E6 = the clock/time *source*; V-E9 = the *TTL value* conventions). Credit "TTL=0 means…," "a missing TTL means eternal." |
| **V-E10** | **Idempotent delete of an absent / already-evicted key** | `delete(K)` for a key that is absent (never inserted, already evicted, or already expired) must be a clean no-op: no negative size accounting, no spurious flush of a non-existent dirty entry, no spurious invalidation broadcast. | **FM-3** (a happy-path delete is insensitive to the absent-key case → negative size / spurious flush passes) | …the delete-of-absent-key boundary and that it is an idempotent no-op (no negative size, no spurious flush/invalidate). Credit "deleting a missing key does nothing / is safe to repeat." |
| **V-E11** | **Re-set / update-in-place accounting delta** | Overwriting an existing key must adjust size accounting by the **delta** (−old_cost + new_cost), not add the new cost as if a fresh insert (which double-counts and breaks the bound); the old value is freed/flushed-if-dirty, and TTL/recency are refreshed per stated policy. | **FM-3** (an insert-as-fresh accounting is insensitive to the existing-key case → double-counts, silently breaks the bound) | …that updating an existing key adjusts size by the delta (not +new), frees/flushes the old value, and refreshes metadata — no double-count. **Distinct from Dep7** (Dep7 = accounting *triggers* evict; V-E11 = the *update-delta* boundary that keeps accounting correct). Credit "re-putting a key updates size by the difference, doesn't double-count." |

### 4.3 Defect-coupling criteria (former Failure-modes — only those with NO `Dep` twin)

Phrased as **concrete coverable claims** (PLAN §1.3 rule 4), never adjectives. Each names a specific defect
coupling AND its resolution; covered iff the decomposition names the same coupling and a guard.
**One-defect-one-place (PLAN §1.3 rule 1):** a defect-coupling is kept here ONLY if it has **no `Dep`-seam or
invariant-criterion twin**. A defect that shares the *same pair, same falsifier, same fix* as an existing
seam/invariant is **not** a separate item — the seam/invariant already carries it. The obvious concurrency
failures are **deliberately NOT listed** because they are already carried: *lost update* = V-I1, *torn read*
= V-I2, *stale read* = Dep5/V-I3, *evict-just-set-key* = Dep1/Dep11, *double-free on evict* = Dep2,
*dirty-entry dropped* = Dep3, *bound exceeded* = V-I4/Dep7, *memory leak from expired* = V-I6, *stats drift* =
V-I7/Dep6, *deadlock* = V-I8. What remains here are couplings with **no** seam/invariant twin, each pinned to
a canon §4 FM class.

| # | Name | FM tag (precludes) | What it requires (coupling + guard) | Truth-maker (covered iff named with a guard) |
|---|---|---|---|---|
| **V-F1** | **Cache stampede / thundering herd on miss** | **FM-4** (propagation under concurrency: N concurrent misses fan into one backing load) | When a hot key is missing (cold or just-evicted/expired), many threads simultaneously miss and all hit the backing store to recompute/reload the same key → backing overload + duplicated work. **No `Dep`-twin** (it is not a two-mechanism data-coupling; it is N concurrent readers funneling to one backing load). Guard: single-flight / request coalescing / a lock per key on miss so one loads and the rest wait. | …that a simultaneous miss on a hot key floods the backing store (stampede) AND a coalescing/single-flight guard (one loads, others wait). Credit "thundering herd on cache miss," "dogpile," "single-flight." Distinct from V-E4 (V-E4 = hot key *present* and contended; V-F1 = hot key *absent* and refilled by many at once). |
| **V-F2** | **Consistent-looking-but-wrong: silent invalidation miss (false PASS)** | **FM-3** false-PASS | An update path that *appears* to invalidate (the invalidation code runs) but, on some interleaving or some shard/replica, fails to actually evict the stale copy — the cache then serves a stale value while every local check says "consistent." "Invalidation ran" does NOT prove "no stale copy survives." **No `Dep`-twin** (Dep5/Dep9 are the *mechanism*; V-F2 is the *false-PASS residual* — the invalidation present but ineffective on a path). Guard: an independent consistency check / read-repair / TTL backstop so a missed invalidation self-heals. | …that an invalidation can *appear* to succeed yet leave a stale copy somewhere (a missed/ineffective invalidation on a path), AND a backstop (read-repair / TTL ceiling / version check) beyond "we called invalidate." Credit any concrete "invalidation can silently miss and a guard is needed" — **no GFSO vocabulary required**. **Mirrors the GFSO faithfulness residual** — the hardest to articulate. |
| **V-F3** | **Shutdown / crash loses unflushed write-back data (no drain channel)** | **FM-7** (no feedback/recovery channel) — *the one runtime mode a static criterion does carry, see §7* | On process shutdown (or crash), dirty write-back entries that were never flushed are lost — there is no channel that drains the write-back buffer on shutdown (or no journal to recover it). **No `Dep`-twin** (Dep3/Dep4/V-I5 cover flush-on-*reclaim*; V-F3 is flush-on-*shutdown/crash* — a different trigger, the lifecycle-end channel). Guard: a shutdown drain / WAL / periodic flush bound so the data-loss window is bounded. | …that process shutdown or crash can lose unflushed write-back data AND a drain-on-shutdown / WAL / bounded-flush guard. The discriminator is *lifecycle-end / crash*, distinct from the per-entry reclaim flush (Dep3/Dep4/V-I5). Credit "flush dirty entries on shutdown," "bounded data-loss window for write-back," "WAL for recovery." |
| **V-F4** | **ABA on a lock-free path (CAS succeeds on a recycled identical bit-pattern)** *(conditional — only if D2 is lock-free)* | **FM-3** false-PASS (on the lock-free substrate) | If the concurrency control (D2) is **lock-free / CAS-based**, a compare-and-swap can succeed against a pointer/value that was freed and recycled to an *identical* bit-pattern (the ABA problem) — the CAS *appears* valid but operated on a stale generation, corrupting the structure. **No `Dep`-twin** (`Dep`-seams are mechanism-pair couplings; V-F4 is a false-PASS *residual of the CAS primitive itself*). Guard: tagged/versioned pointers, hazard pointers, epoch-based reclamation, or double-width CAS. **Vacuous if D2 is lock-based** (a lock-only design need not name it). | …**only if the design chooses a lock-free/CAS scheme**, that ABA can make a CAS falsely succeed on recycled memory AND a guard (version tag / hazard pointer / epoch reclamation). Scope-gated: credit as covered (or N/A) for a purely lock-based design. Credit "ABA problem," "tagged pointers / hazard pointers for lock-free reclamation." |

> **Defect-coupling discipline.** Only four defect-coupling criteria survive (one of them conditional)
> because T07 is *seam-and-invariant dense*: most concrete failures ARE the negation of a seam (`Dep`) or
> invariant criterion and are scored there, not double-counted (PLAN §0 residual concern: F-vs-X
> double-counting on T07 explicitly flagged — enforced here). V-F1 (stampede), V-F2 (silent-invalidation
> false-PASS), V-F3 (shutdown data-loss channel) and V-F4 (ABA on the lock-free path) are the couplings with
> **no** seam/invariant twin: a different trigger (N-readers-to-one-load; an *ineffective* present
> invalidation; a lifecycle-end / crash; a recycled-bit-pattern CAS on the lock-free substrate) than any
> single mechanism-pair seam. **V-F4 is scope-gated** — it bites only if D2 is lock-free and is vacuous
> (auto-covered / N/A) for a lock-based design. FM-1 (insufficiency) and FM-2 (incompatible child criteria)
> couplings are carried by the `Dep`-seams and invariant criteria, not duplicated as a defect-coupling; FM-6
> ("D not determinable at start") does not arise — the mechanisms are determinable from the spec. **V-F3 is
> the one criterion naming an OPERATIONAL mode (FM-7) at design time** — see §7.

## 5. NEGLECTED — declared scope-exclusions (each with its `predictability_verdict`, STD-1/2/3)

> Canon §5.1 STD-1: a decomposition **without** NEGLECTED is incomplete by definition — the auditable "no
> silent skip" record. Each entry carries a **`predictability_verdict`** (STD-2 §5.2: predictability is
> presumed; the *declarer* bears the burden of proving safe-to-skip) and an `invalidation_condition` (when
> the exclusion flips in-scope). Only assumptions whose **omission would otherwise be a foreseeable defect**
> (FM-1.b, §5.2 / §4.2: a predictable external risk left without a mitigating child) — assessed-and-declared-
> skipped, not a dumping ground (PLAN §0 N-inflation caution): an exclusion is listed only if omitting it
> makes an *external* failure look like a cache-logic bug.

| # | Excluded assumption | `predictability_verdict` (why safely excluded) | Truth-maker (covered iff the decomposition declares…) |
|---|---|---|---|
| **N1** | **Durability of the backing store is assumed** | The cache *fronts* a backing store and treats it as durable; designing the backing store's own durability/replication/fsync guarantees is downstream of the cache logic. Declared boundary: if the backing store loses data, that is a named external dependency, not a cache-consistency defect. Invalidation: if the backing store is *not* durable (cache is the system of record), then V-I5/V-F3 durability becomes in-scope as a primary requirement. | …that the backing store's durability is assumed / out of scope (the cache relies on it being durable). |
| **N2** | **Network partition / multi-node consensus handling is out of scope** | The design specifies *single-node* concurrency and the *mechanism* of cross-node invalidation (Dep9), but full partition-tolerance / consensus / split-brain *resolution* (Raft/Paxos, quorum reads) is a distributed-systems layer beyond the store logic. Declared boundary: behaviour under a network partition (CAP trade-off, conflict resolution) is a named exclusion. Invalidation: if strong cross-node consistency under partition is required, a consensus/quorum mechanism becomes in-scope (and V-I9 strengthens to a partition-tolerant guarantee). | …that network-partition handling / cross-node consensus / split-brain resolution is out of scope (the multi-node case is the invalidation *mechanism*, not full partition tolerance). |
| **N3** | **Underlying memory allocator / GC behaviour is assumed sound** | The design assumes allocation/free (or the runtime GC) is correct and reasonably prompt; designing a custom allocator, defragmentation, or GC-pause mitigation is a runtime concern below the cache logic. Declared boundary: allocator fragmentation or GC pauses are an external/runtime property, not a cache-logic defect — unless the design *chooses* an arena it then owns. Invalidation: if memory must be managed manually (off-heap / custom arena), fragmentation and reclamation timing become in-scope. | …that the memory allocator / GC is assumed sound (custom allocation / fragmentation / GC-tuning out of scope). |
| **N4** | **Value immutability vs defensive-copy is a stated choice** | Whether cached values are **immutable** (safe to share by reference — lock-free reads see a stable snapshot) or **mutable-and-defensively-copied** on get/put must be a *declared* assumption, because it drives the whole read-safety story (Dep1/Dep10 pinning, V-I2 torn-read, V-I7). If callers can mutate a shared value in place, "no torn read" is silently broken outside the cache's control. | …that value immutability (share-by-ref) vs defensive-copy is a stated design choice / assumption. Invalidation: if values are mutable and shared without copy, in-place caller mutation becomes an in-scope defect (re-introduces torn reads the cache can't prevent). Credit "assume values are immutable," "copy on get/put." |
| **N5** | **Value serialization / wire format out of scope; cost = a named size function** | The encoding of values for the backing store (serialization / wire format) is downstream of the cache logic and out of scope; but the cost accounting (Dep7) depends on a **size function** that must be *named* (e.g. `sizeof`/weigher), not assumed free. Declared boundary: how values are serialized is an external concern; the cost metric is an explicit pluggable function. | …that value serialization / wire format is out of scope AND that byte-cost is computed by a named/explicit size function (not assumed free). Invalidation: if the backing protocol or a non-trivial weigher is part of the spec, it becomes in-scope. Credit "serialization is out of scope," "size is given by a weigher/size-fn." |

> **N-discipline (STD-1/2/3).** Each N is an assumption whose *failure* would otherwise be misattributed to
> the cache (omitting N1 makes "backing store lost data" look like the cache dropped a write; omitting N2
> makes "partition split-brain" look like a cache-consistency bug; omitting N3 makes "allocator fragmentation
> / GC pause" look like a cache memory leak / stall; omitting N4 makes "caller mutated a shared value" look
> like a cache torn-read bug; omitting N5 makes "serialization cost / weigher wrong" look like a
> bound-accounting defect). Each carries a `predictability_verdict` and an invalidation trigger. **Five**
> assumptions whose omission is a foreseeable *misattribution* (N1 backing durability, N2 partition/consensus,
> N3 allocator/GC, N4 value-mutability, N5 serialization/size-fn). Excluded from N (handled in-band, not new
> exclusions): "single data center / no replication" (covered by N2 + Dep9), "fixed key/value size" (an
> E-style boundary, not an external dependency), "no hardware failure" (covered by N1/V-F3 durability
> framing). Adding those would be N-inflation (PLAN §0 caution).

## 6. Hardest / most-easily-forgotten seams (flag for scorer)

> Not a category — a scorer pointer at the highest-signal `Dep` edges.

- **Dep1 / Dep10 — eviction (or expiry) of an entry concurrently being read/written** (use-after-free; the
  get-vs-reclaim handoff). The single most-forgotten T07 interaction: a parts-list names "eviction" and "the
  read path" as components but drops the *race between them on one entry*. (Dep1 = the policy picking a live
  victim; Dep10 = the lookup-vs-reclaim of one specific key — scorer may credit one if an agent collapses
  them.)
- **Dep3 — evicting a dirty write-back entry must flush, not drop.** Eviction and write-back are designed
  independently; the flush-on-evict edge is the classic dropped seam (a silently lost write).
- **Dep4 — TTL expiry of a dirty entry (expiry vs flush).** Twins neither eviction seam; the expiry path
  reclaiming unflushed data is the lost-write nobody draws.
- **Dep2 — expired-vs-evicted reclamation of the same entry (reclaim exactly once).** Two reclaim paths
  racing on one entry → double-free or both-skip leak.
- **Dep8 — sharding vs the *global* memory bound (per-shard budgets + skew).** Sharding is named for
  parallelism; its interaction with the *global* boundedness invariant under hot-shard skew is routinely
  dropped, silently breaking V-I4.
- **Dep13 — rehash / resize × concurrent ops (key-in-limbo during migration).** The map is sized once on
  paper; the live grow/shrink race (a key migrating between old and new tables, a set lost on a moved bucket,
  a half-rebuilt table read) is the classic dropped dynamic-resize seam. Establishes V-I10 (routing
  stability).
- **Dep14 — delete × in-flight load-through → resurrection.** A delete racing a `getOrLoad` lets the loader
  write back a value the delete already removed; the key silently comes back. Needs a version/generation CAS,
  distinct from single-flight (V-F1). Silent — every local check passes.
