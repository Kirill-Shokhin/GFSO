## Task `T` (verbatim, PLAN §3 T06)

> Design the operating regime that continuously keeps a production data estate **recoverable** within stated
> RPO/RTO targets: which data stores and state are in scope, the backup cadence and retention tiers, the
> restore/failover procedure, periodic restore-drills, and the integrity/freshness checks that keep the
> regime viable over time. Specify the rules so a recovery would actually succeed. Decompose this task.

**Shape.** **Hub-and-spoke, cyclic-maintenance / viability goal.** A central **recovery catalog / runbook**
is the hub; each spoke (a data store, a secret/credential set, a config source, an external dependency) must
be enrolled, and the hub-invariant — *everything required to reconstitute the service within RPO/RTO is
captured and provably restorable* — couples them on every cycle. This is **NOT** a one-shot achievement tree:
there is no terminal "backed up, done" state. The estate drifts (new stores, schema/version changes,
rotated secrets), so the regime is a **sustained loop** — *enroll/scope → back up → verify integrity →
periodically restore-drill → measure RPO/RTO → reconcile drift → repeat* — plus the **standing capabilities**
(scoping, cadence/retention, restore procedure, failover, isolation) the loop draws on. A correct
decomposition is graded as a maintained invariant ("a recovery within RPO/RTO would actually succeed, over
time"), re-generating corrective sub-tasks each cycle — not a graph cycle in the plan (the dependency graph
stays a DAG; the *regime* is what cycles). The richest content (PLAN, engineered) is **NEGLECTED** (declared
scope-exclusions / silent assumptions whose failure makes a *documented* restore fail in practice — the
dominant, load-bearing category) and the **defect-coupling criteria** (the silent-restore-failure modes
those exclusions correspond to).

**Single meta-level.** This decomposes the **DR-regime logic and assumption-frontier** at one level: what is
in scope, how backups are taken/retained/isolated, how a restore/failover runs, how the regime proves
itself (drills, integrity), how RPO/RTO are measured, and which assumptions are *declared* out of scope. It
does NOT spawn org sub-projects (build the storage platform, staff a DR team, run a company-wide DR
exercise). Components are capabilities/passes of one regime design, not departments or tickets. **Who
declares a disaster / authorizes a failover** (the call to cut over, accept data loss, or invoke DR) is the
**orthogonal authority plane** `Del` — see §3; it is not a decomposition node. (Consequence: unlike a
*static* single-meta-level decomposition, this is an inherently **runtime / cyclic** regime — so the
OPERATIONAL failure modes {FM-5,6,7} are genuinely in scope and covered, not N/A-static; see §7.)

## 1. Subtasks `D` — the standing capabilities + the loop passes

> `D` = the children of the decomposition (canon §2.2: `D: T → P(T)`, a DAG).

Each subtask is a **separable capability or loop-pass of the regime** with its own pass/fail criterion on
its *output state* (a backup of store X exists no older than the cadence; a restore-drill of X reproduces a
working store; the RPO measured on the last drill ≤ target), **not** a self-report ("backups are
configured", "we have a DR plan"). Per Constitution Ст. II.1.a a criterion is a predicate over the *outcome*
("a restore of store X into a clean environment passes its application health probe"), never "X is set up".

| # | Name | What it requires | Truth-maker (covered iff the decomposition names…) |
|---|---|---|---|
| **D1** | **RPO/RTO objective + scope enrollment (the recovery catalog = hub)** | Define the recovery objectives — **RPO** (max tolerable data loss) and **RTO** (max tolerable downtime) — and enumerate **which data stores and stateful components are in scope** (every DB, object store, queue/stream, config source, secret store, and external state needed to reconstitute the service). Part of scoping is classifying each enrolled item as **source-of-truth (must be backed up)** vs **derived/secondary (rebuildable from a source — search index, cache, materialized view, read-replica)**: a derived store *may* be excluded from backup **iff** its rebuild is declared and its rebuild-time is bounded (the Dep10 seam). This is the hub: the catalog of "everything that must come back, and how fresh / how fast." Everything downstream measures against it. | …a pass that *defines RPO/RTO and the in-scope inventory* — the recovery objectives **and** the enumerated list of what must be recoverable, **including the derived-vs-source-of-truth classification** (which stores are backed up vs rebuilt-from-source). Credit "set RPO/RTO targets and a catalog/inventory of stores to protect," "decide what's in scope to recover," "rebuild the search index/cache from the DB rather than backing it up." The hub. An agent that names backups but never states *what must be recoverable / how fresh / how fast* has not covered D1. |
| **D2** | **Backup mechanics: type + cadence (capture)** | Take the backups: choose backup **type** per store (full / incremental / differential / continuous-log / snapshot / replication-as-backup) and a **cadence** sized so the worst-case data age ≤ RPO. Includes app-consistent vs crash-consistent capture per store. The *capture* pass — what is actually written to backup storage and how often. | …a pass that *takes backups at a defined frequency/type* sized to RPO (full/incremental/snapshot/continuous, scheduled). Credit "schedule daily/continuous backups," "snapshot the volumes," "log-ship / PITR." Distinct from D1 (the target) and D3 (where it lives / how long). |
| **D3** | **Storage, retention tiers & isolation (where backups live)** | Store the backups with a **retention policy** (tiered: short-term fast-restore + long-term/compliance archive, with expiry) and **isolation** from the primary's failure domain — a separate account/region/medium, ideally **immutable / air-gapped / WORM** so the disaster (or ransomware) that hits primary cannot also destroy the backups. The standing capability that makes a backup *survive the event it protects against*. | …a pass that *retains backups over tiers* **and** *isolates them from the primary failure domain* (separate region/account, immutable/WORM/air-gap, ransomware-resistant). Credit "retention policy with tiers + expiry," "store backups in a separate region/account, immutable." Naming only "keep backups" without isolation covers part of D3; the isolation half is load-bearing (see V-I3, V-F4). |
| **D4** | **Restore / failover procedure (the runbook = recovery path)** | The step-by-step procedure to bring the service back: restore each store, re-create/restore config & secrets, fail over to the recovered environment, in a defined **order** (dependencies first), validated by an application-level health check. The MTTR/RTO-bearing pass — *the recovery actually executed*. | …a pass that *defines how to restore/fail-over* — an ordered runbook to reconstitute the service (restore stores, rewire config/secrets, cut over, verify health), not just "we have backups." Credit "documented restore/failover runbook," "recovery procedure." Distinct from D2 (capture) and D6 (drilling it). |
| **D5** | **Integrity / freshness / monitoring checks (is the regime healthy now?)** | Continuously verify each backup is **valid and current**: backup-job success monitoring, integrity/checksum verification, freshness alerting (last successful backup of store X older than cadence ⇒ alert), and catalog-vs-reality reconciliation (every in-scope store has a recent good backup). The *detect* pass that catches a silently-broken backup *before* a disaster reveals it. | …a pass that *checks backups are succeeding, valid, and fresh* — job-success monitoring, checksum/integrity verification, alert on missed/stale backup, catalog reconciliation. Credit "monitor backup jobs and alert on failure/staleness," "verify backup integrity." Distinct from D6 (full restore-drill) — D5 is the cheap continuous check, D6 is the periodic proof. |
| **D6** | **Periodic restore-drill / DR exercise (the proof pass)** | Periodically **perform an actual restore** (into a clean/isolated environment) and a failover exercise, measure the **achieved** RPO/RTO against target, and confirm the restored service passes an application health check. The pass that converts "we have backups" into "we can recover" — the cyclic act that makes this a maintenance regime. A backup never test-restored is a hypothesis, not a capability. | …a pass that *periodically restores for real and measures the outcome* — scheduled restore-drills / DR game-days that verify a recovery actually succeeds and measure achieved RPO/RTO. Credit "test restores regularly," "run DR drills and measure recovery time." The follow-*through* (an actual measured restore, not a checklist review) is the truth-maker. **Most-forgotten D** — a parts-list stops at "we take backups." |

> **Note on the loop vs the standing capabilities.** D2 (capture) → D5 (continuous check) → D6 (periodic
> drill) are the *take→verify→prove* passes of the running loop; D1 (objectives+scope), D3
> (retention+isolation), D4 (restore procedure) are the *standing capabilities* the loop draws on. Both are
> required: a regime with flawless capture (D2) but no restore-drill (D6) holds backups that may never
> restore; a regime with a perfect runbook (D4) but no isolation (D3) loses both primary and backups to one
> ransomware/region event. Each is ONE component — splitting "back up the estate" into per-store sub-projects
> collapses to its parent `D` (single meta-level; canon §2.2 non-redundancy). **D6 ≠ D5:** D5 is the cheap
> "the backup job ran and checksums" signal; D6 is the expensive "an actual restore reproduces a working
> service and meets RPO/RTO" proof — a backup can pass every D5 check and still fail D6 (see V-F1).

## 2. Dependencies `Dep` — cross-subtask edges as explicit, separately-falsifiable `Dep` edges

> `Dep` = the canon primitive (§2.2): an acyclic relation on `T × T`; `(tₐ, tᵦ) ∈ Dep` iff `criteria(tᵦ)`
> references the output of `tₐ` (with coherence `deadline(tₐ) < deadline(tᵦ)`). **Each `Dep` edge is a
> criterion of a child that references a sibling's output — the glue** — and carries its **own** falsifying
> truth-maker (the anti-mock condition), not "these parts relate" prose.

Each seam is a REAL edge: the *output of one named component feeds the input/state of another*, and the edge
carries its **own** falsifying criterion — not "these parts relate" prose (Constitution Ст. II.5 anti-mock).
T06's seams are **spoke→hub enrollment** edges (every in-scope item must be captured, restorable, and
restore-*ordered*) and **objective-binding** edges (cadence ⊢ RPO, restore+failover time ⊢ RTO, drill ⊢
backup-validity). A seam is covered iff the decomposition names the **same shared artifact** between the
**same two named components** with its breakage.

| # | Name | Pair (source ↔ consumer) | What the edge requires | Truth-maker (covered iff named with its breakage) |
|---|---|---|---|---|
| **Dep1** | **Cadence ⊢ RPO (backup frequency meets the loss target)** | D1 (RPO) → D2 (cadence) | The backup cadence / continuous-replication interval must be set *from* the RPO: worst-case data age between backups ≤ RPO. A cadence chosen independently of RPO silently violates the loss objective. Shared artifact = the RPO target ↔ the schedule interval. | …that backup frequency is *derived from RPO* (interval ≤ tolerable loss), not picked arbitrarily — RPO breach = data older than target at restore. Credit "back up often enough to meet RPO," "RPO drives cadence / continuous-log for low RPO." |
| **Dep2** | **Restore+failover time ⊢ RTO (recovery path meets the downtime target)** | D1 (RTO) → D4 (restore/failover) | The restore+failover procedure must complete within RTO: total time to restore all stores in order + cut over ≤ RTO. A runbook whose measured execution time exceeds RTO fails the objective even if every step works. Shared artifact = the RTO target ↔ the runbook's end-to-end time. | …that the restore/failover procedure is *bounded by RTO* (measured recovery time ≤ downtime target), and that a too-slow-but-correct restore still breaches. Credit "recovery must complete within RTO," "size the restore path / warm standby to meet RTO." |
| **Dep3** | **Drill ⊢ backup validity (only a tested backup is a known-good backup)** | D6 (drill) → D2/D3 (the backup) | The restore-drill is the truth-maker for a backup's restorability: a backup is "good" only once a restore of it has succeeded. An untested backup carries no validity claim; the drill's outcome (restored service health, measured RPO/RTO) *certifies* the capture+storage. Shared artifact = the specific backup ↔ its successful restore. | …that backups are *validated by an actual restore* — restorability is established by drilling, not by the backup job reporting success. Credit "a backup is only proven by a successful test-restore," "untested backup = unknown." The **GFSO faithfulness↔contact** core in domain dress (a backup's restorability is `[e∈S]`, opened only by contact = the drill). |
| **Dep4** | **Integrity check ⊢ restore success (a corrupt backup fails the restore)** | D5 (integrity) → D4/D6 (restore) | Integrity/checksum verification must catch a corrupt/incomplete backup *before* it is relied on, so a restore does not silently start from corrupt data. The check's output (valid/invalid) gates whether the backup is a restore candidate. Shared artifact = the backup bytes ↔ the integrity verdict consumed by restore. | …that integrity verification *gates* restore (a corrupt/partial backup is detected and not used), so restore doesn't begin from bad data. Credit "verify checksums so we don't restore corruption," "detect corrupt backups before relying on them." Distinct from Dep3 (Dep3 = does it restore *at all*; Dep4 = is the *content* sound). |
| **Dep5** | **Cross-store restore ordering (dependencies restored before dependents)** | D4 ↔ enrolled stores (D1) | Restoring the estate has a **dependency order**: identity/secret store and config before the apps that read them; schema/DB before the services that query it; a queue/stream's consumers after its backing store. Out-of-order restore yields a service that can't start or reads inconsistent state. Shared artifact = the restore-order graph over enrolled stores. | …that restore follows a *dependency order* across stores (secrets/config/identity → data → app; no dependent restored before its prerequisite). Credit "restore in dependency order," "bring up the DB/secrets before the app." A spoke→hub coupling unique to hub-and-spoke recovery. |
| **Dep6** | **Point-in-time consistency across stores (restore to a coherent moment)** | D2 (capture) ↔ D4 (restore) across multiple stores | When the service spans multiple stores (DB + object store + cache + queue), the restore must land them at a **mutually consistent point in time** — not each store at its own latest backup. Independent per-store recovery points yield referential inconsistency (an order row pointing at an object that wasn't backed up yet). Shared artifact = a coordinated recovery point / consistency group across stores. | …that a multi-store restore must reach a *consistent recovery point* across stores (coordinated snapshots / consistency group / global PITR), not each store independently. Credit "consistent point-in-time across all stores," "snapshot the dependent stores together." **Hardest seam** — easily missed when each store is backed up well in isolation. |
| **Dep7** | **Drill ⊢ regime update (measured shortfall feeds back the catalog/cadence)** | D6 (drill) → D1/D2/D4 (regime) | A drill that *measures* an RPO/RTO shortfall, a missing store, or a broken runbook step must **feed back** and change the regime (re-scope the catalog, tighten cadence, fix the runbook) — and the catalog must track estate **drift** (newly-added store enrolled, retired store removed). A drill whose findings never update D1–D4 leaves the regime stale and the same recovery fails again. Shared artifact = the drill's measured gap ↔ the catalog/cadence/runbook update. | …that drill findings (and estate drift) *update the regime* — failed drill ⇒ fix cadence/scope/runbook; new store ⇒ enrolled; this is what closes the maintenance loop. Credit "drill findings feed back," "keep the catalog in sync as the estate changes." The seam that makes it a *maintained*, not a one-time, regime. |
| **Dep8** | **Restore env parity ⊢ restore success (restore into a usable target)** | D4 (restore) ↔ target environment (D1 scope) | The restore must land in an environment that can actually *run* the service: compatible engine/OS/instance versions, network/DNS/IAM wiring, capacity, and (if cross-region) a region able to host it. A backup restored into an incompatible or unprovisioned target fails even though the data is perfect. Shared artifact = the recovery environment spec ↔ the restored artifact's requirements. (The *environment/engine* parity is Dep8; the *data's own schema-version* compatibility with the current app code is the distinct V-E6 boundary — do not fold them.) | …that the restore target must be *provisioned and compatible* (version/engine/network/capacity parity; cross-region target exists) for restore to succeed. Credit "restore into a working environment," "ensure the recovery site can host the restored service." Distinct from Dep2 (time) — Dep8 is *can it run at all there* — and from V-E6 (data schema-version skew). |
| **Dep9** | **Failover ⊢ failback (the return leg re-syncs DR-side writes with no loss)** | D4 (failover) ↔ D4 (restore-to-primary) / primary store | Failover is only half the lifecycle: once the disaster is over, the service must **fail back** to the (rebuilt/recovered) primary. Writes accepted *at the DR site while it was live* must be **re-synced back** to primary with no loss before cutting back — a site you can fail *to* but not *back from* is a one-way trap, and the delta written during DR is silently dropped if failback isn't designed. Shared artifact = the set of DR-side writes ↔ their reconciliation into primary. | …that **failback** is designed as the return leg — re-sync the writes taken at the DR site back to primary (delta replication / reverse-sync) with no loss, then cut back — and that failover without a failback path is a one-way trap. Credit "fail back to primary once recovered and re-sync the DR writes," "reverse-replicate before cutting back." Distinct from D4-forward-failover and Dep2 (Dep9 is the *return* leg's data-reconciliation, not the forward recovery time). The most-forgotten leg of the failover lifecycle. |
| **Dep10** | **Derived-store rebuild ⊢ RTO (rebuilt secondary ready within the downtime target)** | D1 (derived class) → D4 (restore) / D1 (RTO) | A store classified **derived/rebuildable** (and therefore not backed up, per D1) must be **rebuilt from its source within RTO**: re-indexing, cache-warming, or replaying from the source-of-truth all consume recovery time, and a derived store whose rebuild exceeds RTO must instead be backed up (or the RTO renegotiated). Shared artifact = the derived store's declared rebuild path ↔ its rebuild-time vs RTO budget. | …that a **derived/secondary store's rebuild-from-source time is counted against RTO** — rebuild it within the target, else back it up. Credit "the search index is rebuilt from the DB and that rebuild must fit RTO," "re-warming the cache counts against recovery time." Distinct from Dep2 (Dep2 = restoring *backed-up* stores; Dep10 = *rebuilding* the deliberately-un-backed-up ones) and from D1 (D1 *classifies* derived vs source; Dep10 *binds the rebuild to RTO*). |

> **Anti-mock note.** Each seam references a concrete *shared artifact* — the RPO target↔schedule (Dep1), the
> RTO target↔runbook time (Dep2), the backup↔its successful restore (Dep3), the backup bytes↔integrity verdict
> (Dep4), the restore-order graph (Dep5), the coordinated recovery point (Dep6), the drill gap↔regime update
> (Dep7), the recovery-env spec↔restored-artifact requirements (Dep8), the DR-side writes↔their failback
> reconciliation (Dep9), the derived-store rebuild path↔its rebuild-time-vs-RTO budget (Dep10). A forgotten
> seam here is an objectively identifiable defect (the restore measurably fails or violates an objective), not
> a nominal pair. None collapse: Dep3 (does it restore *at all*) ≠ Dep4 (is the *content* sound) ≠ Dep6 (are
> *multiple stores* mutually consistent) ≠ Dep8 (can the *target* run it) ≠ Dep9 (can it *return* to primary
> without losing DR-side writes) ≠ Dep10 (is the *rebuilt* derived store ready in time) — different shared
> artifacts and falsifiers (canon §2.2 non-redundancy).

> **FM mapping for `Dep`.** A forgotten/violated `Dep` edge is an **FM-1** defect (a spanning integration
> criterion — the glue — not written / not covered; §4.2 FM-1 insufficiency, §18.10 *hole-i*) when it is a
> coverage hole, and an **FM-2** defect (criteria of two children incompatible / a relational defect at fixed
> composition; §4.2 FM-2) for the shared-artifact seams whose breakage is a mutual-satisfiability conflict
> (Dep5, Dep6, Dep8 — cross-store ordering / consistent-point / target-parity constraints that cannot be
> jointly satisfied without coordination). For a **maintenance** regime the objective-binding and feedback
> seams additionally touch the **operational** axis: Dep7 (drill→regime-update — the catalog tracks estate
> drift and drill findings re-arm the regime) is the **FM-7** feedback channel **and** carries **FM-5**
> (currency — the regime is updated as the estate drifts so it does not run on a stale catalog); Dep1/Dep2/
> Dep10 are objective-binding edges whose unbound state is a **FM-6** determinability concern (a cadence/
> restore-path whose attainability against RPO/RTO was never established). The §7 FM table records this. Per
> one-defect-one-place, a seam's failure is scored **here as a `Dep` item**, never re-listed as a separate
> criterion.

## 3. Authority `Del` — disaster-declaration / failover authority, orthogonal note (NOT scored)

> **`Del` is the canon "who" axis** (§2.3: `Del: T → A`, exactly one agent per task) — **orthogonal** to the
> decomposition plane `{D, Dep, V}` and **NOT scored** as a decomposition item. This is a plane-separation
> note, NOT a NEGLECTED exclusion, NOT a criterion, NOT a completeness hole.

Invoking DR is a high-stakes call: **who declares a disaster**, **who authorizes the failover / cutover**
(accepting the data loss up to RPO and the downtime), and **who calls the recovery complete** is an
**authority/control** question. This is the GFSO **orthogonal authority plane**, not a decomposition node.

**Why authority is orthogonal (derived, not asserted).** A GFSO decomposition is graded on its
artifact/behaviour-predicates and how the work splits ({D, Dep, V}) — predicates on *what must be true about
the regime's behaviour* and *how the work splits*. "Who has the authority to declare the disaster / authorize
the failover" is **not** a predicate over the produced recoverability: the estate is kept recoverable, and a
recovery succeeds or fails to meet RPO/RTO, identically whether the failover is authorized by an on-call
lead, a DR coordinator, or an automated policy. Declaration/authorization is a property of the
**delegation/authority assignment** (in GFSO's primitives, the **Issuer/`Del`** edges — who sets criteria
and authorizes), not of any decomposition node. "Someone declares the disaster and authorizes the cutover"
is exactly the domain's boundary-term for the **authority-assignment plane** the GFSO protocol carries
structurally via `Del`, not a node *within* the regime decomposition.

**Consequences for scoring (scorer rules):**
- A decomposer is **NOT penalized** for omitting "who declares the disaster / authorizes failover" as a
  decomposition item — there is no `D`/`Dep`/`V`/NEGLECTED slot it belongs in. (The *restore/failover
  procedure* D4 and the *runbook ordering* Dep5 ARE decomposition items — they are *how the recovery runs*,
  behaviour; the *authority to invoke it* is the orthogonal plane. Do not conflate them.)
- **Force-fitting failover authority into a criterion or NEGLECTED item is a category error.** An agent who
  writes "the DR coordinator has the authority to declare a disaster and authorize cutover" earns no
  criterion/NEGLECTED credit and loses none — it is a correct statement in a different plane.
- This is **plane-separation**, not a NEGLECTED scope-exclusion (it is *carried structurally by the
  protocol's Issuer/`Del` edges*) and not a completeness hole (nothing is missing from the decomposition).
- **N11 vs this plane (breach-notification split).** The *deadline-bound notification obligation* (a
  regulator/customer notice must go out within a statutory deadline of a qualifying event) is a **behavioural**
  truth-maker and lives in **N11**. The *authority to declare the breach / decide to notify* is the **plane**
  (`Del`/Issuer). Scorer rule: "regulatory breach notification within the statutory deadline is owned by
  Legal/Compliance" → **N11**; "the incident commander has the authority to declare a reportable breach" →
  **plane** (no NEGLECTED credit). Do not double-credit one sentence across both — N11 needs the *deadline-bound
  obligation* named, not merely "someone communicates."

## 4. Criteria `V` — regime predicates (former Invariants + Edge-cases + Failure-modes, COLLAPSED)

> `V` is **derived**: `V(t) = AND(criteria(t))` (§2.2, §3.1 Theorem 1). Every item below is a **predicate of
> the regime** — a `criterion` whose conjunction is the validation. The former Invariants (regime-level
> spanning viability predicates), Edge-cases (boundary-state predicates) and Failure-modes (defect-coupling
> predicates) are **all criteria** and are collapsed here into one section. Each criterion keeps its verbatim
> text + truth-maker and carries an **FM tag**: which canon failure mode(s) it precludes (§4.2 / §4.3 /
> §4.6). The old I/E/F labels are retired — the FM tag replaces them. (Item ids keep an I-/E-/F- prefix
> purely for cross-reference traceability to `reference_buckets_v1.md`; they are NOT separate categories.)

**How to read the FM tag.** Per §4.2/§4.3/§4.6: a **spanning/coverage predicate** a faithful decomposition
must carry (and whose omission is a coverage hole) precludes **FM-1** (Correspondence — joint sufficiency); a
predicate enforcing **mutual satisfiability** of children precludes **FM-2** (Consistency); a predicate
guarding against an **insensitive / gameable / green-but-broken** check (a value that passes where reality
fails) precludes **FM-3** (Verifiability, false-PASS); a predicate enforcing **correct fail-propagation /
ordering / no-stale** precludes **FM-4** (Propagation). For this **maintenance** regime the OPERATIONAL axis
is also in scope: a predicate guarding **stale inputs / estate drift / mid-run baseline change** precludes
**FM-5** (Currency); a predicate guarding **a state not-yet-determinable at decision time** (is the response/
target even attainable?) precludes **FM-6** (Feasibility); a predicate guarding the **post-hoc detect→report→
fix channel** precludes **FM-7** (Feedback).

### 4.1 Global viability criteria (spanning predicates — the maintenance constraint)

A spanning criterion is a regime-level predicate that **spans children** — no single capability establishes
it; it holds only if the whole loop is jointly correct (canon §2.2 joint sufficiency / §3.1). For a
maintenance goal these are the **viability conditions** the regime must hold *over time*. Canonicalized by
the *conserved quantity / enforced predicate*, not by where it is checked (one item per category).

| # | Name | Conserved quantity / predicate | FM tag (precludes) | Truth-maker (covered iff the decomposition asserts…) |
|---|---|---|---|---|
| **V-I1** | **Every in-scope artifact is captured and restorable (catalog completeness)** | For *every* item in the D1 scope there exists a current, restore-tested backup — no enrolled store, secret, or config source is left without a recovery path, and no required-to-reconstitute artifact is missing from the catalog. The hub-invariant: "everything needed to bring the service back is captured and provably restorable." Spans D1, D2, D5, D6, Dep3. | **FM-1** (roster/coverage completeness over all required artifacts) | …that *every* required artifact (not just the obvious DB) has a current, tested backup — completeness of the recovery catalog over all state needed to reconstitute the service. Credit "nothing needed for recovery is left un-backed-up / untested." The headline hub-invariant; distinct from per-store D2. |
| **V-I2** | **RPO and RTO are actually met (and measured, not assumed)** | The *achieved* RPO/RTO — measured on real drills — are ≤ the targets, continuously over time. The objectives are a measured property of the regime, not a documented aspiration. Spans D1, D2, D4, D6, Dep1, Dep2. | **FM-6** (Feasibility: the objectives' attainability is a measured, determinable property — not assumed) | …that RPO/RTO are *demonstrably met and measured* (achieved-from-drills ≤ target), not merely stated. Credit "we actually achieve the RPO/RTO and verify it," "measured recovery point/time within target." Distinct from Dep1/Dep2 (the single binding edges) — V-I2 is the *standing, measured* met-ness over time. |
| **V-I3** | **Backups survive the disaster they protect against (isolation invariant)** | No single failure (region loss, account compromise, ransomware, accidental mass-delete, operator error) can destroy **both** primary and its backups — backups are isolated in a separate failure domain and protected against the same threat (immutable/air-gapped against ransomware; cross-region against region loss). The conserved property: backup survivorship is independent of the primary's failure. Spans D3, and the threat classes in D1/NEGLECTED. | **FM-2** (mutual satisfiability: backup survivorship and primary failure must not share a failure domain) | …that backups are *isolated from the failure they protect against* — same event cannot kill primary and backup (separate region/account, immutable vs ransomware). Credit "3-2-1 / off-site / immutable so the disaster can't take the backups too," "backups not co-located with primary." The invariant whose violation is the classic "we had backups, the ransomware encrypted them too." |
| **V-I4** | **A restore reproduces a working service (not just recovered bytes)** | The success criterion of recovery is an **application-level** working service (passes a health/functional check against `spec`), not "the bytes came back." A restore that recovers data but yields a service that won't start, fails referential integrity, or is missing config/secrets has not met the objective. Spans D4, D6, Dep5, Dep6, Dep8. | **FM-3** (false-PASS: "bytes restored" passes where "service works" fails) | …that recovery success means the *service works* (application health/functional verification post-restore), not that data was restored. Credit "verify the restored service actually functions," "health-check the recovered service end-to-end." Distinct from V-I1 (everything captured) — V-I4 is *the reconstituted whole works*, mirroring the GFSO false-PASS residual (bytes-back ≠ service-back). |

> **Criteria vs the loop passes.** V-I1–V-I4 are *checked across* the regime but are properties of the whole
> running loop, so they live in **§4 Criteria**, not as internal checks of D2/D4/D6 (no double-count). V-I2 is
> the task `spec`'s headline maintenance condition (Constitution Ст. II.1.b: criteria must be jointly
> sufficient for `spec` — "within stated RPO/RTO targets … a recovery would actually succeed") — omitting it
> leaves the central objective uncovered. **V-I2 carries an OPERATIONAL FM (FM-6 feasibility) at design
> time** — for a maintenance regime the *attainability of the RPO/RTO objectives* is a determinability
> question (the §4.3 "before" phase), genuinely in-scope here (see §7), not the static N/A it would be for a
> fully-determinable one-shot task. V-I3 (isolation) and V-I4 (service-works) are the two invariants whose
> silent failure is the entire reason "we had backups" still ends in a failed recovery.

### 4.2 Boundary-state criteria (former Edge-cases)

A boundary-state criterion is a boundary input/state that a naive happy-path regime silently mishandles —
i.e. a predicate the regime must satisfy at the boundary, or the corresponding check is **insensitive** /
**not-yet-determinable** there. Covered iff the decomposition names the same boundary condition and that it
needs a rule.

| # | Name | What it requires | FM tag (precludes) | Truth-maker (covered iff named) |
|---|---|---|---|---|
| **V-E1** | **Partial / corrupt / incomplete backup** | A backup that completed "successfully" but is partial or silently corrupt (truncated, mid-transaction, bit-rot) — the regime must detect it (integrity verification) and fall back to an earlier known-good copy, not restore from it. | **FM-3** (insensitive check: a "successful" job report passes a corrupt backup) | …a partial/corrupt backup boundary and a defined response (detect via integrity + fall back to an earlier good copy), not "the latest backup is always good." |
| **V-E2** | **Region-wide / whole-site outage (the disaster the regime is for)** | The entire primary region/site is lost — restore must be possible from an *isolated* copy into a *different* region, exercising the cross-region recovery path (not just an in-place restore). | **FM-6** (Feasibility: with the whole site gone, the in-place response is not determinable — needs a declared cross-region recovery path) | …a full-region/site loss and recovery from an off-region isolated copy into a different region, distinct from a single-store restore. |
| **V-E3** | **Restore into a different / clean environment** | Recovery often must land in a *new* account/region/cluster (the original is gone or compromised), surfacing hidden environment dependencies (hard-coded endpoints, region-specific resources, IAM, DNS) — the runbook must restore into a clean target, not assume the original surroundings. | **FM-3** (happy-path check insensitive to hidden environment couplings → passes in-place, fails clean) | …restoring into a *different/clean* environment (not in-place) and that hidden environment couplings (endpoints/IAM/DNS) must be reconstructable. Distinct from Dep8 (parity) — V-E3 is the *event* that the original env is unavailable. |
| **V-E4** | **Backup of in-flight / inconsistent / live state** | Backing up a store under active writes (open transactions, in-flight queue messages, an un-quiesced filesystem) yields a crash-consistent-at-best or torn copy — the regime needs app-consistent snapshots / quiescing / log-replay-to-consistent-point, or a declared crash-consistency boundary. | **FM-3** (insensitive: a torn/crash-consistent copy looks like a valid backup) | …backing up live/in-flight state and a consistency mechanism (quiesce / app-consistent snapshot / log replay) or a declared crash-consistency stance. Distinct from Dep6 (cross-store) — V-E4 is *within one store under load*. |
| **V-E5** | **Encryption-key / credential loss + key-rotation lifecycle (can't decrypt the backup)** | Backups are encrypted; if the KMS key / passphrase needed to *decrypt* them is itself lost in the disaster (or never backed up), the data is recovered-but-unreadable — the key/secret material must be independently recoverable, or the backup is worthless. **The rotation lifecycle is part of this boundary:** when keys are **rotated**, the *old* key versions that encrypted *still-retained* backups must be kept available (not destroyed on rotation), or every backup older than the last rotation becomes silently undecryptable — i.e. rotation must not *orphan* in-retention backups. | **FM-3** (insensitive: an encrypted-but-undecryptable backup passes as recovered) **+ FM-5** (Currency: a key-rotation event must propagate to retained backups or it orphans them) | …the encryption-key/secret-loss boundary and that key material must be independently recoverable (escrow / separately-backed-up KMS) for the backup to be usable, **and** that **key rotation retains old key versions while backups encrypted under them are still in retention** (rotation does not orphan older backups). The "encrypted backup we can't decrypt" failure, including its rotation-lifecycle variant (distinct from N1's *external-key-recovery* assumption — V-E5 is the on-restore decryptability boundary). |
| **V-E6** | **Schema / data-version skew on restore (old backup into newer app)** | A backup taken under an *older* schema/data-version is restored into the *current* (newer) application — the data shape no longer matches what the running code expects (dropped/renamed columns, changed encodings, migrated formats). The regime must handle the skew: replay forward-migrations on the restored data, or maintain backward-compatible readers, or pin a code version compatible with the restored data — not assume "the bytes match the running app." Distinct from Dep8 (engine/environment parity) — V-E6 is the *data's own schema-version* vs the *app code*, not the host's compatibility. | **FM-3** (insensitive: a shape-mismatched old backup restores cleanly yet the app fails on it) | …the schema/data-version-skew boundary (old backup ↔ newer app) and a defined response (run forward-migrations on restore / backward-compatible readers / version-pin the recovery), not assuming a restored old backup is shape-compatible with current code. Distinct from Dep8 (host/engine parity). |

### 4.3 Defect-coupling criteria (former Failure-modes — only those with NO `Dep`/`V-I` twin)

Phrased as **concrete coverable claims** (never adjectives — "backups are reliable" is NOT a criterion). Each
names a specific defect AND its resolution; covered iff the decomposition names the same defect and a guard.
**One-defect-one-place:** a defect-coupling is kept here ONLY if it has no `Dep`-edge / `V-I` twin. A coupling
that shares the *same pair, falsifier, and fix* as an existing seam/invariant is **not** a separate item — the
seam already carries it (e.g. "RPO assumed never measured" is carried by V-I2/Dep1; "untested = invalid" by
Dep3; "store missing from catalog" by V-I1; "bytes back but service dead" by V-I4; "DR-side writes lost on
return" by Dep9 — not re-listed). What remains are regime-level FMs with **no twin**, each pinned to a canon
§4 FM class.

| # | Name | FM tag (precludes) | What it requires (defect + guard) | Truth-maker (covered iff named with a guard) |
|---|---|---|---|---|
| **V-F1** | **Backup that never restores / silently corrupt** | **FM-3** (false-PASS) | The backup job reports success and integrity checks pass, yet an actual restore fails (incompatible format, missing dependency, undetectable logical corruption) — "green backup dashboard, no working recovery." The capture *looks* valid but isn't restorable. **No seam twin:** Dep3 is the *drill→validity* edge; V-F1 is the named *false-PASS of capture* the drill exists to catch — a backup can pass D5 and Dep4 and still fail to reconstitute a service. Guard: periodic full restore-drills (D6) treat the backup as unproven until restored, not job-success/checksum alone. | …that a backup can *report success / pass checksums yet not restore* (false-green), AND a guard (actual restore-drills, not job-status, prove restorability). The canonical "we had backups but couldn't recover." Mirrors the GFSO false-PASS residual (the capture's success report ≠ real restorability). |
| **V-F2** | **Restore procedure untested / undocumented (runbook rots)** | **FM-7** (no feedback channel) **+ FM-6** (undetectable on the day) | A documented runbook that is never executed drifts out of date (stale endpoints, removed steps, an undocumented manual step) and is first exercised *during* the real disaster, when it fails. **No twin:** Dep7 is *drill→regime-update*; V-F2 is the named failure of an *un-drilled* runbook — the procedure's correctness was never opened to contact. Guard: the runbook is *executed* in drills (D6) and kept current, not just authored. | …that an untested/undocumented restore procedure fails on the day (first real run during the disaster), AND a guard (drill the runbook regularly, keep it current). Distinct from D4 (a runbook exists) — V-F2 is *it was never proven and has rotted*. |
| **V-F3** | **RPO/RTO assumed but never measured (paper objectives)** | **FM-1** (coverage hole at setup) **+ FM-6** | RPO/RTO are written into the policy but the *achieved* values are never measured, so the real recovery point/time is unknown until a disaster reveals it exceeds target. **No twin with V-I2** at the F-grade: V-I2 asserts the *invariant* (met-and-measured); V-F3 is the concrete *defect-and-guard* that the targets stay paper without a measuring act. Guard: every drill (D6) measures and records achieved RPO/RTO and flags shortfall. | …that RPO/RTO can be *documented but never measured* (unknown real recovery point/time) AND a guard (measure achieved RPO/RTO on every drill, alert on shortfall). Credit "don't just declare RPO/RTO — measure it on drills." |
| **V-F4** | **Backup co-located with primary (same disaster kills both)** | **FM-1.b** (foreseeable, un-mitigated) | Backups live in the same account/region/host/cluster as primary (or are mutable from the primary's credentials), so the very event they protect against — region loss, ransomware with primary creds, mass-delete — destroys them too. **No twin:** V-I3 asserts the *isolation invariant*; V-F4 is the concrete *co-location defect-and-guard* (the most common real-world DR failure). Guard: physically/logically isolate backups (separate region/account, immutable/WORM, off-platform), per 3-2-1. | …that backups can be *co-located / mutable with primary so one event kills both* AND a guard (isolate: separate region/account, immutable, air-gapped). The "ransomware encrypted the backups too / deleted the whole account" failure. |
| **V-F5** | **Backup-region / DR site co-fails (the "safe" copy isn't safe)** | **FM-1.b** **+ FM-2** (criteria conflict) | The chosen backup/DR region or provider shares a failure domain with primary (same provider control-plane, same upstream dependency, correlated outage) — the assumption "the backup region survives the disaster" is false. **Distinct from V-F4** (V-F4 = backup *co-located* with primary; V-F5 = the *backup region itself* co-fails despite separation). Guard: choose a backup target with an *independent* failure domain (different provider/region pair vetted for correlation; offline copy). | …that the *backup region/site can co-fail* with primary (correlated failure domain) AND a guard (independent failure domain / multi-provider / offline copy). Distinct from V-F4 (co-location) — V-F5 is correlated-but-separate. |
| **V-F6** | **Partial-restore inconsistency (some stores recovered, others not)** | **FM-2** (children mutually inconsistent) **+ FM-4** (no fail-propagation) | A restore that succeeds for some stores and fails/partials for others leaves the service in a referentially-inconsistent state (orders without payments, accounts without their secrets) that *appears* up — a partial recovery presented as success. **No twin with Dep5/Dep6** (those are *ordering* and *consistent-point* design edges); V-F6 is the named *runtime partial-failure* and the all-or-nothing guard. Guard: atomic/all-or-nothing recovery to a consistency group; a partial restore is rolled back or flagged not-recovered, not declared up. | …that a *partial* restore leaves inconsistent state presented as recovered AND a guard (all-or-nothing / consistency-group recovery; partial = not-recovered). Distinct from Dep6 (consistent recovery *point*) — V-F6 is *some-stores-up-some-down* at restore time. |
| **V-F7** | **Split-brain / write-divergence on failover (two writable primaries)** | **FM-2** (children mutually inconsistent) **+ FM-4** (no fail-propagation) | On failover, both the recovered DR site *and* the original primary (if it comes back, or never fully died — a partial/network-partition "disaster") accept writes at once, so two authoritative copies **diverge** and cannot be cleanly reconciled (conflicting updates to the same record on each side). **No twin:** V-F6 is *some-stores-down* at restore time; Dep9 is the *failback re-sync* path; V-F7 is the named *dual-writable-primary divergence* the cutover must prevent. Guard: **fencing / quorum / single-writer** — the old primary is fenced off (STONITH, witness/quorum, lease/token) before DR takes writes, so only one site is ever authoritative. | …that concurrent dual-primary writes on failover (split-brain) cause irreconcilable divergence AND a guard (fencing / quorum / witness / single-writer lease so exactly one site accepts writes). Distinct from V-F6 (partial-store restore) and Dep9 (failback re-sync) — V-F7 is *preventing two live writers*, the precondition that makes Dep9's clean re-sync even possible. |
| **V-F8** | **Non-idempotent / non-resumable restore (re-run corrupts or half-applies)** | **FM-4** (no fail-propagation) **+ FM-6** (undetectable on the day) | A restore that is interrupted midway (crash, timeout, operator abort) and then *re-run* or *resumed* yields a corrupted or half-applied state rather than a correct one — partially-written tables, double-applied logs, an import that isn't safe to repeat. Under the real-disaster time pressure where restores *do* get interrupted and retried, a non-idempotent restore turns one failure into a worse one. **No twin with V-F6** (V-F6 = *cross-store* partial leaving inconsistency; V-F8 = *within a single restore's re-run* safety). Guard: restore is **idempotent / resumable / transactional** — re-running or resuming from a checkpoint converges to the correct result (or cleanly rolls back), never half-state. | …that a restore interrupted-and-rerun must be *safe to repeat/resume* (idempotent / checkpointed / transactional) and not leave half-applied corrupt state. Distinct from V-F6 (cross-store partial) — V-F8 is the *re-run/resume safety of a single restore*. |

> **Note on the operational axis (the maintenance difference vs a static task).** Unlike a static one-shot
> decomposition where the runtime FMs {FM-5,6,7} are mostly N/A-static, T06 is a **cyclic maintenance**
> regime whose entire job is runtime capture→verify→drill→measure→feedback — so the operational axis is
> **genuinely carried** by named criteria: **FM-7 feedback** by V-F2 (un-drilled runbook never opened to
> contact) and the seam Dep7 (drill findings → regime update); **FM-6 feasibility** by V-I2/V-F3 (RPO/RTO
> attainability must be *measured*, not assumed determinable), V-E2 (the not-determinable whole-site
> response), V-F2/V-F8 (undetectable-on-the-day runbook/restore correctness); **FM-5 currency** by V-E5
> (key-rotation must propagate to retained backups) and the seam Dep7 (estate drift re-arms the catalog).
> §7 records the full mapping and explains the difference from the static T04, where these were N/A-static.

## 5. NEGLECTED — declared scope-exclusions (THE DOMINANT, LOAD-BEARING CATEGORY; each with its `predictability_verdict`, STD-1/2/3)

> **This is the richest category for T06 by construction (PLAN §3 T06, §4(g)).** A recovery regime is correct
> **only if what it does NOT cover is declared** — the silent assumptions whose failure makes a *documented*
> restore fail in practice. Canon §5.1 STD-1: a decomposition **without** NEGLECTED is incomplete by
> definition — the auditable "no silent skip" record. Each N is an assumption whose **omission would otherwise
> be a foreseeable defect** (Constitution Ст. II.6 / §5.2 / §4.2: a predictable external risk left without a
> mitigating child = FM-1.b), carries a **`predictability_verdict`** (STD-2 §5.2: predictability is presumed;
> the *declarer* bears the burden of proving safe-to-skip), and an `invalidation_condition` (the input under
> which the exclusion flips in-scope). The list is **capped to assumptions whose failure provably breaks the
> documented restore** (PLAN §0 residual: not an open-ended "anything could be assumed" list — "storage is
> durable" or "the backup tool works" stay OUT; their failure is handled *inside* the decomposition by
> D5/V-F1, not as a scope-boundary).

| # | Excluded assumption | `predictability_verdict` (why this is a *declared boundary*, not a forgotten child) | Truth-maker (covered iff the decomposition declares…) |
|---|---|---|---|
| **N1** | **Secrets / KMS keys assumed recoverable elsewhere** | **Foreseeable (FM-1.b if silent) ⇒ either enroll or declare.** A restore needs the secrets/KMS keys to *decrypt and run* the restored data; if their recovery is assumed handled by a separate secret-management process, that assumption must be *declared* — a silent "the keys will be there" is the classic encrypted-backup-we-can't-decrypt failure (cf. V-E5). S-regularity exists (every competent DR plan addresses key recovery), so the *declared* boundary is licensed; the *silent* omission is FM-1.b. Invalidation: if no separate secret-recovery process exists, secrets are an in-scope spoke (enroll in D1). | …that secret/KMS-key recoverability is *named* — either enrolled as an in-scope store or *declared* as handled by a separate secrets process. Silent omission ≠ covered. |
| **N2** | **DNS / external SaaS / third-party state assumed re-creatable** | **Foreseeable ⇒ declare the boundary.** A service depends on external state not in *your* backups — DNS records, third-party SaaS config (payment provider, auth IdP, CDN), partner integrations. The regime must declare these as out-of-backup-scope-but-required-to-reconstitute, with the assumption they are re-creatable from their own systems. Silent omission ⇒ a restore that brings up the data but a dead service (no DNS, no payment integration). Invalidation: if any external state is *not* re-creatable (e.g. one-time provisioning), it must be captured/documented in-scope. | …that DNS / external-SaaS / third-party integration state is *declared* (out-of-backup but required, assumed re-creatable from source) — not silently assumed present. |
| **N3** | **In-flight / un-acked queue & stream messages excluded** | **Foreseeable ⇒ declare RPO-for-transient.** Messages in flight (un-acked queue items, in-buffer stream records, in-progress sagas) between backup points are lost on recovery; the regime must *declare* that transient in-flight state is excluded (recovered-to-last-consistent-point, with replay/idempotency assumed at the app layer) rather than silently implying zero message loss. Invalidation: if exactly-once / zero-message-loss is required, in-flight capture (transaction log shipping, dual-write) comes in-scope. | …that in-flight/un-acked queue & stream messages are *declared excluded* (transient state lost to last consistent point; app-layer replay/idempotency assumed), not silently treated as recovered. |
| **N4** | **IAM / policy / infra-config (the "account itself") assumed re-provisionable** | **Foreseeable ⇒ declare app-vs-infra boundary.** Recovering *data* assumes the surrounding infra exists — IAM roles/policies, network/VPC, security groups, the account/project itself. The regime must declare whether infra is in-scope (IaC-recoverable) or assumed standing; restoring into a clean account (V-E3) exposes this. Silent omission ⇒ data restored into an account with no roles/network = dead. This is the **app-level vs infra-level recovery boundary** explicitly. Invalidation: if a whole-account loss is in the disaster set, infra-as-code recovery is in-scope. | …that the IAM/policy/network/account (infra) layer is *declared* — either IaC-recoverable in-scope or assumed standing — i.e. the explicit app-recovery-vs-infra-recovery boundary. |
| **N5** | **Certificate / clock / token state assumed valid post-restore** | **Foreseeable ⇒ declare.** A restored service can fail on *time-sensitive* state: expired TLS certs (restored from an old backup), clock skew breaking auth tokens / TOTP / cert validation, stale OAuth refresh tokens. The regime must declare that cert/clock/token freshness is handled (re-issued, not restored-stale) rather than assume an old backup's certs still work. Invalidation: if certs/tokens are long-lived and in-backup, no separate handling needed (verdict downgrades). | …that certificate/clock/token freshness is *named* (re-issued/synced on restore, not assumed valid from an old backup) — the "restored service fails because its certs expired / clock is skewed" boundary. |
| **N6** | **"The backup region itself survives the disaster" — the meta-assumption** | **Foreseeable ⇒ MUST declare (the load-bearing one).** The whole regime rests on the implicit assumption that the location of the backups / DR site is *unaffected* by the disaster. This must be made explicit and bounded (which disaster classes the backup site is independent of). Silent omission is the deepest DR failure: planning a recovery whose recovery medium dies with the primary. (V-F5 is the *failure*; N6 is the *declared assumption* whose validity V-F5 tests.) Invalidation: a broader disaster class (provider-wide, geographic) requires a more-independent backup target. | …that the *backup/DR site's own survival* of the disaster is an *explicit, bounded* assumption (which disaster classes it is independent of), not silently presumed. The meta-assumption the entire regime stands on. |
| **N7** | **Which disaster classes are in / out of scope (the threat model)** | **Foreseeable ⇒ declare the threat set.** "Disaster recovery" is undefined without naming *which* disasters: single-store corruption, accidental delete, ransomware, region loss, provider loss, data-center fire, geographic catastrophe — the regime is designed against a *declared* set, and classes outside it are explicitly excluded. Silent omission ⇒ a regime that meets RPO/RTO for the disasters it happened to consider and silently fails the others. Invalidation: a stakeholder requires a class outside the declared set ⇒ re-scope. | …that the *in/out-of-scope disaster classes* are *declared* (the threat model: which failures the regime recovers from, which are excluded) — not an unstated implicit set. The scope-defining N. |
| **N8** | **Compliance / retention-law / data-residency assumed satisfied** | **Foreseeable ⇒ declare (legal boundary).** Retention duration, deletion/right-to-erasure, encryption-at-rest, and *data-residency* (backups may not legally leave a region — conflicting with cross-region isolation V-I3) are governed by external compliance the regime must declare it satisfies or defers to a compliance owner. Silent omission ⇒ either a legal breach or an isolation/residency conflict left unresolved. Invalidation: a residency rule forbidding the chosen backup region forces an in-region-but-isolated design. | …that compliance / retention-law / data-residency is *declared* (satisfied or owned elsewhere), including the residency-vs-cross-region-isolation tension — not silently assumed compliant. |
| **N9** | **Cost / storage-budget ceiling is a fixed input** | **Foreseeable ⇒ declare the constraint.** Backup frequency, retention depth, and warm-standby readiness all trade against cost; the regime *operates within* a given storage/DR budget rather than deriving unlimited retention. Declared boundary: the ceiling is an input that bounds achievable RPO/RTO, not a loop pass. Silent omission ⇒ an RPO/RTO design that is unaffordable and silently degraded. Invalidation: if the budget makes the RPO/RTO targets infeasible, that surfaces as an escalated trade-off, not a silent shortfall. | …that the cost/storage-budget ceiling is a *declared fixed input* bounding achievable retention/cadence/standby (raising it is upstream). Distinct from D2/D3 (use the budget you have). |
| **N10** | **Platform-managed vs self-managed (the shared-responsibility boundary)** | **Foreseeable ⇒ MUST declare which side owns what.** Much of the estate sits on managed platforms (managed DB, object store, SaaS) whose provider handles *some* durability/backup and the team handles the rest — and the boundary is **commonly assumed wrong**: managed-DB automated backups are often **region-local and deletable with the account**, so a region loss or account compromise destroys them too. The regime must *declare* what the platform is assumed to handle (intra-region durability, managed snapshots) vs what the team must add (cross-region copy, immutable export, account-isolated copy). Silent omission ⇒ "the platform backs it up" assumed to mean disaster-proof when it isn't. **Distinct from N4** (IAM/infra app-vs-infra recovery boundary) and **N6** (whether the backup *site* survives) — N10 is *who in the shared-responsibility model is responsible for the backup at all*.
