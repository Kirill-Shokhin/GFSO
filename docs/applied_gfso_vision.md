## 1. Полная спецификация конечного автомата (FSM)

P2P-протокол задача-приёмка формализован как конечный автомат с 10 состояниями и 12 сигналами. Ниже — полная таблица переходов и таймауты по умолчанию.

### 1.1. Таблица переходов

```
Состояния:
  IDLE, REVIEW, CHALLENGED, EXECUTING, BLOCKED,
  VALIDATING, REWORK, DONE, TIMEOUT, ESCALATED

Переходы:

  IDLE → REVIEW
    Триггер: ASSIGN(packet)
    Таймаут: T_review

  REVIEW → EXECUTING
    Триггер: ACCEPT
    Таймаут: deadline

  REVIEW → CHALLENGED
    Триггер: CHALLENGE(reason)
    Таймаут: T_challenge

  REVIEW → TIMEOUT
    Триггер: T_review истёк без ACCEPT/CHALLENGE

  CHALLENGED → REVIEW
    Триггер: ACCEPT_CHALLENGE(new_spec)

  CHALLENGED → EXECUTING
    Триггер: REJECT_CHALLENGE(justification)

  CHALLENGED → REVIEW
    Триггер: T_challenge истёк (авто-ACCEPT_CHALLENGE)

  EXECUTING → VALIDATING
    Триггер: DELIVER(result, self_validation)
    Таймаут: T_validate

  EXECUTING → BLOCKED
    Триггер: BLOCK(reason)
    Таймаут: T_block

  EXECUTING → TIMEOUT
    Триггер: deadline истёк без DELIVER

  BLOCKED → EXECUTING
    Триггер: RESOLVE_BLOCK(action)

  BLOCKED → DONE(cancelled)
    Триггер: CANCEL(reason)

  BLOCKED → ESCALATED
    Триггер: T_block истёк без RESOLVE_BLOCK

  VALIDATING → DONE(pass)
    Триггер: PASS

  VALIDATING → REWORK
    Триггер: FAIL(criteria[])
    Условие: iteration < max_iterations
    Таймаут: T_rework

  VALIDATING → DONE(fail)
    Триггер: FAIL(criteria[])
    Условие: iteration ≥ max_iterations

  VALIDATING → DONE(auto_pass)
    Триггер: T_validate истёк (авто-PASS)
    Примечание: записывается как auto_pass для q_V

  REWORK → VALIDATING
    Триггер: DELIVER(result, self_validation)

  REWORK → BLOCKED
    Триггер: BLOCK(reason)
    Таймаут: T_block

  REWORK → TIMEOUT
    Триггер: T_rework истёк без DELIVER

  TIMEOUT → ESCALATED
    Триггер: автоматический

  ESCALATED → DONE(escalated)
    Триггер: разрешение вышестоящим агентом
    (мета-операция, не P2P-сигнал; конкретный механизм
    определяется организацией)

  ESCALATED → REVIEW (новая задача)
    Триггер: CANCEL текущей + ASSIGN новой
    (переназначение; составная операция из двух P2P-сигналов)

  Любое кроме DONE → DONE(cancelled)
    Триггер: CANCEL(reason) + CANCEL_ACK
```

### 1.2. Таймауты по умолчанию

Конкретные значения определяются организацией; ниже — ориентиры для типичного проектного контекста:

| Состояние | Таймаут | Назначение |
|---|---|---|
| REVIEW | T_review = 1 рабочий день | Executor должен принять или оспорить |
| CHALLENGED | T_challenge = 2 рабочих дня | Issuer должен ответить на challenge |
| EXECUTING | deadline (задаётся в ASSIGN) | Срок выполнения задачи |
| BLOCKED | T_block = 3 рабочих дня | Issuer должен разрешить блокировку |
| VALIDATING | T_validate = 1 рабочий день | Issuer должен принять или вернуть |
| REWORK | T_rework (задаётся при FAIL) | Срок исправления |
| max_iterations | 3 (по умолчанию) | Лимит циклов DELIVER→FAIL |

Таймауты — не штрафы. Они обеспечивают конечность каждого состояния (инвариант 5) и гарантируют, что блокировка не превращается в замалчивание. Истечение таймаута = системное событие, которое автоматически эскалирует ситуацию вверх по иерархии.

## 2. Институциональная память и холодный старт

Из архитектуры графа автоматически следует: каждое решение сохранено с контекстом — кто декомпозировал, на что, с какими критериями, когда, что было в NEGLECTED, какие CHALLENGE были, как разрешены.

Это не отдельная фича («система хранит историю»). Это **следствие**: протокол требует записывать решения, граф хранит записи, данные накапливаются без дополнительных усилий.

### Практические следствия:

**Онбординг.** Новый сотрудник видит историю решений по аналогичным задачам: как декомпозировали, что пошло не так, какие NEGLECTED сработали. Не устная передача знаний — структурированная история с авторством.

**Обучение организации.** Система со временем находит паттерны:
- «На этом типе задач сроки систематически занижаются на 40%»
- «После праздников приёмка задерживается в среднем на 3 дня»

Это не пассивное хранение. Система может предупреждать (при наличии LLM-слоя, §7.3 основного документа) на основе статистики.

**Защита от потери знаний.** Уход ключевого сотрудника не уносит знания — все решения в графе. Каждый выбор декомпозиции, каждый аргумент при CHALLENGE, каждое NEGLECTED с обоснованием — зафиксированы с автором и временной меткой.

**Peer review декомпозиций.** Горизонтальный обмен: система предлагает «у коллеги на аналогичной задаче было 5 шагов, у вас 2 — хотите посмотреть?» Не навязывает чужой план, а предлагает reference. Бесплатный источник качества без дополнительной нагрузки (открытое направление, §18.8 основного документа).

### Cold start

Первые проекты — без исторических данных. Работают только структурные и семантические проверки (CHECK-1–6 (Level 0; CHECK-7–8 требуют объявленной composition function)). LLM работает на общем prior (обучающих данных), без организационного контекста.

С каждым проектом система становится точнее: feedback loop (протокол → граф → LLM → протокол) начинает работать с первых задач. Это нормально и честно — так работает любая обучаемая система. Не продаём то чего ещё нет.

## 3. Дорожная карта к аудиторскому стандарту (GAAP-аналог)

### «Формула = 5%, стандарт = 95%»

«Прибыль» — не формула `доход − расход`. Это стандарт (GAAP/IFRS) на 2000+ страниц, определяющий: что считать доходом, когда его признавать, как учитывать амортизацию, как оценивать потери. Формула проста; процедура — нет.

Параллель с метрикой качества управления:

| Наш вопрос | Бухгалтерский аналог | Статус |
|---|---|---|
| Что считать дефектом criteria? → CHALLENGE/изменение | Когда признавать доход? → при отгрузке или оплате? | Определено |
| Что считать пропущенной зависимостью? → BLOCK на задачу в графе | Что считать расходом? → прямые или накладные? | Определено |
| Все ли переназначения — дефект? → только capability mismatch | Все ли потери — убыток? → амортизация? | Определено |
| За какой период считать? | Отчётный период: квартал? Год? | Открыт |
| Как сравнивать IT и стройку? | Как сравнивать SaaS и ритейл? | Открыт |

Формулы определены. Стандарт (аналог GAAP) — нет. Без стандарта метрики работают внутри одной организации, но не между организациями.

### Дорожная карта

```
Сейчас:
  Формулы определены              ← аналог "прибыль = доход − расход"
  Процедуры частично определены   ← аналог "каждый купец считает по-своему"
  Аудита нет                      ← аналог "доверяй на слово"
  Бенчмарков нет                  ← аналог "0.7 — это хорошо или плохо?"

Нужно:
  Стандарт сбора данных           ← что именно записывать, как классифицировать
  Процедуры измерения             ← пошаговая инструкция
  Независимый аудит               ← внешняя проверка, не самооценка
  Отраслевые бенчмарки            ← "q_D = 0.7 в IT — средне, в стройке — хорошо"
```

Аналогия структурная, не метафорическая:

```
До GAAP:   "Доверяй нашим книгам"
После GAAP: "Аудитор проверил наши книги"

До GFSO:   "Доверяй нашему управлению"
После GFSO: "Аудитор проверил наши графы задач"
```

GAAP не устранил мошенничество. Но сделал его дорогим и рискованным. GFSO делает то же для управления проектами: скрыть проблему = нарушить протокол = обнаруживаемый дефект.

## 4. Применение в государственном секторе и аудите

### Один граф для целой страны

Государственный проект — парадигматический случай HBP: есть цель (построить дорогу), задача сложная (один человек не справится), есть иерархия (министерство → департамент → подрядчик), есть деньги налогоплательщиков → должна быть прозрачность.

Граф государственного проекта:

```
Построить дорогу [Минтранс] — V: ⊥
├── Проектирование [Проектный институт] — V: pass ✓
│   ├── Геодезия — V: pass ✓
│   ├── Экология — V: pass ✓  ← criteria видны, проверяемы
│   └── Утверждение — V: pass ✓
├── Закупка материалов [Подрядчик А] — BLOCKED
│   └── BLOCK reason: "тендер оспорен в суде"
├── Строительство участок 1 [Подрядчик Б] — EXECUTING
│   ├── Земляные работы — V: pass ✓
│   ├── Основание — V: fail  ← criteria: "плотность < нормы"
│   └── Покрытие — Dep: основание → не может начаться
└── NEGLECTED:
    - задержка из-за погоды: P=30%, буфер 2 мес
    - рост цен на битум: P=20%, резерв 15%
```

Что видит гражданин: текущий статус, где проблема, что тормозит, кто отвечает, критерии проверки, чем пренебрегли. Не «доверяй» — «проверяй».

### Непрерывный мониторинг vs периодический аудит

Традиционный аудит — ретроспективный: аудитор приходит раз в год и смотрит что было. Большинство проблем к тому моменту уже превратились в убытки.

GFSO меняет парадигму: граф — живой, данные накапливаются в реальном времени. Аудитор не проверяет прошлое — он видит настоящее.

| Периодический аудит | Непрерывный мониторинг через GFSO |
|---|---|
| Раз в квартал/год | В реальном времени |
| Ретроспективно | Проблема видна до последствий |
| Рассказ менеджмента | Данные из графа, не чей-то рассказ |
| Выборочная проверка | Полное покрытие всех задач в протоколе |
| Дорогой внешний ресурс | Встроен в рабочий процесс (measurement cost ≈ 0, Теорема 10 §13) |

Для государственных проектов это означает переход от «контролируем постфактум» к «наблюдаем в реальном времени». Для крупных инфраструктурных программ с тысячами узлов — принципиальная разница.

Масштабируемость прозрачности: когда Минтранс управляет 500 проектами параллельно, LLM может в реальном времени отвечать: «Покажи все задачи по всем проектам где NEGLECTED сработал и исходные буферы оказались неверными» — без ручного сбора данных от подрядчиков.

## 5. Подотчётность без обвинений

Это один из ключевых аргументов в пользу протокола, который часто понимается неверно.

### Передача ответственности (responsibility transfer)

Когда Issuer назначает задачу (ASSIGN), происходит формальная передача: Executor принимает ответственность за выполнение в рамках заданных criteria. Это не «виноват тот, кто внизу». Это структурированное распределение.

Протокол разделяет дефект процесса и дефект агента:

- **FAIL(criteria)** = задача не выполнена по конкретным критериям. Не «человек плохой» — конкретная criteria не пройдена
- **CHALLENGE** = спека дефектна. Не «человек трудный» — спека содержит конкретный дефект, который Executor обязан указать
- **BLOCK** = внешняя зависимость. Не «человек ленивый» — внешний блокер с конкретным reason
- **Переназначение** = Del(t) изменено. Причина в CANCEL(reason) — capability mismatch ≠ личная некомпетентность в широком смысле

Каждый факт записан с контекстом — нет пространства для произвольной интерпретации.

### Каскадная видимость (cascading visibility)

В иерархии без протокола проблемы обнаруживаются снизу, но видны только локально. Топ-менеджмент узнаёт поздно и без контекста — «что-то пошло не так» без понимания где именно и почему.

В GFSO граф обеспечивает каскадную видимость: FAIL на листовом узле немедленно поднимает статус через дерево зависимостей. Каждый узел, зависящий от проблемного, получает статус «заблокировано». Топ видит не просто «красный» — он видит:

- какая именно criteria провалена
- кто принял декомпозицию (и значит, формально принял риск)
- что было в NEGLECTED (ожидаемое ли событие или сюрприз)
- цепочку зависимостей, затронутых этим FAIL

Разница принципиальная: не «кто виноват», а «где в архитектуре задачи произошёл сбой». Это меняет разговор — с обвинений на диагностику.

### Почему это важно для культуры

Система со структурной подотчётностью парадоксально *снижает* страх. Когда ответственность размыта («ну это все вместе не сделали»), люди боятся любой прозрачности. Когда ответственность структурирована («это criteria c₂ не была выполнена, вот почему, вот кто CHALLENGE не подал»), страх персонального обвинения исчезает — остаётся системный анализ.

Incentive compatibility (Утверждение 8 основного документа) это формализует: честное поведение оптимально при условии, что стоимость непойманного дефекта > стоимости честного сигнала. Не мораль — структура.

## 6. Глубокий разбор метрик: что каждая на самом деле говорит

Пятимерная метрика Q = (q_T, q_D, q_V, q_Dep, q_Del) ∈ [0,1]⁵. Каждая компонента имеет разный эпистемический статус. Это важно понимать при интерпретации.

---

### q_D — СИЛЬНЫЙ ИЗМЕРИТЕЛЬ

**Вопрос:** Все ли подзадачи прошли, а родительская задача тоже прошла?

**Формула:** |{t : ∀ child pass → t pass}| / |{t : неатомарные, DONE}|

**Почему сильный.** Это ground truth в рамках системы: если все дети DONE(pass), а родитель DONE(fail) — это объективный факт, не чьё-то мнение. Декомпозиция была дефектной: что-то важное не попало в подзадачи.

**Слепая зона.** Коррелированные ошибки могут маскировать дефект. Если все дети прошли и родитель прошёл, но реальный результат неудовлетворителен — это не поймает q_D. Это поймает q_V (ретроспективно).

**Практически:** Низкое q_D — сигнал системного дефекта декомпозиции. «Забыли логистику», «не учли документацию», «пропустили интеграционный этап» — всё это записывается в q_D.

---

### q_V — СИЛЬНЫЙ РЕТРОСПЕКТИВНЫЙ ИЗМЕРИТЕЛЬ

**Вопрос:** Насколько надёжна приёмка — сколько pass впоследствии оказались fail?

**Формула:** 1 − |{t : V=pass, позднее fail}| / |{t : V=pass}|

**Почему сильный (при триггере).** Если есть внешний сигнал (жалоба клиента, инцидент, переделка) — q_V точно фиксирует rubber-stamping. PASS который потом оказался FAIL — измеримый факт.

**Слепая зона.** Без триггера — оптимистичен. Если false pass не обнаружен, он не попадает в числитель. Это фундаментальное ограничение любой внутренней метрики: нельзя измерить то, что система не видела.

**Практически:** Систематически низкое q_V у конкретного Issuer — сигнал что валидация формальна. LLM может автоматически флагировать: «Иванов подтверждает приёмку в среднем за 2 минуты, что ниже разумного времени для задач его типа».

---

### q_T — ПРОКСИ

**Вопрос:** Насколько ясны criteria — сколько было оспорено или изменено?

**Формула:** 1 − |{t : criteria оспорены/изменены}| / |{t : DONE}|

**Почему прокси.** Измеряет не качество criteria напрямую, а количество явных сигналов о их некачественности (CHALLENGE, пересмотр). Тишина не означает хорошие criteria — она может означать страх или некомпетентность исполнителя.

**Ключевая слепая зона:** Некомпетентность или страх = тишина → q_T = 1 при плохих criteria. Это систематическое смещение. В организациях с культурой наказания за вопросы q_T будет высоким и ничего не говорить о качестве постановки.

**Практически:** q_T полезен как нижняя граница в относительном сравнении: если q_T упал, точно есть проблема. Если q_T высокий — это не доказательство качества, просто отсутствие измеримых сигналов проблемы.

---

### q_Dep — НИЖНЯЯ ГРАНИЦА

**Вопрос:** Какая доля реальных зависимостей объявлена заранее?

**Формула:** |Dep_declared| / |Dep_declared ∪ Dep_discovered|

**Почему нижняя граница.** Числитель — явные зависимости. Знаменатель — явные + обнаруженные через BLOCK (unexpected). Но пропущенные зависимости, не вызвавшие BLOCK (потому что исполнитель неформально «решил вопрос»), невидимы.

**Ключевая слепая зона:** Пропущенная Dep, не вызвавшая BLOCK — невидима. Если исполнитель обошёл блокировку неформально, не подал BLOCK, граф не знает что зависимость существовала. q_Dep видит только surface-level.

**Практически:** Низкое q_Dep — явный сигнал слабого планирования зависимостей. Высокое q_Dep не означает что все зависимости объявлены — только что те, которые вызвали проблемы, были известны заранее.

---

### q_Del — СЛАБЫЙ ИЗМЕРИТЕЛЬ

**Вопрос:** Насколько корректно делегирование — сколько переназначений из-за несоответствия компетенций?

**Формула:** 1 − |{t : переназначение capability_mismatch}| / |{t : DONE}|

**Почему слабый.** Не потому что метрика неправильная — а потому что данных мало. Capability mismatch — относительно редкое событие. На масштабе 50-100 задач выборка мала, статистическое значение низкое.

**Ключевая слепая зона:** Малая выборка делает q_Del шумным. На масштабе сотен задач сигнал усиливается. Дополнительно: переназначение по другим причинам (приоритет, доступность) не учитывается и не должно — только capability_mismatch.

**Практически:** q_Del значим только в масштабе и в динамике. Не «0.90 — это хорошо», а «q_Del снизился с 0.95 до 0.85 за квартал — что изменилось в процессе найма и делегирования?»

---

### Сводная таблица

| Метрика | Тип | Информативность | Слепая зона |
|---|---|---|---|
| q_D | Ground truth | Высокая | Коррелированные ошибки маскируют дефект D |
| q_V | Ретроспективная | Высокая при trigger | Без trigger: оптимистична |
| q_T | Proxy | Средняя | Страх/некомпетентность → тишина → q_T = 1 при плохих criteria |
| q_Dep | Lower bound | Средняя | Пропущенные Dep, не вызвавшие BLOCK — невидимы |
| q_Del | Слабая | Низкая (мало данных) | Малая выборка: значима только на масштабе |

Два genuine observable (q_D, q_V), два proxy с известными смещениями (q_T, q_Dep), один слабый (q_Del). Не нужно притворяться что все пять одинаково надёжны. Нужно понимать что каждая говорит и чего не говорит.

## 7. Открытые направления

Записаны чтобы не потерялись. Не часть MVP — потенциал для развития.

**Каузальная правильность.** Центральная нерешённая проблема: как определить что декомпозиция «правильная», а не просто формально полная? CHECK-1–6 проверяют структурные необходимые условия; CHECK-7–8 проверяют формальную sufficiency и consistency. Но каузальная правильность (декомпозиция отражает реальную причинно-следственную структуру задачи) требует доменной модели. LLM + историческое сравнение — практический workaround, не решение.

**Калибровка бенчмарков.** «q_D = 0.7 в IT — средне, в стройке — хорошо». Без отраслевых бенчмарков абсолютные значения метрик не интерпретируемы. Нужен deployment ≥ 6 мес с измерением корреляции Q ↔ реальные исходы.

**Adversarial agents.** Текущая модель предполагает добросовестных агентов: Issuer и Executor могут ошибаться, но не саботировать. Для enterprise/government deployment необходим анализ adversarial сценариев: сговор Issuer+Executor (фиктивный PASS), систематическое занижение criteria (low bar), манипуляция NEGLECTED, gaming метрик. Протокол частично защищён: прозрачность делает саботаж обнаруживаемым, peer review создаёт независимый контроль, q_V ретроспективно ловит false positives. Но формальная threat model — открытая задача.

**Единственность протокола.** Является ли текущий FSM единственным решением при A1+A2, или только минимальным? Любой протокол, адресующий 7 failure modes при инвариантах §6.4, изоморфен GFSO FSM?

**Full agent systems.** AI→AI делегирование, непрерывные распределения вместо бинарной валидации — потенциальная связь с общей теорией GFSO (категорный фреймворк, монада Канторовича).
