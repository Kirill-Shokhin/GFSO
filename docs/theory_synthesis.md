# 1. СИСТЕМНЫЙ ВИЖН — GFSO как агент-CTO: плагин + CORE + живая доска
*LIVE-направление, разрабатывается. Confidence: vision/candidate — не построено. Это «фреймворк/продукт» —
четвёртый слой над теормодель→методология→метод(конституция).*

## 1.0. Тезис
GFSO становится **исполняемой системой**: агент действует как **верхний менеджер (CTO)**, который получает
задачу юзера и **проводит её через GFSO** — декомпозирует, делегирует реальным Claude-сабагентам, ведёт всё в
персистентном локальном **GFSO-графе (CORE)**, синхронно отображаемом на **доске в реальном времени**. Это
одновременно (а) полезный продукт для юзера Claude Code и (б) **быстрый полигон для отладки самого GFSO** —
минуты вместо месяцев, без реальной компании. Слой = реализация: теормодель *доказывает* → методология
*выводит+показывает* → метод/конституция (`method_gfso.md`) *управляет* → **этот слой исполняет и делает
наблюдаемым**.

## 1.1. Рекурсивный CTO (организация = живое GFSO-дерево)
Агент-CTO получает задачу → его **основная работа = декомпозиция** (+ последующая **агрегация** результатов
по `V=AND`) → **делегирование**: открывает обычных Claude-сабагентов и назначает им подцели (`Del`). **Ключевое
обогащение (из рекурсии §18.10: единица = свёрнутая декомпозиция):** каждый сабагент — **тоже CTO**, гоняющий ту
же петлю на своём уровне. Организация **самоподобна**: CTO → суб-CTO → суб-суб-CTO, и иерархия менеджмента
**эмерджентна из A2** (превышение ёмкости κ ⟹ разбиение ⟹ делегирование). Никакой особой «оркестрации» сверху —
один и тот же агент на каждом узле, дерево живёт в CORE. Это буквально org-as-GFSO-tree, исполняемое и живое.

## 1.2. CORE = GFSO-граф как СИСТЕМА (не контекст одного агента)
CORE — персистентный локальный store, инстанцирующий **ровно примитивы канона** (§2.2 / `CORE.md`):
`tasks (T) · decomposition (D) · delegation (Del) · dependencies (Dep) · criteria · verdicts (V) · NEGLECTED ·
deadline`. Агент и тулзы **читают/пишут этот граф**. **Зачем системой, а не в контексте одного агента (важно):**
Claude-сабагенты эфемерны, общей памяти/межагентной связи у них нет (упёрся в это на E2). Чтобы делегирование +
агрегация держались через эфемерных сабагентов, **состояние GFSO-дерева обязано жить вне их — в CORE**. CORE —
единый источник истины, к которому подключены и агенты (как воркеры), и доска (как вид). Это и превращает GFSO из
«дисциплины в голове одного агента» в **многоагентную систему**. (При этом даже в контексте одного агента CORE
полезен — агент *и есть* часть про декомпозицию; CORE даёт ему внешнюю проверяемую запись вместо «в уме».)

## 1.3. GFSO-тулзы (операции конституции как инструменты; разные компоненты = разные тулзы)
Агент **оперирует конституцией через тулзы**, и каждая операция пишется в CORE ⟹ наблюдаема и аудитируема:
`create-task · set-criteria · decompose (создать детей + Dep) · delegate (открыть сабагента + назначить Del) ·
write-NEGLECTED (+ predictability_verdict) · check (FORM: связность/композиция/неизбыточность/сепараторность) ·
submit-verdict (V ребёнка) · aggregate (V=AND вверх по дереву) · challenge (FM-7 обратный канал) · block`.
**Обогащение:** этоframework-слой канона (12 сигналов §6.3, CHECK §5.4, FSM §6) — но как **вызовы инструментов
над CORE**, а не текст в одном контексте. «Разные GFSO-компоненты = разные тулзы» (твоя мысль) ⟹ методология
становится **операционально принудительной**: агент физически не может «пропустить шов» молча — он либо вызвал
`write-NEGLECTED`, либо нет, и это видно в CORE/на доске. Метод (конституция) задаёт, *что* эти тулзы обязаны
обеспечить; тулзы — носитель.

## 1.4. Промпт агента ВЫРОЖДЕН по мета-уровням (ключ к простоте)
В силу §18.10 (рекурсия; контакт однороден-по-модулю-задержки; агент = scope-bundle) **system-prompt один и тот
же на любом уровне** — у CTO и у любого суб-CTO. ⟹ промпт = **тонкое обрамление вокруг `method_gfso.md`**:
загрузить конституцию + операционная обвязка (декомпозируй → делегируй тулзами → чек → агрегируй → на стене
стоп-реплан) + доступ к GFSO-тулзам и CORE. **Построить промпт один раз = построить его для всей рекурсивной
организации.** Не нужно проектировать разные промпты на разные уровни — это прямое следствие теории, не удобство.

## 1.5. Alignment — GFSO внутри, обычный язык наружу
Юзеру **не** показываются GFSO-детали под капотом. Агент «думает про себя» — рефлексирует, гоняет GFSO-тулзы,
пишет в CORE и свою память — а юзеру выдаёт **план/статус/результат на его обычном языке**. GFSO — движок, не
интерфейс. **Доска — для тех, кто ХОЧЕТ прозрачность** (менеджер / дебаг GFSO / аудит): она реализует
**ценность наблюдаемости/самоизмеримости канона (§7.2 q-метрики, §14 структурная запись)** как живой UI —
непрозрачность = отсутствующий узел графа = измеримый дефект, теперь буквально видимый.

## 1.6. Управляемый knob = ГЛУБИНА верификации (не полнота)
Полноту мы добили **в методе** (полный край описан; полнота = фича, агент знает, что скипает). Тюнящийся параметр
сместился на **уровень детализации верификации плана** — трейдофф `токены ↔ глубина`. **Обогащение:** это ровно
**verify-vs-explore по ставкам (§5.4-bis / Ст. II.13)** — knob задаёт бюджет `c_check`: дёшево-обратимые узлы →
мельче проверка (explore), risk-nodes / необратимое → полная глубина (verify). И **скип ДЕКЛАРИРУЕТСЯ** (= NEGLECTED-
of-rigor через тулзу), так что честность сохранена — никакого молчаливого «сделано на 100%». Knob может быть
глобальным, по-задачный, или адаптивным (по стоимости каскада Ст. II.10).

## 1.7. Доска + БЫСТРЫЙ полигон (и побочный продукт — корпус данных)
Веб-UI рендерит граф CORE **в реальном времени**: дерево декомпозиции, работающие сабагенты (подсвечиваются),
срабатывающие сигналы, поднимающиеся вердикты `V`, объявленные NEGLECTED, стены `Ŝ\S`. Это доска из вижн-дока,
живая. **Главная ценность — скорость отладки самого GFSO:** смотришь, как GFSO работает и **падает** на реальной
многошаговой задаче за **минуты**, а не ждёшь реальную компанию месяцами; границы канона (верность III.1, качество-
метода III.3) проявляются как **реальные удары о стену**, наблюдаемо. **Обогащение (сильное):** каждый прогон
**порождает данные** — CORE-граф реального запуска = эталонная декомпозиция + criteria + вердикты. Это ровно тот
**корпус, на котором застрял старый roadmap** ([[project_gfso_roadmap]] Phase 2: «нет публичного бенча с эталонными
декомпозициями» / Phase 3: метки валидатора). Живая система **сама производит ground-truth** для E2/E3 — затык
снимается побочно.

## 1.8. Один движок — два лица (CLI-плагин И UI-решение)
«CLI-плагин или web» — **ложная развилка**: один движок (CORE + GFSO-тулзы + конституция-как-system-prompt),
интерфейсы — слои над ним. Агент в Claude Code (CLI) и агент, ведомый из UI, — **один и тот же** над одним CORE.
⟹ это **одновременно** CLI-плагин для Claude Code и полноценное решение изнутри UI; «через какой интерфейс писать»
= выбор слоя, не или-или. **Engine-first:** строить CORE + тулзы + промпт, потом наслаивать виды.

## 1.9. Последовательность + открытые вопросы
**Шаги (по одному, не всё сразу):** метод **DONE** → **(next) промпт агента** = обрамление вокруг `method_gfso`
(§1.4) → минимальная связка **CORE-схема + 3–4 GFSO-тулзы + проводка агента** = **E2-proper** (тестит ВСЮ петлю
decompose→delegate→execute→aggregate→contact) **+ MVP** → **UI-доска** (вид на CORE) — после.
**Открыто:** через какой слой писать сначала (вероятно CORE+тулзы как локальный движок, агент в Claude Code);
формат CORE (файловый store? схема?); как тулзы открывают/координируют сабагентов в Claude Code и собирают их
вердикты обратно в CORE; как доска синхронится с CORE; UX knob'а детализации; как показывать перманентные границы
(III.1/III.3) на доске честно (маркер «не верифицировано контактом», не «зелено»).

# 2. Открытые теоретические хвосты (live, не слиты)
- **Scrum sufficiency-derivation (B).** Структурное вложение — части Scrum ⊂ части GFSO — **доказано** (канон §17.2,
  14 кейсов, 0 unmapped). Открыто: что A1∧A2 *порождают* exploratory-динамику Scrum (почему итеративное уточнение
  работает для неизвестного), а не лишь *содержат* части. ~70% (частично выведено через §17.1). Паркуется на
  E3/декомпозицию — постмортемы это не тестируют.
- **Decomposition-method-quality** (ГЛАВНЫЙ живой фронтир). Как произвести *верный* шов — EMIT форматирует и
  градуирует, но **не гарантирует** верность (Лемма 1). Реальный E2/E3 + demo-блокер (канон §18.10.2). Системный
  вижн (§1) — это и есть апарат, чтобы тестировать его быстро.
- **v4.0** — полный три-слойный рестрактур канона (теормодель / методология / фреймворк разделены *в* каноне; их
  смешение и путало нас). Паркуется, **гейт на успех E2**.
